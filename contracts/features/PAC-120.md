## 0. The rule this contract fixes

A link has at most 5 co-hosts, whichever door adds them. PAC-112 closed the
list door (create and PATCH). This contract closes the single-invitation door
with the same number, decides it under the same kind of lock as the list, and
makes two of this operation's 500s tell the truth: a failed address lookup is a
500 (it was a 404 "user not found", SF-068), and a failed link read is logged
and reported (it was neither, SF-101). The body cap (the ticket's first half)
already exists since PAC-81; this contract changes nothing about it and only
fixes how its proof and its undocumented 400 are recorded (§6, API-097).

## 1. What changes at the HTTP boundary

Only `inviteSchedulingLinkHost` (`POST /api/scheduling-links/{id}/hosts`)
changes. No operation, path or parameter is added or removed. The request body
is unchanged.

| Change | Where |

PAC-21 `{error}` envelope. | 422, schemas |
| The **500** lists its four cases: link read failed (new: now logged and reported, SF-101); address lookup failed (new: was the 404, SF-068); the write failed; the 10 s link-lock bound (PAC-101). Body unchanged, `{"error":"internal error"}`. | 500 |
| The **404** says a storage error while resolving the address is the 500, never "user not found". Both 404 bodies and their meanings are unchanged (API-072). | 404 |

The 200, 201, 400, 401 and 403 are unchanged in shape and meaning. The 413 for

### 1.1 Order of evaluation (binding)

1. requireAuth 401 (and, for a body over 1 MiB, the PAC-81 413 before it,
   unchanged).
2. 400 `"invalid id"`.
3. Link read. A storage error is the **500**, logged and reported under the step
   `invite link read` (§1.2). No link (or a deleted one) is 404 `"not found"`.
4. 403 `"forbidden"`.
5. 400 `"email is required"` (invalid JSON or a blank address).
6. Address resolution (`storage.ConfirmedHolder`, outside any transaction, on the
   pool, unchanged placement). A storage error is the **500**, logged and
   reported under the step `invite lookup` (§1.2). No single domain-confirmed
   holder is 404 `"user not found"`. (Spec OQ-8 default: "user not found" before
   the limit, so the 422 is only ever said about an invitable address.)
7. The write (§3): PAC-71 re-check (a stale session ends as requireAuth's 401),
   the 10 s bound, the link lock, then, in this order: link gone → 404
   `"not found"`; already a host → **200**, row unchanged; the owner's own
   address → today's answer (200, or 201 for a link with no owner row); 5 or
   more co-hosts → **422**; otherwise → **201** with a `pending` row. Any other
   error, including `55P03` past the bound, is the 500 under the step
   `invite failed` (unchanged).

Everything before step 7 is unchanged except the two 500s. The 422 is added
only where a 201 was given before (spec D-4).

### 1.2 The two server errors (binding; spec D-5, D-6, AC-14, AC-15)

Both answer through the existing `writeServerError(w, r, op, err, 500)`
(`backend/api/server_errors.go`): `logServerError` writes
`ERROR <method> <path> -> 500: <op>: <err>` and calls `reportServerError` with
the error wrapped as `<op>: <err>`, then the body is
`genericServerMessage(500)` = `{"error":"internal error"}`.

| Case | Today | Contract | `op` (step name, binding) |
|---|---|---|---|
| `GetSchedulingLinkByID` returns an error | `writeError(w, "internal error", 500)`: same body, nothing logged, nothing reported (SF-101) | `writeServerError`, same status and body | `invite link read` |
| `ConfirmedHolder` returns an error | 404 `"user not found"`, nothing logged (SF-068) | `writeServerError`, 500 | `invite lookup` |
| `ConfirmedHolder` finds no single domain-confirmed holder | 404 `"user not found"` | unchanged | (none) |
| the write fails (not `ErrLinkGone`, not the limit) | 500 under `invite failed` | unchanged | `invite failed` |

The step names are what AC-14 and AC-15 match, in the captured log line and in
the captured Sentry error. **Tests match by step name and never count events**
(spec Pass 2 observed note): a request whose session goes stale in the write
already yields an `invite failed` event before the guarded writer turns the
answer into 401 (`handlers_scheduling_links.go:948-951`). That noise is today's
behaviour on every guarded link write and is out of scope.

### 1.3 Status code and text of the refusal (spec D-4, OQ-2)

422, for consistency with the list's over-5 422 on create and PATCH
(`handlers_scheduling_links.go:549-552`, `:821-824`), which is also a refusal
that depends on the link's state. The text:

- says the link has reached its limit and that a co-host must be removed before
  another is invited, so it reads as a limit on the link, not on the request;
- names the number 5 (the same number the editor shows as "n/5 co-hosts");
- says "reached", which stays true for a link already above 5 (§2);
- is distinct from `coHostListTooLongMsg` and from every other body of this
  operation;
- reveals nothing about the invitee: it is given only after the address has
  resolved to an invitable account, so it says no more than a 201 would.

The enum in `SchedulingLinkHostLimitError` makes any other 422 body a contract
violation, and lets a client branch on the value. `x-enum-varnames` gives the
generated Go constant a stable name (`SchedulingLinkHostLimitReached`).

### 1.4 What stays undocumented (spec m-5, API-097)

The PAC-81 body cap also answers 400 `{"error":"invalid request body"}` when
reading the body fails (`backend/api/middleware.go:387-390`), on every route,
before any handler. The contract names only the cap's 413 (`info.description`),
and this operation's 400 lists only "invalid id" and "email is required". The
spec records this and changes neither the code nor the contract text (spec §5),
so this contract adds the audit row **API-097** ("recorded, not fixed") rather
than a line in the 400. API-097 also carries the record correction of spec §0:
the PAC-112 spec's "no request body is size-limited" (§2.2, §5) has been false
since PAC-81.

## 2. The limit (binding; spec §3.2 items 1-4, OQ-1, OQ-3)

- **Value**: 5, one shared value with the co-host list rule
  (`storage.CoHostListLimit`, `scheduling_links.go:1143`) and the editor's cap
  (smart-calendar-flow `src/components/links/coHostSave.ts`). A plan that changes
  one changes all (OQ-3). The constant may be renamed, not duplicated.
- **Counted rows**: every row of `scheduling_link_hosts` for the link whose
  `user_id` is not the link's `owner_user_id`, whatever its `status`: `pending`,
  `accepted` and `declined` (OQ-1 default). This matches the editor's chips
  ("n/5" counts declined chips too) and PAC-112's "current host" set.
- **Never counted**: the owner's row, whatever its status (accepted, or declined
  by the owner) and whether or not it exists. The owner id is read from the link
  row under the lock (§3 step 1), never from the request.
- **Refused**: an invitation of an account that has no row on the link, is not
  the owner, when the count is 5 or more. Nothing is written.
- **Never refused by the limit**: an account that already has a row on the link
  (any status, any count; the 200 with the row unchanged, PAC-61), including the
  loser of two simultaneous invitations of one new address; the owner's own
  address; and the writes of other operations (accept, decline, leave, and
  removal by the list).
- **The owner's own address**: with an owner row, 200 and the row unchanged.
  With no owner row (a link created before PAC-112, spec §2.5), today's
  `InviteLinkHost` runs and answers 201 with a `pending` owner row. That row is
  not a co-host and is never counted. AC-6 no longer pins it (P2-m2): the
  follow-up "a link's owner can decline their own link, and an old link may have
  no owner row" may change it.
- **Links above 5** (built before this rule): unchanged rows; every new
  invitation is the 422 until the count is 4 or fewer, then 201 again (AC-8).

## 3. The invitation transaction (binding)

`storage.InviteLinkHostCtx` keeps `withLinkWriteTx` (`session.go:175-195`):
`fireGuardedCallHook(ctx)`, the PAC-71 re-check as the first statement
(`FOR KEY SHARE` on the caller's `users` row), then `setLinkLockTimeout` (10 s,
`set_config(…, true)`). Then, replacing `inviteLinkHostLocked`:

1. **The link lock, live only, exclusive against other link writers**:
   `SELECT owner_user_id FROM scheduling_links WHERE id = $1 AND deleted_at IS NULL FOR NO KEY UPDATE`.
   No row → `ErrLinkGone` (404 `"not found"`). After a wait, READ COMMITTED
   re-evaluates the `WHERE` on the newest row version, so a delete committed
   meanwhile gives no row (as today with `FOR SHARE`).
2. **Seam** `afterLinkInviteLock` (§5). A non-nil error rolls back and is
   returned (the 500).
3. **Already a host?**
   `SELECT id, link_id, user_id, status, invited_at, responded_at FROM scheduling_link_hosts WHERE link_id = $1 AND user_id = $2`.
   A row → return it, `created = false` (200). No write.
4. **The owner's own address**: `invitee == owner` → today's `InviteLinkHost`
   (insert `pending` `ON CONFLICT DO NOTHING`, then the existing-row read) and
   its answer. No count.
5. **The count**:
   `SELECT count(*) FROM scheduling_link_hosts WHERE link_id = $1 AND user_id <> $owner`.
   `>= CoHostListLimit` → return a new sentinel (for example
   `storage.ErrCoHostLimitReached`). No write. The handler maps it to the 422.
6. **The insert**: today's `InviteLinkHost` (`ON CONFLICT DO NOTHING` kept as
   defence; under the lock it cannot conflict, since step 3 saw no row and no
   other writer can add one).
7. `COMMIT`.

Steps 3 and 5 are plain reads under the lock. They are exact because **every
writer that can add a host row to an existing link takes this link's lock in a
mode that conflicts with `FOR NO KEY UPDATE` first** (§4.1): invitations (step 1)
and the PATCH (its `UPDATE`, `scheduling_links.go:843-849`). Accept and decline
change only a status. Leave and the list's removals only delete. Create makes a
new link. No other production path inserts into `scheduling_link_hosts`
(`git grep "INSERT INTO scheduling_link_hosts"` in `backend/`, non-test:
`AddLinkHost`, `InviteLinkHost`, the create's owner row). A concurrent removal
can only make a refusal that would otherwise not have been given, never let an
add through past 5.

Nothing in the handler counts hosts. The handler's only new branches are the
sentinel → 422 and the two `writeServerError` calls of §1.2.

## 4. Locks and deadlocks (binding)

### 4.1 Which lock orders concurrent invitations

The invitation's link lock moves from `FOR SHARE` to **`FOR NO KEY UPDATE`**,
the mode the PATCH's `UPDATE` and the delete's `UPDATE` already take
(PAC-101 §4.1). It conflicts with itself, with `FOR SHARE` (bookings, accept,
decline, leave), with the PATCH, the delete, and the erasure's `FOR UPDATE`.
It does not conflict with `FOR KEY SHARE`, so foreign-key checks of rows that
reference the link (a booking insert, a host-row insert) are not blocked by it.

So two invitations on one link run one after the other, and an invitation and a
list save run one after the other. Each decides against the host rows the
previous one committed. That is what spec D-3 and AC-9 / AC-10 require.

Why this mode and not another: it adds **no new lock mode or lock class** to the
link. Every mode involved, and every pair of them, already exists and is already
run together by `TestPAC101_ConcurrentWritesOnOneLinkNeverDeadlock`. The
invitation simply moves from the group of share-locking host writes to the group
of exclusive link writers (PATCH, delete), where the other writer that adds host
rows already is. The alternatives are in §12.

The cost: an invitation now waits for a booking save, accept, decline or leave
in progress on the same link, and they wait for it, as they already do for a
PATCH or a delete. The invitation holds the lock for three short statements and
one insert. Bookings still do not wait for each other (PAC-101 AC-16): the
booking path is unchanged.

### 4.2 Lock orders after PAC-120

| Transaction | Locks, in order | Source |
|---|---|---|
| **invite (changed)** | caller's `users` row `KEY SHARE` (re-check) → link **`NO KEY UPDATE`** → host row (FKs: link `KEY SHARE`, covered by its own lock; invitee `users` row `KEY SHARE`) | this contract §3 |
| PATCH | caller's `users` row `KEY SHARE` → link `NO KEY UPDATE` (`UPDATE` when the slug changes: the `slug` unique key makes it `FOR UPDATE`) → host rows (FK: invitees' `users` rows `KEY SHARE`) | PAC-101 §4.1, PAC-112 §3.2-§3.3 |
| delete (PAC-40) | caller's `users` row `KEY SHARE` → link `NO KEY UPDATE` | PAC-101 §4.1 |
| booking save | link `FOR SHARE` → advisory keys, ascending, one per statement → booking row | PAC-101 §3.1, PAC-82 §3 |
| accept / decline / leave | caller's `users` row `KEY SHARE` → link `FOR SHARE` → caller's host row | PAC-101 §4.1 |
| link create (keyed or not) | caller's `users` row `KEY SHARE` → its own new link row (slug unique index) → key row (keyed, unique index) → owner and co-host rows | PAC-119 §4.2, §4.5 |
| booker erasure | link `FOR UPDATE` (deleted links only) → bookings → owner's `users` row `KEY SHARE` | PAC-101 §4.1, `booker_erasure.go:86-117` |
| generation advance, operator, sign-in | a `users` row `FOR UPDATE` / `FOR NO KEY UPDATE`; no link, host or booking lock | PAC-101 §4.1, PAC-119 §4.5 |

Every link writer takes the link row as its **first** lock on any
scheduling-link object, after at most a `KEY SHARE` on the caller's own `users`
row. That ordering is what PAC-101 proved deadlock-free, and PAC-120 keeps it.

### 4.3 The deadlock argument

A cycle needs a transaction that holds a lock another waits for, while it waits
for a lock held (directly or through the queue) by that other. For each pair
involving the invitation:

| Pair | Who waits | Cycle? |
|---|---|---|
| invite / invite, same link | the second waits at step 1 for the first | No. The first holds the link and then needs only its own new host row and the invitee's `users` row `KEY SHARE`. The second holds only the caller's `users` row `KEY SHARE`, which conflicts with neither. |
| invite / invite, same invitee, two links | none at the link; both take `KEY SHARE` on the invitee's `users` row | No: `KEY SHARE` is compatible with itself. |
| invite / PATCH, same link (spec AC-10) | whichever reaches the link second | No. Both take the link first. After it, the PATCH's later locks are host rows and invitees' `users` rows `KEY SHARE`; the invitation holds none of those exclusively. With the same invitee X (AC-10(b)): invitation first → the PATCH reads X in H and keeps it (200); PATCH first → step 3 sees X (200). `coHostInvite`'s "became a host during the save" cannot fire, because the PATCH reads H after the invitation committed or before it started. |
| invite / delete, same link (AC-12) | whichever reaches the link second | No. A delete takes nothing else. Delete first → the invitation's step 1 re-evaluates to no row → 404, nothing written. |
| invite / booking save | the later of the two at the link | No. The booking's later locks are advisory keys (a class no invitation takes) and its own booking row. The invitation's later locks are a host row and a `users` row. Disjoint. |
| invite / accept, decline, leave | the later of the two at the link | No. After the link, each touches only one host row: the responder's existing row, or the invitation's new row. The invitation reaches step 3/6 only after the responder committed (it waited at the link), or the responder waits at the link. |
| invite / pause, resume | as invite / PATCH (pause and resume are PATCHes of `active`) | No. |
| invite / link create | none: different link rows | No. The create's FK checks on `users` rows are `KEY SHARE`. |
| invite / erasure | none in practice: the erasure takes only deleted links (`deleted_at IS NOT NULL`), the invitation only live ones; during a delete-then-erase race, both take the link first | No. |
| invite / generation advance on the caller | the advance's `FOR UPDATE` waits for the re-check's `KEY SHARE` until the invitation commits, bounded by the advance's own 10 s | No: the invitation never waits on the advance's locks after its re-check. Unchanged from today (PAC-119 §4.5 row). |
| invite / generation advance on the invitee | step 6's FK `KEY SHARE` on the invitee's row waits for the advance's `FOR UPDATE`, bounded by the 10 s link bound | No: the advance takes no link or host lock (PAC-101 §4.1). Unchanged from today. |
| invite queued behind a booking, new bookings queued behind the invite | PostgreSQL's tuple-lock queue makes a new `FOR SHARE` wait behind a waiting `NO KEY UPDATE` | No: the booking holding the lock needs no further lock on the link (its FK `KEY SHARE` is covered by its own `FOR SHARE`). The same queueing exists today behind a waiting PATCH or delete. |

So no new cycle exists. AC-11 (mixed workload at the cap boundary) and the
unchanged `TestPAC101_ConcurrentWritesOnOneLinkNeverDeadlock` are the
falsifiers; AC-9 is the deterministic test of the race itself.

### 4.4 Bound and scoping: unchanged

The 10 s bound (`LinkLockTimeout`) is set with `set_config('lock_timeout', …, true)`
after the re-check and before step 1, as today (PAC-101 §4.2-§4.3). Past it:
`55P03`, rollback, the 500 under `invite failed`, nothing written. The re-check
stays outside the bound.

### 4.5 The PATCH and create list paths: unchanged

`setCoHostList` keeps its over-5 rule, its message and its lookup order
(PAC-112 §3.3). It already runs under the PATCH's `NO KEY UPDATE`, which now
also orders it against invitations. The keep-rule edge (several accounts sharing
one listed address can leave 6) stays out of scope (spec §5).

- `afterLinkInviteLock` receives the **request context** so a test can hold one

- `confirmedHolderLookup` and `linkReadByID` fire for every caller of those

  sites and handlers are unaffected.
- Waits are observed in `pg_stat_activity` (`wait_event_type = 'Lock'`) or

- AC-13 moves the generation with a raw

- AC-9, AC-5b and AC-11 release their requests from a barrier and repeat on

## 12. Alternatives rejected

- **A transaction-scoped advisory lock per link, after `FOR SHARE`**
  (`pg_advisory_xact_lock(<new class>, <link>)`). It would order invitations
  without making them wait for bookings. Rejected: it adds a new lock class to
  the link, a second lock taken after the first (the order every deadlock review
  must then re-prove), and a class number to keep apart from the booking keys
  (`BookingAdvisoryKeys`). It also does not by itself order an invitation against
  the PATCH; that still relies on the row lock. `NO KEY UPDATE` gets both
  orderings from one lock that the PATCH and the delete already take.
- **`FOR UPDATE` on the link**: also conflicts with `FOR KEY SHARE`, so it would
  block every booking or host-row insert's foreign-key check on the link, and
  nothing needs that strength.
- **Keep `FOR SHARE` and count anyway**: two invitations both see 4 and both
  insert (spec §2.5). Not an option.
- **`SERIALIZABLE` for the invitation transaction**: would turn the race into a
  `40001` that the handler must retry or answer as a 500. A retry loop is new
  machinery on a path that has none, and a 500 under ordinary concurrency would
  break AC-9 ("never 500").
- **A conditional insert** (`INSERT … SELECT … WHERE (SELECT count(*) …) < 5`)
  under `FOR SHARE`: the subquery's snapshot does not see another transaction's
  uncommitted insert, so it races exactly as a separate count does.
- **A host-count column on `scheduling_links`, or a trigger enforcing the
  count**: a migration and a second source of truth for a number that one
  `count(*)` over at most a few rows gives, and a trigger would also fire for the
  list path and for links already above 5, whose keep-only saves must succeed
  (PAC-112 AC-32).
- **Deciding the limit in the handler before the write** (spec OQ-8 alternative
  and D-3): saves nothing, races, and AC-13 exists to fail it.
- **Refusing before "user not found"** (OQ-8 alternative): tells the owner of a
  full link who mistyped an address to remove someone.
- **409 for the refusal** (OQ-2 alternative): would be the operation's only
  409 and diverge from the list's 422 for the same limit.
- **Reusing `coHostListTooLongMsg` or `SchedulingLinkValidationError`**: the
  text talks about a list, and this request has none; the spec requires a
  distinct message (§3.2 item 4).
- **A plain `BookingError` for the 422** (no new component): keeps `schemas.ts`
  unchanged, but leaves the body unconstrained. An enum is cheaper than
  validation code and cannot drift (contract-author rules); PAC-119 pinned its
  refusal texts the same way.
- **Moving the operation to the generated server**: the generated wrapper decodes
  the body before the handler, which would move the 400 ahead of the link read,
  the 404 and the 403 and change its text. That is a behaviour change the spec
  does not ask for (MIGRATION.md note).
- **Documenting the body cap's 400 in this operation's 400 now**: the spec puts it
  out of scope (§5), and it applies to every route, so one operation's text is
  the wrong place. Recorded as API-097.
