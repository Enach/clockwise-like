## 0. The rule this contract fixes

A link create can carry an attempt key. One account's key creates at most one
link, however often the create is sent. A retry of the same request within a day
gets the original answer back, co-host outcomes included. Any other use of the key
gets a refusal that says what happened. Each refusal is safe for the editor to act
on. Every such answer is decided under the PAC-71 session re-check, so a revoked
session never learns anything from a key.

## 1. What changes at the HTTP boundary

Only `createSchedulingLink` (`POST /api/scheduling-links`) changes. No operation,
path or status code is added or removed.

| Change | Where |
|---|---|
| New optional request header `Idempotency-Key` (`components/parameters/SchedulingLinkCreateIdempotencyKey`). It uses the same carrier and format as PAC-82's `BookingIdempotencyKey`: 16..255 characters of `A-Za-z0-9-_`, case-sensitive, a bare token, empty = absent. Its scope is the account, and its window is 24 h. | parameter, operation description |
| New 400 message `invalid Idempotency-Key header`, for a bad format, a quoted value, or the header on two or more field lines. It is checked **before the body is read**. | 400 |
| A 201 can be a **replay**: same schema, same `id` and `slug`, current field values and roster, the original `co_host_changes` unchanged, nothing written, and no marker. | 201 |
| The 409 schema becomes `SchedulingLinkCreateConflict`, a `oneOf` of `SchedulingLinkSlugTakenError` (`slug already exists`, unchanged text, now pinned), `SchedulingLinkCreateKeyLinkError` (`idempotency key already used` / `idempotency key expired`, plus `link_id`), and `SchedulingLinkCreateKeyDeletedError` (`idempotency key already used by a deleted link`). | 409, schemas |
| The 500 also covers a failed key read or write, and a wait of more than 10 s on a concurrent create with the same key. | 500 |
| The PAC-112 sentence "Nothing protects a retry after a lost 201: saving again creates a second link (spec §5, accepted risk)" is replaced by the PAC-119 paragraph. | description |
| CORS is unchanged. `Access-Control-Allow-Headers` already lists `Idempotency-Key` on every route (`backend/api/middleware.go:250`, PAC-82). | none |

The 401 (`BookingUnauthorized`) and the 422s are unchanged in shape. Where they now
fall in the order of evaluation is stated in §1.1.

### 1.1 Order of evaluation (binding)

**Keyless** (no header, or an empty value): unchanged. requireAuth 401 → body 400 →
field 422s (the `days` check first) → blank-entry 422 → owner read 500 → zone 500
→ slug generation, or for an explicit slug the slug check 409 / 500 → write
(over-5 422, 500).

**Keyed**:

1. requireAuth 401.
2. **Key 400** (`invalid Idempotency-Key header`), before any byte of the body is
   decoded. So a malformed key with invalid JSON, or with a body that would be a
   422, is still this 400 (spec AC-14).
3. Body 400, field 422s, blank-entry 422: the same checks in the same order as
   keyless.
4. Owner read 500, zone 500.
5. **Resolution R1** (§4.1): the 401 when the session went stale; otherwise
   replay 201, or deleted / expired / key-reused 409; otherwise nothing is stored
   and the create continues.
6. Slug. With no slug sent, generation (500 on failure). With an explicit slug, the
   pre-check. If the slug exists, run **resolution R2**: a stored key answers by
   §1.2, and only when nothing is stored is the answer `409 slug already exists`.
7. The create transaction (§4.2). A unique violation on the slug or on the key
   leads to rollback and then **resolution R3**: a stored key answers by §1.2.
   When nothing is stored, a slug violation is today's 500 (spec §5, out of
   scope), and a key violation with no row found is the 500. The over-5 422 is
   decided inside this transaction, after R1 (spec §3.4, Pass 2 minor 2). Any
   other failure is the 500.
8. Commit, then 201.

Why the key 400 comes before the body. PAC-82 put it before the body for the same
reason: the key is metadata of the attempt, and a client must learn that its key is
unusable before it fixes anything else. Nothing on this route precedes it except
requireAuth (PAC-82 had the slug 404 first, and this route has no path parameter).

Why the owner and zone reads come before R1. The replay's answer needs the zone, as
every 201 does (PAC-72 D-9). A failed zone read is a 500 that writes nothing, and a
retry repeats it. Moving R1 earlier would gain nothing.

### 1.2 Resolution rules (binding; spec §3.2)

R reads the key row for (caller, key) and its link, inside the guarded transaction
of §4.1. The first matching rule wins:

| # | Stored | Answer |
|---|---|---|
| — | no row | nothing stored: the create continues (R1), or the slug 409 / 500 is answered (R2, R3) |
| 1 | the link has `deleted_at` set | 409 `{"error":"idempotency key already used by a deleted link"}` |
| 2 | `now() - created_at >= interval '24 hours'` (database clock, the resolving transaction's `now()`) | 409 `{"error":"idempotency key expired","link_id":"<link id>"}` |
| 3 | `request_sha256` equals the request's digest (§2.3) | 201 replay (§1.4) |
| 4 | anything else, including a `NULL` digest | 409 `{"error":"idempotency key already used","link_id":"<link id>"}` |

A `NULL` digest under 24 h can only be seen by a resolution that races the cleanup
at the boundary instant. It never matches. Refusing is the safe direction, because
the refusal names the caller's own live link.

`created_at` is the original save's stored time. It is set by the column default
`now()` inside the create transaction, which is that transaction's start (spec §3.2
as amended by Pass 2 minor 5). Tests age it with
`UPDATE scheduling_link_create_keys SET created_at = now() - interval '…'`.

### 1.3 Status codes of the refusals (spec D-2, OQ-1)

All three refusals are **409**, each with its own `error` text, in one `oneOf` with
the existing slug 409.

- **Consistent with PAC-82.** PAC-82 answers a reused or expired booking key 409
  `{"error":"idempotency key already used"}` (PAC-82 md §2.2). Rows 2 and 4 are the
  same situation, so they keep the status. Row 4 also keeps the exact text, so one
  word means one thing across the API.
- **Not 422** (the IETF draft's code for a reused key with another payload). The
  draft keeps 409 for "a request with this key is in flight". Here an in-flight
  duplicate is never refused: it waits (§4.3), so 409 is free. PAC-82 made the same
  argument.
- **Not 410 for the deleted refusal.** 410 describes the *target resource*, and the
  target is the collection `POST /api/scheduling-links`, which is not gone. A
  generic client or proxy would read 410 as "stop calling this URL". The conflict is
  between the key and stored state, which is what 409 means, and the editor recovers
  with a new key.
- **Not 404 for the deleted refusal.** 404 would tell the editor that the request
  target is missing. It would also look like the PAC-40 "deleted link" answers of
  the by-id operations, which a create editor must never follow (spec §3.8 item 4).
- **Not 200 for the replay.** The original answer was 201, and a replay must be
  indistinguishable from it (spec §6).
- **`link_id` only on rows 2 and 4.** The editor needs it to become an editor of the
  link (spec §3.8 items 2-3). It is always the caller's own live link, because the
  key's scope is the caller's account. Row 1 names nothing (spec B-1): no read can
  find a deleted link, and the editor must never PATCH it.
- **The envelope stays `{error}`**, with `link_id` as the only addition. A client
  that reads only `error` still shows a message. The `oneOf` is disjoint by `error`
  alone, which is the `PublicBookingConflict` pattern (PAC-82) and PAC-50's
  `SsoWriteForbiddenResponse`. The slug variant is pinned
  (`SchedulingLinkSlugTakenError`) because the free-text `BookingError` would also
  match the deleted body and break the `oneOf`.

### 1.4 The replay (binding; spec §3.4)

- Status 201, schema `SchedulingLinkSaved`, written by the same `writeSavedLink`.
- `id`, `slug` and every other link field come from the link row that R read inside
  its transaction. These are current values (spec OQ-4): an edit made since is
  visible.
- `hosts`: built non-strictly at answer time, exactly as on every 201 (PAC-112
  §2.4). It is not a baseline.
- `co_host_changes`: present exactly when the original request carried a list. It is
  the original answer's object as stored (§3.3), decoded into the same DTO and
  re-encoded: same `addresses` (entries spelled as the original request spelled
  them), same `removed` (`[]`), same counts. Nothing is re-evaluated, invited or
  removed (spec AC-1, AC-3).
- No header marks a replay, and the key is never echoed.

## 2. Decisions

### 2.1 Header, same carrier as PAC-82 (spec D-1, D-2)

Taken from PAC-82 §2.1. `CreateSchedulingLinkRequest` stays closed
(`additionalProperties: false`), and the key is never part of the compared request.
A separate parameter component (`SchedulingLinkCreateIdempotencyKey`) carries the
same schema as `BookingIdempotencyKey`, because the two descriptions differ in scope
(account vs link), window wording and resolution rules. Sharing one component would
put booking prose on a link operation.

### 2.2 Account scope (spec D-3.1)

The key is unique per (owner, key). The owner is the authenticated user, which on
this route is always the link's owner. Another account's identical key is unrelated
(spec AC-6). Another session of the same account resolves the same row.

### 2.3 Request digest: canonical form v1 (binding; spec §3.3)

The server stores `SHA-256(canonical bytes)`, 32 bytes, and never the raw body. The
canonical bytes are Go `encoding/json`'s `Marshal` of a struct whose fields are, **in
this order**:

| JSON key | Value |
|---|---|
| `v` | `1` (the version; a future normalisation change bumps it, and an old digest then never matches, which is row 4: the safe direction) |
| `title` | the trimmed title, as `normalized()` stores it |
| `slug` | `normalizeSlug(slug)` before generation. Absent and `""` are both `""` |
| `duration_options` | the resolved list (`duration_options` over `durations`, default `[30]`), order and duplicates as sent, since the save stores it so |
| `days_of_week` | the resolved list (`days_of_week` over `days` names, default Monday-Friday), order as sent |
| `window_start_time`, `window_end_time` | after `validateSchedulingLink`, i.e. `HH:MM` (`"9:00"` and `"09:00:00"` give `"09:00"`), defaults `09:00` / `17:00`, aliases resolved |
| `buffer_before`, `buffer_after`, `min_notice_minutes` | integers as validated |
| `usage_type` | as validated: trimmed, lowercased, absent = `reusable` |
| `max_uses` | `null` unless `usage_type` is `recurring` (validation clears it otherwise) |
| `booking_horizon_days` | absent or `null` = `60` |
| `refusal_message` | absent or `null` = `generic` |
| `co_host_emails` | `null` when the request carried no list (absent or `null`). Otherwise an array, `[]` included, built as follows: each entry trimmed of ECMA-262 `\s` (`TrimECMASpace`); lowered by **the same lowering the co-host write uses** (`lowerAll`, `scheduling_links.go:1202`, run on the resolution transaction); deduplicated; sorted ascending by bytes |

In short: the digest is taken over **exactly the values the save would store**, plus
the normalised list. It is computed once per request, in R1, after R1's first
re-check (`lowerAll` needs the database), and the same value is passed to the create
transaction and to R2 and R3. Formatting, key order and alias spelling cannot affect
it. Two requests that would save different links, or invite different accounts,
have different digests.

The web lowers with JS `toLowerCase` (`coHostSave.ts:22`), so the two lowerings agree
for ASCII only. A non-ASCII mismatch makes a retry that the web considers unchanged
the row-4 refusal, from which the editor recovers (spec §3.3, Pass 2 minor 4).

## 3. Storage (binding)

### 3.1 A separate key table, not columns on the link

```
scheduling_link_create_keys
  owner_user_id    UUID        NOT NULL  -> users(id) ON DELETE CASCADE
  idempotency_key  TEXT        NOT NULL  CHECK format ^[A-Za-z0-9_-]{16,255}$
  link_id          UUID        NOT NULL  -> scheduling_links(id) ON DELETE CASCADE, UNIQUE
  created_at       TIMESTAMPTZ NOT NULL  DEFAULT now()
  request_sha256   BYTEA       NULL      CHECK NULL or 32 bytes
  co_host_changes  JSONB       NULL      CHECK NULL unless request_sha256 IS NOT NULL
  PRIMARY KEY (owner_user_id, idempotency_key)  -- constraint scheduling_link_create_keys_owner_key
```

- **Unique (owner, key)** is the primary key, named
  `scheduling_link_create_keys_owner_key`. It is the authority for concurrency
  (spec D-4): the second insert of a pair waits for the first and then fails with
  `23505` on that constraint.
- **`UNIQUE (link_id)`** (`scheduling_link_create_keys_link`): one key per link. A
  keyless create writes no row.
- **`request_sha256`**: §2.3. `NULL` after cleanup.
- **`co_host_changes`**: the `co_host_changes` object of the original 201, exactly as
  serialised on the wire (`addresses`, `removed`, the three counts). `NULL` when the
  original carried no list, and `NULL` after cleanup. The CHECK ties it to the
  digest, so cleanup always clears both together, and a row never holds outcomes
  without the digest that guards them.
- **`created_at`**: `DEFAULT now()`, never `clock_timestamp()` and never set by the
  application (§1.2).
- **Index** `scheduling_link_create_keys_retained ON (created_at) WHERE request_sha256 IS NOT NULL`,
  so the hourly cleanup reads only the rows it may clear.

What a row holds after cleanup: owner, key, link id, time (spec §3.6, AC-12). None
of these contains an address. The key is client-chosen from `[A-Za-z0-9_-]`, so it
cannot hold an `@`, and the link's title is not in this table (Pass 2 minor 6 does
not bite, but the fixture follows it anyway).

**Deletion.** Links are never hard-deleted by the product (PAC-40), so a row lives
as long as its link: for ever (spec §3.6). An account deletion cascades through both
foreign keys, and the row goes with the account's links.

### 3.2 Why not columns on `scheduling_links` (the alternative weighed)

Putting the key on the link row, with the outcomes elsewhere or in columns cleared
at cleanup, would save one table. It was rejected for three reasons:

1. **Cleanup would write link rows.** An `UPDATE scheduling_links` takes a row lock
   that conflicts with the `FOR SHARE` every public booking save takes on its link
   (PAC-82 md §3 step 2), and with PATCH and delete. An hourly sweep would queue
   behind bookings and make them wait. Updating key rows locks nothing any other
   writer touches.
2. **AC-12 would depend on the title.** The link row holds the title, so "no column
   of the key store contains an address" would hinge on fixture data (Pass 2 minor
   6).
3. **The PAC-82 argument does not carry over.** PAC-82 rejected a key table because
   the booking row already held everything a replay needs. Here the co-host outcomes
   exist nowhere else and must be stored (spec D-3.3), so a second write happens
   either way.

### 3.3 Retention and cleanup (spec §3.6, D-6, AC-12)

- **Statement**, in its own transaction:
  `SELECT set_config('lock_timeout', '<LinkLockTimeout ms>', true)`, then
  `UPDATE scheduling_link_create_keys SET request_sha256 = NULL, co_host_changes = NULL WHERE request_sha256 IS NOT NULL AND created_at <= now() - interval '24 hours'`.
  The exported production function (name free, for example
  `storage.ClearExpiredLinkCreateKeyData(ctx, db) (int64, error)`) returns the row
  count.
- **Schedule.** `backend/main.go` registers it like the PAC-40 erasure, through
  `cronJob("link-create-key-cleanup", …)` (a PAC-81 tracked unit, awaited by the
  drain), `@every 1h` on its own `cron.Cron`, **plus a start-up run**. The start-up
  run is started on a goroutine after `Start()`, so readiness never waits for it.
  It is stopped with the other crons in `stopScheduling`. A helper shaped like
  `scheduleBookerErasure` (`scheduleLinkCreateKeyCleanup(c cronRegistrar, job) (startup func(), err error)`)
  lets AC-12 assert the `@every 1h` registration and the start-up run with a fake
  registrar.
- **Bound.** A row reaches 24 h at T and is cleared by the first run after T. While a
  backend runs, runs are at most one hour apart, and a restart (every PAC-116 deploy)
  runs it at start-up. So no address typed into a create outlives about 25 h in the
  key store. The one exception is time with no backend running at all, such as a
  maintenance stop. The first start-up after it clears the backlog.
- **Logging.** The count only, never a key, link or address. An error goes to the log
  and Sentry. The next run retries, and a failed run writes nothing.
- **Several backends.** Concurrent runs clear the same rows. A second `UPDATE` that
  waits on the first's row lock re-evaluates its `WHERE` after the first commits
  (READ COMMITTED) and skips the cleared rows. The outcome is idempotent. A rare
  `40P01` between two sweeps scanning in different orders aborts one run, which is
  logged, and the next run finishes the job.

## 4. Transactions (binding)

Every replay or refusal decision is made **only** in the resolution transaction R
(§4.1). Nothing is decided on a bare connection, in the pool, or after a rollback
without a new R. This is the departure from PAC-82 (`scheduling_links.go:552-563`),
required by spec §3.5 and B-2.

### 4.1 The resolution transaction R (R1, R2, R3 are the same function)

One explicit transaction, `db.BeginTx(ctx, nil)` (READ COMMITTED). This route always
has a session guard (requireAuth installs one, `middleware.go:143`). Statements in
this order:

1. `fireGuardedCallHook(ctx)`, before the transaction's first statement, as
   `withGenerationTx` callers do. This is the PAC-71 mid-request seam, and the
   position of spec AC-10's first seam.
2. **Re-check #1**: `recheck` (`SELECT session_generation FROM users WHERE id = $1 FOR KEY SHARE`).
   On a mismatch the guard is marked stale, the transaction rolls back, and R
   returns `ErrStaleSession`.
3. R1 only: `lowerAll` of the trimmed entries, for the digest (§2.3).
4. **Key read**, one statement:
   `SELECT k.link_id, k.request_sha256, k.co_host_changes, l.deleted_at IS NOT NULL, now() - k.created_at >= interval '24 hours', <every column scanSchedulingLink reads, from l> FROM scheduling_link_create_keys k JOIN scheduling_links l ON l.id = k.link_id WHERE k.owner_user_id = $1 AND k.idempotency_key = $2`.
   It is an MVCC read with no row lock, so it never waits.
5. **Seam** `afterLinkCreateKeyRead` (§6): spec AC-10's second position, between the
   key read and the second session check (Pass 2 minor 1).
6. **Re-check #2**: `recheck` again. The transaction already holds `FOR KEY SHARE` on
   the user row, and a generation bump is a non-key `UPDATE`, which `FOR KEY SHARE`
   does not block. So this statement, with its own READ COMMITTED snapshot, sees a
   bump committed after step 2. On a mismatch: stale, rollback, `ErrStaleSession`.
7. `COMMIT`. The transaction wrote nothing, so the commit only releases the lock.
8. Decide by §1.2, in Go, from step 4's row, and return one of: `ErrStaleSession`;
   not stored; replay (link, stored changes); deleted; expired (link id); reused
   (link id). The seam `afterLinkCreateKeyResolved` (§6) fires when the result is
   "not stored", after the commit and before R returns.

No `lock_timeout` is set, and none is needed. The re-check is not under the bound on
any guarded write (PAC-101 §4.3), and step 4 never waits.

On `ErrStaleSession` the handler writes nothing derived from the row. The
`guardedResponseWriter` turns whatever it writes into requireAuth's 401
(`middleware.go:155-215`), with nothing of the link (spec AC-10, AC-29).

The window that stays open: the answer's roster read (`toSchedulingLinkDTO`, outside
any transaction, non-strict) after step 6. This is the exposure every PAC-71 guarded
write accepts (spec D-5).

### 4.2 The create transaction (keyed and keyless)

`CreateSchedulingLinkWithCoHostsCtx` gains the key and the digest. It keeps
`withLinkWriteTx`: re-check first, then the 10 s `lock_timeout`. Statements:

1. Re-check (unchanged, `withGenerationTx`).
2. `set_config('lock_timeout', …)` (unchanged, PAC-101).
3. `INSERT INTO scheduling_links …` (unchanged). This statement can wait on another
   transaction's uncommitted equal slug, at most 10 s, and then fails with `23505`
   on `scheduling_links_slug_key` if that transaction commits.
4. **Keyed only**:
   `INSERT INTO scheduling_link_create_keys (owner_user_id, idempotency_key, link_id, request_sha256) VALUES ($owner, $key, $link, $digest)`.
   This claims the key **before** any host or invitation work, so a concurrent
   duplicate stops here rather than after doing that work. It can wait on another
   transaction's uncommitted equal (owner, key), at most 10 s, and then fails with
   `23505` on `scheduling_link_create_keys_owner_key`.
5. The owner's `accepted` host row (unchanged; seam `createOwnerHost`).
6. The co-host list (unchanged; the over-5 422 is decided here; seams
   `coHostLookup`, `coHostWrite`).
7. **Keyed, with a list carried**:
   `UPDATE scheduling_link_create_keys SET co_host_changes = $json WHERE owner_user_id = $owner AND idempotency_key = $key`.
   `$json` is the serialisation of the `co_host_changes` DTO that the 201 will carry.
8. **Seam** `beforeLinkCreateCommit` (§6): a non-nil error rolls everything back.
9. `COMMIT`.

The storage layer maps a `23505` from step 3 or step 4, identified by the
`pq.Error.Constraint` name, to one sentinel (for example `storage.ErrLinkCreateConflict`).
It keeps the constraint name so the handler can tell a keyless slug violation (still
the 500) from the rest. A failure of any kind rolls back steps 3-7 together, so a
failed or refused create never stores a key (spec §3.5 "Failures store nothing",
AC-9). Keyless creates skip steps 4 and 7 and are otherwise byte-for-byte today's
transaction.

### 4.3 The loser's short transaction (spec §3.5, D-4)

Two requests with the same (owner, key) are in flight:

- **Same base slug** (spec AC-7(a)). The loser waits at step 3 on the winner's slug.
  If the winner commits, the loser gets `23505` on the slug, rolls back, and runs
  R3, which finds the key: replay, or row 4 when the body differs. If the winner
  rolls back, the loser's insert proceeds and the loser creates the link (AC-8).
- **Different slugs** (AC-7(b)). The loser inserts its link, then waits at step 4 on
  the key. If the winner commits: `23505` on the key, rollback (the loser's link
  disappears with it), R3. If the winner rolls back: the loser proceeds.
- **The winner committed before the loser started**: R1 finds the key, and the loser
  never writes.
- **Explicit slug, loser held between R1 and its slug pre-check** (AC-30). The
  pre-check finds the slug, and for a keyed request that means R2, which finds the
  key: replay or row 4, never `slug already exists`.

R3 is a **new** transaction (§4.1). It runs both re-checks, so a generation moved
while the loser waited gives the 401 (AC-29). The new READ COMMITTED transaction
always sees the winner's committed key, because the `23505` is raised only after
the winner commits. R3 takes no lock that can wait, so the 10 s bound cannot hit it.
A loser that waited more than 10 s gets `55P03`, which is the 500 with nothing
stored. PAC-82 observed that `lock_timeout` caps unique-index waits (PAC-82 md §4.5).
A later retry then resolves by §1.2.

### 4.4 PAC-71 session check placement (summary)

| Path | Re-checks |
|---|---|
| keyed R1, R2, R3 | before the key read (#1) and after it (#2), in the same transaction, with `fireGuardedCallHook` before #1 |
| create transaction | first statement, unchanged |
| keyless create | unchanged |
| replay answer's roster read | none (the accepted window, spec D-5) |

### 4.5 Locks and deadlocks

| Pair | Wait? | Cycle? |
|---|---|---|
| create / create, same (owner, key) | the loser waits at step 3 (slug) or step 4 (key) on a winner that is past its own step 3 or 4 | No. The winner's later statements (owner row, invitations, its own key-row update) never wait on the loser's rows. The loser's slug differs in case (b), and in case (a) the loser has inserted nothing yet |
| create / create, same owner, different keys, same explicit or generated slug | step 3 only, as today | No |
| R / anything | `FOR KEY SHARE` on the caller's user row, compatible with a generation bump (non-key `UPDATE`). Blocked only by a `FOR UPDATE` or a delete of that user row, as every re-check is today | No: R holds nothing else |
| cleanup / create | disjoint rows (cleanup touches rows ≥ 24 h old; a create touches its own new row) | No |
| cleanup / R | MVCC read vs row lock: no wait | No |
| cleanup / account deletion (cascade to key rows) | one waits for the other, bounded by cleanup's 10 s `lock_timeout` | No: cleanup holds only key rows and waits on nothing else |
| cleanup / cleanup (several backends) | row locks, re-evaluated after commit | A `40P01` is possible only with different scan orders. It aborts one sweep harmlessly (§3.3) |
| create / booking save, PATCH, delete, PAC-40 erasure | unchanged. The key table has no relation to those locks, and the key row's FK `KEY SHARE` on the link is the create's own uncommitted row | No |
| migration / anything | none in operation (PAC-116 stop-traffic, §5) | No, prevented operationally |

## 5. Migration (binding; spec §3.9, §7)

Next free number on `origin/main` `0f11003`: **040**. Main's latest is
`039_sso_stepup_denial_windows`, and no `origin/*` branch carries 040 or above on
2026-11-15 (checked with `git ls-tree` over every remote branch). Name:
`040_scheduling_link_create_keys`.

```sql

-- PAC-119 (contracts/features/PAC-119.md section 3): the Idempotency-Key of a
-- keyed link create, per account, with the link it created. The request digest
-- and the co-host outcomes are kept for the 24-hour replay window only and
-- cleared by the hourly cleanup; owner, key, link and time are kept for ever.
CREATE TABLE scheduling_link_create_keys (
    owner_user_id   UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    idempotency_key TEXT        NOT NULL,
    link_id         UUID        NOT NULL REFERENCES scheduling_links(id) ON DELETE CASCADE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    request_sha256  BYTEA       NULL,
    co_host_changes JSONB       NULL,
    CONSTRAINT scheduling_link_create_keys_owner_key PRIMARY KEY (owner_user_id, idempotency_key),
    CONSTRAINT scheduling_link_create_keys_link UNIQUE (link_id),
    CONSTRAINT scheduling_link_create_keys_key_format
        CHECK (idempotency_key ~ '^[A-Za-z0-9_-]{16,255}$'),
    CONSTRAINT scheduling_link_create_keys_digest_length
        CHECK (request_sha256 IS NULL OR octet_length(request_sha256) = 32),
    CONSTRAINT scheduling_link_create_keys_outcomes_need_digest
        CHECK (co_host_changes IS NULL OR request_sha256 IS NOT NULL)
);
CREATE INDEX scheduling_link_create_keys_retained
    ON scheduling_link_create_keys (created_at) WHERE request_sha256 IS NOT NULL;
```

- **PAC-116 stop-traffic rule.** It is applied only by the migrate-when-stopped
  procedure: the backend at start, or `paceday-operator`, after taking the

  session (PAC-116 §0, §3; runbook "Applying migrations: stop, migrate, start",

### 7.2 Key lifecycle in the editor (spec §3.7)

- **State**: one key, in a `useRef` of the drawer component (page memory only). It is
  never in `localStorage`, `sessionStorage`, IndexedDB, a cookie, the URL or
  `history.state` (AC-23).
- **Made**: on the first Create link press of a create-mode editor session, when no
  key is held.
- **Re-sent**: on every further Create link press in that session, whatever the last
  failure was (lost answer, budget 503, any 5xx, any 4xx; AC-16).
- **Dropped**:
  - on a 201, whether the editor closes or stays open as an editor of the link;
  - when the drawer closes;
  - on the key-reused or expired refusal (the editor becomes an editor of `link_id`);
  - on the deleted refusal (the next press makes a new key).
- **Opening** the drawer for a new link starts with no key (AC-17).

### 7.3 No close path while a save is pending (spec §3.8 item 6, OQ-8; AC-27)

- the `Sheet`'s `onOpenChange` is wrapped. A request to close (`false`) is dropped,
  and the parent's `onOpenChange` is not called. Radix routes the X button
  (`SheetPrimitive.Close`, `sheet.tsx:60-63`), Escape and a click outside through
  this one callback, so all three are blocked;
- Cancel stays `disabled` (today, `LinkEditDrawer.tsx:757`);
- the X button may also be rendered disabled, but the wrapped callback is the rule.
  `sheet.tsx` may gain an optional prop for this. Its default behaviour for every
  other sheet must not change.

After the save settles, all four close as today. The settled-close tests
(`LinkEditDrawer.pac112.test.tsx:190-197`, `:203-211`, `:306-318`) keep passing.

## 11. Alternatives rejected

- **Columns on `scheduling_links`**: §3.2.
- **Store the full original response** (PAC-82's rejected "response" column): it
  would freeze the link's fields and roster, against spec OQ-4. Only the outcomes are
  stored, because they cannot be rebuilt.
- **Compare against the stored link row** (PAC-82's matching): a link is edited
  freely, so a retry after a rename would be refused (spec D-3.2).
- **Hash the raw body**: key order, whitespace, aliases and defaults would make a
  web retry differ, and the raw body holds addresses. The digest is over the
  normalised form (§2.3).
- **Decide in the handler on the pool, or after rollback on the bare connection**
  (PAC-82 `scheduling_links.go:552-563`): bypasses PAC-71 (spec B-2). Every decision
  is in R.
- **Insert the key row last, with the outcomes, and no UPDATE**: one fewer statement,
  but a concurrent duplicate in AC-7(b) would do all of its lookups and invitations
  before failing on the key, holding `FOR KEY SHARE` on every invitee in the
  meantime. Claiming the key first stops it at once.
- **Pre-generate the link id and insert the key row before the link**: avoids nothing
  that §4.2 does not already handle (the slug wait in case (a) happens first either
  way), and needs an explicit id in `CreateSchedulingLink`.
- **`INSERT … ON CONFLICT DO NOTHING` for the key**: the wait on an uncommitted
  winner happens anyway, and a silent no-op would have to be detected and turned into
  the same R3. `23505` is the explicit signal PAC-82 already uses.
- **410 for the deleted refusal, 422 for the reused key, 200 for the replay**: §1.3.
- **Reusing `BookingIdempotencyKey`**: §2.1.
- **A replay marker header**: the editor treats a replay as a 201 (spec §6), and an
  exposed header would need a CORS change (PAC-82 §2.3).
- **Expiring keys from storage after the window** (forgetting them): spec OQ-2
  default. A forgotten key would make a day-old retry a second link.
- **`clock_timestamp()` for `created_at`**: the spec ages from the transaction's
  `now()` (Pass 2 minor 5). With `clock_timestamp()` two statements of one save would
  disagree with the link's own `created_at`.

### Findings

#### MAJOR

**M-1. After a link refusal, or after any 4xx that follows a lost answer, the links
list never catches up. The failed-baseline texts also send the owner down a path that
does not reach the link.**

The md says, at §7.4 lines 593-595: "When the drawer closes while 'outcome unknown' is
set, the editor invalidates `schedulingLinkKeys.links`. The flag clears on any later
settled answer." Lines 578 and 580 say "reopen the editor to try again". The
requirement is spec §3.8 item 5 (line 300) and AC-22 (line 490).

Constructed sequence:

1. Press 1 is `POST /api/scheduling-links` with `Idempotency-Key: 3f0c…` and
   `{"title":"Intro","duration_options":[30],"co_host_emails":["b@x.com"]}`.
   - The server commits link L, and the response is aborted.
   - The editor sets "outcome unknown".
   - The list cache does not hold L: `onError` invalidates nothing
     (`LinkEditDrawer.tsx:366-371`).
2. The owner changes the title. Press 2 is answered
   `409 {"error":"idempotency key already used","link_id":"<L>"}`.
   - By §7.4 this is a settled answer, so the flag clears.
   - The editor becomes an editor of L.
3. The owner closes the drawer without saving.
   - Nothing invalidates `schedulingLinkKeys.links`.
   - The Links page does not list L until some unrelated refetch, although L exists
     and the editor just named it.

The same happens when press 2 is any 4xx decided **before** key resolution, such as a
server field 422 or a 401. By §1.1 these come before R1, so they say nothing about
whether L exists, yet they clear the flag.

In the failed-baseline variant, "reopen the editor" cannot be followed:

**m-1. §4.1 step 6 (md lines 319-322) rests on a premise that is false in production,
and the AC-10/AC-29 seams must move the generation with a plain `UPDATE`.**

The md says "a generation bump is a non-key UPDATE, which FOR KEY SHARE does not
block". The spec says the same in D-5 (line 602) and §2.1 (line 49). In fact, every
production advance first runs `lockAccountExclusive`, which issues
`SET LOCAL lock_timeout='10s'; SELECT … FOR UPDATE` (`backend/storage/session.go:88-100`,
called from `operator.go:84` and `signin.go:222`). `FOR UPDATE` conflicts with
`FOR KEY SHARE`.

Observed on PG 16:
- **Test 3b (production-shaped advance).** R takes `FOR KEY SHARE` at t=52.6. An
  advance starting at t=53.6 **waits**. Re-check #2 at t=55.6 still reads the old
  generation. The advance commits only at t=55.65, after R's COMMIT.
- **Test 3a (raw update).** With `UPDATE users SET session_generation = session_generation + 1`,
  the bump commits at once and re-check #2 sees it (gen 0, then 1).

Consequences:
- Re-check #2 is harmless belt-and-braces in production.
- AC-10's second seam and AC-29 can only be satisfied by moving the generation the way
  `pac71_guard_writer_test.go:52` does (`moveGeneration`, a raw `UPDATE`).
- A test that calls a production revoke from inside `afterLinkCreateKeyRead`, or while
  the loser waits, blocks on R's or the loser's own `KEY SHARE` until the advance's
  10 s `lock_timeout`.

Fix:
- Correct the rationale in §4.1 step 6.
- State in §6 that these seams use a plain `UPDATE`.
- Add a §4.5 row: "production generation advance vs R or a waiting create: the advance
  waits (bounded by its own 10 s lock_timeout); pre-existing for every guarded link
  write".
