## 0. The rule this contract fixes

An account is a member of an organisation only when the domain has vouched for the
person: the account is **domain-confirmed** (PAC-71), its address's domain is **not
a consumer domain**, and the organisation is **the one for its address's domain**.
That is decided **at every read**, so no stored association can make a member of
someone who fails it. Everyone else belongs to no organisation and is answered
exactly as an account with no organisation has always been answered. Sign-in keeps
the stored association in line, a one-time migration ends the failing ones at
deploy, and the member list says 500 when it cannot read the caller instead of
pretending the organisation is empty.

## 2. Membership (binding; spec §3.1, §3.2, D-1, D-3)

### 2.1 The rule

Account A **belongs** to organisation O exactly when all of these hold at the read:

1. `A.users.org_id = O.id` (a stored association);
2. `A.address_standing = 'domain_confirmed'`;
3. `O.domain` is not on the consumer list (`domain.GenericDomains()` of the running
   release; with 3 below this is the same as "A's address's domain is not on the
   list");
4. `O.domain = addrDomain(A.email)`, exactly, where `addrDomain` is §2.2's one
   expression (`domain.ExtractDomain` in Go).

Otherwise A belongs to no organisation. "Belongs" is the only meaning of
"member", "the caller's organisation", "no organisation", `inOrganization` and
`org` anywhere in the contract.

### 2.2 One domain expression, one membership expression

**`addrDomainSQL(col)`**, the one SQL expression for condition 4 (spec §3.1,
re-challenge N-1). Every place that evaluates condition 4 in SQL uses it verbatim:
the read-time rule, migration 043 and pre-deploy query 1 (§5.5).

```sql
CASE WHEN strpos(<col>, '@') = 0 THEN ''
     ELSE lower(btrim(substr(<col>, strpos(<col>, '@') + 1),
          U&'\0020\0009\000A\000B\000C\000D\0085\00A0\1680\2000\2001\2002\2003\2004\2005\2006\2007\2008\2009\200A\2028\2029\202F\205F\3000'))
END
```

- It mirrors `ExtractDomain` (`backend/domain/domain.go:19-25`): the text after the
  **first** `@` (so `a@b@ACME.com` is `b@acme.com`), `''` with no `@`, trimmed of
  exactly the characters `unicode.IsSpace` reports (the 25 code points above,
  which is what `strings.TrimSpace` trims), then lower-cased.
- `lower()` uses the database's default collation, deliberately **not** an ICU
  collation: checked on `postgres:16.15-alpine` (the production image,
  `docker-compose.prod.yml:32`), whose initdb ctype is `en_US.utf8`, `lower()`
  equalled Go's `strings.ToLower` on all 25 fixtures tried, including `É`, final
  `Σ`, `İ` (U+0130 → `i`), the Kelvin sign (U+212A), `ẞ` (U+1E9E), `ǅ`/`Ǆ`, the Ohm
  sign, Cyrillic, a Deseret letter (U+10400) and every white-space code point;
  `COLLATE "und-x-icu"` differed on `İ` (full case mapping, `i̇`). This is the
  challenge's note 1 answered with evidence, not an assumption (contract-author
  run, 2026-11-19; fixtures in §7).
- **The test that binds it** (AC-14 contract sub-test, `TestPAC148_AddrDomainSQLEqualsExtractDomain`):
  runs the expression on the test database for the fixture set of §7 (which
  includes the spec's cases: ASCII upper case, surrounding white space, a second
  `@`, no `@`, non-ASCII upper case) and asserts equality with `ExtractDomain`. It
  first asserts that the test database's `datctype` is `en_US.utf8` and that
  `version()` reports 16.15, so it cannot pass on a database that differs from
  production. `scripts/test-backend.sh` (and any CI service that provides the test
  database) is pinned to `postgres:16.15-alpine`, the production tag, instead of
  the floating `postgres:16-alpine`.
- If the two ever disagree for some address, the read-time rule **fails closed**
  (the account is not a member); the release check of §5.5 (query 0) confirms the
  production ctype before deploy.

**`effectiveOrgSQL(u)`**, the one SQL expression for "the organisation account `u`
belongs to" (NULL when none). The consumer list is embedded as a SQL array literal
built once from `domain.GenericDomains()` in Go (each entry checked against
`^[a-z0-9.-]+$` when the literal is built, so it cannot inject), never passed by
the caller:

```sql
(SELECT eo.id FROM organizations eo
  WHERE eo.id = u.org_id
    AND u.address_standing = 'domain_confirmed'
    AND eo.domain <> ALL(<listed>)
    AND eo.domain = <addrDomainSQL(u.email)>)
```

The exact text is the plan's; binding are: one expression, defined once in
`storage`, built from `addrDomainSQL` and the Go list; it reads only the account's
own row and the organisation row its `org_id` names (never an organisation by
domain).

### 2.3 Every read of membership goes through it (D-3, AC-4)

Each of these reads `users.org_id` for a membership decision today and must read
`effectiveOrgSQL` instead (or receive a `User.OrgID` that was read through it):

| Reader | Today | Consumers |
|---|---|---|
| `storage.getUserRow` (`GetUserByID`, `GetUserByIDNoOrg`) and `GetUserByEmail` | raw `org_id` into `User.OrgID` | `listOrgMembers`, `getCurrentUser` (`org` hydration), `orgCaller` (organisation AI), `callerOrg` and `getSsoStepupOptions` / start (SSO), the step-up callback's state check (`handlers_sso_stepup.go:458`), `listSsoProviders` |
| `orgMemberSetSQL` (viewer `me` and listed `o`) | raw `org_id` equality | `GetOrgMembers`, PAC-130 rule (b) (§2.5) |
| `storage.ReadOrgAIState` | raw `u.org_id` | parse (and MCP parse), meeting briefs, the probe, the settings read's `AIStatus` |
| `storage.UserInOrganization` | `org_id IS NOT NULL` | settings |
| `storage.lockUserRow` (ConfirmOrgAI, the settings write) | raw `org_id` under `FOR NO KEY UPDATE` | `confirmOrganizationAI`, the settings write's org-AI checks |

`User.OrgID` therefore **means** the effective organisation everywhere above it.

### 2.4 Sign-in keeps the stored association in line (D-3, AC-1, AC-5, AC-6)

`storage.AssociateUserWithOrg` is replaced by one storage step (name the plan's;
here **`ReconcileUserOrg(db, userID)`**), called where `associateOrg` is called
today (Google `handlers_pac71_auth.go:189`, Microsoft `:324`, SSO
`handlers_sso.go:207`), after the sign-in's binding committed. In one transaction:

1. `SELECT email, address_standing, org_id FROM users WHERE id = $1 FOR NO KEY
   UPDATE` (PAC-87's users-row lock, `orgs.go:60`, `org_ai.go:560-570`). The decision
   uses the **stored** standing and address, never the sign-in's evidence or the
   handler's copy of the email.
2. Decide in Go: qualifies ⇔ standing is `domain_confirmed`, `d :=
   domain.ExtractDomain(email)` is not `""`, and `!domain.IsGenericDomain(d)`.
   Nothing keyed on the domain runs before this decision.
3. **Qualifies**: `UpsertOrg(d, DeriveOrgName(d))`, then today's `SetUserOrg`
   semantics under the lock already held (a changed organisation deletes every
   organisation-AI confirmation of the account; an unchanged one deletes those of
   other organisations).
4. **Does not qualify**: if `org_id` is not NULL, `DELETE FROM org_ai_confirmations
   WHERE user_id = $1` and `UPDATE users SET org_id = NULL WHERE id = $1`; if it is
   NULL, nothing more. No organisation is read, looked up or created.

A failure keeps today's handling (SF-071): logged and reported by user id through
`lifecycle.Fail` (`Kind: "org-association"`), the sign-in goes on. An AI call that
read its state before the leave committed may complete once on the organisation's
key (accepted residual, spec §3.2, as PAC-87).

### 2.6 Equal work for a caller who belongs nowhere (AC-1)

For a caller that belongs to no organisation, the sign-in step (§2.4) and the
member-list read run the same statements whatever accounts exist at the caller's
domain, and none of them is keyed on that domain (no `UpsertOrg`, no organisation
read by domain). The member-list read is: the caller's row (through
`effectiveOrgSQL`), then `[]`. `getCurrentUser` reads no organisation for such a
caller. AC-1 pins it with the statement seam of §7.

        'yandex.ru',
        'zoho.com'
        -- consumer-list:end
    ]::text[];

    ending uuid[];
    n_confirmations bigint;
BEGIN
    -- The gate (spec §3.5 B-4; the same check as pre-deploy query 2).
    SELECT string_agg(g.kind || ' ' || g.domain, ', ' ORDER BY g.kind, g.domain)
      INTO blocked
      FROM (SELECT 'sso_provider' AS kind, lower(domain) AS domain
              FROM sso_providers WHERE lower(domain) = ANY(listed)
            UNION ALL
            SELECT 'org_ai_configuration', o.domain
              FROM org_ai_configurations c JOIN organizations o ON o.id = c.org_id
             WHERE o.domain = ANY(listed)) g;
    IF blocked IS NOT NULL THEN
        RAISE EXCEPTION 'PAC-148 migration 043 refused: configuration on a consumer-list domain: %', blocked
            USING HINT = 'Nothing was changed. See docs/runbook.md, "PAC-148 migration gate".';
    END IF;

    -- Every stored membership that fails the rule (§2.1), with addrDomainSQL verbatim.
    SELECT coalesce(array_agg(u.id), '{}')
      INTO ending
      FROM users u JOIN organizations o ON o.id = u.org_id
     WHERE NOT (u.address_standing = 'domain_confirmed'
                AND o.domain <> ALL(listed)
                AND o.domain = CASE WHEN strpos(u.email, '@') = 0 THEN ''
                                    ELSE lower(btrim(substr(u.email, strpos(u.email, '@') + 1),
                                         U&'\0020\0009\000A\000B\000C\000D\0085\00A0\1680\2000\2001\2002\2003\2004\2005\2006\2007\2008\2009\200A\2028\2029\202F\205F\3000'))

    DELETE FROM org_ai_confirmations WHERE user_id = ANY(ending);
    GET DIAGNOSTICS n_confirmations = ROW_COUNT;
    UPDATE users SET org_id = NULL WHERE id = ANY(ending);

    RAISE LOG 'PAC-148 migration 043: ended % organisation memberships and % organisation-AI confirmations',
        cardinality(ending), n_confirmations;
    RAISE NOTICE 'PAC-148 migration 043: ended % organisation memberships and % organisation-AI confirmations',
        cardinality(ending), n_confirmations;
END $$;

- the ending set is exactly the stored memberships failing §2.1, computed with

- for each ending account, **every** organisation-AI confirmation of the account is
  deleted (PAC-87's leaving rule: all of them, not only the organisation left), and

- no other column or row changes: `users.updated_at` is not touched (no trigger

- the count is reported by `RAISE LOG` and `RAISE NOTICE` (AC-7);
- the list between `-- consumer-list:begin` and `-- consumer-list:end` is one
  single-quoted lower-case entry per line, sorted, nothing else on those lines;
  AC-16's test parses exactly that block.

The SQL above was executed by the contract author on `postgres:16.15-alpine`

### 5.4 Recovery: the runbook procedure (binding in substance; spec §7, challenge notes)

The plan adds a section **"PAC-148 migration gate"** to `docs/runbook.md`, under
"Rollback", next to "Rollback on the same host". In substance:

> **When**: `compose logs backend` shows `PAC-148 migration 043 refused:
> configuration on a consumer-list domain: …` and `Dirty database version 43`.
> Use this procedure **only** after this abort. After any other failed migration,
> follow "Rollback on the same host". Never force while a migration is running
> ("being applied by …" means it is still running).
>
> **P** is the version immediately before this release's migration: **42**
> (`042_manager_member_link_erase`). **N** is 43.
>
> 1. **Stop every backend**, so the new image stops restarting and cannot re-run
>    043 against the forced version: `docker compose -f docker-compose.prod.yml stop

>    exited, not `Restarting`.
> 2. **Check the state**: `SELECT version, dirty FROM schema_migrations` must be
>    `43 | t`. Any other answer: stop and follow "Rollback on the same host".
> 3. **Force to P**: `UPDATE schema_migrations SET version = 42, dirty = false;`
>    (equivalent to golang-migrate `force 42`; `schema_migrations` is its single
>    row). Check it reads `42 | f`.
> 4. **Start the previous release's backend image** (the release before this one),
>    as in "Rollback on the same host"'s deploy step. It accepts the database
>    (`VersionCurrent`).
> 5. **Resolve the conflict** reported in the log: for each named `sso_provider` or
>    `org_ai_configuration`, the owner decides to delete it or to drop the domain
>    from the release's consumer list (a new build, with the migration's literal
>    changed to match, AC-16). Never edit the migration to skip the gate.
> 6. **Re-run pre-deploy query 2** (§5.5) against the database. It must return no
>    row; if it returns any, go back to step 5. Only then redeploy the new image,
>    which applies 043 from the start.
>
> Forcing is safe here only because 043's work is one statement that rolled back
> (no data changed). The alternative is always "Rollback on the same host"
> (restore the pre-deploy backup), which is heavier but valid.

### 5.7 Rollback

- The down step is a no-op and cannot restore memberships or confirmations; each
  ended membership was the leak.

  then the previous image, which joins on the domain alone again at the next

## 12. Alternatives rejected

1. **Enforce only at write time** (sign-in plus migration, reads keep raw
   `org_id`). Rejected: spec D-3 requires the rule at every read, and production
   stores mismatches the write path never revisits (`free-address`, fixtures, the
   restore rehearsal, an image rollback window).
2. **A per-handler membership check** (each gate calls a new `IsMember`). Rejected:
   eleven call sites, three SQL readers and the AI-spend path would each need it,
   and the next reader would forget it. Routing `User.OrgID`, `ReadOrgAIState`,
   `UserInOrganization`, `lockUserRow` and `orgMemberSetSQL` through one expression
   (§2.3) makes the wrong answer hard to write.
3. **Pass the consumer list as a query parameter.** Rejected: every membership read
   would carry a 38-element array, and a caller could pass a different list. A
   literal built once from the Go list cannot diverge from it.
4. **`lower(... COLLATE "und-x-icu")`** for a locale-independent fold. Rejected on
   evidence: ICU's full case mapping lowers `İ` to `i̇`, not Go's `i` (§2.2).
5. **Skip, or detach and record, on a gate hit** instead of aborting. Rejected by
   the spec (§3.5): either leaves a configuration of unclear provenance on a domain
   whose members were silently detached.
6. **Make the migration abort leave a clean (not dirty) version** (e.g. a
   pre-migration check outside golang-migrate). Rejected: it would need a second
   code path in the start-up runner for one migration, while the force procedure
   on a known-rolled-back file is short and testable (AC-17).
7. **Remove `GET /api/org/members`** (OQ-3). Rejected by the spec's default (D-7):
   PAC-130 rule (b) would lose its backing disclosure.
8. **A 404 or a dedicated "not a member" error on the member list.** It would
   distinguish "no organisation at your domain" from "you are not vouched for",
   which is G-3's bit; `[]` answers both.
9. **Leave `OrgMember.provider` without an enum, marker deleted.** That is deleting
   the marker, not resolving it (agent definition step 4).
