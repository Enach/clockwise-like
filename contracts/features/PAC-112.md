## 0. The rule this contract fixes

A save from the link editor writes exactly the co-host list the owner sees, in the
same request as the link's fields, and the server's answer to that save says what
happened to every listed address and who was removed. The editor reports those
numbers and nothing else. Create becomes all or nothing, like PATCH already is
(PAC-101). The editor takes the list it edits only from the strict single-link
read.

## 1. What changes at the HTTP boundary

| Operation | Change |
|---|---|
| `createSchedulingLink` | 201 body is `SchedulingLinkSaved` (= `SchedulingLink` + optional `co_host_changes`). All or nothing: link, owner row and invitations in one transaction; every 500 leaves no link. Owner row never demoted (API-048 remnant). New 422s: blank co-host entry; over-5 list that adds someone; unrecognised `days` name (API-053). |
| `updateSchedulingLink` | 200 body is `SchedulingLinkSaved`. New 422s as on create; the over-5 422 is decided inside the transaction, after the link lock (so a deleted link is the 404 first). 500 also when the host rows or a removed host's address cannot be read for `co_host_changes`. |
| `getSchedulingLink` | No behaviour change. The description now states that it is the only read a co-host baseline may come from, so its strictness (PAC-25) is load-bearing. |
| Request schemas | `co_host_emails.items` gains `minLength: 1` and `pattern: '\S'` (blank entries); no `maxItems` (§6.2). `days` descriptions state the 422. |
| `SchedulingLinkValidationError` | Three new messages (§4). |
| New schemas | `SchedulingLinkSaved`, `SchedulingLinkCoHostChanges`, `SchedulingLinkCoHostOutcome`, `SchedulingLinkRemovedHost`. |

`SchedulingLinkSaved` shares `SchedulingLink`'s property map through a YAML
anchor (`&schedulingLinkProperties`), the pattern `Settings`/`SettingsUpdate`
already use (PAC-24 revision 3), so the two cannot drift. `getSchedulingLink` and
`listSchedulingLinks` keep `SchedulingLink`: `co_host_changes` cannot appear in a
read.

No operation, status code or path is added or removed. `inviteSchedulingLinkHost`
and the accept, decline and leave operations are untouched.

## 2. The per-address outcome (binding)

### 2.1 Shape

```json
{
  "id": "…", "title": "…", "hosts": [ … ], "…": "every SchedulingLink property",
  "co_host_changes": {
    "addresses": [
      { "email": "E@acme.com",  "outcome": "already_host" },
      { "email": "g@acme.com",  "outcome": "invited" },
      { "email": "c@nowhere.io","outcome": "not_added" },
      { "email": "a@acme.com",  "outcome": "own_address" }
    ],
    "removed": [ { "user_id": "…", "email": "b@acme.com", "status": "pending" } ],
    "invited_count": 1,
    "removed_count": 1,
    "not_added_count": 1
  }
}
```

- `co_host_changes` is present exactly when the request carried `co_host_emails`
  (non-null, `[]` included) and the save succeeded. Absent otherwise.
- `addresses` has one item per request entry, same order, same length,
  duplicates included. `email` is the entry trimmed, letter case kept. Item *i*
  describes entry *i*, so a client matches outcomes to chips by position.
- `removed`: every non-owner host this save removed, with the status they had.
  Always `[]` on create. Never the owner.
- Counts are of **people**, not entries (spec §3.5):
  - `invited_count`: distinct accounts whose outcome is `invited`;
  - `removed_count`: the length of `removed`;
  - `not_added_count`: distinct entries (trimmed, ignoring case) whose outcome is
    `not_added`. `not_added` has no person, so distinct addresses are the unit.
  - `already_host` and `own_address` are not counted (spec §3.4 table).
- Everything in `co_host_changes` is computed inside the write's transaction, from
  the host rows read there. It is never degraded: a failed read is the 500 with
  nothing changed. The `hosts` roster beside it is still built non-strictly and
  is not a baseline (§5.1).

### 2.2 Which outcome (binding order)

For each entry, with *H* the link's host rows read inside the transaction before
any change, and *carriers* the accounts carrying the entry at any standing,
ignoring case (PAC-71):

1. `own_address`: the entry has exactly one carrier, it holds the address
   domain-confirmed, and it is the owner. The owner's row is not touched.
2. `already_host`: the one domain-confirmed holder, or else any carrier, is a
   non-owner host in *H*, whatever their status. They keep their status (PAC-61,
   PAC-71 AC-43). This is how a host listed by an address they carry only
   unconfirmed is reported (AC-9).
3. `invited`: the one domain-confirmed holder is not in *H* and is not the owner.
   One `pending` row is created for that account in this save. Every entry that
   reaches the same account reports `invited` (AC-18).
4. `not_added`: anything else. No row is written. The owner's own address held
   only unconfirmed, or shared by case-differing accounts, lands here (spec §3.7);
   the owner's row is still unchanged.

`already_host` cannot occur on create (*H* holds only the owner).

### 2.3 Rejected shapes

- **A wrapper** `{ "link": {…}, "co_hosts": {…} }`. Breaks the e2e create that
  reads `id` from the body (`e2e/tests/public-booking.spec.ts:615-630`, frozen by
  spec §6) and every client of the 201/200 body, for no gain.
- **`co_host_changes` added to `SchedulingLink` itself.** Every read
  (`getSchedulingLink`, the list) would then permit a field it never carries, and
  the generated web type would make the editor's baseline type admit outcomes it
  must never use (D-3). A separate response schema says what each operation
  returns.
- **`allOf: [SchedulingLink, {co_host_changes}]`.** `SchedulingLink` is
  `additionalProperties: false`, so the composition rejects every body; and
  PAC-24 revision 3 records that the three generators mishandle `allOf` with
  shared markers. The anchor is the repo's established pattern.
- **Outcomes keyed by lowercased address** (`{"b@acme.com": "invited"}`). Loses
  order and duplicates, and makes a client re-derive the server's normalisation.
  Position is unambiguous.
- **A `reason` on `not_added`** (no account / unconfirmed / shared). Rejected by
  spec D-6 and PAC-71: it would tell the owner about other people's accounts.
- **Counts only, no per-address outcome.** The editor must name each address
  that was not added (AC-11). Counts alone cannot.
- **Outcomes derived by the client from the roster.** Spec D-2: the roster can be
  degraded and is read after the write; a concurrent edit would make it lie.

## 3. Server rules (binding)

### 3.1 Create is all or nothing (spec D-4, AC-15, AC-20 to AC-22)

One transaction holds: the link insert, the owner's `accepted` host row (a plain
insert, never the upsert that demoted the owner, API-048), and every invitation.
Any failure in it (owner row, co-host lookup, co-host write) is
`500 {"error":"internal error"}` and the transaction rolls back: no link, no host
row. Checks that already ran before any write (owner read, zone read, slug
generation and check) keep their answers. Nothing makes create retry-safe (spec
§5, accepted risk).

### 3.2 PATCH (unchanged transaction, new report)

PAC-101's transaction is kept: the UPDATE takes the link lock first; a deleted
link is the 404. Inside it, after the UPDATE: read *H*; evaluate §3.3; compute
the keep set, removals and invitations as today (PAC-61, PAC-71); read each
removed host's address; build `co_host_changes`; commit. Any failure is the 500
with nothing changed (PAC-101).

### 3.3 The list limit (spec §3.6, D-8; P3-m1, P3-m2)

- **Rule.** A list with more than 5 entries (counted as sent) is refused when at
  least one entry reaches no current host. "Reaches" uses the keep rule: some
  carrier of the entry is in *H*. "Current host" means a row in *H*, the owner
  included, any status. On create *H* is the owner alone.
- **Where it is decided (P3-m1).** Inside the write's transaction, after the
  link's lock (PATCH: after the UPDATE), against *H* read there. Never from an
  earlier read. A concurrent change can therefore make a list refused, never let
  one through past the cap. A link deleted before the lock is the 404, not this
  422.
- **The answer.** `422 {"error":"a co-host list longer than 5 can only keep or
  remove co-hosts, and this one names someone who is not a current host of the
  link"}`, nothing changed (fields included on PATCH; no link on create). Worded
  so an owner whose list was overtaken by another tab (spec P3-m1 example) reads
  "someone on your list is no longer a host", not "too many".
- **No pre-check (P3-m2: dropped).** Spec revision 3 recommended refusing more
  than max(5, current co-host count) entries before any lookup. That compares
  entries to people and refuses keep-only lists §3.6 accepts (two spellings of one
  co-host, or the owner's own address). Making it consistent needs the very
  lookups it was meant to save, so it is dropped. Cost is bounded by the order
  instead, which is binding:
  1. entries are deduplicated (trimmed, ignoring case) before any lookup; each
     distinct address is looked up **at most once per save**, and that one result
     serves the limit, the keep set and the invitation;
  2. when the list has more than 5 entries, distinct addresses are looked up in
     request order and the save is refused at the **first** one that reaches no
     current host, before any further lookup and before any removal or
     invitation.

  A refused list therefore costs at most one lookup past its keep-only prefix. An
  accepted list longer than 5 costs at most one lookup per distinct address that
  reaches a current host, which is bounded by the addresses the link's hosts
  carry. A list of 5 or fewer costs at most 5 lookups.
- **What stays accepted.** Any list that only keeps or removes, at any length
  (AC-32): a link with 7 co-hosts can lose one at a time.

### 3.4 Validation before any write (spec D-9)

All 422 (`SchedulingLinkValidationError`), nothing written:

| Case | Message | When |
|---|---|---|
| unrecognised `days` name | `days contains an unrecognised day name` | `days_of_week` absent or null, and any `days` entry, trimmed and ignoring case, is not one of `sun`..`sat`, `sunday`..`saturday`, `0`..`6`. Replaces today's silent drop; for `["Montag"]` it replaces "at least one day is required". A mixed list is refused too. When `days_of_week` is carried, `days` is ignored entirely, unrecognised names included (PAC-40 D-5). Create and PATCH (API-053, widened). |
| blank co-host entry | `co_host_emails must not contain a blank address` | any entry empty or only whitespace. Create and PATCH. |
| over-5 list that adds | §3.3 text | decided inside the transaction (§3.3). |

Order: body decode (400) → existing field validation, where the `days` check runs
at alias resolution and so is reported before the generic day message → blank
entry → (PATCH: slug check 409, then the transaction and §3.3). When a body has
several faults, only the first in this order is reported. 400 keeps meaning "body
is not valid JSON" (spec §6).

The server does not check `format: email`; a non-address string is `not_added`.
`minLength`/`pattern` on the items express the blank rule to generated clients.

### 3.5 What does not change

PAC-61 statuses, PAC-71 grant/keep/remove rules, PAC-101 ordering and the 10 s
lock bound, `getSchedulingLink` strictness (PAC-25), PAC-40 D-5, the
single-invitation operation and both its 404 bodies, accept/decline/leave,
bookings of a removed host (no foreign key, spec §2.4).

## 5. The editor (non-HTTP, binding for the web stage)

### 5.1 Baseline (spec D-3, §3.2, §3.3; AC-6, AC-25, AC-29 to AC-31)

- The baseline is the `hosts` of a `200` from `getSchedulingLink`, non-owner
  rows only. Taken when the editor opens on an existing link and after every save
  that keeps the editor open. Never from `listSchedulingLinks`, never from a
  `SchedulingLinkSaved`.
- New link: the baseline is empty until the first successful save; after it, the
  editor re-reads the created link by the `id` in the 201.
- While the read is pending or after it failed, co-host editing is disabled with a
  visible reason, and every save carries no `co_host_emails`. Other fields still
  save. Reopening the editor retries.
- **Changed** = the chips differ from the baseline as sets of addresses compared
  ignoring case. Unchanged → no `co_host_emails` key. Changed → the complete chip
  list, in the same PATCH or POST as the fields (one request; AC-5).

### 5.2 Chips

- Adding refuses: the owner's own address, any case (AC-14, text below); an
  address already a chip, ignoring case (AC-17, today's text "This co-host is
  already added."); a sixth chip (today's text "You can invite up to 5 co-hosts.",
  AC-33 regression guard). Hydrated chips above 5 are allowed and removable.
- Chips, and the list cache seeded by a save, contain only hosts the server
  returned: no `pendingHost` padding (AC-13). After a save, chips come from the
  strict re-read.

### 5.3 Wording (spec §3.4, §3.9; AC-11, AC-12). "The contract fixes the exact text."

`{n}` comes from `co_host_changes`, never from a client diff.

| Where | Text |
|---|---|
| per address, `not_added` | `{email} couldn't be added as a co-host.` |
| per address, `own_address` | `{email} is your own address — you're the link's owner.` |
| chip refused, own address | `That's your own address — you're the link's owner.` |
| success, list carried | `Link created.` / `Link updated.`, then `{invited_count} co-host(s) invited — they can accept from Paceday.` (always present when `co_host_changes` is; `0 co-hosts invited.` without the dash clause when zero), then `Removed {removed_count} co-host(s).` when > 0, then `{not_added_count} address(es) couldn't be added as a co-host.` when > 0 |
| success, no list carried | `Link created.` / `Link updated.` (today) |
| fallback: list carried, answer has no `co_host_changes` (server without PAC-112, spec §7) | `Link created.` / `Link updated.`, then `Paceday couldn't confirm which co-hosts were added — check the co-host list.` The editor stays open and re-reads the baseline. |
| co-host editing disabled, read pending | `Loading co-hosts…` |
| co-host editing disabled, read failed | `Co-hosts can't be edited right now because the current list couldn't be loaded. Reopen the editor to try again.` |

Singular/plural: `1 co-host`, `2 co-hosts`; `1 address`, `2 addresses`. No
message says "sent", "email" or "no Paceday account".

### 5.4 After a save (spec §3.10, OQ-1 default; AC-11, AC-24)

- Any `not_added` or `own_address` outcome → the editor stays open, lists those
  addresses with the texts above, re-reads the baseline, and from then on edits
  the link by its `id` (a create becomes an edit; no second POST).
- Otherwise the editor closes as today.
- Any 4xx/5xx or network failure: error shown through `apiErrorMessage`, no
  success message, input kept (spec §3.8).

### 5.5 Demo mode (spec §3.13, AC-26)

The demo create and update return the same `co_host_changes` by the rules of §2
and §3.3, with "domain-confirmed holder" meaning an account in the demo directory.
Update treats the list as complete (it already does) and stops adding unknown
addresses as pending; create stops adding unknown addresses. Same texts.

## 6. Decisions

### 6.1 One save, outcomes in its answer (spec D-1, D-2)

Taken from the spec. Contract consequence: the outcome object lives in the
create/PATCH body (§2.3), and per-address `POST /{id}/hosts` calls are no longer
made by the editor. That operation stays for other clients.

### 6.2 No `maxItems` (spec D-8)

`maxItems: 5` would refuse AC-32 (remove one from 7). `maxItems: N` for any
larger N is an invented limit the spec does not have (body size is a follow-up,
spec §5). The rule is in prose on the property and the operation, and in §3.3.

### 6.3 Pre-check dropped, order bound instead (P3-m2)

§3.3. The alternative kept for the record: narrowing spec §3.6 so a keep-only list
may not contain duplicates or the owner's address. Rejected: it would add a
refusal no editor-built list hits, purely to make a cheap counter right, and the
order rule already bounds the cost.

### 6.4 Over-5 decided under the lock (P3-m1)

Alternative: decide it before the transaction from a plain read, as today's field
validation is. Rejected: the race goes both ways (spec challenge P3-m1), and the
one that lets a list past the cap is silent. Under the lock only the visible 422
remains.

### 6.5 Fixed day-name 422 text rather than echoing the name

Echoing `"Montag"` would help a little, but every other message in
`SchedulingLinkValidationError` is a fixed string, and the web renders the
server's text verbatim (PAC-83). A fixed text keeps the response enumerable in
the contract.

## 9. Rollback

No migration. Revert the server PR: answers lose `co_host_changes`, create is
again non-transactional, the 422s disappear. A web build with PAC-112 then shows
the §5.3 fallback. Revert the web PR alone: always safe (server merges first).
Host rows written meanwhile are ordinary rows.
