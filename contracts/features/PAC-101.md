## 0. The rule this contract fixes

Every write that belongs to one scheduling link (a booking, a host row added,
changed or removed, the link's own fields) is ordered against that link's
delete as a whole. It either commits before the delete and is kept in full, or
it writes nothing and answers exactly what it would have answered had the
delete come before the request. Nothing commits on a link after its delete has
committed. For bookings only, a pause (`active = false`) counts like a delete.

## 1. What changes at the HTTP boundary

No operation, schema, status code or body is added or removed. Statuses that
were already documented gain cases:

| Operation | New case | Answer |
|---|---|---|
| `createPublicBooking` | link deleted or paused after the request read it, before the save | `404 {"error":"not found"}`, nothing written (no row, no event, no email). Never 201/409/410/503 |
| `createPublicBooking` | the save waited 10 s for a delete, pause or edit in progress | `500 {"error":"internal error"}`, nothing written |
| `updateSchedulingLink` | delete committed after the read, before the PATCH wrote | `404 {"error":"not found"}`, nothing changed, co-hosts included (already true for the fields since PAC-40 K4-1; now also for co-hosts) |
| `updateSchedulingLink` | a co-host lookup, removal or invitation fails | `500 {"error":"internal error"}` and **nothing** changed. Before: a failed removal or invitation was a silent 200 with the fields changed; a failed lookup was a 500 with the fields already changed |
| `updateSchedulingLink` | a lock not obtained within 10 s | `500`, nothing changed |
| `inviteSchedulingLinkHost` | delete committed after the read, before the host row | `404 {"error":"not found"}`, no host row |
| accept / decline (4 spellings), `leaveSchedulingLink` | delete committed while the request is handled | `404 {"error":"not found"}`, host row unchanged |
| every operation above and `deleteSchedulingLink` | lock wait past 10 s | `500 {"error":"internal error"}`, nothing changed |
| `inviteSchedulingLinkHost` 404 | (API-072) | the two bodies are now named examples, `linkNotFound` and `userNotFound` |

`deleteSchedulingLink` gains a paragraph: a write of the link already in
progress completes first and is kept; the delete waits for it.

**Refusals decided earlier keep their answer.** The race 404 is guaranteed only
for a request that would otherwise have written. A request refused before its
write (400, 403, 409, 410, 422, 429, the 503 before the commit point, the 404
"user not found") keeps that answer even if the link was deleted meanwhile,
and writes nothing either way. This is narrower than spec §3.1's "the same
answer as if the link had been deleted before the request arrived", which
taken literally would require a fresh link read before every refusal; the spec's
own ACs (AC-1..AC-13) only test requests that would have written. Challenge C-9.

The 500 body is `{"error":"internal error"}`, not the spec's
`{"error":"booking failed"}` (§3.4, AC-7): `writeServerError` writes
`genericServerMessage(500)` and "booking failed" is the log label only
(`handlers_booking.go:478`, `server_errors.go:26-57`). Challenge C-1.

## 2. Decisions

### 2.1 404, not 410, for a booking that loses (spec D-3)

410 means "exhausted" in this contract, and a link deleted before the request
already answers 404. A racing loser answering 410 would give two different
answers for the same state depending on timing.

### 2.2 The PATCH is one transaction (spec D-5)

Fields and co-hosts are written together or not at all. This is the only way a
delete can be ordered against the PATCH as a whole (spec challenge B-4): two
separate transactions leave a window in which the delete commits between them.
It changes two observable behaviours, both listed in §1: a failed co-host write
is no longer a silent 200, and a failed co-host lookup no longer leaves the
fields changed. No consumer relies on either (§8).

### 2.3 Pausing blocks bookings, not host writes (spec D-2)

The booking's commit-point check is `active AND deleted_at IS NULL`; a host
write's is `deleted_at IS NULL`. Today an owner can invite to a paused link and
co-hosts can answer on it (`TestPAC40_PausedLinkStaysLiveAndResumes`); that
stays.

### 2.4 The bound applies to the delete too

Spec §3.4 bounds "a write that has to wait for a concurrent delete or edit of
the same link". The delete itself can wait for a PATCH (an edit) or a booking
save. Leaving it unbounded would make the delete the one request-path
transaction on a link with no cap. It gets the same 10 s, and its existing 500
says so. The delete's statement and its 204/404 are unchanged (K4-2).

## 3. The commit point and the "link gone" outcome (binding)

### 3.1 Booking save (PAC-90 / PAC-81 sequence, unchanged before the save)

Order in `ConfirmBooking`, after this work:

1. accepted hosts, host calendar reads (unchanged; no lock held);
2. `beforeBookingConn` seam; connection acquired under the budget (unchanged);
3. `budget.Commit` (unchanged): from here the budget never answers 503;
4. `afterBookingCommit` seam (unchanged);
5. **the save, one explicit transaction on the reserved connection**, on the
   context detached from the request (unchanged):
   1. `BEGIN`;
   2. set the bound for this transaction only (§4.3);
   3. `INSERT INTO bookings (…) SELECT … FROM scheduling_links WHERE id = $1 AND active AND deleted_at IS NULL FOR SHARE RETURNING …`
      (or, equivalently, `SELECT 1 FROM scheduling_links WHERE id = $1 AND active AND deleted_at IS NULL FOR SHARE`
      then the plain `INSERT`, in the same transaction);
   4. zero rows from the locking step → `ROLLBACK`, outcome **link gone**;
      one row → `COMMIT`, outcome **saved**;
6. the reserved connection is released (PAC-90 item 1: normal return, error and
   panic paths), **then** the completion unit starts, only on **saved**.

**Link gone is a distinct result**, never `nil, nil`. The engine returns a
sentinel error (recommended `engine.ErrLinkGone`, wrapping or equal to a
`storage.ErrLinkGone`); `createBooking` maps it with `errors.Is` to
`404 {"error":"not found"}`, before the generic 500 branch. `scanBooking`'s
`ErrNoRows → nil, nil` mapping must not be on this path: a nil booking reaching
`startCompletion` panics on `booking.ID` (spec challenge B-3).

Other results of step 5: a lock-timeout error (SQLSTATE `55P03`), any other
statement error, or a failed `COMMIT` → the existing 500 path. `55P03` and
any error before `COMMIT` prove nothing was saved; a failed `COMMIT` keeps the
existing "outcome unknown" meaning of the 500. The client is not told which.

The existing PAC-81/PAC-90 guarantees hold unchanged: a 503 only before
`budget.Commit`; the answer after it is the handler's own (201, 404 link gone,
500); the connection is released before the completion unit, and on a panic
(the panic path must end the transaction: cancelling the save's context makes
`database/sql` roll it back, after which `Conn.Close` can return; a `Conn.Close`
with the transaction still open blocks on the connection's close lock).

### 3.2 Host writes and the PATCH

All run inside `WithSessionGeneration`'s transaction, the PAC-71 re-check being
its first statement. **They must run in a transaction even when the context
carries no session guard** (today `WithSessionGeneration` without a guard runs
`fn` directly on the pool, autocommit): a PATCH without a transaction is not
atomic and a `SET LOCAL` outside one is a no-op (challenge C-2).

| Write | Statements after the re-check, in order | Link gone when |
|---|---|---|
| invite | bound; `SELECT 1 FROM scheduling_links WHERE id=$1 AND deleted_at IS NULL FOR SHARE`; existing `INSERT … ON CONFLICT DO NOTHING` (+ the existing read of an existing row) | the lock step returns zero rows. **Never** inferred from the insert's zero rows, which already mean "already a host" (PAC-61) |
| accept / decline | bound; the lock step as for invite, then the existing `UPDATE` (its `EXISTS` may stay); or the single statement `UPDATE … WHERE … AND EXISTS (SELECT 1 FROM scheduling_links l WHERE l.id=$1 AND l.deleted_at IS NULL FOR SHARE)` | zero rows (the same 404 as "no host row", by design: PAC-30) |
| leave | as accept, with the existing `DELETE` | as accept |
| PATCH | bound; the existing guarded `UPDATE scheduling_links … WHERE id=$1 AND deleted_at IS NULL RETURNING …` **as the transaction's first lock on the link**; then `CarrierIDs`, `RemoveLinkHostsExcept`, and per address `ConfirmedHolder` + `InviteLinkHost`, all on the transaction; any error rolls everything back | the `UPDATE` returns no row → rollback, 404 |
| delete | bound; the existing `DeleteSchedulingLink` statement, unchanged | (unchanged: zero rows is the K4-2 404) |

The PATCH must never take `FOR SHARE` (or `KEY SHARE` through a host-row insert)
on its link before its `UPDATE`: two PATCHes would each hold a share lock and
wait to upgrade, a deadlock. The `UPDATE` is first, so every later host-row
insert's FK check is covered by the exclusive lock the transaction already holds.

Statements that run before the transaction (link read, owner check, body,
validation, zone read, `SlugExists`) are unchanged. `ConfirmedHolder` on the
invite stays before the write (it decides the "user not found" 404, §1).

## 4. Lock rule and wait cap (non-HTTP interface, binding)

### 4.1 Lock modes

| Transaction | Locks, in order |
|---|---|
| booking save (public, no session) | link `FOR SHARE` → booking row (its FK: link `KEY SHARE`, already covered) |
| invite | caller's `users` row `KEY SHARE` (re-check) → link `FOR SHARE` → host row (FKs: link, invitee `users` row `KEY SHARE`) |
| accept / decline / leave | caller's `users` row `KEY SHARE` → link `FOR SHARE` → caller's host row |
| PATCH | caller's `users` row `KEY SHARE` → link `NO KEY UPDATE` (`UPDATE` when the slug changes) → host rows (FK: invitee `users` rows `KEY SHARE`) |
| delete (PAC-40) | caller's `users` row `KEY SHARE` → link `NO KEY UPDATE` |
| erasure (PAC-40 part B, future) | link `FOR UPDATE` → bookings → owner's `users` row `KEY SHARE` |

`FOR SHARE` is exact: weaker (`KEY SHARE`) does not conflict with the delete's
`NO KEY UPDATE`, so it orders nothing (spec §9.1); stronger (`NO KEY UPDATE`)
conflicts with itself and would serialize bookings of one link (AC-16). The
`users`-row locks other code takes (`FOR NO KEY UPDATE` in `orgs.go`,
`org_ai.go`, `signin.go`; `FOR UPDATE` in `session.go` generation advances,
`operator.go`, `signin.go`) are held by transactions that take no link, host or
booking lock, and no product path deletes a `users` row, so no lock cycle
exists (challenge C-11). PostgreSQL 16 behaviour of these locks was observed,
not assumed (challenge "Verified clean").

### 4.2 Wait cap

- **Value: 10 s** (spec OQ-5, D-6), the value `lockAccountExclusive` uses
  (`storage/session.go:93`). One named value in the backend (recommended
  `storage.LinkLockTimeout = 10 * time.Second`, a package variable so tests
  shorten it; nothing else may reassign it).
- **Meaning: per lock wait, PostgreSQL `lock_timeout` semantics.** It bounds
  each lock acquisition of each statement after it is set, not the request. A
  booking save, invite, accept/decline/leave or delete has one wait on the
  link (plus, for an invite, the invitee's `users` row), so in practice one
  bound. A PATCH can wait once on the link and once per invited account's
  `users` row (only against a generation advance or operator command holding
  it `FOR UPDATE`). The contract does not promise a per-request total
  (challenge C-6).
- **Past the bound**: SQLSTATE `55P03`, the transaction is rolled back, the
  answer is the operation's 500 `{"error":"internal error"}`, nothing changed.
  Not retried automatically.
- The PAC-71 re-check (the transaction's first statement) is **not** under the
  bound: it stays as PAC-71 shipped it.

### 4.3 Scoping (binding)

- The bound is set **inside the writing transaction, after the PAC-71 re-check
  and before the first link lock**, with `SET LOCAL lock_timeout = '<n>ms'`
  (literal) or `SELECT set_config('lock_timeout', $1, true)`. `SET LOCAL` and
  `set_config(…, true)` end with the transaction, commit or rollback, so the
  setting cannot reach the next user of the pooled connection.
- **Forbidden:** a session-level `SET lock_timeout` or `set_config(…, false)`
  on a pooled or reserved connection; a `SET LOCAL` sent outside a transaction
  (PostgreSQL ignores it with a warning: the save would be unbounded); a
  `SET LOCAL lock_timeout = $1` (utility statements take no bind parameters;
  pgx sends a parse error); a multi-statement string with arguments (the
  extended protocol pgx uses rejects it).
- Why it matters here: the backend opens its pool with `stdlib.OpenDB(*cfg)`
  (`storage/db.go:119`) with no `ResetSession` hook, and pgx's default reset
  only pings; a session setting would survive into the next request.
- Storage functions run their statements with `context.Background()` inside
  the transaction, and the booking save is detached from the request on
  purpose, so a lock wait is not cut by the request budget (90 s) in any of
  these paths: the bound is the only cap (challenge C-12).

### 4.4 Ordering against PAC-40's guarded delete

As spec §9.3, and observed on PostgreSQL 16 (§Challenge, Verified clean):
a share-locked write in progress makes the delete wait and is kept; a delete in
progress makes the write wait; when the delete commits, READ COMMITTED
re-evaluates the locking step's `WHERE` on the new row version and returns no
row (link gone); when it rolls back, the write proceeds. A pause behaves as a
delete for the booking's condition. An edit that leaves the link live makes the
write wait and then proceed.

## 7. Alternatives rejected

- **410 for a lost booking.** §2.1.
- **SERIALIZABLE for these transactions.** Retries on 40001 at every caller,
  and it would serialize bookings of a link, breaking AC-16 (spec D-1).
- **An advisory lock per link.** A second lock namespace the delete, the PATCH
  and the erasure job would all have to take in the same order; the row lock
  already exists and every writer already touches the row.
- **`FOR KEY SHARE` for the booking (what the FK takes anyway).** Does not
  conflict with the delete's `NO KEY UPDATE`; orders nothing (spec §9.1).
- **Make the delete take `FOR UPDATE`** so the FK's `KEY SHARE` conflicts.
  It would order a booking against the delete without touching the booking
  path, but not refuse it: the delete is soft, the link row still exists, so
  the FK check passes after the wait and the booking is inserted on the
  deleted link. It also does not cover pause or host writes.
- **`statement_timeout` instead of `lock_timeout`.** Bounds work, not waits: a
  slow but unblocked insert would fail; and it would also cut the PAC-81
  "insert runs to its own result" rule.
- **A session-level `SET` reset before release** (spec §9.5's second option).
  Rejected: the reset is skipped on a panic or a broken connection unless every
  path is covered; `SET LOCAL` needs no reset.
- **Leave the PATCH as two transactions and guard each co-host write.** A delete
  between them gives a 200 whose co-host half did nothing (spec B-4).

The contract-challenger role was played by the same agent, which re-read

### Requests wrongly permitted

None at the schema level: no request schema changed, and every new case is a
status that was already documented with the same body schema (`BookingError`).

### Contract/implementation divergences (all fixed in 1.1)

1. **C-1 (blocking).** Spec §3.4/AC-7 body `{"error":"booking failed"}` does
   not exist; the handler answers `{"error":"internal error"}`
   (`handlers_booking.go:478` → `server_errors.go:54-57`). Fixed: §1, spec
   Decisions correction, manifest AC-7 text.
2. **C-2 (blocking).** Spec §9.2 allows the booking save as one autocommitted
   `INSERT … SELECT … FOR SHARE`, and §9.5 allows `SET LOCAL` for the bound.
   Together they give no bound: observed on PG 16, `SET LOCAL` outside a
   transaction block is ignored with `WARNING: SET LOCAL can only be used in
   transaction blocks`. And `WithSessionGeneration` without a guard runs the
   write with no transaction at all. Fixed: §3.1 step 5 is an explicit
   transaction; §3.2 requires a transaction with or without a guard.
3. **C-3.** The bound placement against PAC-71's "the re-check is the first
   statement of its transaction" (`docs/plans/PAC-71.md:66`). A `SET LOCAL`
   first would break that rule as written. Fixed: §4.3, after the re-check.
4. **C-4 (pgx).** `SET LOCAL lock_timeout = $1` is not valid (no parameters on
   utility statements), and a multi-statement string with arguments is
   rejected by the extended protocol. Since tests shorten the value, the
   implementation would be tempted by both. Fixed: §4.3 lists the two allowed
   forms.
5. **C-5 (pool leak).** `stdlib.OpenDB(*cfg)` has no `ResetSession` hook; a
   session-level setting would leak to the next request. Fixed: forbidden in
   §4.3, and **AC-18** added (§5) so a leak is caught by a test, not by review.
6. **C-6.** Spec AC-15 says "every request finishes within the waiting
   bound", and §3.4 reads as a per-request bound. `lock_timeout` is per lock
   acquisition (PostgreSQL docs; observed `55P03 … while locking tuple`); a
   PATCH can wait more than once. Fixed: §4.2 states per-lock semantics; the
   manifest reads AC-15 as "no request answers 55P03 or 40P01".
7. **C-7.** For the invite, a single `INSERT … SELECT … FOR SHARE ON CONFLICT DO
   NOTHING` returns zero rows both when the link is gone and when the invitee
   is already a host (PAC-61's 200). Fixed: §3.2, link gone comes from a
   separate lock step only.
8. **C-8.** The delete was left unbounded by the spec though it can wait on a
   PATCH. Fixed: §2.4, delete 500 description.
9. **C-9.** Spec §3.1's "same answer as if deleted before" is wider than the
   ACs and than any implementation without a re-read before every refusal.
   Fixed: §1 "Refusals decided earlier keep their answer", stated in each
   operation's description.
10. **C-10.** Description-only bundle changes still change the web's generated
    files. Fixed: merge condition in the manifest.
11. **C-11.** The task asked to check the order against PAC-71's
    `users`-row locks. Verified (see clean list); stated in §4.1. PAC-40 part
    B's "booking creation is one autocommitted insert" is stale after this
    work but its no-cycle conclusion stands (§8).
12. **C-12.** Request budget: storage statements inside these transactions use
    `context.Background()`, and the booking save is detached, so the 90 s
    budget does not cut a lock wait; the 10 s bound is the cap. Stated in §4.3
    so no one relies on the budget instead.

### Uncertainties not actually resolved

1. The 10 s value is a factory default (OQ-5), not an owner answer. It is
   below the budget (90 s) and the web's request bound, so a timeout is

2. Spec OQ-1..OQ-4 are factory defaults, recorded as such (spec Decisions);

### Verified clean (PostgreSQL 16.15, two sessions, `READ COMMITTED`)

- `INSERT INTO bookings(link_id) SELECT id FROM links WHERE id=1 AND active AND deleted_at IS NULL FOR SHARE RETURNING id`
  is accepted; plan `Insert → Subquery Scan → LockRows → Index Scan`, so the
  link lock is taken before the insert and the FK check.
- Delete held (uncommitted `UPDATE … SET deleted_at, active=false`): the
  booking waits (one session in `wait_event_type='Lock'`); delete commits → 0
