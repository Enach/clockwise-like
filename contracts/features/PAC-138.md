# Contract: PAC-138, response address fields are plain strings

- **Process**: light (no spec; the ticket is the spec). Contract revision 1.
- **Base**: origin/main `3ff4797`, bundle sha256 (LF) `83d7d555…`. New bundle sha256:
  the manifest's `contractHash`.

## 1. What changes

Two response fields lose `format: email`; their type stays `string`:

| Schema | Field | Returned by | Server source |
|---|---|---|---|
| `TeamInvite` | `inviteeEmail` | `inviteTeamMember` (inside `TeamInviteResult.invitation`) | `team_invites.invitee_email`, written by `normalizeManagerEmail` (PAC-129 §3.0) |
| `TeamMember` | `email` | `getTeam` (`TeamDetail.members[]`) | `users.email`, the same account address `TeamPerson.email` already carries without the format (PAC-129 contract 1.1, B-1) |

No status, operation, key or `required` list changes. The server's behaviour does
not change; the contract stops describing it as stricter than it is.

**Why.** The server's one address normaliser is trim, lowercase, then
`net/mail.ParseAddress`. It accepts `a&b@x.example` and `pat@x.y`. Generated
clients read `format: email` as a pattern check (`z.email()` in the web, a regex in
`openapi_types.Email`), so a client built from the contract refused a response
describing a write the server had already committed. PAC-129 B-1 removed the format
from `AddTeamPersonRequest.email` and `TeamPerson.email` for this reason; these two
were left behind, and the web carried derived schemas to read them as strings.

## 2. Generated code

- Go (`backend/api/gen`): `TeamInvite.InviteeEmail` `openapi_types.Email` →
  `string`; `TeamMember.Email` `*openapi_types.Email` → `*string`. No handler or
  test uses either generated type (handlers encode `storage.TeamInvite` and
  `storage.TeamMember`), so no Go code changes.
- Web: `TeamInvite.inviteeEmail` and `TeamMember.email` become `z.string()` (the
  latter `.optional()`); the derived schemas in `src/api/teams.ts` are removed.

## 3. Alternatives rejected

- **Keep the format and keep the web's derived schemas.** Every new consumer
  (the MCP, a regenerated Go client, another web call site) would rediscover the
  mismatch after a write had committed. The contract is the place to fix it once.
- **Make the server stricter to match `format: email`.** That would refuse
  addresses the server already stores (PAC-129 accepts them), a behaviour change
  with existing data behind it.
- **Drop the format from every address field in the contract.** Out of scope for
  this ticket; the remaining response fields fed by the same normaliser are listed
  in §4 as follow-ups, each needing its own consumer check.

## 4. Not changed (listed, not fixed)

Response fields still declaring `format: email` whose value comes from the same
normaliser (or from `users.email`, like `TeamMember.email`):

- `TeamInvitePreview.email` (`team_invites.invitee_email`, `getTeamInvite`) and
  `TeamInvitePreview.inviter_email` (`users.email`). The web reads this response
  without a zod parse (`teamInvitesApi.get`), so nothing refuses today.
- Manager: `ManagerTeamMemberGoStruct.member_email`, `ManagerRosterMember.email`,
  `CadenceGap.member_email`, `ManagerAnalyticsMember.email`. The web parses these
  with hand-written schemas (`src/contracts/managerTeam.ts`) that already read
  plain strings (PAC-129 review).

Request side: `InviteEmailRequest.email`, `AddManagerMemberRequest.email`,
`ScanConfirmRequest.emails[]` and the `MemberEmailPath` / `TeamPersonEmailPath`
parameters keep `format: email`. The server does **not** enforce that format on
them: every one is decoded by a hand-written handler into a plain `string` and
validated by `normalizeManagerEmail` alone. A client honouring the format is
therefore stricter than the server (it cannot send `a&b@x.example`), never looser;
that is safe, and left as is per the ticket.

## 5. Consumers

| Consumer | Affected | What happens |
|---|---|---|
| backend handlers | no | encode storage structs, not the generated types |
| backend tests | no | none decodes into `gen.TeamInvite` or `gen.TeamMember` |
| web `src/api/teams.ts` | yes | uses the generated `TeamDetail` and `TeamInviteResult` directly; the PAC-129 review tests with `a&b@x.example` and `pat@x.y` still pass |
| MCP | no | does not read either field |
