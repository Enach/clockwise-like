# Contract — PAC-66: the deployment's cloud identity goes only to hosts the operator approved

- **Linear issue**: [PAC-66](https://linear.app/paceday/issue/PAC-66)
- **Spec**: `docs/specs/PAC-66.md` (accepted, challenge round 3, 0 blocking)
- **Stage**: contract-author, then contract-challenger
- **Fragment edited**: `contracts/openapi/paths/scheduling.yaml`
- **Bundle**: regenerated by `python3 scripts/openapi_assemble.py`. Go code and
  `MIGRATION.md` are regenerated by the api gate (`make openapi` in an LF clone);
  see §9 for what was run and what it printed.

---

## 1. What this contract is for

Three LLM providers (Azure OpenAI, Vertex, Bedrock) authenticate with the
deployment's own cloud identity, not with a key the user typed. The host those
requests go to is built from values in each user's own settings. So any signed-in
user could aim the deployment's bearer token at a host they control, then press
"Test connection". The spec (§2) traces this through every send path.

At the HTTP boundary the fix touches two operations and adds one schema:

| Operation | Change |
|---|---|
| `testLLMConnection` (`POST /api/llm/test`) | New **422** response with body `LLMDestinationRefusal`. This is the send-time refusal. The 500 and 502 descriptions now say a refusal is never either of them. A refused redirect is a 502. The PAC-24 paragraph "NOT resolved here … It needs its own issue" is **replaced**, as the spec's inherited scope requires. |
| `patchSettings` (`PATCH /api/settings`) | Five new 400 messages in the shared `SettingsValidationError` for `azureEndpoint`, `gcpLocation` and `awsRegion`. The operation description states which writes are deliberately *not* refused. |
| Schemas | `LLMDestinationRefusal` (new). Descriptions added to `awsRegion`, `awsProfile`, `azureEndpoint` and `gcpLocation` on the shared settings property map. `LLMTestRequest.llmProvider` now says the check follows this value. |

Two operations change behaviour with **no** contract edit. Both are deliberate (§5):

- `parseNaturalLanguage` (`POST /api/nlp/parse`). A refusal is the existing
  200 `{"intent":"unknown","error":"…"}` (spec AC-13).
- `refreshMeetingBrief` (`POST /api/meetings/{event_id}/brief/refresh`). A
  refusal is the existing 200 with `status: "failed"`, and that failed brief is
  what gets stored (spec AC-14).

No operation is added or removed. No property is added to or removed from a
request or response. No existing response changes shape.

## 2. The send-time refusal is a 422 with a reason, not a 400 or a 403

The probe needs a client error that is distinct from what it already returns
(spec AC-1, AC-4, AC-10: "neither a 502 … nor a 500").

**Chosen: 422 with `LLMDestinationRefusal {error, reason, property?}`.**
The request body is well formed. What cannot be processed is the configuration
the body resolves to under deployment policy. That is what 422 means, and nothing
on this operation uses it yet, so a test can tell a refusal from every other
failure by status alone. `reason` is a closed enum (`provider_not_enabled`,
`destination_not_approved`, `destination_not_set`) because the spec needs three
different user messages (AC-4, AC-1, AC-20). A test that string-matches English
sentences breaks the first time someone improves the wording. `property` names
the stored setting the user must fix. `error` is the same member as
`SchedulingErrorResponse`, so the web settings page, which displays
`data.error` for any non-2xx (`smart-calendar-flow/src/api/client.ts:351-356`),
renders the refusal with no code change. The spec's §5 relies on that.

**Rejected: 400 with `SchedulingErrorResponse`.** 400 already means "your body is
malformed or names a property that is not allowed" on this operation. Here that
is how a submitted destination is refused (PAC-24). Reusing it would make "you
sent `azureEndpoint` in the probe body" and "your *saved* endpoint is not
approved" indistinguishable. The user fixes those two in different places.

**Rejected: 403.** It fits the vocabulary ("the deployment does not authorise
this destination"), but the web client's fallback text for a 403 with no body is
"You don't have permission to do this." (`client.ts:360-361`), and an
intermediary or a future client may treat 403 as an authorisation failure of the
*caller*. The caller is authorised. Their configuration is what is refused.

**Rejected: keep 502 and change the message.** The status today's code returns
for this case is a 502 (spec AC-10, "Fails today"). The spec forbids it. A 502
tells the user the provider is down, so they retry, and no retry can ever
succeed.

**Why a refused redirect is a 502 and not a 422 (AC-8).** In that case a request
*was* sent, to an approved host, and the approved provider's answer could not be
used. That is what 502 already means on this operation. The 422 promises "nothing
was sent". Keeping it to that meaning is what lets AC-1 to AC-4 assert zero
requests from the status code.

`reason` precedence is fixed so that one state never needs two messages. This
answers the round-3 challenge, non-blocking 2. When nothing is approved for the
provider, the reason is `provider_not_enabled`, whatever is stored, including a
host approved only for another provider.

## 3. Write-time refusal reuses `SettingsValidationError`

Spec AC-5 asks for "a 4xx with a JSON error naming that property". Every other
per-property refusal on `PATCH /api/settings` is a 400 through the one shared
`SettingsValidationError` response, with messages that start with the property
name. The PAC-66 messages follow that convention exactly, so a client that already
maps `"<property> …"` messages to form fields needs nothing new.

**Rejected: a 422 here too, for symmetry with the probe.** The settings write has
one error status and one catalogue. Adding a second status for three of its 50
properties would make every client branch on it for no information. The probe
is different because its 400 already carries a different meaning (§2).

**Rejected: a `pattern` on `gcpLocation` / `awsRegion` and `format: uri` +
`pattern: ^https://` on `azureEndpoint`.** The factory prefers making a wrong
request impossible to express (contract-author rules), and this was the first
design. It fails because `Settings` and `SettingsUpdate` share one YAML-anchored
property map (PAC-24 revision 3). A pattern on the map constrains the
**response** too. Rows written before PAC-66 are deliberately kept as they are
(spec D-3: refuse, never rewrite), so `GET /api/settings` would return documents
that violate its own schema. The zod schemas generated in the web repo
(`src/api/generated/schemas.ts`) would then reject a real server response. A
pattern on `SettingsUpdate` alone would break the anchor and the guarantee that
"every `Settings` document is a valid `SettingsUpdate` body". That guarantee is
what lets a client submit back what it read (PAC-24 AC-13, e2e
`settings.spec.ts:54-55`). The handler is the enforcement point, and the property
descriptions say why there is no pattern.

**What the write does not refuse, and why.** Each case is pinned by a criterion:

- `""` for any of the three properties, whatever is approved (AC-15). D-3 relies
  on the user being able to undo a bad value.
- A value equal to the stored one (PAC-24 AC-17, the changed-only rule). The
  round-3 challenge (non-blocking 3) pointed out that AC-5 and AC-17 disagree
  when a client sends back an unapproved value already stored. **This contract
  decides: AC-5 applies only when the value differs from the stored one.** The
  stored value is still refused at send time (AC-9). This keeps the e2e
  whole-document PATCH and the web diff-only save working.
- A write that changes only `llmProvider` onto a stored unapproved endpoint
  (AC-17).
- `awsProfile`, `gcpProject`, `azureDeployment`, `azureApiVersion`,
  `vertexModel`, `bedrockModel` (spec OQ-4, and §7 below).

## 4. Operator configuration: three variables, exact hosts

The approved set is deployment configuration. It is not part of the HTTP
interface, but AC-10 (e2e) and AC-12 depend on its exact form, so it is fixed
here rather than left to the plan.

| Variable | Approves hosts for |
|---|---|
| `PACEDAY_LLM_APPROVED_HOSTS_AZURE_OPENAI` | `azure_openai` |
| `PACEDAY_LLM_APPROVED_HOSTS_VERTEX` | `vertex` |
| `PACEDAY_LLM_APPROVED_HOSTS_BEDROCK` | `bedrock` |

The `PACEDAY_` prefix follows `PACEDAY_ALLOW_STANDINS` (`.env.example`, PAC-43).

**Format.** Comma-separated entries. Whitespace around an entry is trimmed and
empty entries are skipped. Each entry is either a bare DNS host name
(`my-resource.openai.azure.com`) or that host written as `https://<host>` with an
optional single trailing `/`. The URL form is accepted because operators copy the
Azure endpoint from the portal as a URL (round-3 challenge, non-blocking 5).
Anything else is **malformed**: another scheme, a port, a path, userinfo, a
wildcard (`*`, `*.openai.azure.com`), an IP literal, or a trailing dot. A
malformed entry is logged at startup, naming the variable and the entry, and it
approves nothing. Well-formed entries beside it stay approved (spec AC-12, D-6).
No input, malformed or not, approves everything. Unset or empty means nothing is
approved, so the provider is not enabled (D-1, fail closed).

**Matching (spec OQ-2, round-3 challenge non-blocking 4).** A destination
matches when all of these hold:

- Its scheme is `https`.
- Its port is absent or `443`.
- It has no userinfo.
- Its host, compared ASCII case-insensitively, equals an entry for **that
  provider** exactly.

A trailing dot on the destination host is not stripped, so `host.` does not match
`host`. That is the conservative answer: refusing it costs a user one edit, and
accepting it would need a normalisation rule that someone could get wrong. No
suffix or subdomain matching (D-2): `x.my-resource.openai.azure.com` does not
match `my-resource.openai.azure.com`.

**Rejected: built-in vendor suffixes** (`*.openai.azure.com`,
`*-aiplatform.googleapis.com`, `*.amazonaws.com`). Spec OQ-1 explains this. Any
Azure customer can create a resource under `openai.azure.com`, and
`amazonaws.com` includes S3 and API Gateway hosts that log request headers. The
token would leave on a vendor domain an attacker controls.

**Rejected: operator-written wildcards.** An operator with many Azure resources
would like them (OQ-2). But a wildcard is also the easiest way to approve a
suffix by accident (`*.openai.azure.com` is exactly the vendor-suffix hole).
Listing hosts costs an operator a few more lines. A wildcard mistake costs the
cloud credential. If an operator asks for wildcards, that is a new issue with its
own semantics.

**Rejected: one shared list for all three providers.** That is simpler to
configure. But the Azure token would then go to an approved Vertex host (spec D-8,
AC-18 c).

## 5. Parse and brief refresh: behaviour changes, contract does not

Spec D-5 keeps each path's existing "LLM unusable" shape, so no consumer changes:

- The parse consumers are the web natural-language bar (`client.ts:1155`) and
  the MCP tool `clockwise_parse_command` (`mcp/tools.go:195-203`).
- Brief refresh has no web caller.

Both shapes are already in the contract: `scheduling.yaml` parse 200 with
`NLPParseResult.error`, and `habits.yaml` "a 'failed' brief is still returned
with HTTP 200".

**Decision: neither operation is edited.** The spec's inherited scope says that
editing the parse operation at all pulls open finding API-080 (zero-time
`range_start`/`range_end`) into scope under factory §7.1. API-080 is a
serialisation defect that has nothing to do with this issue. The refusal fits the
documented 200 shape without a word changed. The refusal messages are pinned in
the manifest (`sendTimeRefusals`) and in spec AC-13 and AC-14, which is where a
test reads them.

**Rejected: describe the refusal in `NLPParseResult.error`.** That would be more
discoverable. But the schema is the parse response, so editing it edits the
operation, and that pulls in API-080 (above).

**Known inaccuracy left standing, recorded here so it is not lost.** The parse
operation's description says LLM-level failures "do NOT surface as 5xx". A
`Complete` failure is a 500 `text/plain` (`backend/nlp/parser.go:197-200`,
`backend/api/handlers_nlp.go:28-31`), and the operation's own 500 response
already documents a 500. PAC-66 does not make that worse: a refusal happens
before `Complete`. Correcting the sentence is a follow-up (manifest
`followUps.parseDescription5xx`).

## 7. Recorded, not solved: path and project steering on an approved host

Approval is by host (spec D-2, AC-6). The user still controls the rest of the
URL: the Azure endpoint's path, `azureDeployment`, `azureApiVersion`,
`gcpProject`, `vertexModel`, and a Vertex location of the form
`<approved-region-host>/v1/projects/OTHER/…#`. The round-3 challenge checked this
with `net/url` (non-blocking 1). So a user can make the server call **any
operation on an approved host, against any project the deployment identity can
reach**, with the deployment's token. The token itself stays on the approved
host, so this is not the issue's core problem. It is still real, and the issue
names "region / project" as steering values.

This contract does not constrain the path, because the accepted spec says a value
whose effective host is approved is accepted (AC-6). Narrowing that is a
behaviour change the spec did not ask for (contract-author rules). The manifest
records it as `followUps.approvedHostPathSteering`, to be filed beside PAC-66-B
with the product owner as owner. The plan stage should make sure the Vertex
location check rejects values that change the authority. AC-2 already requires
that. A location that keeps the approved authority but injects a path is the case
this follow-up covers.
