## 0. The rule this contract fixes

A co-host invitation is an invitation **to an address**. The owner's side
(the single invite and the co-host list on create and PATCH) never reads
accounts by address, so nothing the owner or an accepted co-host can observe
about a pending invitation (status, body, outcome, count, roster entry,
removal item, limit, work done) depends on whether an account carries the
address. The address is matched to an account only on the **invitee's** side,
for the caller's own address, and only for the address's single
domain-confirmed holder (PAC-71's granting site moves from "invite" to
"accept").

## 2. Behaviour (binding; spec §3)

### 2.1 Single invite (`inviteSchedulingLinkHost`; spec §3.2, D-1, D-15, D-18)

Order (unchanged up to step 5):

1. 400 `"invalid id"`;
2. link read (500 on error; 404 `"not found"` for none or deleted);
3. 403 for a non-owner;
4. body decode; trim leading and trailing ECMA-262 `\s` (`storage.TrimECMASpace`,
   the co-host list's function); blank or invalid JSON → 400 `"email is required"`;
5. the write (PAC-71 re-check, 10 s bound, link lock, link-gone → 404), and
   inside it, against the entries read under the lock, every comparison with
   the database's `lower()`:
   1. equals the owner's stored address (read by the owner's account id) →
      200, the owner's entry as the roster shows it; nothing written. For a
      link with no owner row (pre-PAC-112) the 200 carries the owner as
      `{user_id, email, name?, avatar_url?, is_owner:true, status:"accepted"}`
      and nothing is written (before PAC-149: a `pending` owner row was created);
   2. equals the address of a current entry (pending invitation's recorded
      address, or an accepted/declined entry's account address) → 200 with
      that entry as the roster shows it, status kept (PAC-61); nothing written;
   3. not well-formed → 400 `"email must be a valid email address"`; nothing
      written. Well-formed: `strings.ToLower(trimmed)` is accepted by
      `net/mail.ParseAddress` and its `Address` equals it (the predicate of
      `normalizeManagerEmail`, applied to the ECMA-trimmed value);
   4. the link has 5 or more non-owner entries (pending invitations included)
      → 422 `SchedulingLinkHostLimitError`; nothing written;
   5. otherwise insert a pending invitation (`invitee_email` = trimmed address,
      case kept; `user_id` NULL; `invite_position` 0; `invited_at` NOW()) →
      201 `{email, is_owner:false, status:"pending"}`.

Steps 5.1-5.4 sit inside the write because they need the entries read under
the lock (PAC-120's rule for the limit); that is also what makes the work for
two new addresses identical (§2.6). A 400 from 5.3 is therefore decided after
the lock; a link deleted first answers its 404.

### 2.2 Co-host list (`co_host_emails` on create and PATCH; spec §3.2, D-1, D-7)

Per entry, after the blank check (422, unchanged): trim; then `own_address`
(owner's stored address), `already_host` (a current non-owner entry's
address; status kept), `invited` (well-formed, as §2.1 step 5.3: a pending
invitation is inserted with `invite_position` = 1 + the index of the first
entry equal to it in the request), otherwise `not_added`. Entries equal after
trim and `lower()` share one outcome and one invitation. `invited_count` =
distinct new invitations; `not_added_count` unchanged in definition. Over-5:
refused at the first entry that equals neither the owner's address nor a
current entry. Removal (PATCH): every non-owner entry whose address
(`invitee_email` for a pending invitation, the account's stored address for an
entry) equals no listed entry. The PAC-71 AC-43 keep rule is the same test for
an entry (§3.2 of the spec). No carriers read, no lock on any invitee account.

### 2.3 Address normal form (spec D-15)

| Use | Form |
|---|---|
| trim | ECMA-262 `\s`, both ends (`TrimECMASpace`), both paths |
| blank | empty after the trim |
| well-formed | lowercased trimmed value accepted by `net/mail.ParseAddress` with `Address` equal to it |
| stored / shown | trimmed, letter case kept |
| compared | database `lower()` |

### 2.4 Invitee side (spec §3.3, D-5, D-10)

**Holder match.** The caller C is the holder of address A exactly when
`lower(C.email) = lower(A)`, C's standing is `domain_confirmed`, and no other
account's `lower(email)` equals it (PAC-71 `ConfirmedHolder` semantics, keyed
on the caller's own row). It is computed from the caller's row and one read
of other carriers of the caller's own address; it is never computed for an
address the caller did not supply implicitly as their own.

**List** (`listSchedulingLinkHostInvites` and alias): pending invitations
`h` with `h.user_id IS NULL`, `lower(h.invitee_email) = lower(C.email)`, C the
holder, link not deleted, C not the owner, and no row of C on the link. Item
shape unchanged (`SchedulingLinkHostInvite`). A failed caller-row read or
invitation read → 500, never `[]`.

**Accept / decline** (four spellings, one handler), under the link lock:

1. C owns the link or has an accepted or declined row on it → update that row
   exactly as before (PAC-30: the owner still gets 200 on the owner's row), and
   in the same write delete any pending invitation on the link with
   `lower(invitee_email) = lower(C.email)`;
2. else C is the holder of its address and the link has a pending invitation
   equal to it → `UPDATE` that row: `user_id = C`, `invitee_email = NULL`,
   `status`, `responded_at = NOW()`; `invited_at` and `invite_position` kept
   (the entry keeps its place, spec D-16);
3. else 404 `{"error":"not found"}`, nothing written.

A storage error in the match → 500, nothing changed (D-10).

**Leave**: owner → 400 (first, unchanged). Then under the lock: C has an
accepted or declined row → delete it (and any pending invitation equal to C's
address on the link); else C holds a pending invitation of the link → delete
it (204); else 404. Failed match → 500.

Case 1's extra delete and leave's extra delete exist only for a state no
product path creates (spec §3.3); the storage does not refuse that state (§4.1
explains why no constraint can), so the behaviour is required (spec AC-19).

### 2.5 Roster and removal report (spec §3.4, D-6, D-16)

| Entry | `SchedulingLinkHost` | `SchedulingLinkRemovedHost` |
|---|---|---|
| owner | `user_id, email, name?, avatar_url?, is_owner:true, status` | never removed |
| accepted | `user_id, email (account), name?, avatar_url?, is_owner:false, status` | `user_id, email, status` |
| pending | `email (recorded), is_owner:false, status` only | `email, status` only |
| declined | `email (account), is_owner:false, status` only | `email, status` only |

Order: `invited_at`, `invite_position`, `lower(address)`, address bytes
(`COLLATE "C"`), row id. On create the owner row has position 0 and the
co-hosts 1…n, so the owner is first and co-hosts follow the request. Rows that
predate PAC-149 have position 0 and fall back to the address tiebreak (spec
N-10). An accepted co-host reading the link sees the same entries.

### 2.6 Equal work (spec §3.6, D-11, AC-6)

For a new well-formed address the inviter-side statement sequence is fixed:
re-check, link lock, entries read (the link's rows joined to `users` by
`user_id` for entry addresses), owner address read (by owner id), count,
insert, roster read (create/PATCH). None is keyed on the typed address except
the insert. A seam (§6) records the sequence; AC-6 compares H with N.

### 2.7 Delete (spec §3.3, D-14, AC-17)

`deleteSchedulingLink` deletes the link's rows with `user_id IS NULL` in the
same transaction as setting `deleted_at`, under the link lock. Accepted and
declined rows are kept (PAC-40 D-2). An invitation that committed first is
erased; one that waits on the lock sees the deleted link and answers 404.

### 4.0 Shape

Pending invitations stay in `scheduling_link_hosts` (one id space, one order,
one limit count), as rows with `user_id IS NULL`:

- `user_id` becomes nullable (the FK and `ON DELETE CASCADE` stay for entries:
  spec N-9; `classifiedUserRefs` and `TestPAC71_EveryUserForeignKeyIsClassified`
  are untouched because the column is the same);
- `invitee_email TEXT NULL`: the recorded address of a pending invitation;
- `invite_position INTEGER NOT NULL DEFAULT 0`: request position (§2.5);
- `CHECK ((status = 'pending') = (user_id IS NULL))`: a pending row never
  points at an account (AC-9 by construction); an entry always does;
- `CHECK ((user_id IS NULL) = (invitee_email IS NOT NULL))`;
- `UNIQUE (link_id, lower(invitee_email)) WHERE invitee_email IS NOT NULL`:
  one invitation per (link, address) (spec D-3).

What the storage **cannot** refuse: an invitation equal to an entry's or the
owner's address (the entry's address lives in `users`; a cross-table rule
would need a trigger reading `users`, which this codebase has never used and
which would race with the address writes it does not lock). So AC-19's two
direct inserts are accepted by the storage, and §2.4's defensive behaviour is
required for them.

PAC-71 rule (b) (`storage/emptiness.go:41`) counts rows `WHERE user_id = $1`,
so a pending invitation no longer makes any account non-empty (spec D-9)
without a code change there.

### 4.1 Up

```sql
-- PAC-149 (spec docs/specs/PAC-149.md §3.5, D-8, D-17, AC-10; contract
-- contracts/features/PAC-149.md §4): a pending co-host invitation is to an
-- address, never to an account. Pending rows on live and paused links become
-- address invitations in place (same row id, invited_at and roster position);
-- pending rows on deleted links, for freed placeholder addresses, and those
-- that clash with an entry, the owner or another pending row are dropped.
-- Accepted and declined rows are not touched.
ALTER TABLE scheduling_link_hosts ALTER COLUMN user_id DROP NOT NULL;
ALTER TABLE scheduling_link_hosts ADD COLUMN invitee_email TEXT NULL;
ALTER TABLE scheduling_link_hosts ADD COLUMN invite_position INTEGER NOT NULL DEFAULT 0;

DO $$
DECLARE
    n_deleted_link bigint;
    n_placeholder  bigint;
    n_entry_clash  bigint;
    n_pending_dup  bigint;
    n_holder       bigint;
    n_no_holder    bigint;
BEGIN
    -- 1. On a deleted link (spec D-14): dropped.
    DELETE FROM scheduling_link_hosts h
     USING scheduling_links l
     WHERE h.status = 'pending' AND l.id = h.link_id AND l.deleted_at IS NOT NULL;
    GET DIAGNOSTICS n_deleted_link = ROW_COUNT;

    -- 2. The account carries an operator placeholder (storage.FreedAddress).
    DELETE FROM scheduling_link_hosts h
     USING users u
     WHERE h.status = 'pending' AND u.id = h.user_id
       AND u.email = 'freed+' || u.id::text || '@paceday.invalid';
    GET DIAGNOSTICS n_placeholder = ROW_COUNT;

    -- 3. Equal, under lower(), to the owner's stored address or to the stored
    --    address of an accepted or declined entry of the same link: dropped;
    --    the entry or owner row is kept unchanged.
    DELETE FROM scheduling_link_hosts h
     USING users u, scheduling_links l, users o
     WHERE h.status = 'pending' AND u.id = h.user_id
       AND l.id = h.link_id AND o.id = l.owner_user_id
       AND (lower(u.email) = lower(o.email)
            OR EXISTS (SELECT 1
                         FROM scheduling_link_hosts e
                         JOIN users eu ON eu.id = e.user_id
                        WHERE e.link_id = h.link_id
                          AND e.status <> 'pending'
                          AND lower(eu.email) = lower(u.email)));
    GET DIAGNOSTICS n_entry_clash = ROW_COUNT;

    -- 4. Equal converted addresses on one link (under lower()): keep the
    --    earliest by invited_at, then stored address bytewise, then row id.
    DELETE FROM scheduling_link_hosts h
     USING (SELECT h2.id,
                   row_number() OVER (PARTITION BY h2.link_id, lower(u2.email)
                                      ORDER BY h2.invited_at, u2.email COLLATE "C", h2.id) AS rn
              FROM scheduling_link_hosts h2
              JOIN users u2 ON u2.id = h2.user_id
             WHERE h2.status = 'pending') d
     WHERE h.id = d.id AND d.rn > 1;
    GET DIAGNOSTICS n_pending_dup = ROW_COUNT;

    -- 5. Count, then convert every remaining pending row in place.
    SELECT count(*) FILTER (WHERE c.holder), count(*) FILTER (WHERE NOT c.holder)
      INTO n_holder, n_no_holder
      FROM (SELECT (u.address_standing = 'domain_confirmed'
                    AND NOT EXISTS (SELECT 1 FROM users v
                                     WHERE lower(v.email) = lower(u.email)
                                       AND v.id <> u.id)) AS holder
              FROM scheduling_link_hosts h
              JOIN users u ON u.id = h.user_id
             WHERE h.status = 'pending') c;

    UPDATE scheduling_link_hosts h
       SET invitee_email = u.email, user_id = NULL
      FROM users u
     WHERE h.status = 'pending' AND u.id = h.user_id;

    RAISE LOG 'PAC-149 migration 044: converted % with a holder, % without; dropped % on deleted links, % placeholder, % clashing with an entry or the owner, % clashing with another pending row',
        n_holder, n_no_holder, n_deleted_link, n_placeholder, n_entry_clash, n_pending_dup;
    RAISE NOTICE 'PAC-149 migration 044: converted % with a holder, % without; dropped % on deleted links, % placeholder, % clashing with an entry or the owner, % clashing with another pending row',
        n_holder, n_no_holder, n_deleted_link, n_placeholder, n_entry_clash, n_pending_dup;
END $$;

ALTER TABLE scheduling_link_hosts
    ADD CONSTRAINT scheduling_link_hosts_pending_is_invitation
        CHECK ((status = 'pending') = (user_id IS NULL)),
    ADD CONSTRAINT scheduling_link_hosts_invitation_has_address
        CHECK ((user_id IS NULL) = (invitee_email IS NOT NULL));

CREATE UNIQUE INDEX scheduling_link_hosts_invitation_unique
    ON scheduling_link_hosts (link_id, lower(invitee_email))
    WHERE invitee_email IS NOT NULL;
```

- **Precedence** of the drop categories, so each pending row counts once:
  deleted link, then placeholder, then clash with an entry or the owner, then
  clash with another pending row. The spec's §3.5 does not order them; this
  order is the one under which the fixture's counts are exactly AC-10's.
- **In place** means "the account-keyed row is removed" (spec §3.5) holds in
  substance: after step 5 no pending row carries an account, and the row keeps
  its id, `invited_at` and position (spec N-2).
- The converted address is the account's **current** stored address, case
  kept. "Stored address" in the duplicate tiebreak is compared bytewise
  (`COLLATE "C"`), so the rule does not depend on the database collation.
- Idempotent in effect on an unchanged database (a re-run finds no pending row
  with an account); golang-migrate never re-runs it. One implicit transaction
  (golang-migrate sends the file as one multi-statement exec).
- **Locks**: `ACCESS EXCLUSIVE` on `scheduling_link_hosts` for the `ALTER`s and
  the index, `ACCESS SHARE` on `users` and `scheduling_links`. Applied with no
  backend serving (PAC-116 stop-migrate-start), so contention is nil; the table
  is small.

### 4.2 Down

```sql
-- PAC-149 (contract contracts/features/PAC-149.md §4.2; spec §7, AC-10 down):
-- each pending invitation whose address has a single domain-confirmed holder
-- becomes that holder's pending row again, unless the holder owns the link or
-- already has an entry on it (the existing entry survives); every other
-- invitation is dropped. Never fails on UNIQUE (link_id, user_id). Lossy.
DROP INDEX scheduling_link_hosts_invitation_unique;
ALTER TABLE scheduling_link_hosts
    DROP CONSTRAINT scheduling_link_hosts_invitation_has_address,
    DROP CONSTRAINT scheduling_link_hosts_pending_is_invitation;

UPDATE scheduling_link_hosts h
   SET user_id = hu.id, invitee_email = NULL
  FROM users hu, scheduling_links l
 WHERE h.user_id IS NULL
   AND l.id = h.link_id
   AND lower(hu.email) = lower(h.invitee_email)
   AND hu.address_standing = 'domain_confirmed'
   AND NOT EXISTS (SELECT 1 FROM users v
                    WHERE lower(v.email) = lower(h.invitee_email) AND v.id <> hu.id)
   AND hu.id <> l.owner_user_id
   AND NOT EXISTS (SELECT 1 FROM scheduling_link_hosts e
                    WHERE e.link_id = h.link_id AND e.user_id = hu.id);

DELETE FROM scheduling_link_hosts WHERE user_id IS NULL;

ALTER TABLE scheduling_link_hosts
    DROP COLUMN invite_position,
    DROP COLUMN invitee_email;
ALTER TABLE scheduling_link_hosts ALTER COLUMN user_id SET NOT NULL;
```

The `UPDATE` cannot produce two rows for one (link, holder): the unique index
(dropped only at the top of this file) guaranteed one invitation per
(link, `lower(address)`), and a holder carries exactly one address.

### 4.3 Pre-deploy count (spec §3.5 release-note query, AC-10)

Read only; run against the database at 43 before deploying. The categories and
their precedence are exactly §4.1's.

```sql
WITH p AS (
  SELECT h.id, h.link_id, h.invited_at, u.id AS uid, u.email, u.address_standing,
         l.deleted_at, o.email AS owner_email
    FROM scheduling_link_hosts h
    JOIN users u ON u.id = h.user_id
    JOIN scheduling_links l ON l.id = h.link_id
    JOIN users o ON o.id = l.owner_user_id
   WHERE h.status = 'pending'
), c1 AS (
  SELECT p.*,
         CASE
           WHEN p.deleted_at IS NOT NULL THEN 'dropped: on a deleted link'
           WHEN p.email = 'freed+' || p.uid::text || '@paceday.invalid' THEN 'dropped: placeholder'
           WHEN lower(p.email) = lower(p.owner_email)
             OR EXISTS (SELECT 1 FROM scheduling_link_hosts e JOIN users eu ON eu.id = e.user_id
                         WHERE e.link_id = p.link_id AND e.status <> 'pending'
                           AND lower(eu.email) = lower(p.email))
             THEN 'dropped: clash with an entry or the owner'
         END AS cat
    FROM p
), c2 AS (
  SELECT c1.*,
         row_number() OVER (PARTITION BY c1.link_id, lower(c1.email)
                            ORDER BY c1.invited_at, c1.email COLLATE "C", c1.id) AS rn
    FROM c1 WHERE c1.cat IS NULL
)
SELECT cat AS category, count(*) AS n FROM (
  SELECT cat FROM c1 WHERE cat IS NOT NULL
  UNION ALL
  SELECT CASE
           WHEN rn > 1 THEN 'dropped: clash with another pending row'
           WHEN address_standing = 'domain_confirmed'
            AND NOT EXISTS (SELECT 1 FROM users v
                             WHERE lower(v.email) = lower(c2.email) AND v.id <> c2.uid)
             THEN 'converted: with a holder'
           ELSE 'converted: without a holder'
         END
    FROM c2
) x GROUP BY cat ORDER BY cat;
```

## 10. Alternatives rejected

1. **A separate `scheduling_link_invitations` table** (no FK to users) with
   accepted/declined rows staying account-keyed in `scheduling_link_hosts`.
   Rejected: the roster order (spec D-16: "an entry keeps its position when its
   invitee answers"), the 5-co-host count and the removal set would each span
   two tables, and accepting would move a row between tables, copying its time
   and position. One table with `user_id IS NULL` keeps one id, one order and
   one count, and the CHECKs make "pending ⇔ no account" a storage invariant.
2. **Keep `user_id` required on `SchedulingLinkRemovedHost` and send the nil
   UUID for a pending or declined removal.** It would keep the old web's strict
   parse valid (zod 4.6's `z.uuid()` accepts the nil UUID; checked). Rejected:
   it is an identifier field carrying a sentinel, permanently, which AC-5 ("no
   account identifier") and the next reader would both trip on; the cost it
   avoids is a fallback sentence for minutes. The PAC-130 precedent (keep a
   required key, deprecated, always null) did not apply: the field was already
   nullable there, and here it still carries a real id for accepted entries.
3. **Keep `SchedulingLinkHostRecord` as the single invite's body with
   `user_id` optional.** Rejected: the spec says the answer shows the entry "as
   the link reads show it"; the raw row's `id` is the host-row id that API-020
   showed misleads callers into the accept path, and its timestamps are a second
   format (raw `time.Time`) for nothing. Nobody reads the body.
4. **A 422 for a malformed address** (the team invitation's status). Rejected:
   this operation's 422 is a single-literal schema the e2e and web compare
   exactly; adding a body would make it a union. Every other request-shape
   refusal of this operation is a 400 with `BookingError`, so the new one is too.
5. **Owner's accept on a stray owner-address invitation is the 404** (AC-19's
   literal text). Rejected for §2.4 case 1, see §13 deviation D-a.
6. **A trigger refusing an invitation equal to an entry or owner address**, so
   AC-19 would pass on a storage refusal. Rejected: no trigger exists in this
   codebase, it would read `users` without the lock the address writes take,
   and the product path already decides the same rule under the link lock.
7. **Store the typed address on answered entries too** (show the declined
   entry by the address the owner typed). Rejected: after answering, the row is
   bound to the account and shown by the account's address like every other
   entry; keeping two addresses per row would need a rule for which to show.

## 13. Deviations from the spec, and open for the challenger

- **D-a. Owner's accept with a stray owner-address invitation (AC-19, last
  paragraph).** The spec says "O's accept is the 404". Today the owner's accept
  and decline match the owner's own row and answer 200 (PAC-30, contract
  `acceptSchedulingLinkHostInvite`), and the spec's own §3.3 says an account
  that owns the link "acts on its own entry exactly as today". Making the
  owner's accept a 404 only while a stray invitation exists would be a new
  behaviour visible only in an unreachable state; making it a 404 always would
  change PAC-30 outside this spec. The contract keeps the owner's 200 on the
  owner row and removes the stray invitation in the same write (§2.4 case 1).
  AC-19's owner half is therefore tested as: O's list does not show the link,
  O's accept is 200 on the owner row, the stray invitation is gone, no 500.
  Needs the coordinator's or challenger's confirmation.
- **D-b. Leave also removes a stray invitation** of the caller's own address
  when the caller has an entry (§2.4). The spec states this for accept and
  decline only; leave is given the same rule so the unreachable state cannot
  survive any invitee-side write.
- **D-c. Owner's own address on a link with no owner row** (pre-PAC-112): 200
  with a synthesized owner entry, nothing written (§2.1 step 5.1). The spec
  says "the owner's own entry, as today"; today creates a `pending` owner row,
  which the new CHECK forbids.
- **D-d. Drop-category precedence** in the migration (§4.1) is not in the
  spec; chosen so each row counts once.
- Malformed single invite is a 400, not 422 (alternative 4).
- `TeamInvite.status` `x-enum-varnames` (§1.4) is outside the spec's scope but
  changes nothing on the wire or in generated names.
