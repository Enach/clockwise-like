## 1. What this contract is for

Part A (PAC-66) stopped the deployment's cloud identity from going to a host a
user chose. It left the three providers that are not tied to that identity alone:
OpenAI and Anthropic, which carry a key the user typed, and Ollama, which carries
none. For each of them the user still decides where the server sends the request,
by saving `llmBaseUrl` or `ollamaBaseUrl`. Spec §B1 shows the result: any account
can make the server POST to any address it can reach (cloud metadata, a database
port, loopback) and read success or failure as an oracle. The server also follows
redirects, so an Anthropic key in `x-api-key` follows a redirect to any host.

At the HTTP boundary the fix touches two operations and extends one schema:

| Operation | Change |
|---|---|
| `testLLMConnection` (`POST /api/llm/test`) | The PAC-66 **422** `LLMDestinationRefusal` now also covers `openai`, `anthropic` and `ollama`. The check is made before the key-presence check, so a refused destination with no key is a 422, not the 500 `LLM not configured`. A redirect from an approved destination is never followed and is a 502. The paragraph "The user-key and keyless providers … are unchanged by PAC-66 … PAC-66-B" is **replaced**, as the spec's inherited scope requires. |
| `patchSettings` (`PATCH /api/settings`) | Three new 400 messages for `llmBaseUrl` and `ollamaBaseUrl`, raised only when the write changes the property to a non-empty value. The operation description states the rule and what is deliberately not refused. |
| Schemas | `LLMDestinationRefusal.property` gains `llmBaseUrl` and `ollamaBaseUrl`; the descriptions of its `reason` values are extended (no new value). Descriptions added to `llmBaseUrl` and `ollamaBaseUrl` on the shared settings property map and to `LLMTestRequest.llmProvider` / `llmApiKey`. |

Two operations change behaviour with **no** contract edit, as in part A (§7):
`parseNaturalLanguage` and `refreshMeetingBrief`.

No operation is added or removed. No property is added to or removed from a
request or response. One response enum gains two values (§2).

## 2. The send-time refusal reuses part A's 422, reasons and all

Spec D-B7 says refusals reuse part A's per-path shapes, with a reason that says
which case applies, and leaves the contract stage to decide between a new reason
value and an existing one.

**Chosen: the same 422 `LLMDestinationRefusal`, the same three reasons, two new
`property` values.** The three Part B cases map onto part A's reasons without
changing what any of them means:

| Part B case | `reason` | `property` |
|---|---|---|
| Ollama, nothing approved (AC-B8) | `provider_not_enabled` | absent |
| OpenAI / Anthropic base URL not approved (AC-B1, B2, B6, B11, B19) | `destination_not_approved` | `llmBaseUrl` |
| Ollama effective destination not approved (AC-B9, B10, B18) | `destination_not_approved` | `ollamaBaseUrl`, or `llmBaseUrl` when the destination came from it |

`destination_not_set` is not used: OpenAI and Anthropic fall back to their public
host when the base URL is empty, and Ollama falls back to the shared value, then
to `http://localhost:11434`. Every Part B configuration has a destination; the
question is only whether it is approved.

`property` names the setting the user should change. When both Ollama values are
empty and the built-in default is refused, it is `ollamaBaseUrl`: nothing stored
built that destination, and `ollamaBaseUrl` is where an approved origin would go.

**Rejected: a fourth reason, `destination_not_allowed_path` (or `malformed`), for
a base URL that carries a path, query, fragment or userinfo.** It would tell a
client something slightly more specific. But part A already treats userinfo, an
`http` scheme and a non-443 port as `destination_not_approved`. Under D-B8 an
approved destination *is* a scheme, host and port, so `https://api.openai.com/x`
is simply not one of them. A new value would also make every client that switches
on `reason` handle a case with the same user action (edit that one setting). The
`error` sentence carries the detail.

**Rejected: a 400 at send time.** On this operation 400 means "the probe body is
wrong" (PAC-24). The user fixes a stored base URL somewhere else. This is part A's
argument (PAC-66.md §2) and it applies unchanged.

**Why the destination check runs before the key check.** Today `openai` and
`anthropic` with no key fail in client construction with a 500. If that stayed
first, a user with no key and a forbidden base URL would see "set API key", add a
key, and only then learn the destination is refused. Worse, the probe's answer
would depend on the key, which the spec forbids ("Refusal does not depend on the
key", as part A's rule for the credential). The contract therefore says a refusal
is the 422 whether or not a key is on file. The 500 description says so too.

**Why a redirect is a 502, not a 422.** As in part A AC-8: a request was sent to
an approved destination and its answer could not be used. A 422 keeps its single
meaning, "refused by policy, nothing sent".

## 3. Write-time refusal: `llmBaseUrl` must be approved for *some* provider that reads it

The settings write reuses the shared `SettingsValidationError` 400, with messages
that start with the property name (PAC-66.md §3, for the same reasons).

`ollamaBaseUrl` is read only by Ollama, so it must be an approved Ollama origin.
`llmBaseUrl` is harder: OpenAI, Anthropic **and** Ollama all read it (spec §B2.1).

**Chosen (spec D-B5, answering OQ-B5): approved for at least one of the three.**
The send-time rule, which follows the provider actually used, is what keeps a key
off an Ollama host (AC-B11). The write rule only has to stop values that no
provider could ever send to.

**Rejected: approved for the currently selected provider.** It is stricter, but
the web app's form lets a user type an Ollama address in the Ollama field while
OpenAI is still selected, then switch provider. A selected-provider rule would
refuse that save. It would also make the write's outcome depend on a second
property in the same body, which no other settings rule does. It buys no safety,
because the send-time check refuses the cross-provider case anyway.

**Rejected: a `pattern` on the two properties** (for example
`^https?://[^/?#@\s]+/?$`). The factory prefers making a wrong request
impossible to express, and this is the obvious first design. It fails for the
reason part A recorded: `Settings` and `SettingsUpdate` share one property map,
so the pattern would also bind the **response**. Rows written before this change
are kept (D-B4), so `GET /api/settings` would return documents that break their
own schema, and the generated zod schema in the web repo would reject them. A
pattern cannot express "approved" anyway. The handler is the enforcement point,
and each property's description says why there is no pattern.

**What the write does not refuse:** `""` (always clearable; clearing means "the
provider's fallback", which for `ollamaBaseUrl` is the shared value, not
necessarily `http://localhost:11434`; spec round-3 NB-1); a value equal to the
stored one (PAC-24 AC-17, so the web diff-only save and the e2e whole-document
PATCH keep working); a write that changes only `llmProvider` (AC-B14). Each is
refused at send time instead.

## 4. Operator configuration: two host lists and one origin list

The approved sets are deployment configuration, not HTTP. AC-B5, AC-B9, AC-B15
and AC-B17 depend on their exact form, and spec OQ-B6 asks the contract stage to
fix the entry syntax and the accepted spellings, so they are fixed here and in the
manifest's `operatorConfiguration`.

| Variable | Approves | Built in |
|---|---|---|
| `PACEDAY_LLM_APPROVED_HOSTS_OPENAI` | extra hosts for `openai` | `api.openai.com` |
| `PACEDAY_LLM_APPROVED_HOSTS_ANTHROPIC` | extra hosts for `anthropic` | `api.anthropic.com` |
| `PACEDAY_LLM_APPROVED_ORIGINS_OLLAMA` | origins for `ollama` | none |

**OpenAI and Anthropic use part A's format and matching exactly.** The format is a
bare DNS host or `https://<host>` with an optional trailing `/`. A destination
matches when its scheme is `https`, its port is absent or `443`, it has no
userinfo, and its host equals an entry ASCII case-insensitively. A trailing dot is
not stripped, so it does not match. Using the same rules means one parser and one
mental model for operators. D-B3 asks for exact hosts over secure transport, which
is what part A's syntax expresses.

**Ollama needs a different entry, so it gets a different name.** A self-hosted
Ollama is usually `http://<private-host>:11434` (D-B1). Part A's syntax can
express neither the scheme nor the port. The variable is called `…_ORIGINS_…`
rather than `…_HOSTS_…` because an entry is an origin, and an operator who copies
a part A line into it should get a malformed-entry log, not a silent approval
with a different meaning. An entry is `<scheme>://<host>[:<port>]` with an
optional trailing `/`. The scheme is `http` or `https`. The host is a DNS name
(single labels such as `ollama` or `localhost` are allowed, because that is how
compose services are named), a dotted-decimal IPv4 literal, or a bracketed IPv6
literal. IP literals are allowed here, unlike part A, because a private Ollama is
often reached by address, the operator writes the entry, and Ollama carries no
key. Matching compares scheme, host (textually, case-insensitively) and port
after applying the scheme's default, so `http://h` and `http://h:80` are the same
origin.

**Spellings (OQ-B6, second half).** These count as the approved destination: an
explicit default port (`:443` for `https`, `:80` for `http`), an upper-case host,
an upper-case scheme. These do not: a trailing-dot host, a differently written IP
literal (`127.000.000.001`), a percent-encoded host. They name the same server
only through a normalisation someone could get wrong. Refusing costs the user one
edit; accepting would need a normalisation rule in the hot path.

**What a stored base URL may contain (D-B8).** Exactly
`<scheme>://<host>[:<port>]` with at most one trailing `/`. A `?` or `#` refuses
the value even with nothing after it, because the server builds the request URL
by appending the operation path, and a bare `#` would still truncate it.
Leading or trailing whitespace refuses it too, and nothing is trimmed: a value
the server silently normalises is a value the user cannot predict.

**Rejected: letting an entry carry a path prefix** (for example an
OpenAI-compatible gateway at `https://gw.example/openai`). D-B8 makes approval
cover one operation, and a prefix makes "which operation" depend on the entry. A
gateway that needs a prefix stops working until the product owner answers the
rest of OQ-B6 (manifest `followUps.gatewayPathPrefix`; release note in spec §B7).

**Rejected: one `PACEDAY_LLM_APPROVED_DESTINATIONS` list shared by the three
providers.** It is simpler to configure. But approval must never transfer (D-B5,
AC-B11). A shared list is exactly how an OpenAI key would reach an Ollama host.

**Rejected: letting an operator approve `http` or a non-default port for OpenAI
or Anthropic.** D-B3 forbids it: those requests carry the user's key.

**Malformed entries** (AC-B15) are logged at startup, naming the variable and the
entry. They approve nothing, well-formed siblings stay approved, and the server
starts. No variable value removes the built-in public hosts (D-B2, OQ-B4).

## 5. Ollama: kept, self-hosted only, fail closed

The ticket asks for the Ollama decision to be recorded. It is spec **D-B1**,
"assumed by the factory, pending owner confirmation": Ollama is kept, and it sends
only to an origin the operator approved. Nothing approved means it is not enabled
(the 422 `provider_not_enabled`). On the hosted product, where the operator
approves nothing, Ollama is unavailable. No stored Ollama value is deleted.

This contract follows D-B1 and adds no option that widens who receives a key. The
Ollama list is separate from the OpenAI and Anthropic lists, and a destination
approved for Ollama is never a destination for a key (AC-B11).

**Rejected: drop Ollama** (remove it from the `llmProvider` enums). That deletes a
labelled option the web app offers and invalidates stored provider values. It is
also a breaking enum change for the generated web types, and it is no safer than
"not enabled unless approved". It would change the contract's enums for a
decision the owner has not made.

**Rejected: approve `http://localhost:11434` by default for Ollama.** It would
keep every default account working on a self-hosted install. But loopback on the
hosted product is the operator's infrastructure, which is the very target of
§B1 item 1. The default must fail closed (D-B1). An operator who runs Ollama on
the same host approves it in one line.

## 6. Redirects are never followed for these three providers

Spec D-B6, AC-B7. The contract says so on the operation and in the 502. The
redirect counts as a failed request: no second request, no method change, the key
sent once.

**Rejected: follow a redirect when the target is also approved for the provider,
stripping the key otherwise.** The vendors' chat operations do not redirect. A
followed 301/302/303 turns the POST into a GET on another operation, which D-B8
forbids. "Strip the key" is a per-header rule (Go strips `Authorization` across
hosts but not `x-api-key`, spec §B2.4), and the plan would have to get it right
for each provider. Refusing every redirect is one rule.

## 7. Parse and brief refresh: behaviour changes, contract does not

As in part A (PAC-66.md §5), and for the same reason. Editing
`parseNaturalLanguage` would pull open finding API-080 into scope (factory §7.1).
The refusal fits the documented shapes as they are: parse returns 200
`{"intent":"unknown","error":"…"}`, and brief refresh returns 200
`status: "failed"`, with that failed brief stored. The manifest's
`sendTimeRefusals` pins them for the tests (spec AC-B12).

Spec round-3 NB-2 notes that the redirect and exact-path criteria observe only
the probe. The contract states that the rule applies on every send. The manifest's
`planNotes` asks the plan for one parse-path test if it places the check above
the shared sending step, so the claim is tested rather than assumed.

## 9. Descriptions corrected to match the server (PAC-21)

The probe's description still said that "The provider's own error text is still
echoed on 502", and its 502 said "carrying the upstream error string". PAC-21
(#217) changed the server: the 502 body is the fixed `upstream provider error`
and the 500 for a client-construction failure is the fixed `internal error`
(`backend/api/server_errors.go`). Spec §B2.4 relies on that ("the oracle that
remains is success versus failure"). This contract edits the operation, so it
makes those sentences true (factory §7.2). No behaviour changes. The API-054 row
in the audit register is left to PAC-21's owner.
