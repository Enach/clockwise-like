## 0. The rule this contract fixes

Nothing a Manager-mode answer contains, and no work the server does to produce
it, may depend on whether an account holds an address the caller typed, unless
that account is one the caller can already see in Paceday: a Paceday member of
one of the caller's teams, or a member of the caller's organisation. For those
people, and only those, the roster and analytics say "On Paceday"; Paceday
figures stay behind PAC-60 ownership and consent as before. Everyone else is
treated exactly as an address with no account.

## 1. What changes at the HTTP boundary

No operation, path, parameter, status or schema **shape** changes. The bundle
diff is descriptions plus `deprecated: true` on one property; the generated Go
diff is comments plus one `// Deprecated:` marker. That is what makes AC-16's
"validates against the previous bundle" hold by construction: every PAC-130
answer is an instance of the very same schemas.

README §1 order.

## 2. Visibility and figures (binding; spec §3.1-§3.4, D-1, D-3, D-5, D-7, D-9, D-10)

### 2.1 The visibility rule ("visible on Paceday")

For caller V and a roster address A (the stored `member_email`, already lowercase
and trimmed by the Manager paths), A is **visible** when some row of `users` with
`lower(users.email) = lower(A)`, at **any** `address_standing`, is:

- **(a)** in `team_members` (either role) of a team in which V also has a
  `team_members` row (either role). `team_added_members` (PAC-129) never counts,
  on either side; or
- **(b)** in the organisation member set of V: the accounts `listOrgMembers`
  returns to V (§2.5).

It is decided by **one SQL statement per roster entry per request**, of the same
shape whatever A is. The organisation set inside it is the shared SQL fragment of
§2.5 (parameterised by the viewer and the seam's exclusion list), so (b) adds no
statement. For example:

```sql
SELECT EXISTS (
  SELECT 1 FROM users u
  WHERE lower(u.email) = lower($2)
    AND (
      EXISTS (SELECT 1 FROM team_members v
              JOIN team_members m ON m.team_id = v.team_id
              WHERE v.user_id = $1 AND m.user_id = u.id)
      OR u.id IN (<orgMemberSetSQL($1, $3), §2.5>)
    ))
```

The exact text is the plan's. What is binding: one statement; it returns no row
for an address carried only outside (a) and (b); no other statement runs only
because a carrier exists (AC-8). An account outside (a) and (b) is never consulted,
so a legacy case-collision carrier outside them changes nothing (spec B-1).

Consequences, all deliberate:

- **source `formal`** (a Paceday member of the roster's team, which V reads as a
  member of it) is visible by construction: no statement is needed and none runs.
- **source `added`** (PAC-129) keeps PAC-129's rule: `is_paceday_user` false,
  zeroes, nothing read, nothing stored. It takes none of the three branches.
- **V's own address** on V's own roster (a manual row) is visible when V is in
  any team or has an organisation, as both lists show V to V; PAC-60 never passes
  for oneself (`m.user_id <> o.user_id`), so it is the no-read branch. Before
  PAC-130 the add linked V to themselves with the same outcome (flag true, zeroes).

### 2.2 The three branches

The branch is decided **once per entry per request**, before any of its weeks is
read, in this order. Each read named below fires the engine step seam (§6) after
it runs.

1. `source` `added`: PAC-129 rule (above). Stop.
2. Visibility (`formal`: visible, no read; `manual`/`auto`: the §2.1 statement,
   step `visibility-read`). Not visible → **branch (3) Estimate**.
3. Known account: `formal` → the team member's own account, at any standing (as
   before PAC-130, spec revision 2 option (i)); `manual`/`auto` →
   `storage.ConfirmedHolder(A)` (PAC-71 granting site, step `holder-lookup`). No
   single domain-confirmed holder → **branch (2) No read**.
4. PAC-60: `storage.OwnsTeamWithMember(V, account)` (step `owner-check`). False →
   **No read**.
5. Consent: `analytics_shared_with_manager` of the account, read exactly as today
   (`engine/manager.go:503-516`, step `consent-read`): **no `user_profiles` row
   reads as NOT shared** (branch (2)); a row whose column is NULL reads as shared
   (`COALESCE(…, true)`; the column defaults to true, `016_manager.up.sql:5`).
   Withheld → **No read**. Whether "no row" *should* mean shared is PAC-107's
   question, not this contract's: PAC-130 keeps today's reading.
6. Otherwise → **branch (1) Paceday figures**.

| Branch | `is_paceday_user` | Per week | Cache |
|---|---|---|---|
| (1) Paceday figures | true | the account's `analytics_weeks` row (step `analytics-week-read`); no row → zeroes, `data_available` false | serves and writes only rows with `team_analytics_cache.is_paceday_user = true` |
| (2) No read | true | zeroes, `data_available` false; nothing read, no free/busy request | never read, never written |
| (3) Estimate | false | free/busy through **V's** credential, exactly today's external path: `focus_minutes` 0, `meeting_minutes` = busy, `free_minutes` = 2400 − busy floored at 0; unknown coverage → `data_available` false, not cached | serves and writes only rows with `is_paceday_user = false` |

`team_analytics_cache.is_paceday_user` therefore becomes the **branch marker** of
a cached row; no column is added. A cached row whose marker is not the current
branch's is ignored and, on (1) or (3), overwritten by the fresh computation.

This gives the spec's transitions (§3.4, AC-10 transition, AC-11): leaving V's last
shared team → (3) on the next read, and no Paceday figure is served again; becoming
visible → (1) or (2), and a cached estimate is never served; a pre-PAC-130 row with
Paceday figures for a viewer who now sees the address as not visible is never served
(it carries marker true, the estimate branch serves only false).

**Consent is decided before the cache** (a change from today, where a cached row
was served for up to 4 h after consent was withdrawn). It follows from the spec's
branch table (§3.4: consent is a condition of branch (1), and branch (2) "never
serves from the cache") and is what AC-9's third bullet asserts. Accepted
transitional residual: rows cached **before** deploy on the old linked path while
consent was withheld (marker true, zeroes) can be served on branch (1) for at most
the 4 h TTL after deploy; they show "no data", never someone's figures.

### 2.3 Work done for an address that is not visible (D-10, AC-8)

For H (held outside (a)/(b)) and N (held by nobody), every read is: one
`visibility-read`, then per week `cache-read`, `freebusy` (V's token), and
`cache-write` when coverage is known. Nothing else: no `holder-lookup`,
`owner-check`, `consent-read` or `analytics-week-read`. The index-probe residual
inside the one visibility statement is accepted (spec §3.2).

### 2.4 Errors (D-9, AC-13; SF-010's rule carried forward)

A failed visibility read, holder lookup, ownership check or consent read is the
500 `{"error":"internal error"}` on both `getManagerRoster` and
`getManagerAnalytics` (the existing `ServerError` response). Never an entry shown
as not visible, never an estimate, never "no data". **Nothing is cached for the
failing entry, nor for any entry read after it.** Entries read earlier in the same
request may already have been cached, exactly as under SF-040 today (each cached
row is a correct fact computed on its own branch); the answer is the 500 all the
same. AC-13's test therefore uses a one-entry roster, or asserts only on the
failing entry. The existing SF-040 rules for the per-week reads are unchanged.

### 2.5 Rule (b) is the organisation member list (AC-17; spec B-3)

`listOrgMembers` and rule (b) read the organisation member set through **one
SQL fragment**, `orgMemberSetSQL`, parameterised by the **viewer** (not by an
organisation id) and by an exclusion list of account ids:

```sql
SELECT o.id FROM users o JOIN users me ON me.org_id = o.org_id
 WHERE me.id = $viewer AND me.org_id IS NOT NULL AND NOT (o.id = ANY($excluded))
```

The visibility statement embeds it (so (b) adds no statement, §2.1), and
`storage.GetOrgMembers` is re-expressed through it (keyed by the viewer; its
answer, columns and order unchanged). In production the exclusion list is always
empty; the test seam of §6 (`orgMembersExclude`) supplies it, so AC-17 observes
both endpoints narrow together. Whatever narrows the fragment narrows both;
PAC-148 will. The only permitted difference is error handling: `listOrgMembers`
keeps its documented `[]` fallback when the caller cannot be loaded; the Manager
read never falls back (a failure is the 500, §2.4).

Until PAC-148 lands, (b) carries the list's consumer-domain exposure (spec O-11);
(b) adds nothing to it, since a viewer at such a domain can already enumerate
those accounts through `listOrgMembers`.

## 4. Migration `042_manager_member_link_erase` (binding in substance)

Number checked: main's latest is `041_team_added_members`; no branch on origin and
no spec, plan or contract on any branch claims 042.

### 4.1 Up

```sql
-- PAC-130 (spec docs/specs/PAC-130.md D-6, AC-12; contract
-- contracts/features/PAC-130.md §4): erase every Manager roster link that does
-- not satisfy the visibility rule (§2.1) for the roster's owner. Kept links serve
-- an image rollback only; nothing reads them after PAC-130. Irreversible.
DO $$
DECLARE n bigint;
BEGIN
    UPDATE manager_team_members mtm
       SET member_user_id = NULL
     WHERE mtm.member_user_id IS NOT NULL
       AND NOT EXISTS (
           SELECT 1 FROM users u
            WHERE u.id = mtm.member_user_id
              AND lower(u.email) = lower(mtm.member_email)
              AND (EXISTS (SELECT 1 FROM team_members v
                             JOIN team_members m ON m.team_id = v.team_id
                            WHERE v.user_id = mtm.manager_user_id
                              AND m.user_id = u.id)
                   OR EXISTS (SELECT 1 FROM users o
                               WHERE o.id = mtm.manager_user_id
                                 AND o.org_id IS NOT NULL
                                 AND o.org_id = u.org_id)));
    GET DIAGNOSTICS n = ROW_COUNT;
    RAISE LOG 'PAC-130 migration 042: erased % manager roster account links', n;
    RAISE NOTICE 'PAC-130 migration 042: erased % manager roster account links', n;
END $$;
```

- A link is **kept** only when the linked account itself carries the row's
  address and is in (a) or (b) for the owner. That is stricter than "the address
  is visible": a link to an account that no longer carries the address, or a link
  whose address is visible only through a different account, is erased. Erasing
  more is the safe direction; a kept link has no reader after PAC-130.
- `updated_at` is not touched and there is no trigger on the table, so "no other
  column or row changes" (AC-12) holds. `team_analytics_cache` is not touched
  (spec §5: unreachable, not purged).
- Idempotent **while memberships and organisations are unchanged**: a re-run
  after a membership change erases more, which is the safe direction.
  golang-migrate never re-runs it.
- **Locks**: one `UPDATE`: `ROW EXCLUSIVE` on `manager_team_members`, row locks on
  the erased rows, `ACCESS SHARE` on `users` and `team_members`. It is applied with
  no backend serving (PAC-116), so contention is nil and the duration is one pass
  over a small table.

### 4.2 Down

A no-op that says so on its first line, for example:

```sql
-- 042_manager_member_link_erase.down.sql: changes nothing. The erased links
-- cannot be restored (they were the leaked bit). Development and tests only.
SELECT 1;
```

### 4.3 Operations (PAC-116; spec §7)

- Applied with no backend serving, by PAC-116's automatic stop-migrate-start
  (`docs/runbook.md`, "Applying migrations: stop, migrate, start"). No extra
  traffic step.
- **Image-only rollback is refused** on a database at 042 (PAC-116: the previous
  image cannot start on an unknown version). The spec's "image rollback" (§7)
  is therefore one of: restore the pre-deploy backup (which restores the erased
  links, losing everything written since), or, in development, tests and staging,
  `migrate ... down 1` while 042 is the newest migration (a no-op) and start the
  previous image, which then reads the kept links again and shows erased holders
  as externals.
- Binding text for `docs/runbook.md` "Rollback", added in the stage-4 PR after the
  PAC-119 bullet:

  > - **Going back past PAC-130** (Manager account links, migration
  >   `042_manager_member_link_erase`): this section applies unchanged — fix
  >   forward, or restore the pre-deploy backup and start the previous image. An
  >   image-only rollback does not work: the previous image cannot start on a
  >   database at 042. The down step changes nothing and is for development,
  >   tests and staging (stop the backend, `migrate ... down 1` only while 042 is
  >   the newest applied migration, start the previous image). The up step
  >   **erased** every Manager roster account link except one whose account still
  >   carries the roster address and shares a team or the organisation with the
  >   manager (so a link to an account whose address has since changed is erased
  >   too); no down step or image brings them back, only the backup does. For rollback fidelity without a full restore, snapshot the
  >   table before deploying: `pg_dump -t manager_team_members`. Release note
  >   for PAC-130: Manager mode shows "On Paceday" only for Paceday members of
  >   the manager's teams and organisation; erasing links may make some unbound
  >   legacy accounts empty, so they bind on authoritative evidence at their next
  >   sign-in (PAC-71 rule (b)) — expected, not a support incident.

### 4.4 Release note (spec §7, N-6)

1. Manager mode shows "On Paceday" only for people who are Paceday members of one
   of the manager's teams or are in the manager's organisation; everyone else
   shows a meeting-time estimate from the manager's own calendar, Paceday user or
   not. The analytics note no longer says "non-Paceday users".
2. **Consent inversion** (spec §3.2, OQ-2): a Paceday user who withheld sharing
   and is not visible to the manager now shows that manager a meeting-time
   estimate read through the manager's own calendar access, while their own team
   owner sees "no data"; a member removed from the manager's team moves from "no
   data" to an estimate. No Paceday-held data is read for them.
3. Migration 042 erases stored Manager account links, keeping only a link whose
   account still carries the roster address and shares a team or the
   organisation with the manager (a link to an account whose address changed is
   erased too). **Irreversible**: the down step is a no-op; snapshot
   `manager_team_members` first if you need rollback fidelity.
4. Some unbound legacy accounts become bindable under PAC-71 rule (b).
5. These rows move from the estimate to "On Paceday" with "no data" (spec §3.3,
   §6, AC-10, AC-19), whether `manual` or detected (`auto`):
   - a row for an **unconfirmed** co-member of one of the manager's teams (their
     `formal` entry, when there is no row, keeps its figures);
   - a row for an **unconfirmed** account in the manager's organisation;
   - a row whose address is carried by a letter-case pair of accounts, one of
     them visible to the manager.
6. Withdrawing analytics sharing takes effect on the manager's next read, not
   after the 4-hour cache (§2.2).

## 10. Alternatives rejected

1. **`member_user_id: { type: "null" }`** (make a non-null value impossible to
   express). Rejected after trying it: the pinned `oapi-codegen` v2.4.1 fails on a
   bare `null` type ("error resolving primitive type: unhandled Schema type:
   &[null]"), so `bash scripts/openapi_gen_go.sh` cannot run. `const`/`enum` tricks
   were not adopted: they would change the generated Go type for a field nothing
   reads, for no enforcement the tests do not already give. The property keeps its
   previous type, is `deprecated`, and AC-1/AC-5 assert the value.
2. **Remove `member_user_id` now.** Breaks the web's strict generated schema,
   which requires the key (spec D-4). Removal is a later two-repo ticket (§1).
3. **A new schema field (e.g. `visibility: visible|not_visible`) or a new
   `is_visible` flag** instead of narrowing `is_paceday_user`. Every client already
   renders the badge from `is_paceday_user`; a second field would leave the old one
   carrying the leaked bit for old clients, or two fields that must agree.
4. **Decide the branch per week** (today's `GetMemberWeek` shape). Rejected: the
   flag is per entry, so per-week decisions can disagree with it inside one answer
   (a membership change mid-request), and AC-8's statement count would scale with
   weeks without adding information.
5. **A cache column for the branch.** `team_analytics_cache.is_paceday_user`
   already separates the two cached branches exactly (branch (2) is never cached),
   so a migration on the cache table is unnecessary.
6. **Migration keeps a link when the address is visible through any account.**
   Rejected for the stricter "the linked account itself" (§4.1): a kept link whose
   account is not the visible one would point at the wrong person on rollback.
7. **Answer 403 or 404 for a not-visible address.** That is itself the oracle.
8. **Rule (b) as its own organisation predicate.** It would silently diverge when
   PAC-148 narrows the list (spec B-3); one definition (§2.5) cannot.
