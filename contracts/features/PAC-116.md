## 0. The rule this contract fixes

Consider an up migration file that locks one of `bookings`, `scheduling_links`, `scheduling_link_hosts` or `users`, where that table existed before the file ran. Its first statement that locks the table takes the highest *level* (§2) the file ever takes on that table. The build enforces this with a test that parses the up migration files. The test needs no database, and there is no exemption mechanism.

## 1. What changes at the HTTP boundary

Nothing. `python scripts/openapi_assemble.py --check` on `c2609a6` gives "OK: bundle is in sync (110 paths)". The bundle's sha256 (`git show origin/main:contracts/openapi/openapi.yaml | sha256sum`) is `ae3d6c1c045e66fe898390ff291afa9655c53d1065b451135020738d6f2cef8d`, and this contract leaves it unchanged. The interface this contract binds is a non-HTTP one: the classification of SQL statements into table locks (§3–§4) and the test's failure format (§5).

## 2. Levels (binding)

The modes and conflicts come from PostgreSQL's "Table-Level Lock Modes" and "Conflicting Lock Modes" table (docs §13.3.1, PostgreSQL 16). The live paths take only ACCESS SHARE, ROW SHARE and ROW EXCLUSIVE on covered tables (spec §2.3). A mode's level is the set of those three modes it conflicts with:

| Level | Modes | Blocks (live modes) |
|---|---|---|
| 0 | ACCESS SHARE, ROW SHARE, ROW EXCLUSIVE, SHARE UPDATE EXCLUSIVE | none |
| 1 | SHARE, SHARE ROW EXCLUSIVE | ROW EXCLUSIVE |
| 2 | EXCLUSIVE | ROW SHARE, ROW EXCLUSIVE |
| 3 | ACCESS EXCLUSIVE | all three |

**Rule R1.** In one file, for one covered table T that is not created earlier in the same file, let s1 be the first statement that locks T. Every later statement's level on T must be ≤ s1's level on T. A statement's level on T is the highest level among the locks it takes on T.

**Why this cannot cycle with a live path on T.** The migration waits for its first lock on T while holding nothing on T. Once that lock is granted, it never waits on T again. A live transaction's later request on T may queue behind the migration's *waiting* request. PostgreSQL places a requester that already holds a conflicting lock on the object ahead of that waiter (`ProcSleep`, early deadlock avoidance), and the detector rearranges any remaining soft edges. So no hard cycle forms on T.

**Rule R2.** An up file contains no top-level transaction control (`BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE`, `PREPARE TRANSACTION`, `COMMIT PREPARED`, `ROLLBACK PREPARED`) and no `CONCURRENTLY`. R1 rests on "one file = one transaction" (spec §2.1).

**Rule R3 (fail closed).** A statement that names a covered table T outside literals, and that the classifier cannot classify (§4 "unclassifiable"), fails the check. The exception is when the file's first lock on T was level 3.

## 3. Lexing (binding behaviour; implementation free)

- Comments are removed before classification: `--` to end of line, and `/* */` nested to any depth.
- Literals are not identifiers and do not split statements. This covers `'...'` (with `''`), `E'...'` (with backslash escapes), and dollar quotes `$tag$...$tag$` (tag possibly empty). A dollar-quoted body is kept, but it is visible only to the `DO`/`CALL` rule.
- Statements split on `;` outside literals and comments. A last statement with no `;` counts.
- Identifiers: an unquoted identifier is folded to lower case. A quoted identifier (`"..."`, with `""` as an escaped quote) is taken exactly as written. A qualified name `a.b` or `a.b.c` is the last part. A name matches a covered table when its last part equals it, so `public.users` and `"users"` match, and `"Users"` does not.
- Keywords are case-insensitive, and any run of whitespace is one space.
- Statements are numbered from 1 in file order. Only the statements that remain after comments are removed are counted.

## 4. Classification table (binding)

The *replay* is the classifier's memory across files. It processes every up file in version order before (and including) the one being checked. It records:

- **tables**: names created by `CREATE TABLE` (and renamed by `ALTER TABLE ... RENAME TO`);
- **FKs**: per table, the referenced tables, with the constraint name when one is given and the referencing columns;
- **indexes**: index name → table, from `CREATE INDEX name ON table` and from the named or default index of `UNIQUE`/`PRIMARY KEY`. PostgreSQL's defaults are `<table>_pkey`, `<table>_<cols>_key`, and `<table>_<cols>_idx` for an unnamed `CREATE INDEX ON t (cols)` (as `006` does); an expression index's default name is not modelled, and dropping it fails as "cannot resolve index".

"Covered" means covered and not created earlier in the same file. Statements that lock no covered table are classified only far enough to update the replay.

| Statement | Lock on the named table | Lock on other tables |
|---|---|---|
| `LOCK [TABLE] [ONLY] t1[, t2 …] [IN <mode> MODE] [NOWAIT]` | `<mode>` on each, ACCESS EXCLUSIVE when no mode is given | — |
| `CREATE [TEMP] TABLE [IF NOT EXISTS] t (…)` | t becomes "created in this file" (exempt) | SHARE ROW EXCLUSIVE on each table named by `REFERENCES` (column-level or `FOREIGN KEY … REFERENCES`); ACCESS SHARE on a `LIKE` source |
| `CREATE TABLE t … AS <query>` / `SELECT … INTO t` | t created | ACCESS SHARE on tables read by the query |
| `CREATE TABLE t PARTITION OF p` / `INHERITS (p)` | t created | **unclassifiable** when p is covered |
| `ALTER TABLE [IF EXISTS] [ONLY] t <sub>[, <sub> …]` | the highest of its subcommands below | as the subcommands say |
| — sub `VALIDATE CONSTRAINT`, `SET STATISTICS`, `ALTER COLUMN … SET (attribute_option)` / `RESET`, `CLUSTER ON`, `SET WITHOUT CLUSTER`, `SET (storage_parameter)` / `RESET (…)` where every parameter is `fillfactor`, a `toast.*` or `autovacuum_*` parameter, or `parallel_workers` (PG 16 docs; any other parameter: ACCESS EXCLUSIVE, last row of this group), `ATTACH PARTITION p` (on the parent) | SHARE UPDATE EXCLUSIVE | `VALIDATE CONSTRAINT` of an FK: ROW SHARE on the referenced table (PG 16 docs). `ATTACH PARTITION p`: ACCESS EXCLUSIVE on p |
| — sub `ADD [CONSTRAINT n] FOREIGN KEY (…) REFERENCES r` (with or without `NOT VALID`) | SHARE ROW EXCLUSIVE | SHARE ROW EXCLUSIVE on r |
| — sub `ENABLE`/`DISABLE [ALWAYS\|REPLICA] TRIGGER …` | SHARE ROW EXCLUSIVE | — |
| — sub `ADD [COLUMN] … REFERENCES r` | ACCESS EXCLUSIVE | SHARE ROW EXCLUSIVE on r |
| — sub `DROP CONSTRAINT [IF EXISTS] n`, where n is an FK of t in the replay (by name; or n matches `<anything>fkey<digits?>` and t has an FK whose default name is n) | ACCESS EXCLUSIVE | ACCESS EXCLUSIVE on the FK's referenced table |
| — sub `DROP CONSTRAINT n` ending in `fkey<digits?>` that the replay cannot resolve, on a t with any FK to a covered table | ACCESS EXCLUSIVE | **unclassifiable** for those covered tables |
| — sub `DROP [COLUMN] c`, where c is a referencing column of an FK of t | ACCESS EXCLUSIVE | ACCESS EXCLUSIVE on the referenced table |
| — every other sub (`ADD COLUMN`, `ADD CONSTRAINT … CHECK/UNIQUE/PRIMARY KEY/EXCLUDE`, `ALTER COLUMN TYPE/SET NOT NULL/SET DEFAULT/DROP DEFAULT`, `DROP CONSTRAINT` of a non-FK, `RENAME`, `OWNER TO`, `SET SCHEMA`, `DETACH PARTITION`, …) | ACCESS EXCLUSIVE (PostgreSQL: "ACCESS EXCLUSIVE unless explicitly noted") | — |
| `CREATE [UNIQUE] INDEX [IF NOT EXISTS] [n] ON [ONLY] t …` | SHARE | — |
| `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `REINDEX … CONCURRENTLY`, `DETACH PARTITION … CONCURRENTLY` | **R2 failure** | — |
| `DROP INDEX [IF EXISTS] n[, …]` | ACCESS EXCLUSIVE on the index's table (replay) | an unresolvable index fails ("cannot resolve index n"), whether or not its table is covered |
| `ALTER INDEX n …`, `REINDEX INDEX n` / `TABLE t` | ACCESS EXCLUSIVE on the index's table (conservative) | unresolvable index: as `DROP INDEX` |
| `DROP TABLE [IF EXISTS] t[, …] [CASCADE]`, `TRUNCATE [TABLE] t[, …]` | ACCESS EXCLUSIVE on each t | ACCESS EXCLUSIVE on every covered table each t references (replay); `CASCADE`, or a covered table referencing t: ACCESS EXCLUSIVE on the referencing covered tables too |
| `CREATE [CONSTRAINT] TRIGGER … ON t` | SHARE ROW EXCLUSIVE | — |
| `DROP TRIGGER … ON t`, `CREATE RULE … ON t`, `DROP RULE … ON t`, `CREATE POLICY … ON t`, `ALTER POLICY`, `DROP POLICY` | ACCESS EXCLUSIVE | — |
| `COMMENT ON TABLE t` / `COMMENT ON COLUMN t.c`, `CREATE STATISTICS … FROM t`, `ANALYZE t` | SHARE UPDATE EXCLUSIVE | — |
| `INSERT INTO t …`, `UPDATE t …`, `DELETE FROM t …`, `MERGE INTO t …` (including after a `WITH`) | ROW EXCLUSIVE | ROW SHARE on every covered table t references (FK check; for `INSERT`, `UPDATE`, `MERGE`); ACCESS SHARE on every other covered table named in the statement (reads) |
| `SELECT …`, `WITH … SELECT …`, `CREATE [OR REPLACE] [MATERIALIZED] VIEW … AS …` | ACCESS SHARE on every covered table named; `FOR UPDATE/NO KEY UPDATE/SHARE/KEY SHARE`: ROW SHARE | — |
| `REFRESH MATERIALIZED VIEW v` | ACCESS EXCLUSIVE on v (never covered) | ACCESS SHARE on the covered tables v reads (replay) |
| `DO [LANGUAGE l] $$…$$`, `CALL …` | **unclassifiable** for every covered table named in the body or arguments; ignored when none is named | — |
| `CREATE [OR REPLACE] FUNCTION/PROCEDURE …` | no lock (the body is not executed) | — |
| `CREATE EXTENSION`, `CREATE TYPE`, `CREATE SEQUENCE`, `ALTER SEQUENCE`, `CREATE SCHEMA`, `SET …` / `RESET …` (session or local settings) | no lock on a table | — |
| anything else | **unclassifiable** for every covered table named outside literals; no lock otherwise | — |

In every row, a covered table that the statement also names anywhere else outside literals gets at least ACCESS SHARE, for example in a subquery. A statement's level on T is the highest level over all of its rows. "Unclassifiable" means R3: it fails, unless level 3 is already held on T in the file.

The table is conservative in one direction only. Where PostgreSQL might take a weaker lock than the table says (`ALTER INDEX`, `REINDEX`, the FK-check ROW SHARE of an `UPDATE` that does not touch the FK column), the check can report a violation that would not deadlock. Every such report goes away with a leading `LOCK TABLE … IN ACCESS EXCLUSIVE MODE`. Where PostgreSQL takes a stronger lock than a row says, the row is wrong, and this contract must be revised. Stage 4 may not "fix" it in the code alone.

## 5. The test's interface (binding)

- It runs as part of `make test` (`test-backend`), needs no database, Docker or network, and is not skipped under `-short`.
- **Input:** every `*.up.sql` in the embedded migrations, in ascending version order (the replay of §4). Zero files is a failure.
- **Checker:** a pure function, so ACs can feed synthetic files after the real ones (or alone, AC-6). Its signature is up to the plan (spec OQ-2).
- **Output on failure** (spec AC-18), one block per violation:

  ```
  migration lock order (PAC-116): 040_example.up.sql, table bookings
    first lock:  statement 1, SHARE (level 1): CREATE INDEX idx_x ON bookings (start_time)
    then:        statement 2, ACCESS EXCLUSIVE (level 3): ALTER TABLE bookings ADD COLUMN y TEXT
    fix: put the ACCESS EXCLUSIVE statements on bookings first, or start the file with
         LOCK TABLE bookings IN ACCESS EXCLUSIVE MODE; (see contracts/features/PAC-82.md section 4.4)
  ```

  R2 failures name the file, the statement number and the keyword. R3 failures name the file, the statement, the table, and "cannot classify" or "cannot resolve index n". The statement text is the first 80 characters after comments are stripped and whitespace is collapsed.
- **Covered tables** are one constant listing the four Q1 names. Adding a table is a contract change to this manifest (spec §5).
- **No exemption** (spec D-4). The test reads no allow-list, directive comment or environment variable.

## 9. Alternatives rejected

1. **An exemption directive** (for example `-- pac116: exempt bookings PAC-NN reason`), in the style of `//nolint`. Rejected because a leading `LOCK TABLE … IN ACCESS EXCLUSIVE MODE` always passes and is always correct. An exemption would only let a file keep a weaker first lock *and* a stronger later one, which is exactly the deadlock. False positives from the conservative rows (§4) are fixed the same way, at the cost of a briefly stronger lock that the runbook's maintenance-window guidance already covers.
2. **The plain 8-mode order of the PostgreSQL docs as "strength".** It would forbid `SELECT … FROM users` followed by `UPDATE users` (ACCESS SHARE → ROW EXCLUSIVE) and similar data back-fills, as in 022 and 035, which cannot cycle with a live path: no live path takes a lock that conflicts with ROW EXCLUSIVE. The level table (§2) orders exactly what live paths can wait on.
3. **Superset of conflict sets** (a later mode must conflict with nothing the first did not). This is equivalent to the 8-mode order for these purposes, and has the same false positives as 2.
4. **A PostgreSQL reproduction test** (two sessions, observe `40P01`). The owner rejected it (Q2). It would prove one shape and miss the next.
5. **Setting `lock_timeout` in every migration, or a retrying migrator.** This turns a deadlock into a lock-timeout failure and a dirty schema, which is no better for the operator. It also changes how migrations run, which Q3 keeps unchanged.
6. **A full SQL parser** (for example a cgo binding of PostgreSQL's parser). It would be exact on syntax, but it still needs §4's lock table and the replay, and it adds cgo to a cgo-free backend build. Left to the plan (spec OQ-2) with the hand-written lexer as default.
7. **Checking at run time** (a migration wrapper that inspects `pg_locks`). It sees only what happens on the database at hand, after the fact. The rule must hold for every file before it ships.
8. **Enforcing a cross-table order now** (spec §2.5). `users` has no single safe position among the live paths (erasure takes it last, account deletion first). This needs an owner decision (spec OQ-1).

## Challenge — 2026-11-14

**Verdict**: accept-with-changes (REVISE). B1–B4 below are blocking. Each one is a migration that passes R1–R3 as written and still deadlocks with a live path, or that slips past the fail-closed rule. Contract revision 2 must resolve them before stage 3. Small factual fixes were applied directly in `7266efe` (see N2, N4–N6).

There is no HTTP surface, so the "requests and responses" here are migration files and live transactions.

### Rule defects (blocking)

**B1. R1's "no cycle on T" proof ignores row locks. A level-1 first lock followed by row-locking DML deadlocks.** §2's argument holds for table locks only. When the first lock on T is SHARE or SHARE ROW EXCLUSIVE, live transactions can still hold ROW SHARE on T, and with it **row locks** (`FOR UPDATE`, `FOR NO KEY UPDATE`, FK checks). A later migration statement that waits on one of those row locks closes a cycle once that live transaction asks for ROW EXCLUSIVE on T.

```sql
-- 040_user_flags.up.sql: passes R1 (users: SRE level 1, then RS level 0)
CREATE TABLE user_flags (user_id UUID NOT NULL REFERENCES users(id), flag TEXT NOT NULL);
INSERT INTO user_flags (user_id, flag) SELECT id, 'x' FROM users;
```

Live sign-in: `storage/signin.go:222` calls `lockAccountExclusive`, which runs `SELECT id FROM users WHERE id=$1 FOR UPDATE` (`session.go:97`), then `UPDATE users …` (`signin.go:263`).

1. The sign-in transaction S takes row U `FOR UPDATE` (ROW SHARE on users).
2. The migration M gets SRE on users, which is compatible with ROW SHARE.
3. M's RI check runs `SELECT 1 FROM users … FOR KEY SHARE` on U. It waits on S.
4. S's `UPDATE users` needs ROW EXCLUSIVE, which conflicts with SRE. S waits on M. The result is `40P01`.

This is exactly the shape of the real **migration 022** (`CREATE TABLE … REFERENCES users`, then `INSERT … SELECT … JOIN users`), which the spec's §2.4 lists as "ok". There is a second instance: `CREATE INDEX … ON users (…); UPDATE users SET …;` against `SetUserOrg` (`orgs.go:55` `FOR NO KEY UPDATE`, then `:62` `UPDATE users`). The operator's `advance_all` has the same shape (`operator.go:286`, then `:289`).

Level 0 first is safe, because it blocks no live table request. Level 2 or 3 first is safe, because no live row-lock holder can be present. **Resolve:** add to R1: "when the first lock on T is level 1, no later statement may take or wait for row locks on T". That covers:
- `UPDATE`, `DELETE` and `MERGE` on T;
- `SELECT … FOR …` on T;
- `INSERT … ON CONFLICT DO UPDATE` into T;
- `INSERT`, `UPDATE` and `MERGE` on a table with an FK to T (the RI check);
- RI actions into T (B3).

The remedy stays plain SQL: a leading `LOCK TABLE T IN EXCLUSIVE MODE` (or `ACCESS EXCLUSIVE`), or the DML placed before the SHARE-level statement.

022 then fails AC-17, so the author or owner must pick one of two options:
- (a) Edit 022 to add a leading `LOCK TABLE users IN EXCLUSIVE MODE;`. golang-migrate does not checksum applied files, so only fresh installs change. This needs D-7 and `forbiddenPaths` amended.
- (b) The test pins the exact historic violation set for files ≤ 039. It fails if that set changes, and it is not usable by 040+.

Add ACs for both counterexamples and for the `LOCK … IN EXCLUSIVE MODE` remedy.

**B2. "Overstating is conservative" (§4, last paragraph) is false for the first lock.** Overstating a statement's level is safe only when the statement is not the first lock. If the first lock is overstated, a real upgrade after it is hidden. These rows do that:

| Migration | Contract says | PostgreSQL 16 does | Deadlock |
|---|---|---|---|
| `REINDEX TABLE bookings; ALTER TABLE bookings ADD COLUMN z INT;` | AE first: pass | SHARE on bookings and **AE on each index** | The save's step 6–8 read holds AS on bookings and, while it plans, asks AS on `idx_bookings_link`. That waits on M. M's AE on bookings waits on the save's AS. |
| `TRUNCATE booking_events; CREATE INDEX ON bookings (x); ALTER TABLE bookings ADD COLUMN y INT;` | AE on bookings (referenced by `booking_events`, 009:40) first: pass | no lock on bookings | The real order is SHARE, then AE. That is the AC-1 cycle. |
| `ALTER TABLE archive.bookings ADD COLUMN y INT; CREATE INDEX ON bookings (x); ALTER TABLE bookings ADD COLUMN z INT;` | last-part match, AE first: pass | `archive.bookings` is another table | The AC-1 cycle on `public.bookings`. `CREATE TEMP TABLE bookings` (which makes `public.bookings` "exempt") and `SET search_path` are the same hole. |

`ALTER INDEX` belongs to the REINDEX class: it locks the index, not the table at AE. **Resolve:**
- Make the asymmetry binding: a row may overstate a level only where the statement cannot be the first lock at that level.
- `REINDEX` and `ALTER INDEX` are unclassifiable for the index's covered table unless level 3 is held.
- `TRUNCATE t` takes AE on t only (plus the referencing tables under `CASCADE`), and no lock on the tables t references.
- A qualified name matches only when its schema is `public`.
- `CREATE TEMP TABLE` with a covered name, and any `SET`/`RESET`/`set_config` of `search_path`, are refused (R2-style).

Add ACs for each.

**B3. RI actions on *referencing* tables are missing.** The DML row gives only the FK-check ROW SHARE on the tables t references. A `DELETE` (or a key `UPDATE`) on t also fires RI actions on every table that references t:
- `CASCADE` and `SET NULL` take ROW EXCLUSIVE and row locks;
- `NO ACTION` and `RESTRICT` take ROW SHARE and `FOR KEY SHARE`.

Today's covered chains are:
- organizations → users (`users.org_id … ON DELETE SET NULL`, 007:8);
- users → scheduling_links and scheduling_link_hosts;
- scheduling_links → scheduling_link_hosts and bookings (009, CASCADE).

```sql
DELETE FROM organizations WHERE domain = 'old.example'; -- hidden: RE + row locks on users
ALTER TABLE users ADD COLUMN z INT;                      -- table: first lock on users = AE, pass
```

A sign-in on an affected user arrives after M's update. It holds ROW SHARE on users and waits on M's row lock. M's AE waits on that ROW SHARE, and the result is `40P01`. **Resolve:** in the DML row, `DELETE`, `UPDATE` and `MERGE` on t take ROW EXCLUSIVE, *with row locks* (for B1), on every covered table that references t. This applies transitively over the replay's FKs, whatever the action. `TRUNCATE … CASCADE` takes AE on the same tables. Add an AC with the organizations example.

**B4. Fail-closed has holes through indirection (D-5, R3).** Classification reads only the names in the statement text. PostgreSQL runs code that the text does not name:
- `CREATE FUNCTION touch() RETURNS void LANGUAGE sql AS $$ UPDATE bookings SET notes = notes $$; SELECT touch(); ALTER TABLE bookings ADD COLUMN z INT;` passes. `CREATE FUNCTION` takes no lock, and `SELECT touch()` names no covered table. In reality the file takes RE and row locks, then AE.
- A view over a covered table (`UPDATE v …` on an auto-updatable view, or `LOCK TABLE v IN SHARE MODE`, which recurses into the view's tables).
- A trigger or rule on a non-covered table whose body writes a covered table.

No up file has `CREATE FUNCTION`, `VIEW`, `TRIGGER` or `RULE` today, so this is about the future. **Resolve:** the replay records views, routines, triggers and rules with the covered names that their definitions mention. A statement that reads, writes or locks such a view, calls such a routine, or writes a table carrying such a trigger or rule is unclassifiable for those tables, unless level 3 is held. Add ACs.

### Verified clean

- **Levels.** Against the PG 16 conflict table, the live-mode conflict sets are nested: ∅ ⊂ {RE} ⊂ {RS, RE} ⊂ {AS, RS, RE}. For *table* locks, R1 is sound. A later request conflicts only with live modes that the first lock already excludes. `ProcSleep` puts M ahead of any live waiter whose request conflicts with what M holds.
- **Live paths.** None takes SHARE or stronger on a covered table. No `LOCK TABLE`, `TRUNCATE` or DDL appears in non-test Go. The save's order is as cited (`scheduling_links.go:542`, `:657-663`, `:680-682`, `:758`).
- **One transaction per file.** golang-migrate v4.19.1 `Run` calls `runStatement`, which runs `ExecContext(query)` with no arguments. The app's pool is pgx `stdlib.OpenDB` (`db.go:119`). Exec with zero arguments uses the simple protocol (pgx `conn.go:515-518`).
- **Rows confirmed.**
  - `CREATE [UNIQUE] INDEX`: S.
  - `ADD FOREIGN KEY`, with or without `NOT VALID`: SRE on both tables.
  - `ADD COLUMN … REFERENCES`: AE, plus SRE on the referenced table.
