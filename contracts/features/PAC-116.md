## 0. The rule this contract fixes

No process applies a pending migration while the app is serving. The backend at start, the mutating `paceday-operator encryption <sub>` subcommands (`status` is a read-only probe, §5.1), and `paceday-operator free-address|reassign|advance-all` all apply migrations only through the **migrate-when-stopped procedure** (§3). That procedure holds the maintenance lock, establishes that no backend heartbeat is live and that no other client session is connected, applies the migrations, and releases the lock. Backends that start, or that are running, respect the lock (§4). There is no override.

## 2. Terms (binding)

- **Version state** is read in this order, and every caller uses the same classification (spec D-11, D-12):
  1. **Unknown**: the row's version (clean or dirty) is not the version of any of the binary's embedded `*.up.sql`, either above the highest or in a gap. **Stop with today's golang-migrate error** (`no migration found for version N`, as `Up()` returned via `readUp`/`versionExists`), before any lock or check. Backend start: `log.Fatalf("failed to open database: run migrations: …")` as today. Operator subcommands, `status` included: exit 1 with that text. (Challenge S3.)
  2. **Dirty**: if the maintenance lock `(8400,1)` has a **migrating holder** (below), the state is **in progress**: answer **lock held**, with the holder named ("being applied by `<application_name>` (pid `<p>`)"). Otherwise stop with today's dirty error (`Dirty database version N. Fix and force version.`). A dirty row with no migrating holder may also be a pre-PAC-116 migrator still inside a file; it shows as today's dirty error (spec OQ-2 class). (Challenge S2.)
     **Read order** (confirmation pass, revision 3). Read the version, *then* the holder. A migrator writes the clean version before it unlocks, so a dirty read followed by a holder read showing none can be a migrator that finished between the two reads. Such a lock-free "dirty, no holder" is therefore never final. In §3 it goes on to the lock (step 1), and step 4's read under the lock decides. Under the lock no PAC-116 migrator can be inside a file. A reader that takes no lock (`status`, §5.1) re-reads the version and the holder once. It reports dirty only if the version is still dirty and there is still no migrating holder.
  3. **Pending**: `schema_migrations` is absent or empty, or its clean version is below the binary's highest.
  4. **Current**: clean, and equal to the binary's highest.
- **Live heartbeat**: a row of `encryption_backend_heartbeats` with `seen_at > now() - interval '90 seconds'` (`storage.LiveHeartbeats`, `HeartbeatLive`). When the table does not exist (schema below 034), there are no live heartbeats; the session check still applies.
- **Other session**: a row of `pg_stat_activity` with `datname = current_database()`, `pid <> pg_backend_pid()`, `backend_type = 'client backend'` **or `backend_type IS NULL`**, and `application_name` **not** starting with `paceday-migrate:` (§4.4, challenge S4), read on the migrator's connection. Every such row counts, whatever its `application_name`, user or state. PostgreSQL 16 shows `backend_type` (and `state`, `client_addr`, `backend_start`) as NULL for a session of another role when the reader is neither a member of that role nor of `pg_read_all_stats` (`pgstatfuncs.c`, `pg_stat_get_activity`: only `datid`, `pid`, `usesysid`, `application_name` and the xids are shown to all callers). A filter on `backend_type = 'client backend'` alone would therefore skip exactly those sessions, so a NULL `backend_type` counts (fail closed). The cost: for such a reader, autovacuum workers on this database (shown with a NULL `backend_type`) also count, so the role that migrates should be a superuser, the database owner's role with `pg_read_all_stats`, or be granted `pg_read_all_stats`. The shipped compose role (`POSTGRES_USER`) is a superuser. With full visibility, autovacuum, WAL senders and other background processes are not client backends and do not count. Sessions connected to other databases on the same server do not count. (Challenge 2026-11-14, revision 2.)
- **Serving**: at least one live heartbeat **or** at least one other session.
- **Migrator name**: the `application_name` of the migrator's connection is `paceday-migrate: <caller>`, where `<caller>` is the caller's own name:
  - `paceday-backend`;
  - `paceday-operator encryption <sub>`;
  - `paceday-operator <sub>`.

  PostgreSQL truncates names at 63 bytes, which still keeps the prefix. A maintenance-lock holder whose `application_name` starts with `paceday-migrate:` is a **migrating holder**.

## 3. The migrate-when-stopped procedure (binding)

There is one storage-level function, and the plan names it. Every caller uses it; nothing else in non-test code calls golang-migrate's `Up`/`Migrate` or `storage.runMigrations` directly. Given a DSN and the caller name:

1. Open a **dedicated** database handle limited to one connection, with `application_name` = the migrator name, and read the version state (§2) on it. **Unknown**: close and return today's error. **Dirty with no migrating holder**: go on to step 3, without deciding (§2 "Read order"); step 4 decides under the lock. **In progress**: close and return **lock held**. **Current**: close and return "nothing to do", with **no lock and no serving check** (spec D-5); the caller then continues as in §4.1 / §4.5. **Pending**: go on.
2. At this moment the calling process holds **no other open connection** to the database. Any pool it opened earlier has been closed, or has no open connection (for example `SetMaxIdleConns(0)` with nothing checked out), so its own sessions are never "other sessions" (spec AC-12). The plan decides how each caller arranges this. The handle is used for nothing but steps 1–7, and is closed before the process does anything else.
   **Direct connection.** The migrator connects to PostgreSQL directly or through a session-mode pooler, never through a transaction-mode pooler: session advisory locks (`(8400,1)` and golang-migrate's) and `pg_backend_pid()` mean nothing there. No pooler ships today; the runbook says so (§7).
3. On that connection, `SELECT pg_try_advisory_lock(8400, 1)`. If the lock is not obtained, close the handle and return **lock held**, naming the holder with `storage.MaintenanceHolder`.
4. Read the version state again (§2). Current (another migrator finished): release, close, and return "nothing to do". Unknown or dirty (no other migrator can hold the lock now, so a dirty row is not in progress by a PAC-116 migrator): release, close, and return today's error.
5. Read the live heartbeats and the other sessions (§2). If either is non-empty, release, close, and return **serving**, carrying both lists.
6. Run golang-migrate `Up` on that same connection (its own session advisory lock is taken and released by `Up`, as today). An error is returned as today: the version may be dirty, and runbook "Rollback" applies.
7. `pg_advisory_unlock(8400, 1)`, close the handle, and return "applied" with the old and new versions.

Steps 3–6 run on one connection. The procedure never writes a heartbeat, never writes `operator_audit`, and never applies down migrations.

## 4. The app's side (binding)

### 4.1 Backend start order (amends PAC-84 §5.3 step 3)

Steps 1–2 are unchanged. Step 3 becomes:

> 3. `DATABASE_URL` check. **The migrate-when-stopped procedure with caller `paceday-backend`** (§3), before the serving pool is opened. "lock held" or "serving" → `log.Fatalf("refusing to start: <§5 text>")` (exit 1, before listening). Then open the pool **without** migrating, and apply the pool caps.

Step 4 (key load) is unchanged except for its offline-operation check. After the heartbeat is written, the backend also refuses to start when the maintenance lock has a **migrating holder** (as it does for `decrypt-all` / `reset-lost-key`). It deletes its heartbeat first, then `log.Fatalf("refusing to start: migrations are being applied by <application_name> (pid <p>); start the backend after it ends")`.

### 4.2 Running backend (amends PAC-84 §4.3 "Backend presence")

A refresher tick that finds a migrating holder of the maintenance lock begins the graceful shutdown, exactly as for `decrypt-all` / `reset-lost-key`. It logs `encryption: migrations are being applied by <application_name> (pid <p>); shutting down`. Under §3 this can only happen to a backend whose heartbeat has gone stale and whose pool had no connection open at the check (spec AC-11). This is defence in depth, not a path the rule relies on.

### 4.3 Why one side always sees the other

- **Migrator**: takes the lock (step 3), *then* reads the heartbeats and the sessions (step 5).
- **Backend**: writes its heartbeat (4.1 step 4), *then* reads the lock holder.

Both are autocommitted statements, ordered on the server.

- If the backend's lock read comes before the migrator's step 3, the heartbeat was already committed before step 5, and the migrator refuses.
- Otherwise the backend sees the migrating holder and refuses.

A backend that has opened its pool but has not yet written its heartbeat is an "other session" at step 5. A backend that does nothing during the check, with no open connection and no live heartbeat, has not started (it opens a connection before anything else) or is stopped. That leaves two residual cases:

- a backend alive but silent for more than 90 s with no connection (§4.2);
- a backend **older than PAC-116**, started in the instant between step 5 and golang-migrate taking its lock in step 6 (spec OQ-2).

An older backend started at any other moment is stopped by golang-migrate's own lock and version check (spec §2.1).

### 4.4 Two migrators

Step 3 lets one migrator in at a time. The other gets **lock held**. If it retries after the first one has finished, step 1 or step 4 finds nothing pending. golang-migrate's own lock would serialise them anyway; the maintenance lock makes the second one refuse rather than queue.

**Exactly one applies (spec AC-10, AC-21; challenge S4, option (a)).** The winner's step 5 does not count sessions named `paceday-migrate: …`. Without this, the loser's step-1 or step-3 connection would make the winner refuse as "serving" while the loser refuses as "lock held", and nothing would be applied. Excluding them is safe because such a session can only belong to a process inside §3:
- its connection has read only `schema_migrations` and tried the lock;
- it touches no application table;
- it is closed before that process does anything else (step 2).

Afterwards the process either holds the lock itself (then it is the only migrator) or, before acting on the database, opens its working connection and checks for a migrating holder: the backend through its heartbeat-then-check (§4.1), the operator through §4.5. So a process excluded by name has not served and cannot start to while a migrator holds the lock.

A client that sets this `application_name` by hand is outside the threat model. The name is a cooperation protocol between Paceday processes, like `paceday-backend` in PAC-84 §4.3.

### 4.5 Operator after "nothing to do" (new; spec D-14, AC-23)

A `paceday-operator` subcommand that gets "nothing to do" from §3 opens its working connection(s), then, before any statement on application tables, reads `storage.MaintenanceHolder`. The holder is read **on a connection that the subcommand keeps open (a pinned `*sql.Conn`, or the transaction it then runs in) until it ends**. A pool may close an idle connection (idle and lifetime limits, a bad-connection retry), and the write-then-check needs the operator's presence to be continuous. Otherwise a migrator's step 5 could fall in a gap after the holder read and miss it (confirmation pass, revision 3). On a migrating holder, it refuses with the lock-held text: exit 5 for `encryption` subcommands, exit 1 for PAC-71's. It writes no audit row.
- The mutating `encryption` subcommands already take `(8400,1)` with `TryMaintenanceLock` and get exit 5; this adds nothing for them.
- `status` reports the holder (§5.1).

This is the operator's half of the write-then-check: its working session is visible to a migrator's step 5 once open, and it reads the holder after opening it.

## 5. Refusals and exit codes (binding)

The text can be reworded; every listed field must be present.

**Serving**:

```
<prefix>: pending migrations <from>..<to> were not applied: the app is serving.
  live backend heartbeat: instance <uuid> on "<host>", seen <n>s ago      (one line each)
  other database session: pid <p>, application_name "<name>", user <u>, client <addr>, started <ts>, state <state>   (one line each; hidden fields shown as "?")
Stop every backend first (a graceful stop removes its heartbeat; a killed one stops counting 90 s after it was last seen), close or terminate the sessions listed, then run again. Nothing was changed. See docs/runbook.md, "Applying migrations: stop, migrate, start".
```

**Lock held**:

```
<prefix>: pending migrations <from>..<to> were not applied: the maintenance lock is held by <application_name> (pid <p>, started <ts>); run again after it ends. Nothing was changed.
```

| Caller | `<prefix>` | Serving | Lock held |
|---|---|---|---|
| backend start | `refusing to start` | exit 1 (`log.Fatalf`), before listening | exit 1 (also: dirty in progress, §2) |
| `paceday-operator encryption <sub>` (the mutating subcommands that reach today's `encryption.go:181`; **not** `status`, §5.1) | `encryption <sub>` | **exit 6** (PAC-84's "a backend is running", widened to "the app is serving") | **exit 5** (also: dirty in progress, §2) |
| `paceday-operator free-address\|reassign\|advance-all` | `paceday-operator <sub>` | exit 1 | exit 1 |

For a migration in progress (dirty with a migrating holder), the lock-held text reads "… were not applied: being applied by `<application_name>` (pid `<p>`, started `<ts>`); run again after it ends. Nothing was changed." It never contains "Dirty database version".

No audit row is written for a refusal (as PAC-84 §8.1 already says for exits 2, 4, 5, 6). `downgrade-schema` and `booker-erasure` do not apply pending migrations and are not routed through §3.

### 5.1 `encryption status` is a read-only probe (factory decision 2026-11-14; spec D-10, AC-22)

`status` **never applies migrations, never takes `(8400,1)`, and never refuses as "serving"**. It reads the version state (§2) on its normal connection and acts on it:

- **Unknown**: exit 1 with today's text.
- **Dirty with no migrating holder**, after §2's one re-read: exit 1 with today's dirty text (as when its `Migrate` call failed).
- **In progress**: it prints `encryption status: migrations are being applied by <application_name> (pid <p>); run again after it ends` and exits **5**. The schema is changing under it, so it prints no partial report.
- **Pending**: it prints `encryption status: schema at version <X>; this release's migrations up to <Y> are pending, not applied`. It then prints the serving state: live heartbeats (as today's status already lists them), and the number of other sessions with one line each, using §2's definition minus its own connections. It then prints its usual report for whatever the current schema holds. It exits as today: 0; 3 under `--check` with plain values; 1 if a read fails, for example a column that a pending migration adds.
- **Current**: today's output and exit codes, unchanged.

The below-034 rule (`encryption.go:148-165`) is unchanged and checked first, as today.

## 6. No override (binding)

No flag, environment variable, prompt or configuration skips §3 step 5 or applies migrations by another path. Unknown flags stay usage errors (exit 2). A test seam for the backend suite's own tests is allowed (spec OQ-3, AC-8, AC-9) only in the existing pattern of `backend/storage/test_seams.go`: an unexported variable installed through an exported `Install…(tb TB, …)` function that takes a `testing.TB`, so tests in other packages (`main`, `cmd/paceday-operator`) can reach it. Nothing reachable from `main`, a flag or the environment may call it.

## 7. Runbook text (binding content; wording free)

`docs/runbook.md` gets **"Applying migrations: stop, migrate, start"**, with these points:

1. A release with a migration is applied with **no backend serving**. From PAC-116's implementation on, the backend and `paceday-operator` refuse to apply pending migrations otherwise (they print what they saw).
2. **One backend** (the shipped compose file): "Deploy order" step 4 already does this. `compose up -d backend` stops the old container (graceful drain) before the new one starts and migrates.
3. **Several backends**:
   - stop every backend on every host (`compose stop backend`);
   - start one new backend (it migrates) and wait for `/api/ready`;
   - start the others.

   A new backend started while an old one still serves refuses to start, and Docker restarts it (`restart: unless-stopped`) until the old ones are stopped.
4. **Operator binary newer than the schema**: either start the new backend first (it migrates), then use `compose exec backend /paceday-operator …` as today; or stop every backend and use `compose run --rm --no-deps backend /paceday-operator …`.
5. **Reading a refusal**:
   - a heartbeat line: stop that backend, or wait 90 s if it was killed;
   - a session line: identify it (`SELECT pid, application_name, usename, client_addr, backend_start, state FROM pg_stat_activity WHERE datname = current_database() AND backend_type = 'client backend';`), close it, or as a last resort `SELECT pg_terminate_backend(<pid>);`.

   Monitoring agents connected to the application database must be stopped for the migration (spec OQ-4).
6. **A connection pooler** (none ships; for deployments that add one):
   - its idle server connections stay open after every backend stops, until `server_idle_timeout` (pgbouncer default 600 s), and each one counts as an other session, so the migration is refused until the pooler is stopped or reconnected (`RECONNECT` / `PAUSE` in pgbouncer);
   - migrators (the backend at start, `paceday-operator`) must connect to PostgreSQL directly or through session pooling, never through transaction pooling (session advisory locks).
7. **A lock holder on a dead host.** A session advisory lock is released as soon as its session ends. If the migrating host or its network died, though, the server-side session lingers until TCP keepalive notices: about 2 hours at Linux defaults unless `tcp_keepalives_idle` is set. Meanwhile, starts refuse with "being applied by `<name>` (pid `<p>`)".
   - Find the holder with `SELECT a.pid, a.application_name, a.client_addr, a.backend_start, a.state FROM pg_locks l JOIN pg_stat_activity a ON a.pid = l.pid WHERE l.locktype = 'advisory' AND l.classid = 8400 AND l.objid = 1 AND l.granted;`.
   - Once certain that the process is gone, run `SELECT pg_terminate_backend(<pid>);`.
   - If it died inside a migration file, the file's transaction rolls back and the version stays dirty: follow "Rollback".
8. **The Postgres health check.** `pg_isready -U clockwise -d clockwise` (`docker-compose.prod.yml`) opens a short connection to the application database every few seconds. A backend start whose check falls in that instant is refused as "serving" and retried by Docker a moment later. This is harmless, and a single `refusing to start` line followed by a normal start is expected.
9. There is no override.

This PR adds the section now. Points 2–8 are correct today as procedure. The refusal sentence in point 1 is marked "from PAC-116's implementation on".

## 11. Alternatives rejected

1. **Revision 1: a parser that proves each migration safe against live traffic.** Rejected after the challenge (four blocking counterexamples, one of them the real migration 022). Row locks, FK actions and indirection make a sound static model as large as PostgreSQL's lock manager.
2. **Heartbeats alone.** They miss a backend between opening its pool and its first heartbeat, and every backend older than PAC-84. They are also blind to running operator commands.
3. **`pg_stat_activity` alone, or only sessions named `paceday-backend`.** It misses an idle backend whose pool has no open connection at that instant (heartbeats cover it). Filtering by name would also let unnamed pre-PAC-84 backends, `psql` sessions and operator commands through. All other sessions count; that is the fail-closed choice.
4. **A session advisory lock held by each backend for its whole life (shared), which the migrator tries exclusively.** It pins one connection per backend outside the PAC-81 pool caps, the lock disappears silently if that connection drops, and pre-PAC-116 backends never take it. The heartbeat lease already exists and has a known expiry.
5. **A new lock id for migrations** (for example `(8400,3)`). It would still need a holder lookup, and it would not serialise migrations against `convert` / `rotate-data-key` / the automatic conversion, which `(8400,1)` does for free.
6. **An override flag** (`--apply-while-serving <db name>`, audited). Every refusal is cleared by an action the message names, and the flag's only use is the defect (spec D-4, OQ-1).
7. **The operator stopping the backends itself.** The operator has no access to the container runtime and must not have it. A refusal with instructions keeps the operator in control.
8. **Never migrating from the operator** (requiring the backend to migrate first). The operator's `compose run` path on a stopped stack is how `decrypt-all` / `reset-lost-key` work, and on a stopped stack migrating is safe. Refusing only while serving keeps that path.

## Challenge — 2026-11-14 (revision 2)

**Verdict**: accept-with-changes (REVISE). The "stop traffic" design is sound: write-then-check on both sides closes the race for every backend from PAC-116 on, and both heartbeat ages use the database's `now()`. Three blocking defects remain, all in the edges of §2 and §3, and S1 was fixed directly. Small fixes are in `3b92890`.

### Blocking

**S2. Step 1 reads the version without any lock, so it sees the *transient* dirty row of a migration in progress.** golang-migrate marks the target version dirty *before* the file runs and clean after it (`migrate.go:738-750`). Today every path calls `Up()`, which takes golang-migrate's lock **before** reading the version (`migrate.go:265-277`). It therefore waits out a running migration and never sees that row. The new step 1 and §2 ("a dirty row is not pending: golang-migrate's error stops the path as today") change this.

Example. While migrator A applies 040, a second backend or `paceday-operator encryption status` runs step 1. It reads `040, dirty` and stops with "Dirty database version 40. Fix and force version." That is not "as today". It is also dangerous: runbook "Rollback" tells the operator to fix and `force` a dirty version, while A is still applying it.

**Resolve:** in §2/§3, a dirty row seen while the maintenance lock has a migrating holder (or golang-migrate's lock is held) is "lock held", with the §5 text naming the holder. Only a dirty row with no holder is today's dirty error. Add an AC: hold a migrator inside a file through a seam, then start a backend and run `status`; both say "being applied by …", and neither says "dirty".

**S3. "Nothing pending, so callers behave exactly as today" drops today's refusal of a schema *newer* than the binary.** §2 defines pending as "version below the highest embedded version". A database at 041 with a binary whose highest is 040 is therefore "nothing to do", and §4.1 then opens the pool "without migrating".

Today, `Up()` fails with "no migration found for version 41" (`readUp` → `versionExists`, `migrate.go:536-537`), so an older binary refuses to start on a newer schema. The spec's §2.1 even relies on this for old backends. After PAC-116, a PAC-116+ binary rolled back without its down migrations would serve against the newer schema silently.

**Resolve:** §2 and §3 step 1 must state that a version absent from the binary's files (above its highest, or a gap) stops every path with today's error, before any check. Add an AC: a schema one version above the binary's highest, then backend start and operator both refuse as today.

**S4. **Verdict**: accept-with-changes (REVISE). B1–B4 below are blocking. ### Rule defects (blocking)

**B1. R1's "no cycle on T" proof ignores row locks. A level-1 first lock followed by row-locking DML deadlocks.** §2's argument holds for table locks only. When the first lock on T is SHARE or SHARE ROW EXCLUSIVE, live transactions can still hold ROW SHARE on T, and with it **row locks** (`FOR UPDATE`, `FOR NO KEY UPDATE`, FK checks). A later migration statement that waits on one of those row locks closes a cycle once that live transaction asks for ROW EXCLUSIVE on T.

```sql
-- 040_user_flags.up.sql: passes R1 (users: SRE level 1, then RS level 0)
CREATE TABLE user_flags (user_id UUID NOT NULL REFERENCES users(id), flag TEXT NOT NULL);
INSERT INTO user_flags (user_id, flag) SELECT id, 'x' FROM users;
```

Live sign-in: `storage/signin.go:222` calls `lockAccountExclusive`, which runs `SELECT id FROM users WHERE id=$1 FOR UPDATE` (`session.go:97`), then `UPDATE users …` (`signin.go:263`).

1. The sign-in transaction S takes row U `FOR UPDATE` (ROW SHARE on users).
2. The migration M gets SRE on users, which is compatible with ROW SHARE.
3. M's RI check runs `SELECT 1 FROM users … FOR KEY SHARE` on U. It waits on S.
4. S's `UPDATE users` needs ROW EXCLUSIVE, which conflicts with SRE. S waits on M. The result is `40P01`.

This is exactly the shape of the real **migration 022** (`CREATE TABLE … REFERENCES users`, then `INSERT … SELECT … JOIN users`), which the spec's §2.4 lists as "ok". There is a second instance: `CREATE INDEX … ON users (…); UPDATE users SET …;` against `SetUserOrg` (`orgs.go:55` `FOR NO KEY UPDATE`, then `:62` `UPDATE users`). The operator's `advance_all` has the same shape (`operator.go:286`, then `:289`).

Level 0 first is safe, because it blocks no live table request. Level 2 or 3 first is safe, because no live row-lock holder can be present. **Resolve:** add to R1: "when the first lock on T is level 1, no later statement may take or wait for row locks on T". That covers:
- `UPDATE`, `DELETE` and `MERGE` on T;
- `SELECT … FOR …` on T;
- `INSERT … ON CONFLICT DO UPDATE` into T;
- `INSERT`, `UPDATE` and `MERGE` on a table with an FK to T (the RI check);
- RI actions into T (B3).

The remedy stays plain SQL: a leading `LOCK TABLE T IN EXCLUSIVE MODE` (or `ACCESS EXCLUSIVE`), or the DML placed before the SHARE-level statement.

022 then fails AC-17, so the author or owner must pick one of two options:
- (a) Edit 022 to add a leading `LOCK TABLE users IN EXCLUSIVE MODE;`. golang-migrate does not checksum applied files, so only fresh installs change. This needs D-7 and `forbiddenPaths` amended.
- (b) The test pins the exact historic violation set for files ≤ 039. It fails if that set changes, and it is not usable by 040+.

Add ACs for both counterexamples and for the `LOCK … IN EXCLUSIVE MODE` remedy.

**B2. "Overstating is conservative" (§4, last paragraph) is false for the first lock.** Overstating a statement's level is safe only when the statement is not the first lock. If the first lock is overstated, a real upgrade after it is hidden. These rows do that:

| Migration | Contract says | PostgreSQL 16 does | Deadlock |
|---|---|---|---|
| `REINDEX TABLE bookings; ALTER TABLE bookings ADD COLUMN z INT;` | AE first: pass | SHARE on bookings and **AE on each index** | The save's step 6–8 read holds AS on bookings and, while it plans, asks AS on `idx_bookings_link`. That waits on M. M's AE on bookings waits on the save's AS. |
| `TRUNCATE booking_events; CREATE INDEX ON bookings (x); ALTER TABLE bookings ADD COLUMN y INT;` | AE on bookings (referenced by `booking_events`, 009:40) first: pass | no lock on bookings | The real order is SHARE, then AE. That is the AC-1 cycle. |
| `ALTER TABLE archive.bookings ADD COLUMN y INT; CREATE INDEX ON bookings (x); ALTER TABLE bookings ADD COLUMN z INT;` | last-part match, AE first: pass | `archive.bookings` is another table | The AC-1 cycle on `public.bookings`. `CREATE TEMP TABLE bookings` (which makes `public.bookings` "exempt") and `SET search_path` are the same hole. |

`ALTER INDEX` belongs to the REINDEX class: it locks the index, not the table at AE. **Resolve:**
- Make the asymmetry binding: a row may overstate a level only where the statement cannot be the first lock at that level.
- `REINDEX` and `ALTER INDEX` are unclassifiable for the index's covered table unless level 3 is held.
- `TRUNCATE t` takes AE on t only (plus the referencing tables under `CASCADE`), and no lock on the tables t references.
- A qualified name matches only when its schema is `public`.
- `CREATE TEMP TABLE` with a covered name, and any `SET`/`RESET`/`set_config` of `search_path`, are refused (R2-style).

Add ACs for each.

**B3. RI actions on *referencing* tables are missing.** The DML row gives only the FK-check ROW SHARE on the tables t references. A `DELETE` (or a key `UPDATE`) on t also fires RI actions on every table that references t:
- `CASCADE` and `SET NULL` take ROW EXCLUSIVE and row locks;
- `NO ACTION` and `RESTRICT` take ROW SHARE and `FOR KEY SHARE`.

Today's covered chains are:
- organizations → users (`users.org_id … ON DELETE SET NULL`, 007:8);
- users → scheduling_links and scheduling_link_hosts;
- scheduling_links → scheduling_link_hosts and bookings (009, CASCADE).

```sql
DELETE FROM organizations WHERE domain = 'old.example'; -- hidden: RE + row locks on users
ALTER TABLE users ADD COLUMN z INT;                      -- table: first lock on users = AE, pass
```

A sign-in on an affected user arrives after M's update. It holds ROW SHARE on users and waits on M's row lock. M's AE waits on that ROW SHARE, and the result is `40P01`. **Resolve:** in the DML row, `DELETE`, `UPDATE` and `MERGE` on t take ROW EXCLUSIVE, *with row locks* (for B1), on every covered table that references t. This applies transitively over the replay's FKs, whatever the action. `TRUNCATE … CASCADE` takes AE on the same tables. Add an AC with the organizations example.

**B4. Fail-closed has holes through indirection (D-5, R3).** Classification reads only the names in the statement text. PostgreSQL runs code that the text does not name:
- `CREATE FUNCTION touch() RETURNS void LANGUAGE sql AS $$ UPDATE bookings SET notes = notes $$; SELECT touch(); ALTER TABLE bookings ADD COLUMN z INT;` passes. `CREATE FUNCTION` takes no lock, and `SELECT touch()` names no covered table. In reality the file takes RE and row locks, then AE.
- A view over a covered table (`UPDATE v …` on an auto-updatable view, or `LOCK TABLE v IN SHARE MODE`, which recurses into the view's tables).
- A trigger or rule on a non-covered table whose body writes a covered table.

No up file has `CREATE FUNCTION`, `VIEW`, `TRIGGER` or `RULE` today, so this is about the future. **Resolve:** the replay records views, routines, triggers and rules with the covered names that their definitions mention. A statement that reads, writes or locks such a view, calls such a routine, or writes a table carrying such a trigger or rule is unclassifiable for those tables, unless level 3 is held. Add ACs.
