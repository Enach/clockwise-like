## 0. The rule this contract fixes

Paceday holds addresses of people who are not the account owning the row.
When such a person asks to be erased, one operator command finds every stored
copy of the address in other people's data **inside the database** (no value of
a row that does not match ever reaches the command's process), erases each copy
(delete, or anonymise a booking), keeps an account's own data and the earlier
operator records, writes one address-free audit record, and prints counts. It
takes its locks in one fixed order that no live path reverses, so it can wait
for a live request or make one wait, but never deadlocks with one.

### 1.1 The erased live booking (spec §3.4, AC-6)

```json
{ "id": "…", "link_id": "…", "booker_name": null, "booker_email": null,
  "booker_erased_at": "2026-11-20T09:14:03Z", "start_time": "…", "end_time": "…",
  "status": "confirmed", "notes": "", "created_at": "…" }
```

- Erased **iff** `booker_erased_at` is present; then both `booker_name` and
  `booker_email` are `null` (never `""`, which the database keeps, PAC-40's
  rule) and `notes` is `""`.
- Not erased: exactly today's object. `booker_erased_at` is **absent** (not
  `null`), so an answer with no erased booking is JSON-equal to what the server
  sends today (same keys and values; the generated record may order the keys
  differently from today's `storage.Booking` encoding, which no JSON parser
  observes; revision 2, note 5). This is what lets the backend half merge first (§5).
- Every other field is unchanged by the erasure: `start_time`, `end_time`,
  `status`, `link_id`, `created_at`, and the link's `uses_count` and busy time
  (the booking row stays, AC-4).
- The handler (`api/handlers_scheduling_links.go:968` `listBookings`, today
  encoding `storage.Booking` as is) answers through the generated
  `gen.SchedulingLinkBookingRecord`, mapping `booker_erased_at` the way
  `archivedBookingDTO` does (`:1257-1271`); `storage.GetBookingsByLink` reads
  `booker_erased_at`. Instants UTC with a `Z` suffix, as the archive.

## 2. The command (binding; spec §3.1, §3.6, §3.7, OQ-5)

```
paceday-operator erase-address -operator <name> -reason <text>
                               [-dry-run] [-account-held-acknowledged] [-max-duration 5s]
    < one line: the address
```

### 2.1 Input, in this order, before any database connection (AC-10)

1. **Flags.** The flag set's own output is discarded (`flag` echoes an unknown
   flag, which could be the address, e.g. `-pat@x.example`); any parse error
   is the fixed usage text. `-operator` and `-reason` must be non-blank after
   `strings.TrimSpace` (PAC-71 `OperatorRun.validate`). `-max-duration` is a Go
   duration in **[1s, 8s]** (default 5s; §7). **Any positional argument** is
   refused ("arguments are not accepted; give the address on standard input"),
   whatever it holds. `DATABASE_URL` must be set.
2. **Standard input.** Read at most 4097 bytes; more than 4096 is refused. The
   bytes must be valid UTF-8 without U+0000. The address is everything before
   the first LF (U+000A); whatever follows must be empty after trimming the
   PAC-129 set (§3.1), else "more than one line on standard input". The
   address is trimmed of the PAC-129 set (`storage.TrimAddressSpace`); empty is
   "no address on standard input".
3. **Validity.** The one address normaliser's rule (spec §2.3,
   `api/handlers_manager.go:870-880` `normalizeManagerEmail`): with
   `l = strings.ToLower(t)`, `net/mail.ParseAddress(l)` must succeed and its
   `Address` must equal `l`. Not a valid address (two `@`, `not-an-address`, a
   display name) is "not a valid address". The rule moves to `storage` (one
   function both the normaliser and the command call), so the two cannot
   drift.
4. **The address in the operator name or the reason** (spec §3.6): refused
   when, for either field `f`, `strings.Contains(strings.ToLower(f), l)` or
   `strings.Contains(fold(f), fold(t))`, where `fold` maps each rune to the
   smallest rune of its `unicode.SimpleFold` orbit. No database lowercasing is
   available before connecting; the Go lowercasing is the rule's Go half and
   Unicode simple folding covers what a libc `lower()` equates on top of it
   (over-refusal only costs the operator a rewording).
5. Every refusal above: exit **2**, one fixed line on standard error
   (`erase-address: <reason>; usage: paceday-operator erase-address -operator
   <name> -reason <text> [-dry-run] [-account-held-acknowledged]
   [-max-duration 5s] < address`), no database connection, no input echoed.

The command's values are then: `t` (trimmed input, letter case kept), `g =
strings.ToLower(t)`; `d` is read from the database (§3.2).

### 2.2 Schema, migrations and the maintenance lock (spec §3.5 last bullet, AC-14)

- **Erasure**: as PAC-71's subcommands (`cmd/paceday-operator/main.go:56-103`):
  `storage.MigrateWhenStopped` with caller `paceday-operator erase-address`; a
  refusal (the app is serving and a migration is pending) or an error is exit 1.
- **Dry run**: never migrates. It opens the database without migrating (as
  `booker-erasure status`).
- Both: `holdPresence` (a migrator holding the maintenance lock is exit 1),
  then `storage.SchemaVersion`: not present, dirty, or below the version of
  `*_erase_address.up.sql` (045) is exit 1 "the database schema is at N, below
  045 (PAC-134); nothing changed and no migration applied" (dry run) or "…"
  after a refused migration.
- `application_name` = `paceday-operator erase-address` (PAC-84 4.3).

### 2.2a The connection always uses the extended protocol (revision 2, B-1)

`storage/db.go:61-67` parses `DATABASE_URL` with `pgx.ParseConfig`, which
honours `default_query_exec_mode=simple_protocol` in the DSN (common behind
pgbouncer). In that mode pgx interpolates every bind into the statement text
client-side, so the address would reach the server's statement text: the log
line of any failed statement (`log_min_error_statement = error`, the default;
the tool's expected exit-1 errors `lock_timeout` and `statement_timeout` are
such failures) and `pg_stat_activity.query`. Observed on 16.15 through
`database/sql` with the pgx stdlib driver v5.10.0: with the DSN's default mode
the server logged `STATEMENT:  SELECT 1/0 WHERE lower($1) <> ''`; with
`default_query_exec_mode=simple_protocol` it logged `lower(
'probe-addr@x.example' )`; with that same DSN and the parsed config's
`DefaultQueryExecMode` overridden to `pgx.QueryExecModeDescribeExec` it logged
`lower($1)` again.

Binding: the command opens its pool through a storage function that parses the
DSN and then sets `cfg.DefaultQueryExecMode = pgx.QueryExecModeDescribeExec`
**whatever the DSN says** (extended protocol, unnamed statement, server-side
binds; it needs no named prepared statement, so it also works behind
pgbouncer's transaction pooling). The override applies to every connection the
command opens, the dry run's included. No other exec mode may be configured for
this command. AC-15 gains a case (§14). The §2.3 preflight cannot detect the
client-side mode, which is why the override, not a check, is the rule.

### 2.3 Statement-logging preflight

The address reaches PostgreSQL only as bind parameters (§3), and PostgreSQL's
defaults never log bind values (`log_statement = none`,
`log_min_duration_statement = -1`, `log_parameter_max_length_on_error = 0`;
production sets none of them, `docker-compose.prod.yml:31-50`). A deployment
that turned statement logging on would write the address to the server log
with the parameters of every logged statement. The first statement of the
transaction therefore also reads `log_statement`, `log_min_duration_statement`,
`log_min_duration_sample`, `log_transaction_sample_rate`,
`log_parameter_max_length` and `log_parameter_max_length_on_error`, and the run
stops with exit 1 ("statement logging could record the address; see the
runbook") when `log_parameter_max_length_on_error <> 0`, or when
`log_parameter_max_length <> 0` and any of `log_statement ∈ {mod, all}`,
`log_min_duration_statement >= 0`, `log_min_duration_sample >= 0`,
`log_transaction_sample_rate > 0` holds, or (revision 2, note 3) when
`current_setting('auto_explain.log_min_duration', true)` is not `NULL` and is
`>= 0` (a loaded `auto_explain` logs plans, and a custom plan shows a bind as a
constant). Nothing has been read from a table at that point.

| 3 | a matching account and no `-account-held-acknowledged`: erasure refused after the account check; dry run completed | none (erasure); none but the record (dry run) | erasure: none; dry run: one (`erase_address_dry_run`) |

Account ids in ascending order. On exit 3 for an erasure only the `accounts=`

command: the address in any form, a name, a title, a note, a slug, a token, a
digest of the address, or the id of a row it erased or would erase. Only
counts, account ids, the audit record's id and fixed words.

### 2.6 Errors (spec §3.7, AC-15)

Standard error gets `erase-address: failed: <class>; no data changed`, where
`<class>` is one of: `database unreachable`, `schema too old (at <n>, needs
45)`, `schema dirty`, `migration refused` (followed by PAC-116's fixed refusal
text, which holds no row data), `maintenance lock held by a migrator`,
`statement logging could record the address`, `duration bound exceeded
(<d>)`, `lock wait timeout`, `deadlock`, `sqlstate <5 chars>`, `connection
closed`, `unclassified`. The class comes from `engine.ErasureErrorClass`
(SQLSTATE only, shape-checked, `engine/booker_erasure.go:100-140`) plus the
duration and connection cases; **never** the driver's message, which can
repeat row data. The command does not use `runPAC71`'s `fmt.Fprintln(errw,
err)` (`main.go:93-95`) for anything after §2.1.

## 3. Matching and the statements (binding in substance; spec §3.3, §3.4)

### 3.1 Binds and the match expression

| Bind | Value | Source |
|---|---|---|
| `:t` | the trimmed input, letter case kept | Go (§2.1) |
| `:g` | `strings.ToLower(:t)` | Go |
| `:d` | `lower(:t)` under the database's default collation | the database (`input_lower`) |
| `:acc` | the matching account ids, `uuid[]` (empty when none) | the database (`accounts`) |

The address never appears in any statement's text. Implementations number the
binds positionally per statement (a statement binds exactly the ones it uses:
PostgreSQL refuses an unreferenced, untyped parameter with 42P18 "could not
determine data type of parameter", and pgx refuses an argument count that
differs from the placeholders; both observed through `database/sql` with the
pgx stdlib driver in revision 2).

For a stored text value `c`:

```
M(c) :=  ( char_length(paceday_trim_ecma(c)) = char_length(:g)
           AND paceday_go_lower(paceday_trim_ecma(c)) = :g )
      OR lower(paceday_trim_ecma(c)) = :d
```

- Left: the Go half of the rule ("their Go lowercasings are equal"), through
  `paceday_go_lower` (§4), the twin of Go's `strings.ToLower` pinned by AC-21.
  The `char_length` test is a sound pre-filter: Go's lowercasing maps each code
  point to exactly one code point (checked over every scalar value, §4.3), so
  equal Go lowercasings imply equal lengths; it skips the expensive branch of
  `paceday_go_lower` on most rows (§7).
- Right: the database half, `lower()` under the database's own collation, on
  both sides (`:d` is the database's `lower()` of `:t`).
- Both sides are trimmed of the PAC-129 set: the input in Go
  (`TrimAddressSpace`), stored values with `paceday_trim_ecma` (migration 041),
  the same 26 code points, pinned by `pac129_test.go`.
- Locale: correct under `C` as under `en_US.utf8`; executed on both (§4.3).
  Under `C`, `lower()` folds ASCII only and the left half carries the rest
  (AC-20).
- Never wider than the code's own equalities (spec §3.3): the left half equates
  what the added-person key (T1) equates, the right half what the co-host
  unique index (T7) equates.

For a stored outcomes document `k` (T8):

```
J(k) := EXISTS (SELECT 1 FROM jsonb_array_elements(
            CASE jsonb_typeof(k->'addresses') WHEN 'array' THEN k->'addresses' ELSE '[]'::jsonb END
         || CASE jsonb_typeof(k->'removed')   WHEN 'array' THEN k->'removed'   ELSE '[]'::jsonb END) AS e(v)
        WHERE jsonb_typeof(e.v->'email') = 'string' AND M(e.v->>'email'))
```

(`addresses[].email` and `removed[].email`, `storage/scheduling_links.go:1497-1521`;
any other shape is ignored, never an error.)

### 3.3 The transaction

One `READ COMMITTED` transaction on one connection, begun with the duration
context (§7). Two phases:

- **Discovery** (dry run and erasure): sequential scans that **take no row
  lock**, and record the keys of matching rows in a temporary table that never
  leaves the database (`pac134_found`, dropped at commit or rollback). This is
  where the time goes (§7).
- **Erasure** (erasure only): in the fixed order of §6.1, lock the parents and
  the found rows, re-check each row's match and ownership under its lock
  (READ COMMITTED re-evaluates the `WHERE` of a locked row that changed), and
  write. This phase holds locks for milliseconds at the measured scale.

A row committed before the run starts is found by discovery and erased. A row
committed after the discovery statement of its place is not guaranteed to be
erased (a new copy; a rerun finds it), which is spec §3.5's "committed after
the run's statement on that place". It **may** be erased (revision 2, note 2):
an assignment inserted under a found roster entry before `lock_roster`, or a T1
row deleted and re-added with the same `(team_id, email)` before `erase_t1`, is
reached through its key. So an erasure's erased counts can differ from a dry
run taken a moment before (they are equal on a quiescent database, AC-7).
`kept_account_own` counts are as of discovery (note 7): a row whose ownership
changes before its lock is decided by the re-check (a found row that became the
account's own is skipped, not erased), but the kept count is not recomputed.

Statements, in order. `-- erasure only` marks the second phase. Every
statement returns only counts, except `input_lower` (the input's own
lowercasing) and `accounts` (the matching account ids).

```sql
-- [settings]  (first statement; binds: the bound as '<n>ms')
SELECT set_config('statement_timeout', :bound, true), set_config('lock_timeout', :bound, true),
       set_config('idle_in_transaction_session_timeout', '1000ms', true),
       current_setting('log_statement'), current_setting('log_min_duration_statement'),
       current_setting('log_min_duration_sample'), current_setting('log_transaction_sample_rate'),
       current_setting('log_parameter_max_length'), current_setting('log_parameter_max_length_on_error'),
       current_setting('auto_explain.log_min_duration', true);

-- [input_lower]
SELECT lower(:t);

-- [accounts]
SELECT u.id FROM users u WHERE M(u.email) ORDER BY u.id;
--   erasure with accounts and without -account-held-acknowledged: ROLLBACK, exit 3 (nothing else runs)

-- [found_table]

    link_id uuid, owner_id uuid, row_key text) ON COMMIT DROP;

FROM team_added_members a WHERE M(a.email);

-- [find_t2]

SELECT 't2', i.invited_by = ANY(:acc), i.id, i.team_id
FROM team_invites i WHERE M(i.invitee_email);

-- [find_t3]
INSERT INTO pac134_found (place, own, row_id)
SELECT 't3', r.manager_user_id = ANY(:acc), r.id

-- [find_t5]
INSERT INTO pac134_found (place, own, row_id)

-- [find_t6]
INSERT INTO pac134_found (place, own, row_id)

FROM team_analytics_cache c WHERE M(c.member_email);

-- [find_t7]

SELECT 't7', l.owner_user_id = ANY(:acc), h.id, h.link_id
FROM scheduling_link_hosts h JOIN scheduling_links l ON l.id = h.link_id
WHERE h.invitee_email IS NOT NULL AND M(h.invitee_email);
```

Notes that bind the implementation:

- **Lock order inside a statement.** Each `… ORDER BY … FOR UPDATE` puts
  `LockRows` above `Sort`, so rows are locked in the stated order (observed with
  `EXPLAIN` on 16.15, §12). Data-modifying CTEs of one statement run in an
  unspecified order, so each place is its own statement, in the order above.
- **Erased counts** are the `RETURNING` counts; `kept_account_own` comes from
  `counts`; T4's erased count is `erase_t4`'s.
- **`erase_t3`** cascades nothing: `erase_t4` already deleted the assignments of
  the locked entries, and no new one can reference a locked entry (its FK check
  takes `KEY SHARE` on it).
- The `UPDATE` of T9 leaves `bookings_booker_erased_blank` satisfied; T8's
  leaves `scheduling_link_create_keys_outcomes_need_digest` satisfied. No
  statement can fail a CHECK or FK with the address in the message.
- Two concurrent runs: the second's `lock_*` statements wait for the first's
  commit, after which the re-checks drop the rows the first erased; erased
  counts add up (AC-12), both kept counts are reported (spec §3.5).
- A dry run runs `settings` to `counts`, then `audit`, and commits: no row lock,

### 4.1 Up

1. `paceday_go_lower(t text) RETURNS text`, `LANGUAGE sql IMMUTABLE PARALLEL
   SAFE`, **not** `STRICT` (so the planner inlines it: a `CASE` is not provably
   strict; `NULL` in, `NULL` out):

   ```sql
   SELECT CASE WHEN octet_length(t) = char_length(t)
               THEN lower(t COLLATE "C")
               ELSE translate(t, <1798 code points>, <their Go lowercases>)
          END
   ```

   - Pure ASCII text (UTF8: bytes = characters): `lower()` under the `C`
     collation, which PostgreSQL defines as A–Z → a–z only, whatever the
     database's locale; Go does exactly that on ASCII.
   - Any other text: one `translate()` over every code point U+0001..U+024F
     with its Go lowercase (identity entries included, so a character of a
     common address is found near the start of the list) followed by every
     higher code point that Go's `strings.ToLower` changes (Unicode 15.0.0 in
     go1.26.0: 1433 changed code points; 1798 entries). Go lowercases with the
     simple mapping, one code point to one code point (verified for every
     scalar value: no length change), so a per-character `translate` is exact.
   - Built inside a `DO` block from two `integer[]` lists with `chr()` and
     `string_agg(... ORDER BY ordinality)`, then `EXECUTE format(... %L, %L)`:
     the migration file holds no non-ASCII byte (PAC-129's `paceday_trim_ecma`
     convention). The block refuses a non-UTF8 database and list lengths other
     than 1798.
   - Locale-free and setting-free, hence `IMMUTABLE`: `lower(… COLLATE "C")`,
     `translate`, `octet_length`, `char_length`. The database collation's
     `lower()` is not used here: it differs by locale (§4.3).
   - **No index, CHECK or generated column may use it.** A Go upgrade that
     changes Go's tables turns AC-21 red; the fix is a new migration that
     replaces the function, which would silently corrupt anything stored from
     it.
2. `operator_audit_action_check` is dropped and re-added with the ten actions:
   PAC-84's eight plus `erase_address` and `erase_address_dry_run` (PAC-84

## 6. Locks (binding; spec §3.5, PAC-101 §4.1–§4.2, PAC-129 D-8)

### 6.1 The tool's order

Discovery takes no row lock. The erasure phase acquires, in this order, and
holds everything until commit:

1. `teams` rows of found T1/T2 rows and of found T3 entries' assignments,
   `FOR NO KEY UPDATE` (PAC-129 D-8's mode), by `id`;
2. T1 rows `FOR UPDATE`, by `(team_id, email COLLATE "C")`;
3. T2 rows `FOR UPDATE`, by `id`;
4. T3 rows `FOR UPDATE`, by `(manager_user_id, member_email COLLATE "C")`;
5. T4 rows `FOR UPDATE`, by `(manager_user_id, team_id, member_email COLLATE "C")`; then T3 deleted (held);
6. T5 rows, then T6 rows, `FOR UPDATE`, by `id`;
7. `scheduling_links` rows of found T7/T9 rows, **`FOR SHARE`** (PAC-101's
   booking-save mode), by `id`;
8. T7 rows `FOR UPDATE`, by `id`;
9. T9 rows `FOR NO KEY UPDATE`, by `id`;
10. T8 rows `FOR UPDATE`, by `(owner_user_id, idempotency_key COLLATE "C")`;
11. the `operator_audit` insert (a new row; no FK).

It never locks a `users` row (the account check is a plain read) and takes no
advisory lock. Table-level locks are `ROW SHARE`/`ROW EXCLUSIVE`, which no live
path conflicts with.

- **PAC-101 §4.1**: a link before its host and booking rows. `FOR SHARE` is the
  weakest mode that orders the tool against the invite and PATCH (`NO KEY
  UPDATE`), the delete (`NO KEY UPDATE`) and PAC-40's erasure (`FOR UPDATE`),
  and it does not block booking saves or accept/decline/leave (`FOR SHARE`),
  which is what AC-13 describes (a booking by X commits while the run is
  open). The tool never upgrades a link lock (PAC-101's PATCH note).
- **PAC-101 §4.2**: the tool's own waits are bounded by `lock_timeout` = the
  bound, and its whole transaction by the bound (5 s default, at most 8 s,
  §7), below the live 10 s per-wait cap, so a live request waiting on a row the
  tool holds gets it before its own cap. At the measured scale the erasure
  phase holds its locks for about 20 ms.
- **PAC-129 D-8**: a team row before that team's membership, added-person and
  invitation rows.

manager's entries cannot both match one address today; the order keeps the
no-cycle argument independent of that fact. Behaviour is unchanged **except**
that a confirm racing an erasure (or a Manager delete) of the same entry now
answers `skipped` instead of a 23503 500.

### 6.3 The lock-order table (one row per live writer of T1–T9)

Built from **every** `INSERT`, `UPDATE` and `DELETE` on the T1–T9 tables in
non-test Go code (a multi-line search of `backend/**/*.go`, 52 statements on
these tables and their parents, listed per writer below) and from every
cascade into them (`teams` → T1, T2, T4; `manager_team_members` → T4;
`users` → T1 SET NULL, T2–T8; `scheduling_links` → T7–T9). No product path
deletes a `users` or `scheduling_links` row (links are soft-deleted; PAC-101
§4.1, PAC-40), so those cascades have no live writer. "Tool rows" = rows of the
tool's set (§6.1) the writer locks.

Why a row cannot close a cycle, one of:

- **(S) serialized**: the writer takes the same parent (team or link) first, in
  a mode that conflicts with the tool's; whichever is second waits holding
  nothing the other wants (the tool holds only lower-ordered parents and their
  rows; no live writer takes two teams, two links, or a team and a link).
- **(1) one row**: the writer locks at most one tool row per transaction. To be
  in a cycle it would have to hold one tool row and wait for another.
- **(O) same order**: the writer locks several tool rows in the tool's order.
- **(N) none**: the writer never locks a row the tool locks.

## 7. Duration bound and scale (spec §3.5, OQ-8, AC-22a, AC-22b)

- **Bound**: 5 s by default; `-max-duration` accepts 1 s to 8 s (revision 2,
  note 8). Enforced by the command, PostgreSQL 16 having no
  transaction timeout: a `context.WithTimeout` around `BeginTx` … `Commit`; at
  the deadline the driver cancels the in-flight statement and `database/sql`
  rolls the transaction back; the command exits 1 with `duration bound
  exceeded (<d>)`. Server-side backstops, set by the first statement with
  `set_config(…, true)` (transaction-local, PAC-101 §4.3): `statement_timeout`,
  `lock_timeout` = the bound, and `idle_in_transaction_session_timeout` =
  1 s (the command sends its statements back to back; tests that hold the
  transaction open through a seam raise it through that seam, §10). A frozen
  or killed client therefore holds the tool's locks at most
  `statement_timeout + idle timeout` = bound + 1 s, at most 9 s, below the live
  10 s cap (revision 1's bound-sized idle timeout allowed 18 s at a 9 s bound).
  **Amended 2026-11-19 (stage 4, challenger note N-1):** the sentence above is
  false as written (both timers restart with every statement); see "Stage-4
  amendments", N-1, for the mechanism and the bound restated from the run's
  start.
- **Scale and measurement (AC-22b evidence)**: one throwaway
  `postgres:16.15-alpine` on the authoring workstation (Docker Desktop), no
  index on any matched expression, `max_parallel_workers_per_gather = 0`
  (serial, the worst case), the statements of §3.3 through `PREPARE`/`EXECUTE`:
  1,000,006 bookings over 10,000 links; 100,000–100,002 rows each in T1, T2, T3,
  T4, T5, T6, T7, T8 (each with three `addresses` and one `removed` item) and
  `operator_audit`; 10,000 accounts; 5 % of all stored addresses non-ASCII;
  X's copies in every place.

  | Run | Total (`clock_timestamp() - now()`) | Largest statements |
  |---|---|---|
  | dry run | **1.68 s** | `find_t9` 0.59 s, `find_t8` 0.57 s, `count_t10` 0.14 s |
  | erasure (committed) | **2.30 s** | `find_t9` 0.92 s, `find_t8` 0.85 s; erasure phase (12 statements) ≈ 20 ms |
  | rerun (idempotence) | **1.82 s** | all erased counts 0; `operator_audit kept=1` |

  The erased counts equalled the dry run's (T1 2, T2 2, T3 2, T4 2, T5 1, T6 1,
  T7 2, T8 2, T9 6; T10 kept 1). The first design (one locking statement per
  place, no discovery, the plain `translate` function) took **> 5 s** and hit
  `statement_timeout` on the 1 M-row link statement; §13 alt. 5.
- **When the bound is hit** (runbook): rerun off-peak; if it is still hit, rerun
  with `-max-duration` up to `8s`, the most the command accepts. The bound
  protects live requests.

> ## Erasing an address
>
> Use `paceday-operator erase-address` (PAC-134) when someone asks to be erased

> Paceday account must be searched by address too: entries added to a team by
> address are not linked to their account.
>
> **Precondition:** the web release that reads erased live bookings (PAC-134)
> is deployed. An older web shows the whole bookings list of an affected link as
> unreadable.
>
> 1. Put the request's ticket reference in `-reason`. Never put the address in
>    `-operator` or `-reason` (refused).
> 2. Give the address on standard input, never as an argument, for example
>    `printf '%s\n' "$ADDR" | paceday-operator erase-address -operator <you> -reason <ticket> -dry-run`
>    with `ADDR` read by `read -rs ADDR` (silent: not echoed, not in the shell
>    history).
> 3. **Dry run first** (`-dry-run`): it prints per place what would be erased
>    and what is kept, changes nothing, applies no migration, and writes an
>    address-free `erase_address_dry_run` record.

>    account (in any letter case). The tool still erases the copies in other
>    people's data, never the account or what the account owns (its own
>    bookings on its own links, its own roster entries, entries and invitations
>    it authored, its own keyed creations): those are reported as
>    `kept_account_own`. To go on, rerun with `-account-held-acknowledged`; the
>    record names the account ids. The copies come back through normal use
>    while the account exists; deleting the account is not this tool (no
>    account deletion exists yet).
> 5. Run the erasure (same command without `-dry-run`). It is one transaction:
>    everything or nothing.
>

> roster rows with their assignments, 1:1 occurrences, cached Manager figures

> co-host outcomes of keyed link creations (a retry of that creation then gets

> container logs (until rotation), Sentry, events on providers' calendars,

> matches, so a rerun erases them.
>
> Exit codes: 0 done (or dry run done); 1 failed, nothing changed (database,

> If the person was active during the run (booked, was invited), rerun once:

## 13. Alternatives rejected

1. **Stream candidate addresses into the command and match in Go.** Simplest
   way to apply Go's lowercasing, and the spec forbids it: other people's
   addresses would leave the database.
2. **A lookup table or a PL/pgSQL per-character loop for Go's lowercasing.**
   Slower than one `translate()` by an order of magnitude and no simpler to
   pin.
3. **An expression index or generated column on `paceday_go_lower(…)`.** Would
   make discovery an index scan, but adds write cost to the hottest tables
   (bookings) for a rare operator command, and an index over an `IMMUTABLE`
   function that a later migration must replace (Go upgrade) is silently
   corrupted. The measured scan fits the bound (§7).
4. **ICU `lower()` as the Go twin.** Full case mapping (`İ` → `i̇`, final
   sigma `Σ` → `ς`) and ICU-version dependent: not Go's simple mapping, not
   `IMMUTABLE`.
5. **One locking statement per place, no discovery phase.** The first design.
   Measured: more than 5 s (the 1 M-row link-lock statement alone hit the
   5 s `statement_timeout`), and every lock would have been held during full
   scans, making live requests wait seconds. Discovery without locks, then a
   short locked phase, keeps lock holding to milliseconds.
6. **Links `FOR NO KEY UPDATE`.** Would make booking saves wait for the tool,
   contradicting AC-13's interleaving and spec §3.5 "live requests come first";
   `FOR SHARE` orders everything that needs ordering.
7. **Always send `booker_erased_at` (null when not erased).** Cleaner schema,
   but the old web's strict parse would reject **every** bookings list at the
   backend deploy. Absent-unless-erased keeps today's bytes. **A `oneOf` of two
   strict shapes** was rejected for the generators (oapi-codegen unions, a zod
   union of strict objects) and because the archive already uses the nullable
   form. **A placeholder string** (`"[erased]"`) can be typed by a booker
   (PAC-40 §2.2).
8. **Lock the manager's `users` row to serialize Manager writers.** It would
   block sign-in and every request of that manager, and `users` after links
   would reverse PAC-40's erasure order (link → owner `users`).
9. **`SKIP LOCKED` in the two sweeps (L-1, L-2).** Avoids waiting but changes
   which rows a sweep handles in a run; ordered locking keeps their behaviour.
10. **Refuse to run on a non-libc database** to justify a cheaper pre-filter on
    the `lower()` half. Unneeded: the `char_length` pre-filter is applied to the
    Go half only, where it is provably sound.

## 16. Deviations from the spec, and open for the challenger

- **D-1 (live paths L-1, L-2, L-3).** The spec says the tool takes locks
  compatible with the live paths; the table found three live writers whose own
  order could form a cycle with any multi-row erasure. They are aligned to the
  tool's order (behaviour and answers unchanged). L-3 also removes a 500 the
  erasure (or a Manager delete) could cause in a concurrent confirm.
- **D-2 (AC-11b for W19 and W26).** A fresh-key or unkeyed booking save and a
  new link create never contend with the tool, so those cases assert
  completion without waiting; W19's outcome is AC-13's. Keyed retries of a
  booking or creation the tool is erasing do contend (on the key's unique
  slot) and are real-contention cases ending in 409 key reused (revision 2,
  note 1).
- **D-3 (discovery then lock).** "Committed after the run's statement on that
  place" is read as "after the discovery statement of that place".
- **D-4 (T7 own).** A pending invitation on a link owned by a matching account
  is "kept: account's own", by spec §3.2's general rule; the case list does
  not name it. Its effect: an owner's invitation of its own address (refused by
  the product since PAC-149, possible only by direct insert) is kept.
- **D-5 (statement-logging preflight).** An exit-1 condition the spec does not
  list, implementing "never in the database log" against a deployment that
  turned on bind-value logging.
- **D-6 (operator/reason check).** Before any connection there is no database
  lowercasing; Go lowercasing plus Unicode simple folding is used (§2.1 item 4).
- **D-7 (input limits).** 4096 bytes, valid UTF-8, no U+0000, one line: exit 2.
- **D-8 (`-max-duration`).** The runbook's "raise it within the 10 s cap" as a
  flag, 1–8 s (revision 2).
- **D-9 (AC-17's fifth class)** and **D-10 (PAC-129's negative docs test
  adapted)**: §11, §9.
- Open: whether `FOR SHARE` on links (rather than a stronger mode) is the
  right reading of "live requests come first" for co-host accept/decline/leave,
  which then contend on the invitation row itself (W21–W23) and answer 404 if
  the tool wins.

## Stage-4 amendments (dated 2026-11-19, backend-implementer)

- **N-1 (§3.3, §7).** Right before `lock_teams`, and again before every
  later statement of the erasure phase (each lock/erase statement and the
  audit insert), one statement
  `SELECT set_config('statement_timeout', $1, true), set_config('lock_timeout', $1, true)`
  sets both timers to the time left until the run's deadline (deadline − now,
  less a 20 ms margin for the round trip before the next statement starts,
  at least 1 ms); its name in the statement recorder is `budget`. So every
  lock-phase statement is ended by the server by the deadline even when the
  client is gone. The deadline is fixed when the run starts (`start + bound`).
  `main` traps SIGINT and SIGTERM (`signal.NotifyContext`): Ctrl-C cancels
  the context, which cancels the in-flight statement and rolls the run back
  (exit 1, class `interrupted`, a class §2.6 did not list).
  **§7's bound, restated, measured from the run's start:** a statement of
  the run ends by `start + bound` (server-side in the lock phase; the
  discovery phase takes no row lock); a client that freezes between two
  statements is ended by the 1 s `idle_in_transaction_session_timeout`; so
  the tool holds a row lock at most until `start + bound + 1 s` (≤ 9 s after
  it started), below the live 10 s per-wait cap. Test:
  `TestPAC134_N1_LockPhaseEndsByTheDeadline` (a lock-phase statement contended
  near the deadline is ended by the server's own `lock_timeout` or
  `statement_timeout`, never later than the deadline; every `budget` is the
  time left).
- **N-2 (§3.3 `analyze_found`).** `ANALYZE pac134_found (place, own, row_id,
  team_id, link_id, owner_id)`: `row_key` has no statistics.
- **N-3 (§2.3, §3.3 `settings`).** The preflight is one boolean computed in
  SQL from `pg_settings.setting` (unitless: ms for the durations, bytes for
  the lengths): it refuses when `log_parameter_max_length_on_error <> 0`, or
  `log_parameter_max_length <> 0` and any of `log_statement IN ('mod','all')`,
  `log_min_duration_statement >= 0`, `log_min_duration_sample >= 0`,
  `log_transaction_sample_rate > 0`; or when `auto_explain.log_min_duration`
  is listed and is a number `>= 0` (a listed value that is not a number also
  refuses). Not listed (the module not loaded: a placeholder set in

  booking or of a link creation the tool is erasing does **not** wait on the
