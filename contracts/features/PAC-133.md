## 0. The rule this contract fixes

Per requested address, a free/busy read ends in one of three outcomes: readable
(windows complete), unknown with the windows the provider did report, or unknown
with none. Unknown is never presented or used as free. Reported windows block
wherever they appear, whatever the outcome of the address that carries them; an
unknown address with no reported windows blocks nothing (D-11). Everything below
is that rule applied to each reader and each consumer, plus the inherited fixes
the operations carry: the cache answers only the same range and is bounded
(SF-033), both lookups refuse a window that does not move forward (SF-034,
API-077), the MCP free-slot tool reads real calendars (SF-102), compression apply
checks real attendees (SF-103), and NLP parse reports a failed suggestion step
(SF-037 first clause).

## 2. Operations

### 2.1 `queryFreeBusy` (participant lookup)

Order (binding):

1. requireAuth 401 (unchanged); handler 401 `unauthorized` when the user id is
   missing (unchanged).
2. 400s, in this order, all JSON (`writeError`): `invalid JSON`,
   `emails is required`, `max 20 emails per request`,
   `start_time must be RFC3339`, `end_time must be RFC3339`, then **new**
   `end_time must be after start_time` when `end_time` is equal to or before
   `start_time` (compared as instants). No cache read, no provider call (AC-10).
3. Settings read (500 on failure, unchanged).
4. Per address, lowercased and trimmed (unchanged): personal domain → `unknown`,
   `[]`, no call, not cached; cache hit (§4) → served; else queued.
5. One provider call for every queued address under the 5 s child timeout, with
   the requester's own Google or Outlook credential (unchanged, PAC-67). The
   reader's outcome per address (§3) is the coverage:
   - readable → `known` with its windows;
   - unknown → `unknown` with the windows reported for it, possibly `[]`;
   - a failed or timed-out call → every queued address `unknown`, `[]`
     (unchanged; the error is still not surfaced).
6. Caching (§4), then the answer. `participants[].status`, `busy{}` and
   `results[].coverage`/`busy` carry the same status and windows (AC-5, AC-12).

Shape unchanged (`FreeBusyQueryResponse`), so the web's `contract.test.ts:91` and
the link editor keep working; the link editor's chip turns "unknown" for an
unreadable co-host with no code change (spec §3.5 item 6). Manager analytics for
an external member already maps `unknown` to "no data" (AC-11 follows).

`status` keeps two values (PAC-41 D-2). A partial answer is `unknown`, not a third
value: a client that reads `status` only would otherwise need a code change to
stop treating the third value as free, and the participant lookup's consumers
need "is it complete?", which two values answer.

### 2.2 `getCalendarFreeBusy` (raw lookup)

Order (binding):

1. requireAuth 401 (unchanged).
2. 400s, plain text (`http.Error`), in this order: `invalid start param`,
   `invalid end param`, then **new** `end must be after start` (end equal to or
   before start). All three **before** the credential is loaded, so a caller with
   no Google credential gets the 400 here, not the 401 (AC-16, spec m-7).
3. Credential: 401 `calendar not connected` (no Google credential, including an
   Outlook-only user), 500 on a read failure (unchanged).
4. One Google `freebusy.query` call with `primary` plus every distinct element of
   `attendees` (split on `,`, no trimming, no lowercasing, first-appearance
   order). A failed call is the 500 `{"error":"internal error"}` (unchanged).
5. The 200: `{"own": …, "calendars": [ … ]}`.

The 200 (`RawFreeBusyAnswer`, binding):

- `own`: the caller's own calendar, `RawFreeBusyOwnKnown`
  (`{"status":"known","busy":[…]}`) or `RawFreeBusyOwnUnknown`
  (`{"status":"unknown"}` or with a non-empty `busy`). It is identified by its key,
  never by an address the caller would have to guess (spec §3.3 item 1). The own
  calendar being unknown is a 200, never the 500 (AC-17).
- `calendars`: exactly one entry per distinct requested element, spelled as sent,
  in first-appearance order. An element equal to the caller's own address (or to
  `primary`) is still listed there; it then shares `own`'s outcome.
  - `RawFreeBusyCalendarKnown`: `address`, `status: known`, `busy` (required,
    complete, `[]` = free), optional `group`.
  - `RawFreeBusyCalendarUnknown`: `address`, `status: unknown`, `busy` **only when
    windows were reported, and then `minItems: 1`**, optional `group`. So an
    unknown calendar never appears with an empty window list (AC-14, AC-20): `[]`
    in this answer always means "readable and free".
  - `group` (`RawFreeBusyGroup`): only on an address Google answered under
    `groups`. `members` are the expansion's calendars, each a
    `RawFreeBusyCalendar` without `group`, in Google's order, `[]` when the
    expansion failed. The group's own `busy` is every window its members reported
    (concatenated in member order, not merged). The group is `known` iff the
    expansion has no error and every member is known (AC-15).
- A calendar Google answered that is neither requested nor a member of a
  requested group is dropped.
- Window keys stay `start`/`end` (`RawGoogleBusyWindow`, PAC-26), including the
  zero time on an unparseable timestamp (unchanged, spec §5).

Example (AC-14's world: S seeded 10:00-11:00, U unseeded, own calendar empty):

```json
{
  "own": {"status": "known", "busy": []},
  "calendars": [
    {"address": "s@x.test", "status": "known",
     "busy": [{"start": "2026-11-23T10:00:00Z", "end": "2026-11-23T11:00:00Z"}]},
    {"address": "u@x.test", "status": "unknown"}
  ]
}
```

The two variants of each union are told apart by `status` alone (disjoint
one-value enums, the `PublicBookingConflict` pattern). `oapi-codegen` generates
`RawFreeBusyOwnCalendar` and `RawFreeBusyCalendar` as unions with
`As…`/`From…` helpers; the route stays handwritten (MIGRATION note), so no server
code is generated for it.

**Second opinion (API-091, AC-18).** A Go contract test decodes the handler's 200,
for a readable, an unknown (with and without windows) and a group answer, into
`gen.RawFreeBusyAnswer` with `DisallowUnknownFields`, decodes each union into
exactly one variant (strict, `DisallowUnknownFields`, `status` checked), and
fails on an unknown entry with `"busy": []`. `TestPAC26CalendarFreeBusyWindowKeys`
is rewritten to the envelope and keeps its `start`/`end` assertion.

**Breaking change and consumers.** The old 200 was `map[string][]TimeSlot`.

### 2.3 `suggestMeetingSlots`

- 200 `ScheduleSuggestions` gains `unknown_attendees` (**required**, `[]` when
  everyone was read). Members: every requested attendee whose outcome is unknown
  (§3), a group named by the group address, spelled as sent, once each, in request
  order; never the own calendar, never a readable attendee, never a group member
  by its own id (AC-21, AC-22, AC-24, AC-25).
- The busy set that constrains the slots: the own calendar's windows, every
  readable attendee's windows, and every window reported for an unknown attendee
  or a group's member (D-11). An unknown attendee's missing time does not
  constrain.
- The own calendar unknown → error → the operation's 500 `internal error`
  (`writeCalendarFailure` → `writeServerError`, step `suggestMeeting`), no slot
  (AC-23).
- Unchanged: 30-minute steps, at most 3 slots 1 h apart, the 400s, the 401.
- **Contract correction.** The 500's description claimed the
  `out-of-hours meeting allowance reached` body. `Suggest` never returns
  `ErrOutOfHoursAllowance` (only `CreateMeeting` does,
  `engine/smart_schedule.go:308`; a spent allowance only drops out-of-hours
  candidates, `canScheduleOutOfHours`). The description now says so.

Compatibility: an older web reads the answer without a runtime schema
(`src/api/client.ts:1144`), so the new member is ignored; the generated zod schema
changes in the types PR.

### 2.4 `previewCompression`

- A candidate position is proposed only if every attendee (non-self, not declined)
  is readable and no reported window (any attendee, readable or unknown, or a
  group's member) overlaps it. Unknown at the position → not proposed, next
  candidate (AC-29). A failed check → not proposed (spec §5, P2-m2).
- Own-time handling unchanged (spec §5).
- Calls: at most one free/busy call per evaluated candidate per meeting with
  attendees; the plan may make fewer (e.g. one per meeting over the work day,
  evaluating every candidate from it) (AC-35).
- **503 listed**: the shared `RequestBudgetExpiredError`, when the budget ends
  before the answer; never a 200 with fewer proposals or days (AC-36). The
  middleware already answers it (PAC-81); the contract now lists it here and in
  `info.description`.

### 2.5 `applyCompression`

Per parsed proposal, in order (binding; spec §3.6 items 2-4, OQ-8 default):

1. Read the event (`getEvent`), once. Failure → `"<event_id>: <error text>"`
   (today's form, unchanged).
2. Attendees by the preview's rule (`extractAttendees`: non-self, not declined).
   None → move with no free/busy call (AC-33 second half).
3. One free/busy call for exactly those attendees over
   [`proposed_start`, `proposed_end`] (AC-33 first half).
4. Check set = proposed interval minus the event's current interval (from the
   read; an event with no timed start/end excludes nothing).
5. Decision, first match wins:
   1. any reported window (any attendee, any outcome, any group member)
      overlapping the check set → `"<event_id>: attendee conflict at proposed
      time"` (AC-31, AC-34 second half);
   2. the call failed, or any attendee unknown →
      `"<event_id>: attendee availability unverified"` (AC-30, AC-32);
   3. else update the event and write the `meeting_moved` audit row, as today.
6. A proposal not moved writes nothing.

Conflict wins over unverified because a reported window is a known clash
(D-11); telling the caller "conflict" is the more useful and more certain answer.
Bound: one free/busy call and exactly one event read per proposal (AC-35). The
answer's shape is unchanged (`applied`, `failed`); the reasons are documented on
`CompressionApplyResult.failed`. The web reads `failed` as strings with no parse
(`focusWireTypes.test.ts:91` unchanged).

### 2.6 `parseNaturalLanguage`

When the intent is `schedule_meeting` with a range and `Suggest` returns an error
(spec §3.5 item 7, AC-28):

- `error` already set (by the model's JSON) → kept unchanged (precedence);
- else `error` = exactly
  - `No Google calendar is connected, so Paceday cannot suggest meeting times.`
    when the error is `engine.ErrCalendarNotConnected`;
  - `Paceday could not suggest meeting times for this request. Try again later.`
    for any other error (including the own calendar unknown);
- `suggested_slots` absent; every other member as today; HTTP 200.

A successful step sets no error. A budget expiry during the step is the existing
503 (the middleware answers first). The underlying error goes to the server log
(step `nlp suggest`), never into the answer. The web half (AC-43, including
P3-m1's bullet: any error is shown in place of "No available slots found…") is the
web UI PR's (§9).

## 3. Provider reader rules (binding, non-HTTP)

Both readers answer **every requested address** (the exact string requested) with
an outcome, or fail as a whole. Names are free; the semantics are binding and are
what PAC-129 consumes (`PAC-129.md` §6 "Unknown per address comes from PAC-133's
readers").

Suggested Go shape (in `calendar`):

```go
type FreeBusyEntry struct {
    Known   bool          // readable: Busy is complete
    Busy    []TimeSlot    // reported windows; for a group, all members'; never nil
    Members []FreeBusyMember // Google group only; nil otherwise
}
type FreeBusyMember struct { ID string; Known bool; Busy []TimeSlot }
// GetFreeBusy(ctx, ids, min, max) (map[string]FreeBusyEntry, error)
// The map has exactly one key per distinct requested id.
```

Every consumer gets the outcome from the reader; none re-derives "free" from an
empty list (D-1).

### 3.1 Google (`CalendarClient.GetFreeBusy`)

- One `freebusy.query` with every requested id (unchanged). A failed call returns
  the error (the whole call fails).
- Matching a requested id R to the answer: exact key, else a case-insensitive
  match, else not mentioned.
- If R is a key of `groups` → **group**: members = the group's `calendars`
  (expansion). Each member's outcome by the calendar rule below (a member absent
  from `calendars` is unknown). The group is readable iff the group's `errors` is
  empty **and** every member is readable; its `Busy` is every member's reported
  windows. An expansion error → unknown, with any windows its members reported
  (AC-3).
- Else if R is a key of `calendars` → `errors` non-empty → **unknown, windows
  kept**; else **readable** with its windows (possibly none) (AC-1, AC-2).
- Else → **unknown, no windows** (AC-2's D).
- A `calendars` entry that is neither requested nor a member of a requested group
  is dropped.
- Timestamp parsing unchanged (spec §5).

### 3.2 Microsoft (`OutlookClient.GetFreeBusy`)

- One `getSchedule` call with every address (unchanged; PAC-129 batches it). A
  failed call (transport, non-2xx, undecodable body) returns the error.
- The response decode gains each `value[]` entry's `error` member.
- Matching: `scheduleId` exact, else case-insensitive.
- Entry with a non-null `error` → **unknown**, with the windows of its items
  whose status is not `free` (AC-4's A and E).
- Entry without `error` → **readable** with those windows (possibly none) (AC-4's
  B and C).
- Requested address with no entry → **unknown, no windows** (AC-4's F).
- An entry for an unrequested address is dropped. No group concept.

### 3.3 The dead WebCal path

`WebcalClient.GetFreeBusy` (no production caller, spec §2.1) must satisfy the new
signature: it answers every address **unknown, no windows**. That is the only
answer consistent with D-11 for a reader that reads nothing; the path stays dead
and out of scope otherwise.

## 4. Participant lookup cache (binding)

- **Key**: requester id, lowercased address, start instant, end instant (instants
  compared as instants, so two offsets of the same instant share a key). Nothing
  else is reused (AC-8).
- **Entry**: outcome (`known`/`unknown`) and windows (partial windows included).
- **TTL**: 15 minutes from the store; a hit does not extend it. `unknown` is
  cached exactly like `known` (D-2, AC-7). Not cached: anything from a call made
  while the requester's credential is recorded as lost (PAC-67 AC-20, unchanged);
  personal-domain addresses (no call).
- **Bound**: least-recently-used, **10,000 entries** per `FreeBusyService` (one
  per process for the handler). Adding past the maximum evicts the least recently
  used; a hit makes an entry most recently used; an expired entry is never served
  and is removed when found or evicted (AC-9). The maximum is an unexported field,
  `0` meaning 10,000, so a test sets 2.
- Why 10,000: an entry is an address plus a few windows (well under 1 KiB), so the
  bound caps the cache near 10 MiB while holding far more than the link editor's
  working set (spec §3.2 item 3: hits will be rare after the exact-range key, by
  design, P2-m1).

## 5. Engine consumers and the blocking rule

### 5.1 D-11, binding on every consumer (PAC-129 included)

| Consumer | Reported windows of an unknown address / group member | Unknown with no windows | Presented as |
|---|---|---|---|
| Participant lookup | carried in all three views | `[]` | `unknown` |
| Raw lookup | `busy` (non-empty) | no `busy` | `status: unknown` |
| Suggestions | constrain slots | does not constrain | named in `unknown_attendees` |
| Compression preview | reject the position | reject the position (unknown) | not proposed |
| Compression apply | conflict | unverified | `failed` reason |
| PAC-129 team availability (added people) | **must block** | does not block | counted unknown |

PAC-129's contract at `6192cd8` says "unknown does not block"
(`PAC-129.md:304-306`). Under D-11 it must read: an added person whose
availability is unknown does not block **beyond the busy windows reported for
them**, and those block as a busy person's do. The factory updates PAC-129
separately (spec §3.1 item 5); until then this contract wins. Cross-reference
renumbering for PAC-129: its AC-4 → PAC-133 AC-1/AC-5; AC-5 → AC-4/AC-6; AC-7 →
AC-8; AC-15 → AC-20.

## 6. MCP tools (binding, outside the bundle)

The MCP server keeps relaying backend bodies as text (`jsonResult`) and its
`Error: …` convention. Schemas below are the tool definitions (`mcp/tools.go`).

### 6.1 `clockwise_find_free_slots`

| Argument | Type | Required | Meaning |
|---|---|---|---|
| `start` | string, RFC3339 | yes | unchanged |
| `end` | string, RFC3339 | yes | unchanged |
| `attendees` | string | **no (new)** | comma-separated addresses; trimmed, empty elements dropped (`splitEmails`), joined with `,`, sent as `attendees`. Absent or empty → no `attendees` parameter. The tool never names the user's own calendar (AC-19). |

Description (exact text):

> Read free/busy for a date range: the user's own calendar (always) and any
> attendees given. Each calendar is "known" (its busy windows are complete) or
> "unknown". Unknown means not checked, never free: the person may be busy at
> times not listed. Busy windows shown for an unknown calendar are real and still
> block.

Answer: the backend's `RawFreeBusyAnswer` body as text, unchanged by the tool, so
an unknown calendar carries `"status":"unknown"` and never `"busy":[]` (AC-20).
The 400 `end must be after start` reaches the model as `Error: …` (spec §3.4 item
3). The tool computes no slots.

### 6.2 `clockwise_create_event`

| Argument | Type | Required | Meaning |
|---|---|---|---|
| `title` | string | yes | unchanged |
| `attendees` | string | yes | unchanged (comma-separated) |
| `duration` | string | no | unchanged (minutes, default 30) |
| `preferred_date` | string | no | unchanged |
| `location` | string | no | unchanged |
| `start` | string, RFC3339 | **no (new)** | book exactly this start (with `duration`) after a re-check |
| `accept_unknown` | boolean | **no (new)** | `true` accepts booking past the attendees named in `accepted_unknown`; any other value, or absent, is false |
| `accepted_unknown` | string | **no (new)** | comma-separated attendees whose unknown availability is accepted, echoed from the first answer |

Description (exact text):

> Schedule a meeting with the smart scheduler. If every attendee's calendar was
> checked, the first suggested slot is booked. If some attendees' availability is
> unknown (their calendar could not be checked), nothing is booked: the answer
> gives the exact proposed start and end and the unknown attendees. To book that
> slot anyway, call again with the same title, attendees and duration, plus
> start (the proposed start), accept_unknown=true and accepted_unknown (the
> unknown attendees listed). The slot is checked again before booking.

Behaviour (binding; spec §3.5 item 4, AC-26):

**A. Without `start`** (whatever `accept_unknown` says, AC-26 (e)):
1. `POST /api/schedule/suggest` as today. Backend error → `Error: …`. No slot →
   `Error: no available slot found` (unchanged).
2. `unknown_attendees` empty → create at the first slot exactly as today (AC-26
   (f)).
3. Else **no create request**. Text (times RFC3339 as decoded):

   ```
   Not booked yet: the availability of these attendees could not be checked (unknown, not free): <u1>, <u2>.
   Proposed slot: start <S>, end <E>.
   To book this exact slot anyway, call clockwise_create_event again with the same title, attendees and duration, start="<S>", accept_unknown=true and accepted_unknown="<u1>,<u2>".
   ```

**B. With `start`** (unparseable → `Error: start must be RFC3339`; nothing booked):
1. E = `start` + duration. One `GET /api/calendar/freebusy?start=S&end=E&attendees=…`
   with the call's attendees. Backend error → `Error: …`, nothing booked.
2. Refusals, first match wins, **no create request**, text
   `Not booked: <reason>. Call clockwise_create_event again without start to get a new proposal.`:
   - `own` unknown → reason `your own calendar could not be checked`;
   - any window (in `own`, or any entry of any status, or a group member)
     overlapping [S, E) → reason `someone is busy at that time`  (AC-26 (c));
   - the set of unknown addresses (case-insensitive) is not a subset of
     `accepted_unknown` → reason `the availability of <names not accepted> could
     not be checked` (AC-26 (d)).
3. Unknown addresses present, all accepted, but `accept_unknown` is not `true` →
   no create request; the answer is A.3's text for start S (a first-call answer
   for that slot).
4. Else exactly one `POST /api/schedule/create` with start S and end E (never a
   recomputed slot), title, attendees, location as today; its body relayed (AC-26
   (b)). With no unknown attendee this is "a call with a start books that start
   after the same check" (spec §3.5 item 4).

Why the raw lookup and not suggestions for the re-check: §13 alternative 4.

### 6.3 `clockwise_suggest_meeting`

> Find the best meeting slots for a set of attendees without creating the event.

## 13. Alternatives rejected

1. **Raw lookup: keep the map, add an `unknown: [...]` list beside it** (spec
   OQ-2). Any reader of the map still sees an unknown address as `[]`, which is
   the defect.
2. **Raw lookup: one schema with an optional `busy` and a prose rule "unknown has
   no empty list".** Cheaper for the generator, but permits the exact wrong
   response (`{"status":"unknown","busy":[]}`). The `oneOf` with disjoint
   `status` and `minItems: 1` makes it inexpressible (agent rule "make the wrong
   request impossible").
3. **A third status (`partial`) on the participant lookup.** Breaks PAC-41 D-2's
   two values for every client that branches on `status`; consumers only need
   "complete or not". Partial windows ride on `unknown`.
4. **MCP re-check through suggestions over exactly [S, S+duration]** (challenge
   pass 3's example). It works for a slot the scheduler produced, but adds the
   work-hours, lunch and out-of-hours-allowance filters (anchored on a different
   week than the first call) to the question "is anyone busy then?", so a valid
   proposed slot can be refused for a reason that is not availability, and an
   unknown own calendar comes back as an opaque 500. The raw lookup answers the
   exact slot with per-calendar outcomes; `createScheduledMeeting` still applies
   its own allowance rule at booking.
5. **Server-side state for the MCP acceptance (a token).** The tool is stateless
   and the spec chose echoed names (P2-M1); a token would add storage and expiry
   for no extra safety, since re-verification happens anyway.
6. **Unverified wins over conflict in apply.** "Conflict" is certain and
   actionable; "unverified" is not. Reported windows block (D-11).
7. **A partial 200 (or marked unchecked candidates) when preview's budget runs
   out.** PAC-36 removed partial weeks; the 503 is retryable and already the
   middleware's answer (spec B-1).
8. **Cache key on the hour bucket of the range** to keep hit rates up. Answers a
   different question than the one asked (SF-033 in a smaller form); the spec
   accepted the hit-rate cost (P2-m1).
9. **A Graph base address in configuration.** Production never needs another
   Graph address; a test seam adds no deployable surface (PAC-80).
10. **Lowercasing and trimming raw-lookup attendees.** A behaviour change the spec
    does not ask for, and the MCP tool already trims; names come back as sent.
