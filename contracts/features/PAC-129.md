## 0. The rule this contract fixes

A team owner can put a person on a team by email, at once, without sending them
anything and without them having or getting Paceday access. That person is a
member **of the team** (not of a manager's private roster), visible to every
member, counted in Find a time through **the owner's** calendar credential, and
gets nothing back. Invitations stay a separate, explicit action that now also
adds the person and is never duplicated. Removal names a person by address and
deletes them from the team's data. Every membership write is ordered on the
team row (PAC-25) and capped at 50 members.

## 2. Storage (binding; migration 041)

### 2.1 Why a separate table

An added person is a row of a new table `team_added_members`, keyed by
`(team_id, email)`, not a `team_members` row with a nullable `user_id`.

- `team_members.user_id` is the primary key's second half and every read joins
  `users`; a nullable `user_id` would break the PK, every `JOIN users`, the
  PAC-25 owner count, `ListTeamsForUser` and the PAC-71 carrier logic at once.
- The kind is then a fact of the schema: a row in `team_members` is a Paceday
  member, a row in `team_added_members` is an added person. An address can be in
  at most one of the two for a team (the writes keep it so under the team lock;
  §4).
- The upgrade on acceptance is "delete the added row, insert the membership,
  mark the invitation accepted", in one transaction. At the HTTP boundary the
  entry is identified by its address, which does not change, so it is the same
  entry with a new kind (spec D-4).

Notes (binding):

- **The index is on stored status**, because an index cannot read `now()`. It is
  still "one live pending invitation per team and address": every write that
  creates a pending row first sweeps that address's lapsed stored-pending rows to
  `expired` in the same transaction (§3.3 step 5), so a lapsed row can never block
  a fresh one, and two live ones can never coexist.
- **The sweep is the same rule as preview and accept** (`expires_at <= now()`,
  `storage/teams.go` `GetTeamInviteByToken`, PAC-122 SF-002), so it changes no
  answer: a swept row was already answered 410 "invite is expired".
- **Only live pending rows are de-duplicated.** Expired, accepted and declined
  rows are kept (lowercased). In AC-26's fixture the two `cy` rows are swept to
  `expired` and neither is deleted; `bob`'s row is unchanged; for `ann` the newer
  row survives, lowercase.
- **Lowercasing all rows** (not just pending ones) is needed for the CHECK. It
  changes no answer: invitations are matched case-insensitively today
  (`strings.EqualFold` on accept, `lower()` in the Manager removal).
- **The address trim set (binding; revision 1.2, P2-B1, P2-M1).** Exactly these
  26 code points, the union of ECMAScript WhiteSpace and LineTerminator and of Go's
  `unicode.IsSpace` (which adds U+0085; ECMAScript adds U+FEFF):

  U+0009, U+000A, U+000B, U+000C, U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000, U+2001, U+2002, U+2003, U+2004, U+2005, U+2006, U+2007, U+2008, U+2009, U+200A, U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF.

  It is defined here once. Its two twins must equal it:
  - SQL: `paceday_trim_ecma` above, built from `chr()` calls only (no escape
    string; `E'\v'` is the letter `v`, which made revision 1.1's function turn
    `victor@agency.gov` into `ictor@agency.go`).
  - Go: one function, for example `storage.TrimAddressSpace`, trimming exactly
    this set (an explicit table of the 26 runes, not `strings.TrimSpace` plus
    extras), used by the one address normaliser of §3.0.
- **Tests that pin the set (binding).**
  - SQL (storage package, testcontainers, after migration 041): for every code
    point from U+0000 to U+FFFF that PostgreSQL text can hold (U+0000 and the
    surrogates U+D800-U+DFFF cannot, and are skipped with that reason),
    `paceday_trim_ecma(chr(c) || 'a' || chr(c)) = 'a'` holds exactly for the 26
    code points of the list; for every other one the value is unchanged. Also:
    `paceday_trim_ecma('victor@agency.gov') = 'victor@agency.gov'` and
    `lower(paceday_trim_ecma('Victor@Agency.gov')) = 'victor@agency.gov'`.
  - Go: for every rune from U+0000 to U+FFFF except the surrogates (not valid
    runes), `TrimAddressSpace(string(r)+"a"+string(r)) == "a"` exactly for the 26
    of the list. The same 26-entry table is the expected value in both tests.
- **Trimming covers more than spaces**: a legacy `'dee@x.example'` followed by a
  tab becomes `dee@x.example` and is de-duplicated with its twin.
- **Empty after trimming** (P2-m1): a legacy invitation whose address is only
  characters of the set would fail `invitee_email <> ''`. The up step deletes such
  rows first and logs the count (`RAISE LOG`, in the PostgreSQL server log, and
  `RAISE NOTICE` to the migrating client). The runbook gives the pre-flight count
  query (§10.1). Such an invitation could never be accepted (no account holds an
  empty address).
- **Storage normalises on write** (challenge M-2, factory decision):
  `storage.CreateTeamInvite`, and every insert into `team_added_members`, store
  `lower(TrimAddressSpace(address))` whatever the caller passes. A caller that
  passes a mixed-case address (tests do, §8) therefore never trips the CHECK. The
  request path has already produced exactly this form (§3.0), so storage's
  re-normalisation is a no-op there.
- **No backfill** (spec OQ-8): no added person is created from Manager
  assignments or from pending invitations. Member lists and rosters read as

## 3. Operations (binding)

Common definitions:

- **Address normalisation**: `normalizeManagerEmail` (trim, lowercase,
  `net/mail.ParseAddress`, parsed address equals the input). The same rule for
  the body of add and invite and for the `{email}` path of removal.
- **Paceday member at an address**: a `team_members` row of the team whose user's
  `lower(users.email)` equals the address. An account carries one address
  (`storage/identity.go:135-140`), so this reveals nothing about other addresses.
- **Pending**: stored status `pending` and `expires_at > now()` (database clock).
  **Lapsed**: stored `pending`, `expires_at <= now()`.
- **Member count** for the cap: `team_members` rows plus `team_added_members` rows
  of the team. Invitations do not count. The cap is **50**, owner included.
- **The adding owner** of an added person: `added_by`, when that account is
  currently an owner of the team. Otherwise there is none and the person's
  availability is unknown.

### 3.0 One address normaliser (binding; revision 1.2, P2-M1)

There is one address normaliser, used on every request path that takes an
address and by storage:

1. trim the set of §2.2 (`TrimAddressSpace`) from both ends;
2. lowercase;
3. `net/mail.ParseAddress`; the parsed address must equal the result of step 2.

Blank after step 1: 400 `email is required` (body) or 400 `invalid email` (the
`removeTeamPerson` path). Refused at step 3: 422
`email must be a valid email address` (body) or the same 400 `invalid email`
(path). `normalizeManagerEmail` becomes this function (so Manager add,
inviteTeamMember, addTeamPerson and removeTeamPerson share it); its only change
for Manager add is that a leading or trailing U+FEFF is now trimmed instead of
reaching `ParseAddress`. Every decision read inside the §4 transactions (own
address, Paceday member at the address, existing added entry, pending invitation,
carriers) compares this normalised form, and storage writes this same form, so a
decision and its write can never be about two different strings.

**Tests (binding).** With a byte-order mark (U+FEFF) at the start, and separately
at the end, of the address:
- O adds `\uFEFF` + O's own address → 422 `you cannot add your own address`, no
  row;
- with `pat@x.example` added, adding `pat@x.example` + `\uFEFF` → 200 with the
  existing entry, one entry (AC-4's rule);
- inviting `\uFEFF` + M's address (M a Paceday member) → 200 `already_member`, no
  added entry, no invitation, no email.

### 3.1 `addTeamPerson` (new; spec §3.1, §3.10)

**Request validation (contract 1.1, challenge B-1, factory decision).**
`AddTeamPersonRequest.email` is a plain `type: string` (no `format: email`), and
`TeamPerson.email` and `TeamAnalyticsPerson.email` carry no `format` either. The
generated decoder therefore accepts any JSON string, and the server's one address
normaliser (§3.0: trim the §2.2 set, lowercase, `net/mail.ParseAddress`) is the
only validator. With `format: email` the generated `openapi_types.Email`
refused `"  PAT@Ext.Example "` and `""` as 400 `invalid body` (so AC-4 failed and
the documented 400/422 were unreachable), and its encoder refused `pat@localhost`,
which the normaliser accepts, after the row had committed. Re-checked against the
new schema: `"  PAT@Ext.Example "` reaches step 6 and is 200 (AC-4); `""` and
`"   "` are 400 `email is required`; `"not-an-email"` is 422
`email must be a valid email address`; `pat@localhost` is stored and encodes;
`{"email": 5}` and a non-JSON body are the wrapper's 400 `invalid body`.

Order (binding): 401 → 400 `invalid team id` → 400 `invalid body` (the generated
wrapper's decode failure) → 400 `email is required` (blank after trim) → 422
`email must be a valid email address` → transaction T-add (§4):

1. PAC-71 re-check (stale: 401, nothing written).
2. `SELECT … FROM teams WHERE id = $1 FOR NO KEY UPDATE`; no row → 403.
3. Caller's membership; not a member or not `owner` → 403; a storage error → 500
   (SF-074 fixed here, OQ-12).
4. Address = caller's own address → 422 `you cannot add your own address`.
5. A Paceday member at the address → 422
   `this address belongs to a Paceday member of this team`.
6. An added entry exists → 200 with it, unchanged; except that if it has no
   adding owner (§3, "adding owner"), `added_by` becomes the caller (spec OQ-1:
   "until an owner re-adds them"). The name is never changed by a repeat.
7. Member count ≥ 50 → 422
   `this team has reached its limit of 50 members; remove someone before adding another`.
8. Insert `(team_id, email, display_name = trimmed name or '', added_by = caller)`
   → 201.

The answer is a `TeamPerson` with `kind: "added"`, `userId: null`, `role: null`
and `invitation` (the address's pending invitation, if a legacy one exists, else
null). Nothing about any account is looked up, so the answer for an address held
by a confirmed account and for one held by nobody differ only in `email` and
`name` (AC-2). No email is sent. No invitation is created.

### 3.2 `removeTeamPerson` (new; spec §3.8)

Order: 401 → 400 `invalid team id` → 400 `invalid email` → transaction T-remove:

1. Re-check; 2. team lock (no row → 403); 3. caller's membership (not a member →
   403; storage error → 500); 4. address ≠ caller's own address and caller not
   `owner` → 403;
5. Under the lock: the Paceday members at the address, the added entry, and every
   `team_invites` row of the team with that `invitee_email` (any status).
6. None → 404 `{"error":"person not found"}`, nothing written.
7. A Paceday member there is `owner` and no other owner would remain → 422
   `the team owner cannot be removed`, nothing written.
8. Delete them all → 204.

A Paceday member may remove themselves by their own address (owner or not).
Nothing else of the person exists on the team path: added people's figures are
never stored. A manager's roster row or assignment for the address is never
touched (AC-37).

### 3.3 `inviteTeamMember` (changed; spec §3.7)

Before the transaction, unchanged: 401 → 400 `invalid team id` → (owner check
moves into the transaction) → 400 `email is required` → 422
`email must be a valid email address`. Note the owner check used to precede the
body checks; now a non-owner with a malformed body gets the 400/422 before the
403. No information leaks (the body is the caller's own). Then transaction T-invite:

1. Re-check; team lock (no row → 403); owner check (not an owner → 403; a storage
   error is **still 403** on this existing operation, OQ-12).
2. Paceday member at the address → **200** `{outcome: "already_member",
   invitation: null, person}`; nothing written, no email.
3. Address not on the team and member count ≥ 50 → 422 `TeamMemberLimitError`.
4. Address not on the team → insert the added entry (`name` trimmed, `added_by`
   caller). Address already an added person with no adding owner (§3) →
   `added_by` becomes the caller, as in §3.1 step 6 (challenge m-9); the name is
   not changed.
5. A pending invitation exists → **200** `{outcome: "already_pending", invitation:
   <it, token included>, person}`; no new invitation, no email.
6. Else: `UPDATE team_invites SET status='expired' WHERE team_id=$1 AND
   invitee_email=$2 AND status='pending' AND expires_at <= now()`; insert the new
   invitation (7 days); commit; then send the email as today (tracked unit,
   PAC-81; without SMTP the skip is logged with the invite id and the answer is the
   same, PAC-122 SF-066) → **201** `{outcome: "added_and_invited", …}` when step 4
   inserted the entry, else `{outcome: "invited", …}` (the address already was an
   added person; challenge m-8).

`person` is the address's `TeamPerson` after the call. Because the transaction
holds the team lock, two concurrent invitations of one address give one 201 and
one 200 `already_pending`; the partial unique index is the backstop (a violation
would be a 500, never a second pending row).

### 3.4 `acceptTeamInvite` (changed; spec §3.7, §3.8)

Unchanged before the write: 401; sweep then token read (404 / 410); the PAC-71
granting check (403 `this invite is for a different email address`, AC-22). Then
transaction T-accept:

1. Re-check (stale: 401; neither upgrade nor create is written, AC-25).
2. Lock the invitation's team row; no row → 404 `invite not found`.
3. Re-read the invitation **by id** under the lock, with its effective status. No
   row → 404 `invite not found` (removal first, AC-30). Not pending → 410
   `invite is <status>`.
4. Caller already a member → mark accepted, 204.
5. Added entry for the address → delete it; insert `team_members(role 'member')`;
   mark accepted; 204. Never refused by the cap.
6. Else (legacy) member count ≥ 50 → 422 `TeamFullError`, nothing changes; else
   insert membership, mark accepted, 204.

The seam `afterAcceptMembershipStep` (§11) lets AC-19 inject a fault after step
5's insert: the rollback leaves X added and the invitation pending.

### 3.5 `getTeamAvailability` (changed; spec §3.3-§3.5)

The members searched are the Paceday members (own credential, PAC-81 per-item
pool of 4, focus blocks, as today) **and** the added people, read only through
their adding owner's credential (§6). The fragment's description is binding on:
the owner-credential consequences (quota, audit trail, credential loss recorded
as the owner's, inference), the coverage rule (unreadable via PAC-133, personal
domain, own batch failure → unknown; unknown never free; busy blocks; unknown
does not block unless it has reported windows (below); an unreadable Paceday
member counts unknown but does not block),
and the counts. With the requester's own credential never used for an added
person, AC-13 and AC-29 follow.

**Blocking follows PAC-133 D-11** (contract 1.1, challenge M-4): busy windows the
provider reported for an address block a slot **even when that address is
unknown** (for example a Google `internalError` that still carries a 13:00-14:00
window: no offered slot overlaps 13:00-14:00). Only an unknown person with **no**
reported windows does not block. The counts are unaffected: such a person is
counted unknown on every slot, and an offered slot never overlaps a reported window.

`TeamSlot` gains `free_count`, `unknown_count`, `total_count` (all required).
Unknown is decided per member for the day, so `unknown_count` is the same on every
slot of one answer, and `free_count = total_count - unknown_count`. `quality_score`
keeps the Paceday members as divisor, so an existing score does not move when
people are added (pinned in its description).

## 4. Transactions and lock order (binding; spec D-8, PAC-25, PAC-120 style)

Every membership write is one transaction with this prefix, before any read its
decision rests on:

1. **Always one storage-owned transaction** (challenge m-1, the PAC-101 C-2
   rule behind `withLinkWriteTx`): storage begins it itself, with or without a
   session guard, so the team lock is never taken in autocommit and released at
   once. `fireGuardedCallHook`, then `RecheckSessionGeneration`
   (`storage/session.go:121`) as its first statement (stale → `ErrStaleSession` →
   requireAuth's 401). `WithSessionGeneration` alone is not enough: without a guard
   it runs the function straight on the pool (`session.go:158-163`).
2. `SELECT 1 FROM teams WHERE id = $1 FOR NO KEY UPDATE` (the PAC-25 lock; no row →
   the operation's "team gone" answer). No `lock_timeout` of its own, as PAC-25
   today; the request budget bounds the wait.
3. Seam `afterTeamLock(op, teamID)` (§11).
4. Every decision read: the owner/membership check, the Paceday-member and
   added-entry lookups, the carrier lookup, the invitation lookups, the cap count.
5. The writes. `COMMIT`.

The writes under this rule: `addTeamPerson`, `removeTeamPerson`,
`inviteTeamMember` (every outcome), `acceptTeamInvite` (upgrade, legacy create,
already-member), `removeManagerTeamMember` with `team_id`, and the existing PAC-25
`removeTeamMember` (unchanged: it already locks first; its pre-lock owner check is
not a decision about the target and is left as is). `acceptTeamInvite` reads the
invitation once before the lock only to learn its team; its decision re-reads it
under the lock (§3.4).

### 4.1 Orders this produces

| Race | Outcome |
|---|---|
| removal ∥ acceptance (both paths, AC-30) | serialised on the team row. Removal first: invitation gone, acceptance 404, nothing written. Acceptance first: 204, then the removal finds the membership by address and deletes it and the invitations. Every run ends with X absent and no invitation. |
| add ∥ add, one address (AC-24) | one 201, one 200 (existing entry). |
| add ∥ acceptance of X (AC-24) | add first: the acceptance upgrades (one entry). Acceptance first: the add finds a Paceday member, 422. One entry either way. |
| add ∥ add at 49 members (AC-23) | one 201, one 422 limit. |
| PAC-25 removal ∥ any of the above | serialised; the owner count is read under the lock, so a team always keeps an owner. |
| any write ∥ `deleteTeam` | the delete's row lock waits or is waited for; a writer that waits then finds no row (403 / 404). |

### 4.2 Deadlock analysis (reasoned, not observed)

Each writer holds, in order: its caller's `users` row `FOR KEY SHARE` (re-check),
then the team row `FOR NO KEY UPDATE`, then row locks on `team_members`,
`team_added_members`, `team_invites` of that team only, and FK `KEY SHARE`s on
`users` rows it inserts references to (the caller, or the accepter, who is the
caller). No writer takes a second team's lock or another account's row
exclusively. Account deletion takes its own `users` row `FOR UPDATE` and then
cascades into `teams` (creator) and `team_members`; it waits for a writer holding
`KEY SHARE` on that row, never the reverse, because no team writer waits for an
account row while holding the team lock except the KEY SHARE on an account it
already holds. Detection confirm inserts assignments (FK `KEY SHARE` on the team
row), which `NO KEY UPDATE` does not block. No cycle.

## 5. Manager mode (binding; spec §3.9, D-13)

### 5.1 Read-only added people in the team-scoped roster

`getManagerRoster` and `getManagerAnalytics` take `include_added` (default
false). With `true` and a `team_id`, a person added to the team for whom the

## 6. Provider batching (binding; spec §3.5, D-11, AC-14)

A team-path entry point on `FreeBusyService` (for example
`QueryForTeam(ctx, credentialOwnerID, emails, start, end)`) is used by
`FindSlots` and by the analytics path for added people. `Query` (used by
`POST /api/freebusy` and Manager analytics) is not changed by PAC-129.

- Batch size: **50** addresses for a Google credential, **20** for Microsoft.
- At most **3** batches in flight per request (a bounded group of its own,
  alongside the member pool of 4).
- Each batch: its own time limit of **5 s** (today's single-call limit), shortened
  to the budget left minus the PAC-81 stop margin (10 s).
- A batch that fails, or hits its own 5 s, makes **only its addresses** unknown.
- A batch not started because the budget reached the stop margin, or cut by a
  shortened deadline, is the budget error → the operation's **503**
  (`RequestBudgetExpired`), never a 200 that omits people.
- Unknown per address comes from PAC-133's readers (per-calendar errors,
  addresses missing from the answer). Personal domains are unknown without a call.
- **Caching (contract 1.1, challenge M-3, factory decision; PAC-133 §5 hands the
  decision to PAC-129).** The cache is the existing **process-wide** one: the
  team engine, and so its `FreeBusyService`, is built once in `newTeamHandlers`
  (`handlers_teams.go:33-35`) and lives for the process. The key is PAC-133's
  (the credential owner, the address, start and end); PAC-129 changes no key.
  - A batch the request budget prevents from starting, or cuts short, writes
    **nothing** to the cache. Otherwise a retry within 15 minutes would answer 200
    with those people unknown, the outcome the 503 exists to prevent.
  - A batch that fails on its own 5 s limit, or that the provider refuses (an
    error for the whole call), is cached as `unknown` for **15 minutes**. This is
    today's PAC-67 behaviour; `TestPAC67_TemporaryFailureLookupIsStillCached`
    (`engine/pac67_credentials_test.go:180`) stays pinned and unchanged.
  - A result computed while the owner's credential is recorded as lost is not
    cached (PAC-67 AC-20, unchanged).
  - Per-address unknown answers inside a successful batch (PAC-133's unreadable
    addresses) are cached as PAC-133 specifies.
- A refused renewal is recorded on the credential owner (PAC-67), by the token
  source built for that owner, never for the requester.

At the cap (49 added + owner) the worst case is 3 Microsoft batches (20+20+9) in
one round: a slow tenant costs one batch limit, not three.

## 13. Alternatives rejected

1. **Nullable `team_members.user_id` plus an `email` column.** Breaks the PK and
   every join; mixes the PAC-25 owner logic with rows that cannot be owners;
   makes "an address in both kinds" a data state rather than an impossibility.
2. **Added people inside `members`, with an `Accept`-header or `?v=2` switch.**
   A version switch on one operation is a second contract to keep; a new key is
   additive and ignored by the old web, which reads `members` unvalidated.
3. **A `kind` value added to `TeamMember` with `userId` nullable.** Changes a
   required field to nullable in a shape old clients read; breaks AC-8.
4. **Removal by an opaque person id.** An id would be the account id for one kind
   and a synthetic id for the other, which either leaks account existence or adds
   a column for nothing. The spec names the person by address (§3.8), which also
   makes "acceptance first" removable.
5. **Extending `removeTeamMember` to accept an address in `{userId}`.** A path
   parameter that is a UUID or an address depending on its shape is a
   wrong-request-made-possible.
6. **Keeping the bare `TeamInvite` as the 201 and a different body for the 200.**
   Two shapes for one operation; `already_member` has no invitation to return.
   One `TeamInviteResult` for both. (Revision 1 claimed backend tests read the
   top-level `token`; none do, §8.)
7. **409 for "already pending".** The spec makes it success-shaped (SF-012 fix
   option "200 or 409": 200 chosen).
8. **`source: "added"` always in the Manager roster.** Breaks the old web's strict
   zod parse (§5.1). The `include_added` flag mirrors the `members`/`people`
   split.
9. **Measuring added people in the Manager roster through the manager's
   credential without storing.** Possible, but the spec asks only for no stored
   figure and no signal; owners already get the figures in team analytics.
   Leaving the Manager rows unmeasured avoids a second read path with its own
   quota and cache behaviour.
10. **A list of unknown addresses in Find a time.** Widens what a member learns
    beyond the counts the owner accepted (§3.4).
11. **Batching inside `FreeBusyService.Query`.** Would change `POST /api/freebusy`
    and Manager analytics timing and 503 behaviour, which the spec does not ask
    for, and collide with PAC-133's edits to `Query`.
12. **A unique index using `expires_at > now()`.** Not expressible (`now()` is not
    immutable). Stored-status index plus sweep-before-insert instead (§2.2).

### BLOCKER

**P2-B1. `paceday_trim_ecma` removes the letter `v`, so migration 041 corrupts addresses and the CHECKs refuse valid ones.**

The cause is at `:96`: `E' \t\n\v\f\r'`. PostgreSQL escape strings have no `\v` escape. The documented escapes are `\b \f \n \r \t`, octal, hex and Unicode, and any other backslashed character stands for itself. `E'\v'` is therefore the letter `v`, and U+000B (VT) is missing from the set.

Observed on a throwaway postgres:16, with migrations 001-040 from main and 041 from §2.2. Enumerating `paceday_trim_ecma('a'||chr(c)) = 'a'` over the BMP gives exactly:

`9,10,12,13,32,118,160,5760,8192-8202,8232,8233,8239,8287,12288,65279`

118 is `v`, and 11 is absent. Consequences:

- `paceday_trim_ecma('victor@agency.gov')` returns `ictor@agency.go`.
- A legacy invitation `victor@agency.gov` is rewritten in place by the up step's UPDATE. Its token stays valid, but acceptance then answers 403 for good, because the address no longer matches.
- A legacy `Victor@Agency.gov` makes the up step abort. Trim-then-lower is not idempotent here: the trailing `v` is trimmed, then `v` is the leading character after lowercasing. The result was `ERROR: check constraint "team_invites_email_normalised" … is violated by some row`, so the deploy stops.
- After the migration, every write of a valid address that starts or ends with `v` violates a CHECK. Observed: `INSERT … team_invites … 'victor@agency.gov'` and `INSERT … team_added_members … 'dev@team.dev'` were both refused. Any address on a `.gov` or `.dev` domain, or any local part starting with `v`, would give 500 on invite and on add.

**Fix:** in the function, replace `\v` with `chr(11)`, keeping the rest of the E-string. Then add a test for AC-26 or the migration that asserts the trimmed set is exactly the ECMAScript set: the BMP enumeration above minus 118, plus 11.

### MAJOR

**P2-M1. The request normaliser and the storage normaliser trim different characters, so the decision reads and the write use different addresses.**

- §3.1 (`:237-238`) keeps `normalizeManagerEmail` on `strings.TrimSpace`.
- §2.2 has storage re-normalise with `trimECMA`, which strips U+FEFF.
- Observed with Go: the two sets differ in exactly U+0085 (TrimSpace only) and U+FEFF (ECMA only).
- `net/mail.ParseAddress` accepts `"pat@x.example﻿"` and `"﻿pat@x.example"`, and the parsed address equals the input. The normaliser therefore returns them with the BOM still there.

The T-add and T-invite decision reads (own address, Paceday member at the address, existing added entry, pending invitation) then compare the BOM form, while storage writes `pat@x.example`. Concretely, each of these breaks the "one kind per address" invariant of §2.1 or ends in an avoidable 500:

- With `pat@x.example` already added, `{"email":"pat@x.example﻿"}` misses step 6 and inserts. The result is a primary-key violation and a 500, not AC-4's 200.
- `inviteTeamMember` with M's address plus a BOM misses `already_member` and adds M as an added person. If a pending invitation exists, it misses `already_pending`, and the insert hits `team_invites_one_pending`, giving 500.

**Fix (contract text):** use one normal form, applied once, before every decision read. The address normaliser trims the union of the two sets (Unicode White_Space plus U+FEFF) before lowercasing and `ParseAddress`. Storage then trims with exactly that function, and `paceday_trim_ecma` covers the same union by adding `chr(133)`. Then state "the same character set" as a list of code points in §2.2, so both twins can be checked against the list.
