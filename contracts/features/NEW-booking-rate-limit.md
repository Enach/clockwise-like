## 2. The 429 body is the existing envelope with its message pinned

**Chosen**: `{"error":"rate limit exceeded"}`, schema `BookingRateLimitError`
with `error` constrained by `enum`. The spec (§3, AC-1) asks for "a JSON error
body of the same shape as the endpoints' other errors"; every booking error is
`{"error": string}` written by `writeError`. The message is the one the detect
limiter already sends (`handlers_sso.go:25`), so the backend has one rate-limit
sentence. Pinning it with an enum follows the PAC-21 `calendar not connected`
precedent: a client can branch on status alone, and a test can assert the body
exactly, without the contract permitting any other string.

**Rejected: a richer body** such as `{"error", "retry_after_seconds", "limit"}`.
It would duplicate the header, diverge from every other booking error (the web
error path reads only `error`), and the spec says the web must not show a server
string at all on 429 (AC-10, AC-11), so extra fields buy no consumer anything.
It would also make the booking 429 different from the detect 429 for no reason.

**Rejected: reusing `BookingError` unchanged.** It permits any string, so a
server that answered 429 with, say, the text of an internal error would conform.
"Prefer making the wrong response impossible to express."

## 3. `Retry-After` is a required, bounded integer, defined per operation

**Chosen**: two response components, each declaring `Retry-After` as
`required: true`, `type: integer`, `minimum: 1`, `maximum` equal to the window
(600 for booking, 60 for slots). AC-1 demands "a positive integer number of
seconds no greater than the time remaining in that client's window (rounded up,
at least 1)"; the bounds make a zero, negative, HTTP-date or longer-than-window
value non-conforming in the contract itself, not only in a unit test.

**Rejected: one shared `RateLimited` response for both operations.** It could not
state the right bound or the right limit for each, so its description would be
vague exactly where the spec needs precision (AC-9: "the limits ... are stated
in the operations' descriptions"), and its `maximum` would have to be 600 for
both, letting the slot listing claim a 10-minute wait.

**Rejected: a shared `components/headers` entry.** Same problem: one schema, one
bound. Inlining the header in each response costs six lines and keeps each
bound truthful.

The header is not exposed to cross-origin pages (no
`Access-Control-Expose-Headers`, `middleware.go:61-85`). The spec keeps CORS
unchanged (§5); the response descriptions say so, so a future consumer that
wants the value knows it must also change CORS.

## 4. Ordering: the limit is the first thing the handler does

The descriptions say the limit is checked and counted atomically before the link
lookup, before the body is read and before any validation. This is spec D-4 and
D-8 transcribed, and it has a consequence the contract must state: **429 takes
precedence over every other status on these operations**, including 404 for an
unknown slug (AC-5) and 410 for an exhausted link. A client therefore cannot use
the limiter to probe whether a slug exists once it is over the limit, and a
probing client spends its budget on unknown slugs.

For the slot listing the same ordering is stated, so "every request counts"
(spec §3) holds for invalid `date`/`duration` queries too (AC-7: "with or
without a date").

**Rejected: limiting only requests that would otherwise succeed (or only 201s).**
D-4: counting only successes lets probing and 409 conflict-spam run unbounded,
and checking after the lookup would let the 404/200 difference leak for free.

**Rejected: putting the limit in route middleware and saying so.** Where the
check lives is the plan's choice; the contract states the observable order only.

## 5. What the contract says about identification and scope

Client identification is transcribed from PAC-39 (`ratelimit_detect.go:12-18`,
`:94-114`) and the auth fragment's detect 429 wording, and pinned to one exact
address with no IPv6 prefix grouping (spec D-7). The descriptions also state:
counting is per client across all links (D-3); the two budgets are independent
(AC-6); counts are per process, so N per replica, and a restart clears them
(spec §5, §7, API-062 residue); expired clients are swept on a request at most
once per window (AC-8, the PAC-39 pattern); CORS preflight is not counted,
because `corsMiddleware` answers `OPTIONS` before routing (`middleware.go:79-82`).

Not stated, deliberately: whether the e2e stack may raise the limits (spec Q1).
The contract documents the production values. If the plan adds a test-only
override, it is operator configuration on the e2e compose, not part of the HTTP
interface, and the plan must keep production at 20/10 min and 120/1 min (spec
Q1: "must not lower them in production to suit tests"). A challenger who thinks
the override must appear in the contract should say so.

### Contract/implementation divergences

The only divergence that blocks is blocking item 1. Two others are imprecise but do not block:

1. **`"end must be after start"` is listed as a 400 message the handler "already
   returns", but in practice it never fires.** It can only fire when a
   `time.Duration` overflows.
   - Every path that reaches `handlers_booking.go:285` has already passed
     `durationAllowed` (`:278`), which requires a positive duration.
   - When `end` is given, `int(end.Sub(start).Minutes()) > 0` implies
     `end > start`.
   - When `end` is omitted, `end = start + n min`, which is after `start`
     unless `n * time.Minute` overflows. That needs a link duration option above
     about 153,722,867 minutes.
   - `validateSchedulingLink` only requires each option to be `> 0`
     (`handlers_scheduling_links.go:219-222`), so such a link can exist.

   Documenting the message is therefore literally true. The rationale should
   still say it is practically unreachable, so the plan does not write a test
   that expects it from a plain inverted `end`. That request answers
   `"invalid duration"`.
2. **"Written to every host's calendar" overstates what `ConfirmBooking` does**
   (`engine/booking.go:241-271`). It loops over accepted hosts only. It skips a
   host whose user record or calendar client cannot be loaded, and it ignores a
   `CreateEvent` failure. The booking row and the 201 are written either way.
   Suggested wording: "written to each accepted host's connected calendar
   (failures are skipped; the 201 does not depend on them)". This does not
   affect the rate-limit shape.
