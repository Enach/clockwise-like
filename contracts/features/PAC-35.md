## 2. The failure state is a redirect to `/?error=auth_failed`

The spec requires a sign-in that did not produce a session to land "back in the
app on a visible sign-in failure state" (§3, AC-1..AC-5, D-2), never on
`/auth/callback`.

**Chosen: `302` to `<FRONTEND_URL>/?error=auth_failed`, with no `auth_token`
cookie.** This is the URL the web app's completion page already navigates to
on its own failure branch (`smart-calendar-flow/src/pages/AuthCallback.tsx:25`).
So the server-side failure (AC-1..AC-4) and the client-side second line of
defence (AC-6) reach one state, and the web change is one reader for one URL.
The value is a fixed literal. It carries no provider, cause or code. The cause
goes to the server log and Sentry only (spec D-2, PAC-21's rule). The
documented status stays `302`, so the two outcomes of a callback differ only in
`Location` and in whether the cookie is set. That is what a browser navigation
can observe.

On the failure path the server neither sets nor expires `auth_token`. If the
browser already held a session for some account, it keeps it. Clearing it would
be a behaviour the spec does not ask for, and it would log a user out because a
*different* sign-in attempt failed.

Rejected:

- **Keep a non-redirect error (5xx JSON on the API origin).** This is today's
  Microsoft behaviour, and the spec names it as the defect (§2.2): a raw JSON
  page on the API origin with no way back into the app.
- **`/auth/callback?error=…`.** The spec says the user is "not sent to the
  sign-in completion page" (AC-1). That page also has a success path that
  re-reads the session, and reusing it would make a stale cookie look like
  success.
- **A dedicated `/auth/error` route.** D-2 says no new page is required. A
  second URL would also split the server-side and client-side failure states
  that AC-5/AC-6 require to be the same.
- **A cause code in the URL (`?error=session_unavailable`, etc.).** The spec
  forbids showing server detail, and a code nobody displays is an information
  leak with no reader.

What is **not** redirected (spec D-1, OQ-1): state mismatch, token exchange
failure, Google userinfo failure, token save failure, OIDC setup or exchange
failure, the PAC-45 domain mismatch, and an unconfigured Microsoft client keep
their current non-302 responses. The Microsoft `302` description lists them by
name, so a reader does not assume every failure redirects.

## 3. `login_hint`: one shared parameter, a plain string, never a 400

**Chosen: `components.parameters.LoginHint`, `type: string` with no `format`,
referenced by all three start routes.** The description carries the forwarding
rule: at most 254 characters, exactly one `@`, and `net/mail.ParseAddress`
accepts it with an empty display name and an `Address` equal to the whole
value; since revision 2 also a local part limited to `[A-Za-z0-9._+-]`
(revision 3 adds the apostrophe: `[A-Za-z0-9._+'-]`) and a
domain that is a DNS hostname (two or more LDH labels, the last containing a
letter, no IP literal). A value that fails is dropped and the redirect still
happens. See "Revision 2" below for why the first rule was not enough.

Why a plain string, given the factory's "make the wrong request impossible to
express" rule: AC-10 requires that a malformed hint does **not** stop sign-in.
`format: email` (the old schema) invites a request validator or a generated
wrapper to answer 400. That would turn a convenience field into a way to break
sign-in. So the contract states the rule in prose, and the plan pins it in Go
(AC-10). The rule is stated in terms of a standard-library function so the
test and the implementation cannot disagree on what "a valid email" means.

Forwarding goes through the OAuth library's URL builder, so the value is
URL-encoded and cannot add a parameter to the provider request. No other query
parameter of the start request is copied. Both facts are in each `Location`
description, because AC-10 asserts them.

**The SSO hint must belong to `{domain}` (spec D-10, added at this stage).**
Challenge round 1 non-blocking 6 left this to the contract. A hint at another
domain is dropped. The test is the one the PAC-45 callback check already uses
(`domain.EmailBelongsToDomain`: exact, case-insensitive, no subdomains). This
sends one organisation's IdP no address from outside that organisation. It
costs nothing, because the web app only reaches `/api/auth/sso/{domain}` from
a detection on the same email.

Rejected:

- **`format: email` and a 400 on a bad hint.** Breaks AC-10, as above.
- **Three inline parameter copies.** That is today's shape. The Microsoft copy
  had already drifted to a one-line "ignored" note. One component means one
  rule.
- **The detection answer carries the hint** (spec OQ-3, the other option). The
  server would build `redirect_url` with `?login_hint=<email>`. Rejected for
  three reasons. Detection is anonymous and rate limited, and echoing the
  submitted email back in it adds nothing the client does not already hold.
  `redirect_url` would stop being a fixed per-domain path. And the web app
  would then have two hint mechanisms: it appends the hint itself for Google
  and Microsoft (`AuthDialog.tsx:104`, `:108`). Chosen instead: the client
  appends `?login_hint=` to `redirect_url` exactly as it does for the other two
  routes.

The hint is advisory (spec D-4). The parameter description says it never
selects, creates or links an account. §6 of the spec keeps the PAC-45 identity
check, and AC-8/9 only assert what reaches the provider.

## 4. SSO detection: no schema change

`SsoDetectResponse` keeps `{type, provider_name?, redirect_url?}` (API-010).
The defect is on the client, which reads a `domain` field the server never
sent. The contract describes what is (README §7 rule 2). `redirect_url` is
already the destination, so the fix is for the client to follow it. The
description now says three things: the path is on the API origin (AC-7, spec
challenge round 1 non-blocking 1); the domain segment is lowercased and not
URL-escaped; and there is no `domain` field.

Rejected:

- **Add `domain` to the answer so the current client code works.** That makes
  two sources of truth for one destination, and it fixes a client bug by
  growing the server. The client still has to build a URL from it, which is
  the error-prone step AC-7 is about.
- **Make `redirect_url` absolute (`APP_URL` + path).** This is a server
  behaviour change the spec does not ask for. `APP_URL` is also the callback
  base, not necessarily the origin the browser uses for the API. The client
  already knows its API base.
- **A `pattern` on `redirect_url`.** The domain segment is whatever domain the
  admin stored, unescaped. A pattern stricter than the code would make the
  contract lie for an odd stored domain. That is API-060 / PAC-22's territory.

## 5. Disconnect: 409 `CalendarDisconnectUnsupported` for Outlook and webcal

Spec D-8 (revision 3) constrains the "not performed" answer. It must delete
nothing. The web client must classify it as a **failure**, neither as success
nor as "server unreachable". And (challenge round 4, non-blocking 3) the app
must be able to tell it apart from other failures, so it can say "not available
yet" rather than "Failed to disconnect".

**Chosen: `409` with `{error, provider}`, `additionalProperties: false`.**

- `requestApi` throws `ApiHttpError` for any non-2xx
  (`smart-calendar-flow/src/api/client.ts:400-407`). So a 409 is a failure,
  never a success. `withFallback` rethrows it and does not switch to preview
  data (`:491-503`).
- This operation returns no other 409, so status alone identifies it. The
  generic `401` (middleware) and `500` stay distinguishable.
- 409 fits the meaning: the request conflicts with the state of the resource,
  here the caller's calendar provider.
- `error` is a fixed, true sentence ("disconnecting this kind of calendar is
  not available yet"). A client that only shows `data.error`
  (`apiErrorMessage`, `client.ts:351-356`) therefore still shows something true
  before the web change lands. `provider` (`outlook` | `webcal`) lets the app
  name the kind of calendar.

The Google split follows `getAuthStatus`'s rule: blank or unrecognised means
Google (spec D-8 revision 3). The one place disconnect does **not** follow
`getAuthStatus` is a settings read failure. Status answers "google" there, but
disconnect answers `500` and deletes nothing (spec **D-9**, added at this stage
from challenge round 4 non-blocking 1). Following the status fallback would let
a transient read error delete an Outlook or webcal user's Google credential,
which D-8 exists to prevent.

Rejected:

- **`204` and do nothing.** The client shows "Disconnected" over a
  still-connected calendar, which spec §3 forbids.
- **`200` with `{performed: false}`.** The client classifies it as success, so
  both surfaces toast. This was challenge round 3 blocking 1.
- **`200`/`202` with no JSON content type.** `requestApi` throws
  `ApiUnreachableError` (`client.ts:414-415`), and the session falls into
  preview data with a mock disconnect.
- **`501 Not Implemented`.** It is honest about the cause, but it is a 5xx:
  `apiErrorMessage` maps it to "The server had a problem", and a 5xx reads as a
  server fault in logs and Sentry. The user did nothing wrong and the server
  did not fail.
- **`422`.** Nothing about the request is invalid. There is no body.
- **`403`.** It reads as a permission problem, and the client maps 403 to
  "You don't have permission".
- **Reuse `ErrorResponse`.** It is a shared component that is structurally
  identical everywhere, with `additionalProperties: false`. It cannot carry
  `provider` without changing every operation that uses it.

The Google path is unchanged apart from the cookie: the token row is deleted
and Google Meet turns not connected, as today (spec §6). The `204` is still
answered when there was no row.

## 6. Logout: 204

Spec AC-12 needs a response with no body that the strict client classifies as
success. `requestApi` returns `undefined` on 204 before any content-type check
(`client.ts:409`). The lenient `apiFetch` does the same (`src/lib/api.ts:93`).
`200` with no Content-Type passes `apiFetch` but not `requestApi` (API-063).

Rejected: **`200` with `application/json` `{}`.** It works for both clients,
but it invents a body that carries nothing, and the spec says "with no body".
Logout with an expired session stays a `401` (spec §5).

## 7. The user's picture and the login provider

**Picture (spec OQ-6, owner: contract-author): keep `avatarUrl`.** This is
the server's current name, so the change is web-only and the backend and web
deploy in any order (spec §7). A rename would couple the two deploys, as
PAC-24's did, for no gain. The description now also records something the old
text did not say: every sign-in overwrites the picture, and Microsoft and SSO
write `""`. So a Microsoft sign-in clears a picture an earlier Google sign-in
stored. That is current behaviour, not changed here. A follow-up is listed in
the manifest.

Rejected: **rename to `avatar`** (the web's current spelling). That changes the
server to match a client bug, and it couples the deploys.

**`provider` (U-13, x-uncertain resolved).** Determined by reading, not by
deleting the marker:

- `users.provider` is `TEXT NOT NULL DEFAULT 'google'` with no CHECK
  (`backend/storage/migrations/006_auth.up.sql:8`).
- Its only writer is `storage.UpsertUser` (`backend/storage/users.go:21`). No
  `UPDATE users` touches it (`orgs.go:36` only sets `org_id`).
- Every call site of `UpsertUser` in the repository's history
  (`git log -p -S'UpsertUser('`) passes `"google"`, `"microsoft"` or `"sso"`.
  The e2e seed inserts `'google'` (`e2e/seed/seed.sql:70-76`).

So the value set is closed: `enum: [google, microsoft, sso]`. The description
also states what the code does: `ON CONFLICT` does not update `provider`, so it
is the provider of the **first** sign-in.

Rejected: **also add a CHECK constraint** (the audit's U-13 suggestion). Spec
§7 says no migration, and a CHECK is a schema change with its own rollback. It
is listed as a follow-up.

### Requests wrongly permitted

1. **`GET /api/auth/google?login_hint=alice%40acme.com%26prompt%3Dnone`**
   (decoded hint `alice@acme.com&prompt=none`) — the LoginHint rule
   (`auth.yaml:798-808`) **forwards** it, while spec AC-10 says a hint "not a
   valid email address (including one carrying extra URL parameters)" gets
   "no hint forwarded". The rule is: ≤254 chars, one `@`, `net/mail.ParseAddress`
   returns empty Name and `Address == value`. RFC 5322 `atext` includes `& = ? # /`,
   so `ParseAddress` accepts all of these. I ran the rule as written (Go 1.25.5,
   `net/mail`) and got:

   | hint | rule result |
   |---|---|
   | `alice@acme.com&prompt=none` | **forwarded** |
   | `alice@acme.com&prompt=consent&redirect_uri=x` | **forwarded** |
   | `alice&prompt=none@acme.com` | **forwarded** |
   | `alice@acme.com?x=y` | **forwarded** |
   | `alice@acme.com#frag` | **forwarded** |
   | `alice@[127.0.0.1]`, `alice@localhost`, `alice@acme` | forwarded |
   | `"a b"@acme.com`, `alice@acme.com ` (trailing space), empty | dropped |

   URL-encoding does stop the extra text from becoming a *separate* provider
   parameter, so AC-10's second clause holds. Its first clause ("no hint
   forwarded") does not: Google and Microsoft receive
   `login_hint=alice%40acme.com%26prompt%3Dnone`. A test written straight from
   AC-10 with that input fails against an implementation that follows the
   contract exactly. So the contract and the spec contradict each other on the
   exact input AC-10 names. (`startSsoLogin` drops these values anyway, because
   D-10's `EmailBelongsToDomain` sees the domain `acme.com&prompt=none`. Google
   and Microsoft have no such second check.)
   **Fix (contract shape only):** tighten the LoginHint rule in
   `components.parameters.LoginHint.description` (and repeat it in the manifest's
   `schemasChanged` line). Keep the schema a plain `string` with no `pattern`,
   so the request is still never a 400. Add two conditions on top of the current
   three: (a) the local part uses only `[A-Za-z0-9._+-]`; (b) the domain is a DNS
   hostname: two or more dot-separated labels, each
   `[A-Za-z0-9]([A-Za-z0-9-]*[A-Za-z0-9])?`, with no IP literal. Each value in
   the table marked forwarded except `alice@acme.com` is then dropped. That is
   conservative: a dropped hint costs the user only a prefill (D-4), and the
   web's zod `.email()` check already refuses these values before sending. Also
   name `alice@acme.com&prompt=none` as an AC-10 example in the description, so
   the plan's test uses it.

The challenger is right: RFC 5322 `atext` includes `& = ? # /`, so

`components.parameters.LoginHint.description` (fragment

states five conditions, all required:

1. at most 254 characters;
2. exactly one `@`;

4. the local part uses only `A-Z a-z 0-9 . _ + -`;
5. the domain is a DNS hostname: two or more dot-separated labels, each
   `[A-Za-z0-9]([A-Za-z0-9-]*[A-Za-z0-9])?`, the last containing at least one

the challenger worded them still accept `alice@127.0.0.1`: four all-digit
labels are valid LDH labels, and `ParseAddress` accepts the dotted quad
without brackets. Requiring a letter in the last label is the cheapest way to
say "no IP literal" for both the bracketed and the bare form.
