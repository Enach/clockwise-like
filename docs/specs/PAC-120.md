## 0. The ticket's premise, corrected

The ticket has two halves. **The first half is already built.** The ticket and PAC-112 spec §2.2 both say no API request body is size-limited (PAC-112 spec `:119`, `:364`). That has been false since PAC-81 Part A (`48f6c60`, #247) and Part B:

- the backend refuses any request body over 1 MiB with 413 `{"error":"request body too large"}`, before any handler, on every route (`backend/api/middleware.go:365-397`, wired at `backend/api/routes.go:39`);
- nginx refuses the same bodies with the same JSON bytes (`nginx/nginx.conf:77-78`, `:121-130`);
- the contract states the rule once for every operation (`openapi.yaml:40-41`);
- the web already renders a 413 (PAC-83, §2.7).

PAC-112's claim was probably drawn from a grep for `http.MaxBytesReader`, which the cap does not use: it reads through `io.LimitReader`.

So this spec does **not** propose a new body limit. For the first half it asks only for what is missing: a proof that the cap is wired on the real route chain (§2.4 shows that no backend test proves it), and a record that the PAC-112 claim is wrong. **The second half, the co-host cap on the single invitation, is real and is the substance of this spec.**

The ticket's "around `:840-870`" for the invitation handler has drifted. It is now `handlers_scheduling_links.go:904-957`.

## 1. Problem

**Co-hosts.** A link's co-hosts are the people whose calendars decide its free slots. PAC-112 gave the link editor a limit of 5 co-hosts, and the server enforces it on the complete list that create and edit send. A second way in has no limit: the operation that invites one person at a time. Any API caller (a script, an old web build, a future client) can call it repeatedly and give a link 6, 20 or 500 co-hosts.

What that costs:
- **Every slot read grows with the host count.** Each public slot request reads every accepted host's calendar (PAC-25, PAC-112 §3.3). A link with hundreds of hosts makes the public booking page slow for every booker, and spends the owner's and co-hosts' provider quotas.
- **The editor cannot show such a link honestly.** It shows "n/5 co-hosts" and refuses to add past 5, but a link built through the other door can already be past 5. PAC-112 had to add a special case so such links could at least be pruned (D-8, AC-32, AC-33).
- **The limit is only as strong as its weakest door.** The PAC-112 cap bounds the invitation lookups that one save does under the link's lock. Repeated single invitations do the same lookups, without a bound.

**Body size.** As §0 says, the body cap exists in both layers. The remaining risk is a silent regression: e2e runs through nginx, so if the backend's wiring were removed, e2e would still see nginx's identical 413 and stay green. Only a direct-to-backend caller would notice, in production.

## 2. Current behaviour

### 2.1 The body cap (PAC-81)

**Backend.** `bodyCapMiddleware(maxRequestBody)` with `maxRequestBody = 1 << 20` (`middleware.go:365-367`):
- a declared `Content-Length` over the cap is 413 without reading (`:377-380`);
- otherwise it reads at most cap+1 bytes through `io.LimitReader` (`:381-382`). More than the cap is 413 (`:383-386`). A read error is 400 `"invalid request body"` (`:387-390`);
- a body of exactly the cap is passed on. The handler gets an in-memory copy (`:391-392`), so it sees the whole body or never runs;
- the 413 is `writeError` (`backend/api/handlers_settings.go:479-483`): `Content-Type: application/json`, body `{"error":"request body too large"}\n`. That is the PAC-21 error envelope.

**Where it sits.** `RegisterRoutes` applies, outer to inner (`routes.go:26-40`):
1. `sentryMiddleware`;
2. `loggingMiddleware`;
3. `corsMiddleware`;
4. `bodyCapMiddleware`;
5. `budget.Middleware` (the 90 s handler budget);
6. then, per group, `requireAuth`, which installs the PAC-71 `guardedResponseWriter` (`middleware.go:85-232`).

Consequences of that order, all true today:
- **CORS headers are on the 413.** `corsMiddleware` sets them before calling the next handler (`middleware.go:234-258`), so a browser can read the 413.
- **The access log records 413**, since logging is outside the cap (PAC-81 AC-A13).
- **413 comes before authentication.** An oversized body to a protected route without a session gets 413, not 401. The guarded writer never exists for that request, so a PAC-71 re-check cannot replace the 413.
- **413 comes before every handler check**: before a 404 for a deleted link, before a 403, before an `Idempotency-Key` 400.
- **Reading the body is outside the 90 s budget.** It is bounded by the server's read timeout of 30 s (`backend/internal/lifecycle/lifecycle.go:207`).
- It applies to every method, GET and DELETE included.

**nginx** (production and the e2e stack):
- `client_max_body_size 1m` at server level (`nginx.conf:77-78`);
- under `/api/`, `error_page 413` goes to a named location that answers the backend's exact JSON bytes (`:121-130`). nginx answers it **without contacting the backend**. That is pinned by `TestOversizedAPIBodyIsJSON413` (`nginx/test/nginx_test.go:434-459`) and by e2e `edge.spec.ts:85-98`;
- in production, therefore, **nginx answers every oversized `/api/` body**, and the backend's cap is defence in depth: it covers direct callers such as the dev compose's port 8080, and a misconfigured proxy;
- `/mcp/` inherits the server-level 1 MiB but has no `error_page`, so its 413 is nginx's HTML page (`nginx.conf:132-150`). The MCP server itself has no body cap (`mcp/main.go:121-138`). See OQ-6;
- the operator's outer TLS proxy doc says nothing about body size (`docs/operator/proxy.md`). An outer proxy with a smaller limit would answer first, in its own format.

**The contract** states the rule once, in `info.description` (`openapi.yaml:40-41`: "A request body over 1 MiB is refused with 413 … by the backend and by nginx alike"). No operation lists a 413 response of its own.

**Not related**: the outbound limits (`backend/internal/outbound/outbound.go:102-115`, `ReadLimited`; the webcal ICS fetch at 10 MiB, `outbound.go:42`, used at `backend/calendar/webcal_client.go:77`; the JWKS read at `backend/auth/ms_idtoken.go:483`, the only `http.MaxBytesReader` in the backend). These bound responses Paceday reads from other servers, not requests it receives.

### 2.3 How large legitimate bodies are

PAC-81's contract review already found that no operation accepts a body near 1 MiB (`contracts/features/PAC-81-part-a.md:391-392`). Re-checked here:
- **Settings PATCH**: a flat object plus working-hours and lunch-break arrays. A few KB at most.
- **Habits**: one habit's fields.
- **Event create and PATCH with attendees**: an attendee list of e-mail addresses. Even 500 attendees is under 30 KB.
- **NLP input**: one text field with no length check (`handlers_nlp.go:21-23`). The editor sends one sentence.
- **Scheduling-link create and PATCH**: fields plus a co-host list. The list's length has no schema bound (`openapi.yaml:11141`, `:16382`: "`maxItems` is deliberately not set"), and the server's over-5 rule refuses long lists that add someone (§2.6).
- **Public booking**: name, e-mail, times and free-text notes, none length-checked (`handlers_booking.go:362-380`).
- **Org AI and SSO admin**: configuration objects, a few KB.

So 1 MiB is far above every legitimate body, and no route needs a larger limit. Several free-text fields have no length cap of their own, so the body cap is their only bound (§5, OQ-7).

### 2.5 The single invitation today

`POST /api/scheduling-links/{id}/hosts` → `inviteHost` (`handlers_scheduling_links.go:904-957`), in order:
1. A malformed id is 400 `"invalid id"` (`:907-911`).
2. Reads the link (`GetSchedulingLinkByID`, which does not find a deleted link). A read error is 500 (`:912-916`). No link is 404 `"not found"` (`:917-920`).
3. Someone other than the owner is 403 `"forbidden"` (`:921-924`).
4. Decodes `{"email"}`. Invalid JSON or a blank e-mail is 400 `"email is required"` (`:925-931`).
5. Resolves the address with `storage.ConfirmedHolder` (`backend/storage/identity.go:160`): exactly one account holding it domain-confirmed, ignoring case (PAC-71). **No holder and a storage error both answer 404 `"user not found"`** (`:934-937`). That is SF-068, and it contradicts the contract's 500 (Inherited scope).
6. Writes through `storage.InviteLinkHostCtx` (`backend/storage/guarded_writes.go:162-172`):
   - `withLinkWriteTx` (`backend/storage/session.go:175-195`): the PAC-71 generation re-check when a session guard is present, then the 10 s lock bound (`setLinkLockTimeout`, `scheduling_links.go:507-511`; `LinkLockTimeout`, `:498`);
   - `inviteLinkHostLocked` (`scheduling_links.go:813-822`): `lockLiveLinkForShare` (`:520-528`, `SELECT 1 … WHERE id = $1 AND deleted_at IS NULL FOR SHARE`), then `InviteLinkHost` (`:293-314`);
   - `InviteLinkHost` inserts a `pending` row with `ON CONFLICT (link_id, user_id) DO NOTHING`. With no row returned, it reads the existing row and reports `created = false` (PAC-61).
7. Answers: `ErrLinkGone` is 404 `"not found"` (`:942-947`); another error is 500 `"invite failed"` through `writeServerError` (`:948-951`); otherwise 201 with the new row or 200 with the existing row unchanged (`:952-956`).

**Nothing counts the link's hosts.** No limit applies at any step.

Two more facts this spec depends on:
- **Re-inviting is never an add.** An existing host of any status, the owner included, gets 200 and an unchanged row. The owner's own address resolves to the owner, whose row already exists, so the owner gets their own row back with 200.
- **The lock does not order two invitations against each other.** `FOR SHARE` "conflicts with the delete's FOR NO KEY UPDATE … and not with another FOR SHARE" (comment, `scheduling_links.go:513-519`). Two invitations on one link run concurrently. A PATCH takes the link's row lock through its `UPDATE` (`:197`), which does conflict with `FOR SHARE`, so a PATCH and an invitation are ordered. A booking save also locks the link `FOR SHARE` (`scheduling_links.go:530-543`). **A count read under today's lock is therefore racy between invitations**: two invitations on a link with 4 co-hosts could both see 4 and both insert.

**Host rows and statuses.** A host row is `pending`, `accepted` or `declined`. Declining keeps the row (`RespondToHostInvite`, `scheduling_links.go:434-449`). Leaving and removal delete it. The editor's chips are every non-owner host of the strict read, declined included (smart-calendar-flow `src/components/links/LinkEditDrawer.tsx:207-208`, `:242`). Its add cap counts those chips (`:524`, "You can invite up to 5 co-hosts.", `src/components/links/coHostSave.ts:15`; counter "n/5 co-hosts", `LinkEditDrawer.tsx:866`).

**Contract** (`contracts/openapi/paths/booking.yaml:1582-1673`): 200, 201, 400, 401, 403, two 404 bodies (API-072), and a 500 that covers "Lookup or invite failed, or the lock on the link was not obtained within 10 seconds". It names no limit and no 422.

### 2.6 The PAC-112 over-5 rule, and whether it can be reused

`setCoHostList` (`scheduling_links.go:1257-1331`) applies to the complete list on create and PATCH:
- it reads the host set H inside the write's transaction (`readLinkHostSet`, `:1185-1206`, every host row of any status);
- `limited := len(entries) > CoHostListLimit` (`:1270`; `CoHostListLimit = 5`, `:1143`);
- each distinct address is looked up once. When `limited`, the first one that reaches no current host (the owner counts) fails the save with `ErrCoHostListTooLong` (`:1281-1283`; "reaches", `lookupCoHost`, `:1349-1357`);
- the handlers answer 422 with `coHostListTooLongMsg` (create `:549-552`, PATCH `:821-824`; text at `:409`).

**The rule is about the length of a list, not the size of a link.** It answers "may this list add someone?". A single invitation carries no list. What carries over is the **intent**: no save may take a link past 5 co-hosts by adding someone, while saves that only keep or remove are always allowed. For the list path, that falls out of list semantics: the list is the complete set, so a list of 5 or fewer that adds someone leaves at most 5 co-hosts. There is one edge case. The PAC-71 keep rule keeps every account carrying a listed address, so two accounts sharing one address could leave 6 (§5).

For the single invitation, the same intent reads: **an invitation that would add a host row is refused when the link already has 5 co-hosts or more.** The code itself (`setCoHostList`, `CoHostListLimit`, the 422 text) cannot be reused unchanged: the text talks about a list, and the lock is different (§2.5). The constant 5 and the "decided inside the write's transaction, against the host set read there" discipline can be.

The PATCH's lock order is: the guarded `UPDATE` first, as the transaction's first lock on the link, "never FOR SHARE first and an upgrade after, which would let two PATCHes deadlock" (`scheduling_links.go:843-849`). Whatever lock orders invitations against each other must not bring that deadlock back (AC-10).

## 3. Desired behaviour

### 3.1 Body size

1. **Unchanged rule** [F, D-1]: every API request body over 1 MiB is refused with 413 and the JSON error body, before anything else, by both layers. No route gets a larger or smaller limit (OQ-5).
2. **The backend's own refusal is proven through its real route chain**, on a public route and on a protected one, so removing it fails a backend test even though nginx would hide it in e2e.
3. The proof covers what the order guarantees today:
   - the 413 carries the CORS headers for an allowed origin;
   - on a protected route, an oversized body without a session gets 413, not 401;
   - the handler never runs;
   - a body of exactly 1 MiB reaches the handler.
4. The record is corrected. The defect register shows that the body-size claim in PAC-112 spec §2.2 and §5 is wrong, and points to PAC-81.

### 3.2 Co-hosts per link on the single invitation

1. **The cap** [F, D-2]. An invitation that would add a new host to a link is refused when the link already has **5 or more co-hosts**. Nothing is written. A co-host is any host of the link other than its owner, whatever their status: pending, accepted or declined [OQ-1].
2. **What is never refused by the cap**:
   - re-inviting someone who is already a host, at any count: the existing answer, their row unchanged (PAC-61);
   - the owner inviting their own address: the existing answer, the owner's row unchanged;
   - removing, leaving, accepting and declining, at any count.
3. **Links already above 5** keep their co-hosts. Their owner can remove people, by the editor's list (PAC-112 AC-32) or by any other existing means. They can invite again once the link has 4 or fewer.
4. **The refusal** [F, D-4]:
   - its status is 422 [OQ-2];
   - its message is distinct from every other answer of this operation, and from the list's over-5 message;
   - the message says the link already has the maximum number of co-hosts and that one must be removed before inviting another. It reads as a limit on the link, not on the request;
   - it reveals nothing about the invitee beyond what a 201 would have revealed. It is only given for an address that resolves to an invitable account.
5. **Where it sits among the existing answers** [F, D-4]. The invalid id 400, the link read, the 404 and 403, the body 400, the PAC-71 resolution ("user not found") and the 500 for a failed lookup all come first and are unchanged, except for item 7. The cap is decided after them, in the write.
6. **Decided at the write, never before it** [F, D-3]:
   - the count is taken inside the write's transaction, after the link is locked, as PAC-112 decides its rule (P3-m1);
   - concurrent writes that add hosts to one link are ordered so that, together, they never take the link past 5. Two simultaneous invitations on a link with 4 co-hosts give exactly one success and one refusal. An invitation running alongside a list save never leaves more than 5 either. Today's lock does not order invitations against each other (§2.5), so this is new;
   - the PAC-101 guarantees stay: a link deleted meanwhile is the 404 "not found" with nothing written; a lock wait over 10 s is the 500 with nothing written; no deadlock with PATCH, delete, booking, accept, decline or leave.
7. **A failed lookup is a server error, not "user not found"** [F, D-5; OQ-4; SF-068]. When resolving the address fails because of a storage error, the answer is the operation's documented 500 with nothing written. "User not found" stays the answer only for an address no single account holds domain-confirmed.
8. **The session guard still wins.** A session whose generation moved gets requireAuth's 401 instead of the refusal, as for every other answer of this operation (PAC-71).
9. **Nothing else changes for clients.** The editor never calls this operation, and MCP has no tool for it, so neither needs a change. The link editor's own limit of 5 stays as it is.

## 4. Acceptance criteria

"Co-hosts" means non-owner host rows of the link, any status (OQ-1). "Invitable" means an address held domain-confirmed by exactly one account (PAC-71). Each AC names its layer: `[unit]` = backend Go tests (handler or storage, with Postgres), `[contract]` = the OpenAPI fragment and bundle, `[e2e]` = Playwright against the compose stack.

**Body size**

AC-1. Given the backend's production route chain (`RegisterRoutes`, no nginx), when a protected route receives a POST whose body is 1 MiB + 1 byte, with no session and an allowed `Origin`, then the answer is 413 with `Content-Type: application/json` and body exactly `{"error":"request body too large"}` plus a newline. It carries `Access-Control-Allow-Origin` for that origin and is not 401, and the handler did not run. The same route given exactly 1 MiB and a valid session does not answer 413. *Regression guard: passes today, fails if the backend's cap is unwired.* [unit]

AC-2. Given the same chain, when the public booking route receives a POST of 1 MiB + 1 byte for a live link's slug, then the answer is the same 413 and no booking row exists for that link afterwards. *Regression guard.* [unit]

**Co-host cap on the single invitation**

AC-3. Given a link whose owner is accepted and which has exactly 5 co-hosts (2 pending, 2 accepted, 1 declined), when the owner invites a sixth, invitable address, then the answer is 422 with the new refusal message (distinct from `coHostListTooLongMsg` and from every other body of this operation). The link's host rows (users and statuses) are identical before and after. *Fails today: 201.* [unit]

AC-4. Given a link with 4 co-hosts, when the owner invites a fifth, invitable address, then the answer is 201 with a `pending` row, and the link has 5 co-hosts. [unit]

AC-5. Given a link with 5 co-hosts, and separately one with 7 (seeded directly), when the owner re-invites an existing co-host of each status (pending, accepted, declined), then each answer is 200 with that host's row unchanged (status and `responded_at`), and no row is added. [unit]

AC-6. Given a link with 5 co-hosts, when the owner invites their own domain-confirmed address in any letter case, then the answer is 200 with the owner's own row, which is unchanged (`accepted`). [unit]

AC-7. Given a link with 5 co-hosts, when the owner invites an address that no account holds domain-confirmed (none, unconfirmed only, or two accounts), then the answer is 404 `{"error":"user not found"}`, never the 422. [unit]

AC-8. Given a link with 7 co-hosts (seeded directly):
- when the owner invites a new invitable address, then the answer is the 422 and nothing changes;
- when the owner PATCHes the list without one co-host (6 entries, keep-only), then that succeeds as PAC-112 AC-32 requires;
- after further removals leave 4 co-hosts, an invitation of a new invitable address is 201. [unit]

AC-9. Given a link with 4 co-hosts and two different invitable addresses, when the owner sends both invitations at the same moment (released together from a barrier, repeated for at least 20 rounds on fresh links), then in every round exactly one answer is 201 and the other is the 422, and the link ends with exactly 5 co-hosts. No round answers 500. *Fails today: both 201, 6 co-hosts.* [unit]

AC-10. Given a link with 4 co-hosts, when an invitation of a new address X runs concurrently with a PATCH whose list is the 4 plus a different new address Y, in either commit order and for at least 20 rounds, then:
- the link never ends with more than 5 co-hosts;
- each answer is one of 201, 200, the 422 or the PATCH's 200;
- no round answers 500, which also proves no deadlock (40P01) and no lock timeout (55P03). [unit]

AC-11. Given a link with 4 co-hosts that the owner deletes while an invitation is waiting on the link's lock, then the invitation answers 404 `{"error":"not found"}` and no host row is written (PAC-101, unchanged). [unit]

AC-12. Given a session whose generation is advanced while an invitation that would be refused by the cap is in flight, then the answer is requireAuth's 401, not the 422 (PAC-71, unchanged order). [unit]

## 5. Explicitly out of scope

- **A new or different body limit, per-route limits, or `http.MaxBytesReader`.** The PAC-81 cap already does the job in both layers (§0, §2.1). Replacing an `io.LimitReader` cap with `MaxBytesReader` would change nothing observable.
- **Field-length limits** on free text that only the body cap bounds today: booking notes and names, NLP text, link titles, event descriptions (OQ-7). They are real, but they are about each field's meaning (stored size, provider limits, LLM cost), not about transport.
- **The MCP server's own request size** and its HTML 413 behind nginx (OQ-6). MCP is a separate process behind a bearer token, not the API.
- **The keep-rule edge on the list path.** A list of 5 or fewer entries could keep 6 or more accounts when several accounts carry one listed address (§2.6). PAC-112 accepted it, and it needs accounts sharing an address, which PAC-71 already treats as "couldn't be added".
- **Pruning existing links above 5.** They keep their co-hosts (§3.2 item 3). A read-only count at release is suggested in §7.
- **Making the single invitation use the list path, or deprecating it.** It stays a supported operation with its own contract.
- **Any web change.** The web never calls this operation, and already renders 413.

## 6. What must not change

- **The body cap's bytes and order** (PAC-81 AC-A12, Part B D-7): `TestPAC81_BodyCap*`, `TestOversizedAPIBodyIsJSON413`, e2e `edge.spec.ts:85`. AC-1 and AC-2 add the missing wiring proof.
- **PAC-61**: re-inviting keeps status. `TestSchedulingLinksReinviteKeepsExistingHostStatus` (`handlers_scheduling_links_test.go:323`). AC-5 extends it to links at and above the cap.
- **PAC-71**: who can be invited, "user not found" for a non-invitable address. `TestPAC71_AC28_AC40_GrantingSitesResolveOnlyDomainConfirmedHolders` (`pac71_address_test.go:58`, invitation sub-test `:79-86`). AC-7 keeps it ahead of the cap.
- **API-072 / PAC-101 AC-14**: the two 404 bodies. `TestPAC101_InviteNotFoundBodiesDiffer` (`pac101_test.go:521-537`). It does not exercise a failed lookup, so AC-13 does not contradict it. PAC-112 §6 calls the failed-lookup 404 part of the contract, but the contract's text says 500 (Inherited scope). This spec follows the contract text.
- **PAC-101**: atomic against delete, 10 s bound, no deadlock under mixed concurrent writes. `TestPAC101_ConcurrentWritesOnOneLinkNeverDeadlock` (`pac101_test.go:545`) and the AC-8 rollback tests (`:328`, `:344`). AC-10 and AC-11 extend them.

## 7. Rollback

Code and contract only: no migration, no stored data. Reverting the backend restores unbounded invitations and the 404 on a failed lookup. A refused invitation wrote nothing, so there is nothing to undo. The AC-1 and AC-2 tests can stay after a revert.

Suggested for the release, not a gate: before deploying, the release manager runs one read-only count of links with more than 5 non-owner host rows, and records it in the release note. Those links will refuse new invitations (§3.2 item 3), and their owners might ask why.

## 8. Open questions

Owner of each: the product owner, answering in Linear before the contract stage. Each default applies otherwise.

- **OQ-1: Which hosts count towards the 5?** Declined rows stay on the link (§2.5). **Default: every non-owner row, pending, accepted and declined.**
  - This matches what the editor counts ("n/5 co-hosts" is the chips, declined included) and PAC-112's "current host" set.
  - Alternative: count only pending and accepted, so a declined invitee frees a seat. The editor would then disagree with the server about when "5" is reached.
- **OQ-2: 422 or 409 for the refusal?** **Default: 422.** It follows PAC-112 D-9 (every new refusal on these operations is 422), and no current client branches on it.
  - 409 would describe "the link is full" as a state conflict, closer to its meaning, but would be the operation's only 409.
- **OQ-3: Should the cap be 5 everywhere, as one shared value?** **Default: yes, the same value as the list rule**, so the editor, the list and the invitation always agree. A plan that changes one must change all.
- **OQ-4: Take SF-068 (lookup error is 404) into this work?** **Default: yes.** Same handler, the contract already says 500, and the factory's touch-it-fix-it rule applies to the contract's truthfulness here. It is a one-branch change, and AC-13 is its test.
- **OQ-5: A smaller body cap for unauthenticated routes** (public booking, `/api/auth/detect`)? **Default: no.** 1 MiB is already small, nginx answers first in production, and the free-text fields need field limits (OQ-7) rather than a transport limit.
- **OQ-6: The MCP server's request size.** The MCP server accepts any size when reached directly (dev compose publishes `3001:3001`, `docker-compose.yml:97-98`). Behind nginx it gets nginx's HTML 413, not JSON. **Default: out of scope.** The factory opens a follow-up: give `/mcp/` the JSON 413 and give the MCP server its own cap.
- **OQ-7: Field-length limits** for booking notes and names, NLP text, titles and descriptions. **Default: out of scope.** The factory opens one follow-up covering them, with the silent-failure register's validation-gap pattern as its frame.
- **OQ-8: Order of the cap against "user not found".** **Default: "user not found" first** (§3.2 item 5), so the 422 is only ever said about an invitable address and never hides a typo behind "the link is full".
  - Alternative: refuse at the cap before resolving the address, saving one lookup. That is cheaper, but the owner of a full link who mistypes an address gets told to remove someone.

## 9. Decisions

- **D-1 [F]: no new body-size mechanism.** The first half of the ticket is already satisfied by PAC-81 (§0). This work adds only the backend wiring proof (AC-1, AC-2) and the register correction.
- **D-2 [F]: the single invitation is capped by link size, not by request.** The PAC-112 rule's intent ("no save takes a link past 5 by adding someone; keep and remove always work") is carried over. Its list-length mechanics do not apply to a request that has no list (§2.6).
- **D-3 [F]: decided at the write, and invitations are ordered against each other.** A count under today's shared lock is racy (§2.5), so a plain count would let two invitations reach 6. How they are ordered is the plan's choice, constrained by AC-9 to AC-11 and the PAC-101 deadlock rule.
- **D-4 [F]: a distinct 422, after the existing answers.** It leaves every current answer and its order intact, and adds one outcome only where a 201 would otherwise have been given.
- **D-5 [F, pending OQ-4]: the failed lookup becomes the documented 500** (SF-068), aligning the code with the contract text rather than the reverse.
