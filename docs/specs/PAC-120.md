## 0. The ticket's premise, corrected

The ticket has two halves. **The first half is already built.** The ticket and PAC-112 spec §2.2 both say no API request body is size-limited (PAC-112 spec `:119`, `:364`). That has been false since PAC-81 Part A (`48f6c60`, #247) and Part B:

- the backend refuses any request body over 1 MiB with 413 `{"error":"request body too large"}`, before any handler, on every route (`backend/api/middleware.go:365-397`, wired at `backend/api/routes.go:39`);
- nginx refuses the same bodies with the same JSON bytes (`nginx/nginx.conf:77-78`, `:121-130`);
- the contract states the rule once for every operation (`openapi.yaml:40-41`);
- the web already renders a 413 (PAC-83, §2.7).

PAC-112's claim was probably drawn from a grep for `http.MaxBytesReader`, which the cap does not use: it reads through `io.LimitReader`.

So this spec does **not** propose a new body limit. For the first half it asks only for what is missing: a proof that the cap is wired on the real route chain (§2.4 shows that no backend test proves it), and a record that the PAC-112 claim is wrong. **The second half, the co-host cap on the single invitation, is real and is the substance of this spec.**

The ticket's "around `:840-870`" for the invitation handler has drifted. It is now `handlers_scheduling_links.go:904-957`.

## 1. Problem

**Co-hosts.** A link's co-hosts are the people whose calendars decide its free slots. PAC-112 gave the link editor a limit of 5 co-hosts, and the server enforces it on the complete list that create and edit send. A second way in has no limit: the operation that invites one person at a time. Any API caller (a script, an old web build, a future client) can call it repeatedly and give a link 6, 20 or 500 co-hosts.

What that costs:
- **Every slot read grows with the host count.** Each public slot request reads every accepted host's calendar (PAC-25, PAC-112 §3.3). A link with hundreds of hosts makes the public booking page slow for every booker, and spends the owner's and co-hosts' provider quotas.
- **The editor cannot show such a link honestly.** It shows "n/5 co-hosts" and refuses to add past 5, but a link built through the other door can already be past 5. PAC-112 had to add a special case so such links could at least be pruned (D-8, AC-32, AC-33).
- **The limit is only as strong as its weakest door.** The editor's and the list's limit of 5 means nothing while another operation can add a sixth host. What this cap bounds is **the number of hosts, and so the cost of every slot read**. It does not bound address lookups: the invitation resolves the address before the write, outside any lock (`handlers_scheduling_links.go:934`), so each call costs one lookup whether it is refused or not. That is one lookup per request, the same as any other authenticated call, and is weighed in OQ-8.

**Body size.** As §0 says, the body cap exists in both layers. The remaining risk is a silent regression: e2e runs through nginx, so if the backend's wiring were removed, e2e would still see nginx's identical 413 and stay green. Only a direct-to-backend caller would notice, in production.

## 2. Current behaviour

### 2.1 The body cap (PAC-81)

**Backend.** `bodyCapMiddleware(maxRequestBody)` with `maxRequestBody = 1 << 20` (`middleware.go:365-367`):
- a declared `Content-Length` over the cap is 413 without reading (`:377-380`);
- otherwise it reads at most cap+1 bytes through `io.LimitReader` (`:381-382`). More than the cap is 413 (`:383-386`). A read error is 400 `"invalid request body"` (`:387-390`);
- a body of exactly the cap is passed on. The handler gets an in-memory copy (`:391-392`), so it sees the whole body or never runs;
- the 413 is `writeError` (`backend/api/handlers_settings.go:479-483`): `Content-Type: application/json`, body `{"error":"request body too large"}\n`. That is the PAC-21 error envelope.

**Where it sits.** `RegisterRoutes` applies, outer to inner (`routes.go:26-40`):
1. `sentryMiddleware`;
2. `loggingMiddleware`;
3. `corsMiddleware`;
4. `bodyCapMiddleware`;
5. `budget.Middleware` (the 90 s handler budget);
6. then, per group, `requireAuth`, which installs the PAC-71 `guardedResponseWriter` (`middleware.go:85-232`).

Consequences of that order, all true today:
- **CORS headers are on the 413.** `corsMiddleware` sets them before calling the next handler (`middleware.go:234-258`), so a browser can read the 413.
- **The access log records 413**, since logging is outside the cap (PAC-81 AC-A13).
- **413 comes before authentication.** An oversized body to a protected route without a session gets 413, not 401. The guarded writer never exists for that request, so a PAC-71 re-check cannot replace the 413.
- **413 comes before every handler check**: before a 404 for a deleted link, before a 403, before an `Idempotency-Key` 400.
- **Reading the body is outside the 90 s budget.** It is bounded by the server's read timeout of 30 s (`backend/internal/lifecycle/lifecycle.go:207`).
- It applies to every method, GET and DELETE included.

**nginx** (production and the e2e stack):
- `client_max_body_size 1m` at server level (`nginx.conf:77-78`);
- under `/api/`, `error_page 413` goes to a named location that answers the backend's exact JSON bytes (`:121-130`). nginx answers it **without contacting the backend**. That is pinned by `TestOversizedAPIBodyIsJSON413` (`nginx/test/nginx_test.go:434-459`) and by e2e `edge.spec.ts:85-98`;
- in production, therefore, **nginx answers every oversized `/api/` body**, and the backend's cap is defence in depth: it covers direct callers such as the dev compose's port 8080, and a misconfigured proxy;
- `/mcp/` inherits the server-level 1 MiB but has no `error_page`, so its 413 is nginx's HTML page (`nginx.conf:132-150`). The MCP server itself has no body cap (`mcp/main.go:121-138`). See OQ-6;
- the operator's outer TLS proxy doc says nothing about body size (`docs/operator/proxy.md`). An outer proxy with a smaller limit would answer first, in its own format.

**The contract** states the rule once, in `info.description` (`openapi.yaml:40-41`: "A request body over 1 MiB is refused with 413 … by the backend and by nginx alike"). No operation lists a 413 response of its own.

**Not related**: the outbound limits (`backend/internal/outbound/outbound.go:102-115`, `ReadLimited`; the webcal ICS fetch at 10 MiB, `outbound.go:42`, used at `backend/calendar/webcal_client.go:77`; the JWKS read at `backend/auth/ms_idtoken.go:483`, the only `http.MaxBytesReader` in the backend). These bound responses Paceday reads from other servers, not requests it receives.

### 2.3 How large legitimate bodies are

PAC-81's contract review already found that no operation accepts a body near 1 MiB (`contracts/features/PAC-81-part-a.md:391-392`). Re-checked here:
- **Settings PATCH**: a flat object plus working-hours and lunch-break arrays. A few KB at most.
- **Habits**: one habit's fields.
- **Event create and PATCH with attendees**: an attendee list of e-mail addresses. Even 500 attendees is under 30 KB.
- **NLP input**: one text field with no length check (`handlers_nlp.go:21-23`). The editor sends one sentence.
- **Scheduling-link create and PATCH**: fields plus a co-host list. The list's length has no schema bound (`openapi.yaml:11141`, `:16382`: "`maxItems` is deliberately not set"), and the server's over-5 rule refuses long lists that add someone (§2.6).
- **Public booking**: name, e-mail, times and free-text notes, none length-checked (`handlers_booking.go:362-380`).
- **Org AI and SSO admin**: configuration objects, a few KB.

So 1 MiB is far above every legitimate body, and no route needs a larger limit. Several free-text fields have no length cap of their own, so the body cap is their only bound (§5, OQ-7).

### 2.5 The single invitation today

`POST /api/scheduling-links/{id}/hosts` → `inviteHost` (`handlers_scheduling_links.go:904-957`), in order:
1. A malformed id is 400 `"invalid id"` (`:907-911`).
2. Reads the link (`GetSchedulingLinkByID`, which does not find a deleted link). A read error is 500 `{"error":"internal error"}` through `writeError`, so **nothing is logged and nothing reaches Sentry** (`:912-916`; `writeError`, `handlers_settings.go:479-483`). Contrast step 7's `writeServerError`. This is the M-2 item (Inherited scope). No link is 404 `"not found"` (`:917-920`).
3. Someone other than the owner is 403 `"forbidden"` (`:921-924`).
4. Decodes `{"email"}`. Invalid JSON or a blank e-mail is 400 `"email is required"` (`:925-931`).
5. Resolves the address with `storage.ConfirmedHolder` (`backend/storage/identity.go:160`): exactly one account holding it domain-confirmed, ignoring case (PAC-71). It runs on `h.db`, outside any transaction and before any lock. **No holder and a storage error both answer 404 `"user not found"`** (`:934-937`). That is SF-068, and it contradicts the contract's 500 (Inherited scope). The link read in step 2 uses the same `h.db` (`:912`), so a blunt fault (a closed pool) fails step 2 first and never reaches this branch (AC-14 is written against that).
6. Writes through `storage.InviteLinkHostCtx` (`backend/storage/guarded_writes.go:162-172`):
   - `withLinkWriteTx` (`backend/storage/session.go:175-195`): the PAC-71 generation re-check when a session guard is present, then the 10 s lock bound (`setLinkLockTimeout`, `scheduling_links.go:507-511`; `LinkLockTimeout`, `:498`);
   - `inviteLinkHostLocked` (`scheduling_links.go:813-822`): `lockLiveLinkForShare` (`:520-528`, `SELECT 1 … WHERE id = $1 AND deleted_at IS NULL FOR SHARE`), then `InviteLinkHost` (`:293-314`);
   - `InviteLinkHost` inserts a `pending` row with `ON CONFLICT (link_id, user_id) DO NOTHING`. With no row returned, it reads the existing row and reports `created = false` (PAC-61).
7. Answers: `ErrLinkGone` is 404 `"not found"` (`:942-947`); another error is 500 `"invite failed"` through `writeServerError` (`:948-951`); otherwise 201 with the new row or 200 with the existing row unchanged (`:952-956`).

**Nothing counts the link's hosts.** No limit applies at any step.

Two more facts this spec depends on:
- **Re-inviting is never an add.** An existing host of any status gets 200 and an unchanged row. Two simultaneous invitations of the **same** new address give 201 and 200 today: the second insert finds the first's row through `ON CONFLICT DO NOTHING` (`scheduling_links.go:293-314`).
- **The owner's row.** No constraint guarantees that a link has a row for its owner. `migrations/009_scheduling_links.up.sql` is the only DDL on the table, and no migration backfills one. What holds in practice:
  - every current create path inserts it, `accepted`, in the create's transaction (`scheduling_links.go:1456-1460`);
  - leave refuses the owner (`handlers_scheduling_links.go:1028-1031`);
  - **but the owner can decline their own link.** `respondToInvite` has no owner check (`handlers_scheduling_links.go:984-1004`), and `RespondToHostInvite` updates any row (`scheduling_links.go:434-449`). The owner's row is then `declined`;
  - **links created before PAC-112 can lack an owner row.** The old create inserted it as a separate write, and a failure left the link created (PAC-112 spec §2.2, "the link stays created"). For such a link, the owner inviting their own address inserts a `pending` owner row and answers 201 today.

  Neither matters for the count, which is of non-owner rows only (§3.2 item 1). It matters for what the owner's self-invitation answers (§3.2 item 2, AC-6). The owner's self-decline and the missing owner row are recorded as observed and are out of scope (§5).
- **The lock does not order two invitations against each other.** `FOR SHARE` "conflicts with the delete's FOR NO KEY UPDATE … and not with another FOR SHARE" (comment, `scheduling_links.go:513-519`). Two invitations on one link run concurrently. A PATCH takes the link's row lock through its `UPDATE` (`:197`), which does conflict with `FOR SHARE`, so a PATCH and an invitation are ordered. A booking save locks the link `FOR SHARE` and then takes advisory locks (`scheduling_links.go:663-669`, `:683-690`). Accept, decline and leave also lock `FOR SHARE` (`:823-840`). The booker erasure locks the link `FOR UPDATE` (`backend/storage/booker_erasure.go:86-117`). **A count read under today's lock is therefore racy between invitations**: two invitations on a link with 4 co-hosts could both see 4 and both insert. Any new ordering for invitations changes who waits on whom among all these writers, which is why AC-11 runs them together.
- **A PATCH that adds the same person an invitation is adding.** The list path writes each new invitee through `coHostInvite`, which fails the whole save with a 500 when the row already exists: "became a host during the save" (`scheduling_links.go:1403-1418`). Today that cannot happen, because the PATCH's exclusive lock orders it against the invitation's `FOR SHARE`, and the PATCH reads H after the lock. A new ordering that stopped serialising the two would turn that collision into a 500 (AC-10(b)).

**Host rows and statuses.** A host row is `pending`, `accepted` or `declined`. Declining keeps the row (`RespondToHostInvite`, `scheduling_links.go:434-449`). Leaving and removal delete it. The editor's chips are every non-owner host of the strict read, declined included (smart-calendar-flow `src/components/links/LinkEditDrawer.tsx:207-208`, `:242`). Its add cap counts those chips (`:524`, "You can invite up to 5 co-hosts.", `src/components/links/coHostSave.ts:15`; counter "n/5 co-hosts", `LinkEditDrawer.tsx:866`).

**Contract** (`contracts/openapi/paths/booking.yaml:1582-1673`): 200, 201, 400, 401, 403, two 404 bodies (API-072), and a 500 that covers "Lookup or invite failed, or the lock on the link was not obtained within 10 seconds". It names no limit and no 422.

### 2.6 The PAC-112 over-5 rule, and whether it can be reused

`setCoHostList` (`scheduling_links.go:1257-1331`) applies to the complete list on create and PATCH:
- it reads the host set H inside the write's transaction (`readLinkHostSet`, `:1185-1206`, every host row of any status);
- `limited := len(entries) > CoHostListLimit` (`:1270`; `CoHostListLimit = 5`, `:1143`);
- each distinct address is looked up once. When `limited`, the first one that reaches no current host (the owner counts) fails the save with `ErrCoHostListTooLong` (`:1281-1283`; "reaches", `lookupCoHost`, `:1349-1357`);
- the handlers answer 422 with `coHostListTooLongMsg` (create `:549-552`, PATCH `:821-824`; text at `:409`).

**The rule is about the length of a list, not the size of a link.** It answers "may this list add someone?". A single invitation carries no list. What carries over is the **intent**: no save may take a link past 5 co-hosts by adding someone, while saves that only keep or remove are always allowed. For the list path, that falls out of list semantics: the list is the complete set, so a list of 5 or fewer that adds someone leaves at most 5 co-hosts. There is one edge case. The PAC-71 keep rule keeps every account carrying a listed address, so two accounts sharing one address could leave 6 (§5).

For the single invitation, the same intent reads: **an invitation that would add a host row is refused when the link already has 5 co-hosts or more.** The code itself (`setCoHostList`, `CoHostListLimit`, the 422 text) cannot be reused unchanged: the text talks about a list, and the lock is different (§2.5). The constant 5 and the "decided inside the write's transaction, against the host set read there" discipline can be.

The PATCH's lock order is: the guarded `UPDATE` first, as the transaction's first lock on the link, "never FOR SHARE first and an upgrade after, which would let two PATCHes deadlock" (`scheduling_links.go:843-849`). Whatever lock orders invitations against each other must not bring that deadlock back (AC-10).

## 3. Desired behaviour

### 3.1 Body size

1. **Unchanged rule** [F, D-1]: every API request body over 1 MiB is refused with 413 and the JSON error body, before anything else, by both layers. No route gets a larger or smaller limit (OQ-5).
2. **The backend's own refusal is proven through its real route chain**, on a public route and on a protected one, so removing it fails a backend test even though nginx would hide it in e2e.
3. The proof covers what the order guarantees today:
   - the 413 carries the CORS headers for an allowed origin;
   - on a protected route, an oversized body without a session gets 413, not 401;
   - on a public route, the handler never runs for an oversized body;
   - a body of exactly 1 MiB reaches the handler whole.
4. The record is corrected. The defect register shows that the body-size claim in PAC-112 spec §2.2 and §5 is wrong, and points to PAC-81. The cap's own 400 for a failed body read stays undocumented and is recorded, not fixed (Inherited scope, m-5).

### 3.2 Co-hosts per link on the single invitation

1. **The cap** [F, D-2]. An invitation that would add a new host to a link is refused when the link already has **5 or more co-hosts**. Nothing is written. A co-host is any host of the link other than its owner, whatever their status: pending, accepted or declined [OQ-1]. The owner's own row, whatever its status and whether or not it exists, is never counted.
2. **What is never refused by the cap**:
   - re-inviting someone who is already a host, at any count: the existing answer, their row unchanged (PAC-61). That includes the loser of two simultaneous invitations of the same new address, which gets the 200 and never the refusal;
   - the owner inviting their own address. With an owner row (accepted, or declined by the owner), that is today's 200 and the row unchanged. With no owner row (a pre-PAC-112 link, §2.5), it is never the refusal and adds or changes no co-host row; what the owner's own row becomes is left to the follow-up named in §5, which may change it (P2-m2);
   - removing, leaving, accepting and declining, at any count.
3. **Links already above 5** keep their co-hosts. Their owner can remove people, by the editor's list (PAC-112 AC-32) or by any other existing means. They can invite again once the link has 4 or fewer.
4. **The refusal** [F, D-4]:
   - its status is 422 [OQ-2];
   - its message is distinct from every other answer of this operation, and from the list's over-5 message;
   - the message says the link already has the maximum number of co-hosts and that one must be removed before inviting another. It reads as a limit on the link, not on the request;
   - it reveals nothing about the invitee beyond what a 201 would have revealed. It is only given for an address that resolves to an invitable account.
5. **Where it sits among the existing answers** [F, D-4]. The invalid id 400, the link read, the 404 and 403, the body 400, the PAC-71 resolution ("user not found") and the 500 for a failed lookup all come first and are unchanged, except for items 7 and 10. The cap is decided after them, in the write.
6. **Decided at the write, never before it** [F, D-3]:
   - the count is taken inside the write's transaction, after the link is locked and after the PAC-71 re-check, as PAC-112 decides its rule (P3-m1);
   - concurrent writes that add hosts to one link are ordered so that, together, they never take the link past 5. Two simultaneous invitations of different new addresses on a link with 4 co-hosts give exactly one success and one refusal. An invitation running alongside a list save never leaves more than 5 either. Today's lock does not order invitations against each other (§2.5), so this is new;
   - an invitation and a list save that add **the same** person stay ordered against each other, so the list save never fails with the 500 "became a host during the save" because of the invitation (§2.5);
   - the PAC-101 guarantees stay: a link deleted meanwhile is the 404 "not found" with nothing written; a lock wait over 10 s is the 500 with nothing written; no deadlock with PATCH, delete, booking, accept, decline, leave, pause or resume, proven by a mixed run at the cap boundary (AC-11).
7. **A failed lookup is a server error, not "user not found"** [F, D-5; OQ-4; SF-068]. When resolving the address fails because of a storage error, the answer is the operation's documented 500 with nothing written, and the detail is logged and reported to Sentry (PAC-21). "User not found" stays the answer only for an address no single account holds domain-confirmed.
8. **The session guard still wins.** A session whose generation moved before the write's re-check gets requireAuth's 401 instead of the refusal, as for every other answer of this operation (PAC-71). A generation that moves after the write's re-check does not override the refusal, as it does not override any other answer decided there.
9. **Clients.** The editor never calls this operation, and MCP has no tool for it, so neither changes behaviour. The web gets one PR that only regenerates its generated types from the new bundle (M-1). The link editor's own limit of 5 stays as it is.
10. **A failed link read is reported** [F, D-6; factory decision on M-2]. The 500 `{"error":"internal error"}` for a link read that fails keeps its status and body, and the detail is now logged and reported to Sentry, as the contract's 500 already says (PAC-21).

## 4. Acceptance criteria

"Co-hosts" means non-owner host rows of the link, any status (OQ-1). "Invitable" means an address held domain-confirmed by exactly one account (PAC-71). Each AC names its layer: `[unit]` = backend Go tests (handler or storage, with Postgres), `[contract]` = the OpenAPI fragment and bundle, `[e2e]` = Playwright against the compose stack. Each AC also says whether it **fails today** (the plan writes it first and sees it red) or is a **regression guard** (green today; it fails on a wrong implementation of this work, as the AC says).

**Body size**

AC-1. Given the backend's production route chain (`RegisterRoutes`, no nginx):
- when a protected route receives a POST whose body is 1 MiB + 1 byte, with no session and an allowed `Origin`, then the answer is 413 with `Content-Type: application/json`, body exactly `{"error":"request body too large"}` plus a newline, and `Access-Control-Allow-Origin` for that origin. It is not 401;
- when a route behind the same chain whose test handler echoes the length of the body it read receives exactly 1,048,576 bytes with a valid session, then that handler answers with 1048576.

*Regression guard: green today; red if the backend's cap is unwired (the first half answers 401) or moved inside requireAuth.* [unit]

AC-2. Given the same chain, when the public booking route receives a POST of 1 MiB + 1 byte for a live link's slug, then the answer is the same 413, the booking handler did not run (no booking row for that link afterwards, and a handler-entry seam never fired). *Regression guard.* [unit]

**Co-host cap on the single invitation**

AC-3. Given a link whose owner is accepted and which has exactly 5 co-hosts (2 pending, 2 accepted, 1 declined), when the owner invites a sixth, invitable address, then the answer is 422 with the new refusal message (distinct from `coHostListTooLongMsg` and from every other body of this operation). The link's host rows (users and statuses) are identical before and after. *Fails today: 201.* [unit]

AC-4. Given a link with 4 co-hosts, when the owner invites a fifth, invitable address, then the answer is 201 with a `pending` row, and the link has 5 co-hosts. *Regression guard: red if the cap counts the owner or uses "more than 4".* [unit]

AC-5. Given a link with 5 co-hosts, and separately one with 7 (seeded directly), when the owner re-invites an existing co-host of each status (pending, accepted, declined), then each answer is 200 with that host's row unchanged (status and `responded_at`), and no row is added. *Regression guard: red if the cap is checked before "already a host".* [unit]

AC-5b. Given a link with 4 co-hosts and one new invitable address, when the owner sends two invitations of that same address at the same moment (barrier, at least 20 rounds on fresh links), then every round answers one 201 and one 200, never the 422 and never 500, and the link ends with 5 co-hosts. *Regression guard: red if the count is taken before the conflict is resolved.* [unit]

AC-6. Given a link with 5 co-hosts:
- whose owner row is `accepted`, when the owner invites their own domain-confirmed address in any letter case, then the answer is 200 with the owner's row, unchanged (`accepted`);
- whose owner row the owner has declined, the same request answers 200 with the row unchanged (`declined`);
- with no owner row (seeded so), the same request is never the 422, and no co-host row is added or changed. What the owner's own row becomes is not pinned here; the §5 follow-up may change it (P2-m2).

*Regression guard: red if the cap refuses the owner or counts the owner's row.* [unit]

AC-7. Given a link with 5 co-hosts, when the owner invites an address that no account holds domain-confirmed (none, unconfirmed only, or two accounts), then the answer is 404 `{"error":"user not found"}`, never the 422. *Regression guard: red if the cap is decided before the resolution (OQ-8).* [unit]

AC-8. Given a link with 7 co-hosts (seeded directly):
- when the owner invites a new invitable address, then the answer is the 422 and nothing changes (*fails today: 201*);
- when the owner PATCHes the list without one co-host (6 entries, keep-only), then that succeeds as PAC-112 AC-32 requires (*regression guard*);
- after further removals leave 4 co-hosts, an invitation of a new invitable address is 201 (*regression guard: red if the refusal is sticky*). [unit]

AC-9. Given a link with 4 co-hosts and two different invitable addresses, when the owner sends both invitations at the same moment (released together from a barrier, repeated for at least 20 rounds on fresh links), then in every round exactly one answer is 201 and the other is the 422, and the link ends with exactly 5 co-hosts. No round answers 500. *Fails today: both 201, 6 co-hosts.* [unit]

AC-10. Given a link with 4 co-hosts, for at least 20 rounds each and in either commit order (forced with seams where needed):
- **(a)** an invitation of a new address X runs concurrently with a PATCH whose list is the 4 plus a different new address Y. Then the link never ends with more than 5 co-hosts; each answer is one of 201, 200, the 422 or the PATCH's 200; no round answers 500, which also proves no deadlock (40P01) and no lock timeout (55P03);
- **(b)** an invitation of a new address X runs concurrently with a PATCH whose list is the 4 plus **the same** X. Then no round answers 500, in particular never "became a host during the save"; the PATCH answers 200 and the invitation 201 or 200; the link ends with exactly the 4 plus X.

*(a) fails today: when the PATCH commits first (5 co-hosts), the uncapped invitation then adds a sixth. (b) is a regression guard: red if the new ordering stops serialising an invitation against a PATCH.* [unit]

AC-11. *The no-500 / no-deadlock guard under mixed load (P2-m1). AC-9 stays the deterministic test of the cap race.* Given a link that starts with exactly 4 co-hosts, two of them able to answer, and a pool of new invitable addresses, when each round runs concurrently (released together):
- at least two invitations of distinct new addresses;
- bookings of distinct free slots;
- an accept, a decline and a leave by existing co-hosts;
- a PATCH of fields only, and a PATCH of the co-host list;
- a pause and a resume;
- and, in the last round, a delete of the link;

for at least 10 rounds, then:
- no answer is 500 (no deadlock 40P01, no lock timeout 55P03);
- after every round, the link has at most 5 co-hosts (the pool's addresses are each held by exactly one account, so the keep-rule edge of §5 cannot arise);
- each invitation answers 201, 200, the 422 or 404 "not found" (after the delete);
- every booking answered 201 exists, and none answered otherwise does (PAC-101 AC-15 semantics);
- after the delete, no host row changed for any request answered 404.

*Regression guard for no 500 and no deadlock: red if a new ordering deadlocks or times out with bookings, accept, decline, leave, pause, resume or delete (factory decision on M-3). The at-most-5 assertion may go red on today's code, but only in rounds where the list PATCH commits first, so it is not this AC's falsifier; AC-9 is (P2-m1).* [unit]

AC-12. Given a link with 4 co-hosts that the owner deletes while an invitation is waiting on the link's lock, then the invitation answers 404 `{"error":"not found"}` and no host row is written (PAC-101, unchanged). *Regression guard.* [unit]

AC-13. Given a link with 5 co-hosts, an invitable new address, and a session whose generation is advanced by a raw `UPDATE users SET session_generation = session_generation + 1` **in the decisive window: after requireAuth's generation read and before the write transaction's re-check** (the guarded-call seam at the start of the write, `session.go:182-186`; or `afterAuthHook`, `middleware.go:61-64`, `:145-146`, followed by the bump), when the owner invites, then the answer is requireAuth's 401 and no host row is written. A cap decided outside the write (from a count read before it) would answer the 422 in this window, so this AC fails on that implementation. *Regression guard on the cap's placement. A generation moved before requireAuth's read gives 401 whatever the cap does, and one moved after the write's re-check correctly leaves the 422 standing; neither timing is this AC.* [unit]

**Silent failures on this operation**

AC-14. Given the link read succeeds and **only the address lookup** fails with a storage error, injected at the lookup itself (a seam on the resolution, not a closed pool, which would fail the link read first, §2.5), when the owner invites, then the answer is 500 with the operation's documented internal-error body, never 404 `"user not found"`, and no host row is written. A captured log line and a captured Sentry event each name the lookup step of this operation (for example "invite lookup"), so the link-read branch cannot satisfy the AC. The assertion matches the event by its step name and does not count events: a stale session already yields an "invite failed" event before the 401 (challenge Pass 2, observed note). *Fails today: 404, nothing logged (SF-068).* [unit]

AC-15. Given the link read fails with a storage error (injected at the read), when the owner invites, then the answer is still 500 `{"error":"internal error"}`, no host row is written, and a captured log line and a captured Sentry event each name the link-read step of this operation, matched by step name, not by event count. *Fails today: nothing logged or reported (M-2, SF-101 to be).* [unit]

**Contract, generated types and journey**

AC-16. Given the bundle, then `inviteSchedulingLinkHost`:
- documents the 422 with its exact body and states the rule: 5 co-hosts of any status; the owner never counted; an add only; re-invite and own address never refused; decided at the write;
- documents a failed lookup and a failed link read under the 500, both logged and reported;
- `make contract` passes. *Fails today: no 422.* [contract]

AC-17. Given the regenerated bundle, then the web's committed generated types for this operation carry the 422 and the rewritten 500, the web PR changes no file outside its generated directory, and the cross-repo `openapi-check` passes on the paired branches. *Fails today: the web's types have no 422.* [contract]

AC-18. Given the compose stack, an owner and a link built with 5 co-hosts, when the owner invites a sixth invitable user through `/api/` (through nginx), then the answer is 422 with the documented body, and the strict single-link read still lists exactly the same 5 co-hosts. *Fails today: 201.* [e2e]

[e2e]

## 5. Explicitly out of scope

- **A new or different body limit, per-route limits, or `http.MaxBytesReader`.** The PAC-81 cap already does the job in both layers (§0, §2.1). Replacing an `io.LimitReader` cap with `MaxBytesReader` would change nothing observable.
- **Documenting the body cap's 400** for a failed body read (m-5). Recorded in Inherited scope for the contract stage's notes and an audit row; not changed here.
- **Field-length limits** on free text that only the body cap bounds today: booking notes and names, NLP text, link titles, event descriptions (OQ-7). They are real, but they are about each field's meaning (stored size, provider limits, LLM cost), not about transport.
- **The MCP server's own request size** and its HTML 413 behind nginx (OQ-6). MCP is a separate process behind a bearer token, not the API.
- **The keep-rule edge on the list path.** A list of 5 or fewer entries could keep 6 or more accounts when several accounts carry one listed address (§2.6). PAC-112 accepted it, and it needs accounts sharing an address, which PAC-71 already treats as "couldn't be added".
- **The owner's row** (m-2): the owner declining their own link, and pre-PAC-112 links with no owner row (whose owner's self-invitation creates a `pending` owner row). Both are observed (§2.5), neither affects the count, and both stay as they are. Follow-up candidate for the factory: "A link's owner can decline their own link, and an old link may have no owner row".
- **Pruning existing links above 5.** They keep their co-hosts (§3.2 item 3). A read-only count at release is suggested in §7.
- **Making the single invitation use the list path, or deprecating it.** It stays a supported operation with its own contract.
- **Any hand-written web change.** The web never calls this operation and already renders 413. Its only change is the regenerated types (M-1).

## 7. Rollback

Code and contract only: no migration, no stored data. Reverting the backend restores unbounded invitations, the 404 on a failed lookup and the unlogged link-read 500. The web's regenerated-types PR is reverted with the contract (it carries no behaviour). A refused invitation wrote nothing, so there is nothing to undo. The AC-1 and AC-2 tests can stay after a revert.

Suggested for the release, not a gate: before deploying, the release manager runs one read-only count of links with more than 5 non-owner host rows, and records it in the release note. Those links will refuse new invitations (§3.2 item 3), and their owners might ask why.

## 8. Open questions

Owner of each: the product owner, answering in Linear before the contract stage. Each default applies otherwise.

- **OQ-1: Which hosts count towards the 5?** Declined rows stay on the link (§2.5). **Default: every non-owner row, pending, accepted and declined.**
  - This matches what the editor counts ("n/5 co-hosts" is the chips, declined included) and PAC-112's "current host" set.
  - Alternative: count only pending and accepted, so a declined invitee frees a seat. The editor would then disagree with the server about when "5" is reached.
- **OQ-2: 422 or 409 for the refusal?** **Default: 422**, for consistency with the list's over-5 422 (`handlers_scheduling_links.go:549-552`, `:821-824`), which is also a refusal that depends on the link's state, not on a malformed body. No current client branches on it. (PAC-112 D-9 is narrower, "every new validation failure is 422", and is not the reason; m-8.)
  - 409 would describe "the link is full" as a state conflict, closer to its meaning, but would be the operation's only 409.
- **OQ-3: Should the cap be 5 everywhere, as one shared value?** **Default: yes, the same value as the list rule**, so the editor, the list and the invitation always agree. A plan that changes one must change all.
- **OQ-4: Take SF-068 (lookup error is 404) into this work?** **Default: yes.** Same handler, the contract already says 500, and the factory's touch-it-fix-it rule applies to the contract's truthfulness here. It is a one-branch change, and AC-14 is its test.
- **OQ-5: A smaller body cap for unauthenticated routes** (public booking, `/api/auth/detect`)? **Default: no.** 1 MiB is already small, nginx answers first in production, and the free-text fields need field limits (OQ-7) rather than a transport limit.
- **OQ-6: The MCP server's request size.** The MCP server accepts any size when reached directly (dev compose publishes `3001:3001`, `docker-compose.yml:97-98`). Behind nginx it gets nginx's HTML 413, not JSON. **Default: out of scope.** The factory opens a follow-up: give `/mcp/` the JSON 413 and give the MCP server its own cap.
- **OQ-7: Field-length limits** for booking notes and names, NLP text, titles and descriptions. **Default: out of scope.** The factory opens one follow-up covering them, with the silent-failure register's validation-gap pattern as its frame.
- **OQ-8: Order of the cap against "user not found".** **Default: "user not found" first** (§3.2 item 5), so the 422 is only ever said about an invitable address and never hides a typo behind "the link is full".
  - Alternative: refuse at the cap before resolving the address, saving one lookup. That is cheaper, but the owner of a full link who mistypes an address gets told to remove someone.
  - Cost under the default (m-3): every call to a full link still costs one address lookup, outside any lock. That is the same per-request cost as any authenticated call, and the cap was never meant to bound lookups, only hosts (§1).

## 9. Decisions

- **D-1 [F]: no new body-size mechanism.** The first half of the ticket is already satisfied by PAC-81 (§0). This work adds only the backend wiring proof (AC-1, AC-2) and the register correction.
- **D-2 [F]: the single invitation is capped by link size, not by request.** The PAC-112 rule's intent ("no save takes a link past 5 by adding someone; keep and remove always work") is carried over. Its list-length mechanics do not apply to a request that has no list (§2.6).
- **D-3 [F]: decided at the write, and invitations are ordered against each other.** A count under today's shared lock is racy (§2.5), so a plain count would let two invitations reach 6. How they are ordered is the plan's choice, constrained by AC-9 to AC-11 and the PAC-101 deadlock rule.
- **D-4 [F]: a distinct 422, after the existing answers.** It leaves every current answer and its order intact, and adds one outcome only where a 201 would otherwise have been given.
- **D-5 [F, pending OQ-4]: the failed lookup becomes the documented 500** (SF-068), aligning the code with the contract text rather than the reverse.
- **D-6 [F] (factory decision on M-2): the failed link read keeps its 500 and is now logged and reported** (§3.2 item 10, AC-15), for the same reason as D-5: the contract's 500 already says so. It becomes a register item (SF-101 to be).
- **D-7 [F] (factory decision on M-1): two repositories.** The web gets one PR that only regenerates its generated types; it follows the contract's merge (README §1).
