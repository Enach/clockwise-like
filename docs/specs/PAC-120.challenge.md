### Major

**M-1. "No web change" is false. The contract change regenerates the web's committed types, so this is a two-repo change.**
- §3.2 item 9 says "neither needs a change". §5 puts "Any web change" out of scope.
- The web commits per-operation response types generated from the bundle. `inviteSchedulingLinkHost` is there with every response and its description: smart-calendar-flow `src/api/generated/types.ts:13071` onward (200 at `+18`, 201 at `+27`, 400 at `+36`).
- AC-14 adds a 422 and rewrites the 500's description. That changes `types.ts` (and possibly `schemas.ts`). README §2, stage 2 gate item 4 says "generated code is in sync in both repos". README §1 fixes the order: contract merges, then types regenerate. The cross-repo `openapi-check` runs on every PR against the paired branch (README §3).
- **Resolve**: say the web gets a regenerated-types PR with no behaviour change. Name it in "What must not change" next to `schedulingLinks.test.ts:112` and `:193`, and drop "any web change" from §5.

**M-2. Inherited scope misses a second contract-vs-code gap on the same operation: the link-read 500 is never logged or sent to Sentry.**
- `inviteHost` answers a failed link read with `writeError(w, "internal error", 500)`, not `writeServerError` (`backend/api/handlers_scheduling_links.go:912-916`). `writeError` only writes the body (`backend/api/handlers_settings.go:479-483`). The detail goes nowhere.
- The contract's single 500 for this operation says "The detail is written to the server log and Sentry only (PAC-21)" (`contracts/openapi/paths/booking.yaml:1664-1669`).
- The spec uses exactly this argument to take SF-068 in: the contract says 500 and the code disagrees (README §7.2). The same reasoning covers this branch, and AC-13 requires log and Sentry on the sibling branch. I found no row for it in `docs/factory/silent-failures.md` (searched for the handler and for unlogged `internal error`). §2.5 step 2 describes this branch only as "A read error is 500".
- **Resolve**: either take it in (it is the same kind of change as SF-068, with an AC like AC-13 for the link read), or record it as a known contract gap with a register row. Silently leaving it contradicts §7.2, which the spec relies on.

**M-3. Only PATCH and delete-while-waiting have falsifiers for the "no deadlock" promise. The cap path never runs under the mixed workload.**
- §3.2 item 6 promises "no deadlock with PATCH, delete, booking, accept, decline or leave" under the new ordering. AC-10 covers PATCH and AC-11 covers delete. §6 leans on `TestPAC101_ConcurrentWritesOnOneLinkNeverDeadlock` for the rest. That test cannot exercise the new code:
  - its link has at most 3 co-hosts (owner, b, c and the invitee d: `backend/api/pac101_test.go:548-559`, `:623-628`), so the count never reaches 5 and the refusal path never runs;
  - each round sends **one** invitation, always for d (`:626-628`), so two invitations never race each other alongside bookings, accept, decline, leave or delete.
- This matters because today's host writes all take `FOR SHARE` (`backend/storage/scheduling_links.go:520-528`, `:813-822`), and bookings take `FOR SHARE` plus advisory locks (`:663-669`, `:686-688`). Any ordering that is new for invitations (a stronger row lock, or a separate lock taken before or after the share lock) changes who waits on whom with bookings, a queued delete and the erasure's `FOR UPDATE` (`backend/storage/booker_erasure.go:86-117`). Only a mixed run at the cap boundary can show the absence of a cycle.
- AC-10 also uses two different addresses (X by invitation, Y by PATCH). The case where the PATCH's list adds the **same** address the invitation adds is untested. If the new ordering ever stops serialising an invitation against a PATCH, the PATCH's `coHostInvite` turns that collision into a 500 ("became a host during the save", `scheduling_links.go:1403-1418`).
- **Resolve**: add a criterion that runs the PAC-101 mixed workload (bookings, accept, decline, leave, pause, resume, delete) on a link that starts at 4 co-hosts, with at least two distinct new invitations per round. Assert: no 500, never more than 5 co-hosts, each invitation 201, 200, the 422 or the 404. Add an AC-10 variant where the PATCH's list adds the same address as the invitation.

**M-4. AC-12 does not say when the generation moves, so a test can be written that fails correct code or passes wrong code.**
- The guard overrides an answer only when an in-request re-check marked it stale (`backend/api/middleware.go:181-201`). The write's re-check is a `FOR KEY SHARE` read of `users` (`backend/storage/session.go:131`), which does not block a generation bump.
- So, for a cap refusal decided inside the write (§3.2 item 6):
  - generation moved **before requireAuth's read**: 401 at the door, whatever the cap code does. The test passes vacuously;
  - moved **between requireAuth and the write's re-check**: 401. This is the only timing that tells a correct placement from a count taken before the write;
  - moved **after the write's re-check**: the 422 stands, correctly. AC-12 as worded ("while … in flight") demands 401 here and would fail correct code.
- **Resolve**: pin the window as "after requireAuth's generation read and before the write transaction's re-check". The existing guarded-call seam fires at the start of `withLinkWriteTx` (`session.go:182-186`). State that a cap decided outside the write would answer 422 in that window, which is what makes the AC fail on a wrong implementation.

**M-5. AC-13 can pass today unless it requires the link read to succeed.**
- The handler reads the link and resolves the address on the same `h.db` (`handlers_scheduling_links.go:912`, `:934`). A blunt injection (closed pool, broken connection) fails the link read first, and the link read already answers 500 `{"error":"internal error"}` today (`:912-916`). That gives the same status and body AC-13 asks for, so the test is green on unchanged code.
- **Resolve**: say in the Given that the link read succeeds and only the address lookup fails. Make the log and Sentry assertion name the lookup's operation, so it cannot be satisfied by the link-read branch (which, per M-2, logs nothing today anyway).

### Minor

**m-1. The same-address race is not covered.** AC-9 uses two **different** addresses. Two simultaneous invitations of the **same** new address on a link with 4 co-hosts must give 201 and 200, never 422. Today `ON CONFLICT DO NOTHING` gives 201 and 200 (`scheduling_links.go:293-314`). A cap that checks the count before "already a host" would turn the loser into a 422, and AC-5 only covers the sequential re-invite. Add the variant.

**m-2. The owner-row claim has no cited invariant.** §2.5 (`PAC-120.md:130`) says the owner's own address "resolves to the owner, whose row already exists". No constraint guarantees an owner row, and no migration backfills one (`backend/storage/migrations/009_scheduling_links.up.sql` is the only DDL on the table). Every current create path inserts it (`scheduling_links.go:1453-1460`), and leave refuses the owner (`handlers_scheduling_links.go:1028-1031`). But the owner can still **decline** their own link: `respondToInvite` has no owner check (`handlers_scheduling_links.go:984-1004`), and `RespondToHostInvite` updates any row (`scheduling_links.go:434-449`). So AC-6's "unchanged (`accepted`)" holds only because of what was seeded. Either cite the invariant or say what a link with no owner row answers. Record the owner's self-decline as observed, out of scope.

**m-3. §1 overstates what the cap bounds.** Bullet 3 says repeated invitations "do the same lookups, without a bound". Under the OQ-8 default the address is resolved **before** the cap, outside any lock (`handlers_scheduling_links.go:934`). So a full link still costs one lookup per call, refused or not. The cap bounds hosts and slot-read cost, not lookups. Reword it, or make it a reason to weigh OQ-8.

**m-4. AC-1's halves need sharper falsifiers.**
- "The handler did not run" is vacuous with no session: requireAuth stops it with or without the cap (`middleware.go:97-100`). The 413 status is the real guard, and that is fine. Drop the clause or attach it to a public route.
- "The same route given exactly 1 MiB and a valid session does not answer 413" passes if anything else refuses the body. Require proof that the handler received all 1,048,576 bytes, or a specific handler answer.

**m-5. The body cap's 400 is undocumented.** §2.1 notes that a read error is 400 `"invalid request body"` (`backend/api/middleware.go:387-390`). That 400 applies on **every** route, including this one, whose 400 lists only "invalid id" and "email is required" (`booking.yaml:1628-1633`). The contract's global rule mentions only the 413 (`contracts/openapi/openapi.yaml:40-41`). This is a PAC-81 legacy, so record it (an audit row, or a sentence in OQ-6 or OQ-7) rather than fixing it here. The spec says the first half is "already built", so it should say what is still not described.

**m-6. AC-16 constrains test code, not product behaviour.** It is a plan obligation, and it is not falsifiable by any product change. Keep it, but label it as a regression constraint. Also state that the seeded 7-host link must leave the hosts able to accept and decline through the API, which the journey does (`e2e/tests/pac112-cohosts.spec.ts:443-446`).

**m-7. Most ACs lack "fails today" or "regression guard" labels.** AC-4, AC-5 (both links), AC-6, AC-7, AC-8 bullets 2-3, AC-11 and AC-12 pass on unchanged code. That is legitimate for guards, but only AC-1 and AC-2 say so. Label them, so the plan knows which tests must go red first (README stage 4).

**m-8. OQ-2's rationale leans on PAC-112 D-9, which is narrower than quoted.** D-9 is "every new **validation failure** is 422" (`docs/specs/PAC-112.md:438`). A full link is link state, not a malformed body, which is the OQ's own 409 argument. The default can stand, but restate the rationale as "consistency with the list's over-5 422", which is a state-dependent refusal too (`handlers_scheduling_links.go:549-552`).

### Citations I checked and found right (selection)

- **Body cap**: `bodyCapMiddleware` reads `io.ReadAll(io.LimitReader(r.Body, limit+1))` whatever the `Content-Length`. So a chunked body or one with no length (`ContentLength == -1`) is 413 once it passes 1 MiB. A declared length over the cap is 413 unread (`middleware.go:365-397`). Wired at `routes.go:39`, between CORS and the budget.
- `RegisterRoutes` is the only router (`backend/main.go:398-399`). No handler reads a body outside it, and the only `ParseForm` is in a test fake (`backend/internal/oauthfake/oauthfake.go:149`). Every handler's body is the middleware's in-memory copy, whether it decodes with `json`, `io.ReadAll` (`handlers_settings.go:112`, `handlers_llm.go:38`, `handlers_org_ai.go:99`, `handlers_sso.go:322`, `handlers_daily_recap.go:57`) or generated wrappers.
- No compressed request bodies are decoded anywhere, and there are no uploads: no `FileReader`, `FormData` or file input in web `src/` outside the generated types. 1 MiB is ample for every legitimate body.
- No backend test sends an oversized body through `RegisterRoutes`. The four PAC-81 tests wrap the middleware directly (`pac81_middleware_test.go:24-79`). The gap in §2.4 is real.
- nginx: `client_max_body_size 1m` and the JSON `@api_body_too_large` (`nginx/nginx.conf:77`, `:119-128`). `/mcp/` has no `error_page` (`:136-150`). nginx's 413 carries no CORS headers, which is harmless because the SPA and `/api/` share an origin.
- Lock facts in §2.5: `FOR SHARE` for invitations (`scheduling_links.go:520-528`); the PATCH's `UPDATE` as its first link lock (`:843-849`); the re-check as `FOR KEY SHARE` (`session.go:131`).
- Web: no `/hosts` call outside generated types, and both test pins are as cited (`src/api/schedulingLinks.test.ts:112`, `:193`). `isRequestTooLarge` at `src/api/client.ts:154-157`.
- MCP: no scheduling-link tool. `mcp/main.go:121-138` has no cap.
- e2e: `linkWith` is the only `/hosts` caller in e2e (`pac112-cohosts.spec.ts:79`). AC-32 invites 7 (`:444`).
