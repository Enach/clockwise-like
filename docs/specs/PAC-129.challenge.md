# Challenge — PAC-129 — 2026-11-18

- **Spec**: `docs/specs/PAC-129.md` at `7446f94` (branch `factory/pac-129-spec`).
- **Read against**: clockwise-like `origin/main` `285be20`; smart-calendar-flow `origin/main` `d18dee7`; smart-calendar-flow PR #174 (PAC-128, open). Every claim below was read with `git show origin/main:<path>` / `gh pr view|diff`. Spec line numbers are `PAC-129.md:<n>`.

**Verdict**: **revise**. On the agent definition's scale this is **reject**: return to spec-author. There are 2 BLOCKERs, 10 MAJORs and 13 MINORs.

The spec's reading of today's code is mostly accurate, and its core decisions hold: the person is a team member, not a manager-roster row; there is no account resolution; unknown is never shown as free; the upgrade is atomic. Two problems block it. First, the spec lets non-owners use the owner's credential and records no decision about it. Second, an existing Manager-mode code path voids two of the spec's own guarantees: removal withdraws everything (D-5), and figures are never persisted (D-6).

## Blocking

### B-1. Non-owner members get results from the owner's credential, and the spec records no decision about it

**What the spec says.** It justifies owner-credential free/busy as "exactly what that owner's calendar already shows" (`PAC-129.md:186`, D-2 `:386`). Its desired behaviour then has *any* member run Find a time over added people (`:189-193`, AC-13 `:264` "when M runs Find a time").

**What the code does.**
- Availability is open to any member (`backend/api/routes.go:271`; `handlers_teams.go` `availability` behind `requireMember`).
- The free/busy read runs on the credential of whoever is passed as requester. A permanent refusal is recorded as that account's loss (`backend/engine/freebusy_service.go:140-165`).
- So a non-owner M's request would spend the owner's provider quota. It would appear in the owner's provider audit trail. If refresh fails, it would mark the owner's calendar lost.
- M also gets the union of busy times for people M may have no standing to see. M can be in a different organisation from the owner and X. The slot gaps are busy time, because every busy interval is a hard block (`engine/team_availability.go:87-104`).

**Why this blocks.**
- The owner gives the owner's own view, but the reader is someone else.
- OQ-6 already accepts that figures derived from the owner's view are owner-only (`:372`, D-6 `:390`). Find a time is the same data, given to the same non-owners, at day granularity.
- Neither §5 nor §8 mentions this delegation. "Do not widen" (`:146`) is asserted only for analytics.

**What would resolve it.**
1. Add an OQ with a default: who may cause a read through the owner's credential (owner only, or any member).
2. State what a non-owner may learn about an added person's busy time from Find a time.
3. State whether the owner is told that members' requests use their calendar connection.
4. Add an AC at `[contract]` that pins the chosen answer. For example: a non-owner's Find a time either makes no call with the owner's token, or makes one and is answered under the stated rule.

### B-2. Manager mode bypasses D-5 and D-6, and OQ-13 makes it reachable

**The removal path.** The spec names one removal path. The codebase has two.
- `DELETE /api/manager/team/members/{email}?team_id=` removes formal memberships, the manager's assignment and the team's pending invites (`backend/api/handlers_manager.go:362-408`, `backend/storage/manager.go:215-238`).
- It does this **without the team-row lock**: the owner-role check runs outside the transaction (`handlers_manager.go:385-398`). D-8's ordering (`:392`) therefore does not cover it.
- Today it would leave an added person on the team. It would also race an upgrade on accept, so the person could end up a Paceday member after the owner "removed" them.

**The roster default (OQ-13).** It adds added people to the owner's Manager roster "as formal members already do" (`:379`). That default carries over three things the spec forbids.
- **Account resolution.** Synthetic formal rows set `MemberUserID` (`handlers_manager.go:684-696`). That makes `is_paceday_user` true (`:277`, `:620`).
- **Roster writes.** Any patch or schedule on a synthetic member goes through `getOrCreateScopedMember`, which **writes a roster row** (`handlers_manager.go:708-744`). OQ-13 says "No roster row is written".
- **Persisted figures.** Once a roster row exists, manager analytics reads the person's week through the manager's credential and **persists** it in `team_analytics_cache` (`backend/engine/manager.go:484-516`). That contradicts D-6 "never persisted" (`:390`) and AC-17's last bullet (`:283`).
- **Precedence.** If the manager already has an assignment for the same address, the assignment wins the merge (`handlers_manager.go:681-683`). The roster then shows "On Paceday" (`Team.tsx:956-958`) beside the team list's "not on Paceday" for the same person. AC-2 then fails on the screen even if it passes on the wire.

**What would resolve it.**
1. State the required outcome of the Manager-mode team-scoped removal when the address is an added person. Bring that removal under D-8's ordering requirement.
2. Restate OQ-13's default as observable requirements. Does an added person in the owner's roster carry an account flag? Can cadence be set or a 1:1 scheduled? Can their figures be persisted?
3. Add ACs at `[contract]`:
   - removal via the Manager path leaves no added entry and no pending invite;
   - the Manager roster shows no account indicator for an added person;
   - no `team_analytics_cache` row exists for an added person after any manager read.

## Non-blocking — MAJOR

### M-1. OQ-6's default contradicts AC-17

OQ-6's default says non-owners "see the row's existence without figures" (`PAC-129.md:372`). AC-17 says "a non-owner member sees no per-person row for X" (`:282`). Both cannot be tested. Pick one and align D-6 (`:390`) with it.

### M-2. OQ-2's default turns "free" into a new false claim once counts exist

Today the server makes no per-slot count claim (`engine/team_availability.go:21-25`). The spec adds "N free / busy / unknown" (`:191`, AC-10 `:257`). It still counts an unreadable or disconnected **Paceday member** as *free*, because OQ-2 keeps them free (`:368`).

The pinned behaviour is only that such a member does not block slots. `TestPAC81_TeamAvailabilityUnreadableMemberTreatedFree` asserts `len(slots) > 0` and nothing about counts (`backend/engine/pac81_test.go:268-287`).

So the default is unsound for the new count: "3 of 5 free" would include a member whose calendar was never read. Either count them as unknown (slot offering unchanged, so nothing pinned breaks), or state and test why "free" is acceptable there. AC-10 needs a Paceday member with no calendar in its fixture to pin it.

### M-3. SF-032 lives in a shared provider method; the spec names three consumers and has more

`calendar.(*CalendarClient).GetFreeBusy` (`backend/calendar/freebusy.go:15-41`) and `OutlookClient.GetFreeBusy` (`calendar/outlook_client.go:110-143`) are also used by:
- `GET /api/calendar/freebusy` (`backend/api/handlers_calendar.go:210`). The MCP tool `clockwise_find_free_slots` calls this (`mcp/tools.go:129-137`).
- smart scheduling (`backend/engine/smart_schedule.go:71`).
- compression (`backend/engine/compression.go:130`, `:172`), through `engine/cal_iface.go:89`.

AC-11 (`:260`) lists team availability, manager analytics and `/api/freebusy` only. AC-28 (`:317`) requires MCP answers unchanged.

The spec must state, for each of these surfaces, whether an unreadable calendar changes what it returns. Otherwise AC-28 is either silently false or forces an unstated constraint. Alternatively, it should split SF-032 into a prerequisite ticket (rule 7: "is it one spec?").

### M-4. OQ-7's default is not a default, and nothing says what happens at a provider limit

"50 per team. To confirm against the providers' per-request free/busy address limits" (`:373`, also `:163`) leaves the gate open.

- The free/busy service sends **all** addresses in one call with one 5 s timeout (`freebusy_service.go:126-165`). The Google reader sends every item in one `Freebusy.Query` (`calendar/freebusy.go:16-25`).
- A provider refusal degrades **every** address to unknown (`freebusy_service.go:178-191`).
- Google's freeBusy documents a maximum of 50 calendars per query. The Microsoft limit was not verified here or by the spec.
- The e2e fake does not model any limit (`e2e/fake-google/freebusy.go:15-54`).

Required: a decided cap, and a stated requirement that no added person is reported unknown *because of* the number of people on the team. Add an AC at the cap (49 added people plus the owner) that can fail.

### M-5. The legacy invite rows conflict with AC-20 and AC-26

**Today's rows.**
- Invites were not normalised before `ee6e4ab` (2026-08-12, which added `normalizeManagerEmail` at `handlers_teams.go:201`).
- Duplicates accumulate by design today (SF-012, `storage/teams.go:234-243`; no uniqueness in `013_teams.up.sql:17-26`).
- So production can hold several pending rows per `(team, address)`, in mixed case.

**What the spec asks.**
- AC-20 asks that no second invitation exists (`:293`).
- AC-26 asks that "every ... invite reads exactly as before" after migration (`:311`).
- AC-19 assumes one pending invitation per added person (`:289-291`).

**What is missing.** The spec must say:
- what becomes of existing duplicate and mixed-case pending invites;
- whether AC-20's guarantee covers them;
- what accept does for a legacy invite with no added entry (OQ-8 creates none, `:374`).

Then add the legacy case to AC-26's fixture.

### M-6. PAC-128 is not in Backlog; PR #174 is open on the same files and changes D-7's premise

**What the spec claims.** "PAC-128 is in Backlog ... If PAC-128 lands first, nothing here changes" (`:31`, D-7 `:391`).

**What is actually there.** smart-calendar-flow PR #174 ("Team invite: suggest people from calendar contacts", opened 2026-11-17, mergeable) rewrites the same code:
- `InviteDialog` in `ProtectedHoursTab.tsx`;
- `ContactEmailAutocomplete` (new `exclude`, `onSubmit`, `autoFocus` and `label` props);
- `CreateTeamDialog`, which loops `inviteMember` per address.

**Why it matters.**
- The `exclude` behaviour AC-3 needs (`:232`) **does not exist on main**: there is no exclude prop in `src/components/team/ContactEmailAutocomplete.tsx:7-19`. It arrives with #174.
- #174 treats `status: "pending"` members as "pending invitees". This spec redefines that state.
- Under OQ-4 every invite in #174's create-team loop also adds the person, counts toward the cap, and hits AC-20's "already pending" answer. #174 renders that answer as a failed address if it is an error.

**What is required.** State the ordering against #174. State what an "already pending" invite answers: success-shaped or error. State what "pending" means on the web member model.

### M-7. GDPR position for people without an account is a default, not a decision

The spec's defaults add up as follows:
- adding is silent (OQ-3, `:369`);
- every member sees the person's email (OQ-5, `:371`);
- there is no erasure path except owner removal (OQ-10, `:376`);
- §5 defers the erasure tool (`:323`).

Personal data not obtained from the person normally carries an information duty. The spec never says who the controller is for these records, or on what basis Paceday holds them without telling the person. OQ-10's promised "manual operator procedure documented in the runbook" has no AC, and `docs/runbook.md` has no such section today.

**What is required.**
- Put the controller and notification position to the owner as an explicit OQ.
- Make the runbook erasure procedure an AC, or drop the promise.
- State that an erasure request from a person who **has** an account also covers their added entries. Account deletion does not reach them, because they are not linked to the account.

### M-8. The added-person label and the two "Add person" controls

**The label.**
- §3 shows added people as "not on Paceday" (`:179`). AC-27 (`:315`) makes demo say the same.
- An added person may well hold an account: AC-8 (`:244`) is built on exactly that.
- So the label is a false statement for those people, and the spec otherwise sets out to stop false statements (SF-051, SF-054).

**The two controls.**
- An owner in Manager mode sees two controls: the existing Manager "Add person" (`src/pages/Team.tsx:1127-1300`, a private roster row with account resolution) and the new team add.
- Both would be called "Add person" and they behave differently. The spec gives no requirement that tells them apart.

**What is required.** A truthful label requirement (for example, describe the membership kind, not the account). Also a requirement that the two controls state their different effects.

### M-9. SF-053 is claimed as inherited but only partly closed

**What SF-053 covers.** `silent-failures.md:164` covers name/index matching, missing rows shown as 0, invented `free_minutes`, and a wrong week label. All are visible at `src/api/teams.ts:438-452`.

**What the ACs cover.**
- AC-16 (`:277`) tests attribution with duplicate names, and invented free time only for the **added** person's row.
- AC-17 (`:279-283`) covers "no data" on the server, not on the web.

**What is not covered.**
- The web still labels the current week whatever `date` was asked (`teams.ts:438-441`).
- It still invents free time for Paceday rows (`:452`).
- The owner-excluding filter that feeds the index fallback is untested (`:443`).

Add these to AC-16, or name what stays open.

### M-10. Caps and the acceptance path

D-8 (`:392`) and AC-23 (`:301`) bound adds and invites. They do not state:
- whether **accepting a legacy invite** (no added entry, OQ-8) can take a team past the cap;
- what happens to existing teams already above 50 (there is no cap today, `:161`);
- whether the owner counts toward the 50.

Each needs a sentence and an AC clause.

## Non-blocking — MINOR

1. **The "busy" count can never be non-zero.** Every busy interval, including Paceday focus blocks, is a hard block (`engine/team_availability.go:87-104`, `:154-160`). An offered slot therefore always has 0 busy. AC-10's "0 busy" (`:257`) cannot fail. Either drop the busy count or define slots that include busy members.
2. **AC-13 and the cache.** A *known* result cached before the owner disconnects keeps being served for up to 15 minutes. Only degraded results computed while lost are not cached (`freebusy_service.go:167-189`). AC-13 (`:264`) must state its timing relative to the cache, or the test passes or fails by accident.
3. **AC-25 is incomplete.** It (`:307`) covers add and removal but not the add-on-invite write (OQ-4) or the upgrade on accept. Both are new account-data writes under the PAC-71 re-check.
4. **AC-26's last clause cannot fail** (`:311`). "Refused while serving" holds for every migration through the runner (`backend/storage/migrate_when_stopped.go:421-520`). Move it to §6.
5. **AC-28 cannot fail today** (`:317`). It belongs in §6, and M-3 decides whether it is true.
6. **AC-17's fixture omits the owner** (`:279`). The owner is a Paceday member with or without a stored week, and the AC does not say whether the owner is P1 or a third member. The averages are ambiguous.
7. **AC-5 compares against "every member's address"** (`:236`), but a member is listed by one address (`storage/teams.go:209-216`). An account can hold several confirmed addresses (`storage/identity.go:199`). Say whether a secondary address of a member is refused. Refusing it would reveal that the addresses are linked.
8. **The owner-credential batch and the PAC-81 budget.** The batch runs on its own 5 s timeout, not the per-item pool (`freebusy_service.go:132-134`; pool at `team_availability.go:76-86`). Say whether a budget cut during it is the 503 or "unknown" (§6 row `:341`).
9. **New references to accounts.** Any new reference to an account (for example, who added the person) must be classified in the PAC-71 emptiness inventory. `TestPAC71_EveryUserForeignKeyIsClassified` fails otherwise (`backend/storage/pac71_test.go:100`, `storage/emptiness.go:74-108`). §2 does not mention it. State the requirement, and what happens to added people when the adding owner's account is deleted (OQ-1 covers only loss of ownership).
10. **The §7 old-web claim is conditional.** "The old web lists only account members" (`:359`) holds only if the contract keeps added people out of `members`. The old web renders whatever `members` holds, unvalidated (`src/api/teams.ts:172-177`, `:144-154`). The README §1 deploy order also creates a new-backend/old-web window on every release, not only on rollback. State the requirement, not the hoped-for outcome.
11. **Attendee emails in the URL.** Scheduling puts every attendee's email in the URL query (`src/components/team/FindATimeTab.tsx:67-78`). The spec extends that to people who never consented (`:193`). Either state it as accepted or require otherwise.
12. **Demo and the web "Pending" state.** The demo slot finder and the web count only `status === "active"` (`src/demo/teams.ts:22`, `src/api/teams.ts:424`, `FindATimeTab.tsx:69`). The demo invite creates `pending` (`src/api/teams.ts:541-549`). AC-27 (`:315`) must say whether an invited-and-added person counts in demo Find a time and the attendee list.
13. **Stale or imprecise citations** (see below).
