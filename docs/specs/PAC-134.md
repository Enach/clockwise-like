# Spec — PAC-134: Operator tool: erase an email address across all tables (GDPR)

- **Linear**: https://linear.app/paceday/issue/PAC-134/operator-tool-erase-an-email-address-across-all-tables-gdpr
- **Status**: draft
- **Author**: spec-author
- **Base**: origin/main `c1b6564` (includes PAC-129, PAC-130, PAC-148, PAC-149)
- **Inherited scope**: no `x-uncertain` marker and no open `api-audit.md` finding sits on an operation this touches. One contract **statement** becomes false and must be corrected: `listSchedulingLinkBookings` says "A live or paused link never holds an erased booking … `booker_name` and `booker_email` here are always the values the booker typed" (`contracts/openapi/openapi.yaml:8933-8935`). After this ticket a live or paused link can hold an erased booking (§3.4).

## 1. Problem

People who never signed up for Paceday still end up in its database, by
address, because Paceday users put them there: a team owner adds or invites
them, a manager's roster lists them, a link owner invites them as a co-host, or
they book a meeting through a public link. When such a person asks to be
erased (GDPR Art. 17), the operator has no tool for it. Today the only path is
a hand-typed SQL block in the runbook (PAC-129 AC-27) that:

- misses several places that hold the address (co-host address invitations
  added by PAC-149, public bookings on live links, stored co-host outcomes of
  keyed link creations);
- matches some tables with a different normalisation from the code that wrote
  them;
- leaves no record that the erasure happened, and nothing that proves it was
  complete;
- is easy to get wrong under pressure (a typo in one `DELETE` silently erases
  nothing, or the wrong thing).

The cost: Paceday cannot answer an erasure request reliably, and an operator
who tries can leave copies behind without knowing it.

### 2.3 Normalisation in code

The one address normaliser trims the PAC-129 26-code-point set, lowercases,
and requires `net/mail` to parse the result to itself
(`api/handlers_manager.go:865-880`, `storage/address_trim.go:25`). The database
equivalent is `lower(paceday_trim_ecma(x))` (`041…:8-15`). Tables differ in what
they store (column "How stored" above): T3/T4 use `btrim` (spaces only), T7/T8/T9
keep letter case.

## 3. Desired behaviour

### 3.1 The command, in one paragraph

An operator, on the server, gives one address plus their name and a reason.
The tool finds every stored copy of that address in third-party data,
erases each one (delete or anonymise, per §3.4), records that an erasure ran —
with counts, never the address — and prints the counts. A dry run prints
the same counts and changes nothing. Running it again finds nothing and
changes nothing. It never prints, logs or stores the address.

### 3.2 Boundary with accounts

- When the normalised address equals, under `lower()`, the address of **any
  account** (including a case-variant), the tool **refuses**: it changes
  nothing, names the account id(s), and points at the account paths
  (`free-address`, and the missing account deletion, OQ-1). The refusal has its
  own exit code. A dry run reports the counts **and** the refusal, with the same
  exit code.
- Rationale: a person with an account is a user, not a third party. Erasing
  copies of their address while the account keeps it is incoherent (the copies
  would come back through normal use), and their team-added entries are their
  data as a user (PAC-129 §3.11 note). The sequence for an account holder who
  wants everything gone is: free the account's address, then run this tool
  (the address then matches no account).
- An address equal to a `free-address` placeholder matches its account and is
  refused like any other.
- An account's connected calendar address (A') does not make the address
  "account-held" for this rule (it is the account's own setting, removable by
  `reassign`); the tool does not read or change it, and says so in the runbook.

### 3.3 Matching

- **Input**: normalised by the one address normaliser (§2.3). An input that is
  empty or not a single valid address after normalisation is a usage error;
  nothing is read.
- **Rows**: a stored value matches when trimming the PAC-129 set and
  lowercasing it, **in the database**, equals the normalised input lowercased
  by the database. Both sides are lowercased by the same function, so a
  difference between the Go and database lowercase tables cannot cause a miss.
  This one rule applies to every table, whatever that table stores (case kept,
  `btrim`-only, or legacy unnormalised rows). Case variants and leading/trailing
  space variants are all matched.
- **In JSON** (T8): an outcome entry matches when its `email` value matches by
  the same rule. The row's stored outcomes are cleared as a whole (§3.4).
- **Not matched** (out of scope, §5): substrings in free text; sub-addresses
  (`a+tag@x`), dot variants, `googlemail.com`/`gmail.com`, IDN vs punycode —
  these are different addresses.

### 3.4 Per-place decision

| Place | Decision | Why |
|---|---|---|
| T1 added person | **delete** the entry | the entry is the address; same as removal from the team |
| T2 team invitation, every status | **delete** the invitation | its token stops working; an accepted invitation's member stays a member (membership is account-bound) |
| T3 roster entry | **delete** (its assignments T4 go with it) | as the runbook; the entry is the address |
| T4 assignment | **delete** | |
| T5 1:1 history | **delete** | keyed by the person's address |
| T6 cached figures | **delete** | a cache; recomputed only for roster entries |
| T7 co-host address invitation | **delete** the invitation | as if the owner removed it; the link and its other hosts are unchanged |
| T8 stored co-host outcomes | **clear** the stored request digest and outcomes of each matching key, as the 24-hour expiry does; owner, key, link and time stay | a keyed retry of that creation within 24 h then gets the existing "key reused" answer instead of a replay |
| T9 booking | **anonymise** into PAC-40's erased state (name and email blank, erasure time set), on **any** link — live, paused or deleted — and any status; notes per OQ-2 (recommended: blanked too) | the booking keeps its times, status, calendar references and use count, so busy time and `uses` do not change; already-erased bookings no longer match and are not counted again |
| T10 earlier operator records | **kept, counted** (reported as "kept") | accountability record of an operator action (OQ-4) |
| free text (§2.2) | **not touched, not searched** | §5 |
| in-process free/busy cache | **not reachable**; expires within 15 minutes | stated in the runbook |

An erased booking on a live or paused link is shown to its owner as erased
(the way the archive shows one), never as a booking with a blank name and
blank email; the contract statement in "Inherited scope" is corrected.

### 3.5 Transaction, concurrency, idempotence

- One run is **one transaction**: either every place in §3.4 is erased and the
  audit record written, or nothing changes. Every lock wait inside it is
  bounded; a timeout, deadlock, cancellation or database error rolls everything
  back and exits with the failure code. The operator reruns.
- The run does not stop the app and does not block it beyond the bounded waits
  on the rows it changes.
- **Live writes**: a matching row committed **before the run starts** is
  erased. A row written concurrently and committed after the run's statement on
  that place is not (it is a new copy, e.g. the person booked again); a rerun
  finds it. The runbook says to rerun once if the person was active.
- **Two concurrent runs** for the same address both succeed; no row is
  counted by both; their counts add up to the rows that existed.
- **Idempotence**: a second run finds zero everywhere, changes nothing, exits
  success, and writes an audit record with zero counts.
- **Migrations**: the command behaves like the PAC-71 subcommands — pending
  migrations are applied only when the app is not serving, otherwise it refuses
  and changes nothing; it refuses while a migrator holds the maintenance lock.
  The **dry run never applies a migration**: on a schema older than the one
  this ticket needs it exits with the failure code and says so.

### 3.6 Audit record

- One operator audit record per non-dry run that commits (zero counts
  included), with: the action (erase address), operator, reason, time,
  per-place counts (erased and kept), whether any account matched (always
  "no" when it committed).
- It contains **no address, no hash or other derivative of the address, no
  name** from the erased rows, and no row ids of erased rows. (A hash of an
  address is still personal data and is reversible by dictionary.)
- The operator name and the reason are refused (usage error, nothing read) when
  either contains the normalised address, compared case-insensitively. The
  runbook tells operators to put the request's ticket reference in the reason —
  that is how a later audit ties the record to the request.
- A dry run writes no audit record (like `booker-erasure status`), OQ-6.
- A failed run writes no erasure record (nothing changed).
- No activity entry is written for the users whose data changed, and nobody is
  emailed (OQ-3).

### 3.7 Output and exit codes

- Output, on success and on dry run: one line per place of §3.4 with its count
  (erased, or would-be-erased on a dry run, or kept), and a total; on a dry run,
  a line stating nothing changed. Account refusal adds the account id(s).
- **Never** the address, a name, a title, a note, a link slug, or a row id of an
  erased row — on standard output, standard error, the backend log or Sentry.
  Database errors are reported by class (SQLSTATE or a fixed word), never by the
  driver's message, which can repeat row data (as `storage/focus_blocks.go:153-159`
  already warns).
- How the address reaches the command must keep it out of the shell history and
  process listings if possible (OQ-5).
- Exit codes:
  - **0** done (including "nothing found"), or dry run done;
  - **1** failure: database unreachable, schema too old, migration refused,
    maintenance lock held, lock timeout, deadlock, any query error — nothing
    changed;
  - **2** usage: missing or invalid address, missing operator or reason,
    operator/reason containing the address — nothing read;
  - **3** refused: the address belongs to an account (§3.2) — nothing changed.

### 3.8 Runbook

The "Erasing an address" section is rewritten to use the tool: when to use it,
how to run the dry run first, the account-holder sequence (§3.2), what it erases
and keeps (§3.4), what it cannot reach (free text, in-process cache ≤ 15 min,
backups ≤ 14 days, container logs until rotation, provider calendars, sent
emails, re-detection from a manager's calendar §2.6), the exit codes, the
rerun advice, and that the hand-written SQL is withdrawn. It keeps listing
every place of PAC-129 §3.11, so PAC-129 AC-27 still holds.

## 5. Explicitly out of scope

- **Account holders' erasure / account deletion.** No account deletion exists
  today (§2.4); this tool refuses account-held addresses. Follow-up (OQ-1).
- **Free text**: titles, notes of other bookers, activity entries (typed NLP
  text, meeting titles), meeting briefs, analytics top titles, no-meeting-zone
  labels. Neither searched nor changed: substring matching would erase other
  people's content and has no reliable boundary.
- **Address equivalence beyond trim and lowercase** (sub-addressing, dots,
  domain aliases, IDN).
- **Suppression of re-ingestion** (manager detection from a calendar, a new
  invitation, a new booking): no blocklist is kept (OQ-4b).
- **Copies outside the database**: backups (until their 14-day retention),
  container logs (until rotation), Sentry, providers' calendar events, emails
  already sent, the backend's in-process free/busy cache (≤ 15 minutes). The
  runbook states them.
- **Notifying anyone** (the erased person, team owners, managers, link owners):
  the operator answers the requester through whatever channel the request came
  by (OQ-3).
- **An HTTP, web or MCP surface**: operator-only, like every other
  `paceday-operator` command.
- SF-005 (booker email not validated): unchanged; the matching rule tolerates
  invalid stored values.

## 7. Rollback

- Reverting the code removes the command; **erasures already done stay done**.
  Only a backup taken before the erasure (≤ 14 days) holds the values, and
  restoring one to undo an erasure defeats the request; after any restore the
  operator must rerun the erasures done since that backup (the runbook keeps a
  list via the audit records' times and the ticket references in their
  reasons).
- The audit action is a schema change (the allowed-action list). Its down step
  must not delete or rewrite erase records (PAC-71 rule); the contract stage
  decides how (e.g. the down step leaves the widened list in place or refuses
  while erase records exist).
- The live-bookings contract change (erased bookings on live links) is
  additive for readers that check the erased marker; the web must render it
  before the backend can erase a live booking, per the cross-repo ordering
  (README §1). A web rollback without a backend rollback shows erased live
  bookings as blank rows — not a data loss.
