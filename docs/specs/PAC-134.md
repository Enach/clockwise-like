# Spec — PAC-134: Operator tool: erase an email address across all tables (GDPR)

- **Linear**: https://linear.app/paceday/issue/PAC-134/operator-tool-erase-an-email-address-across-all-tables-gdpr
- **Status**: draft, revision 1 (answers challenge round 1 on `c99938a`, recorded at the end)
- **Author**: spec-author
- **Base**: origin/main `c1b6564` (includes PAC-129, PAC-130, PAC-148, PAC-149)
- **Inherited scope**: no `x-uncertain` marker and no open `api-audit.md` finding sits on an operation this touches. One contract **statement** becomes false and must be corrected: `listSchedulingLinkBookings` says "A live or paused link never holds an erased booking … `booker_name` and `booker_email` here are always the values the booker typed" (`contracts/openapi/openapi.yaml:8933-8935`). After this ticket a live or paused link can hold an erased booking (§3.4).

## 1. Problem

People who never signed up for Paceday still end up in its database, by
address, because Paceday users put them there: a team owner adds or invites
them, a manager's roster lists them, a link owner invites them as a co-host, or
they book a meeting through a public link. People who **do** have an account
end up there the same way, in entries that are not linked to their account
(PAC-129 §3.11). When such a person asks to be erased from that data
(GDPR Art. 17), the operator has no tool for it. Today the only path is a
hand-typed SQL block in the runbook (PAC-129 AC-27) that:

- misses several places that hold the address (co-host address invitations
  added by PAC-149, public bookings on live links, stored co-host outcomes of
  keyed link creations);
- matches with a rule that differs from the code that wrote some of the rows
  (§2.3);
- leaves no record that the erasure happened, and nothing that proves it was
  complete;
- is easy to get wrong under pressure (a typo in one `DELETE` silently erases
  nothing, or the wrong thing).

The cost: Paceday cannot answer an erasure request reliably, and an operator
who tries can leave copies behind without knowing it.

### 2.3 Normalisation and lowercasing in code — two different functions

- The one address normaliser trims the PAC-129 26-code-point set, lowercases
  **with Go's `strings.ToLower`**, and requires `net/mail` to parse the result
  to itself (`api/handlers_manager.go:865-880`, `storage/address_trim.go:25`).
  T1–T4 are written in that form.
- Co-host comparisons use **PostgreSQL `lower()`** instead, because Go's
  lowercasing "is not that comparison for non-ASCII text"
  (`storage/scheduling_links.go:1523-1527`). T7 and T8 keep the case typed;
  T9 keeps the case typed; `users.email` keeps case, `email_key` is database
  `lower()`.
- PostgreSQL `lower()` depends on the database's character-type locale. Under
  `C` (the e2e stack: `e2e/docker-compose.e2e.yml:64`) it lowercases ASCII only:
  `lower('Ünal@Ext.Example') = 'Ünal@ext.example'`; under `en_US.utf8` it gives
  `ünal@ext.example`. Go gives `ünal@ext.example` everywhere. `net/mail` accepts
  such addresses.
- So one person's address can be stored as `ünal@…` (Go-lowered, T1–T4),
  `Ünal@…` (case kept, T7–T9, `users.email`) and compared by a lowercasing that
  does not equate the two on a `C`-locale database.

### 2.6 Locks of the live paths

PAC-101 fixes the lock order of link, host and booking writes
(`contracts/features/PAC-101.md:157-175`: booking save takes the link
`FOR SHARE` before the booking row; invite/accept/PATCH take the caller's
`users` row, then the link, then host rows; "erasure (PAC-40 part B)" takes the
link `FOR UPDATE`, then bookings, then the owner's `users` row) and a 10 s wait
cap per lock wait, past which a live request answers 500 (`:178-195`). PAC-129
D-8 (`docs/specs/PAC-129.md:696`): every team membership write takes the team
row lock before any read its decision rests on.

### 2.7 Re-creation paths

Manager detection writes `auto` roster rows from the manager's calendar
(`engine/manager.go:191`, `:270`); a person still on that calendar is detected
again after any erasure. An account holder's address comes back through normal
use (invitations, added entries, bookings) as long as the account exists.

## 3. Desired behaviour

### 3.1 The command, in one paragraph

An operator, on the server, gives one address plus their name and a reason.
The tool finds every stored copy of that address in other people's data
(§3.4), erases each one (delete or anonymise), records that an erasure ran —
with counts, never the address — and prints the counts. A dry run prints the
same counts and changes no data. Running it again finds nothing to erase. It
never prints, logs or stores the address, and never touches an account.

### 3.2 Boundary with accounts

- The tool **never changes an account** or anything an account owns: its
  address, settings, identity, sessions, its own memberships, its accepted or
  declined co-host entries, its links, its bookings as owner. Account deletion
  is not this tool (OQ-1).
- When the address matches (§3.3 rule) the address of one or more accounts
  (case variants, freed placeholders included), the person is still a third
  party **in other people's data**, and PAC-129 §3.11 [O] requires those copies
  to be reachable. So:
  - **without** the account acknowledgement, a run changes nothing and exits
    with the "account-held" code, printing the matching account ids; a dry run
    prints the counts and the account ids and exits with the same code;
  - **with** the account acknowledgement, the tool erases the third-party
    copies of §3.4 exactly as for anyone else, prints the account ids, and
    records them in the audit record; a dry run with the acknowledgement exits
    0.
  - The runbook explains the consequence: the copies come back through normal
    use while the account exists (§2.7), and if the person wants the account
    gone too, that is account deletion (OQ-1), not this tool.
- The account check is a snapshot taken inside the run's transaction: an
  account created while the run is in progress is not seen. That is acceptable
  because the tool never touches accounts; the only effect is that the run did
  not ask for the acknowledgement.
- An account's connected calendar address (A') is not considered by the
  account check and never changed; the runbook says so.

### 3.3 Matching

- **Input**: trimmed of the PAC-129 set; it must be a single valid address
  under the one address normaliser's validity rule (§2.3). An input that is
  empty or not a valid address is a usage error; nothing is read.
- **Two lowercasings, both sides.** The code has used two lowercasing
  functions — the Go one and the database's `lower()` — and the database one
  depends on the database's locale (§2.3). A stored value matches the input
  when, after trimming the PAC-129 set from both:
  - their Go lowercasings are equal, **or**
  - their database lowercasings are equal.
  This rule is the same for every place in §3.4 and for the account check, and
  must hold whatever the database's locale (`C` included). It does not depend
  on how a given place stored the value (Go-lowered, database-lowered,
  `btrim`-only, case kept, legacy unnormalised).
- **Hygiene**: the input reaches the database only as a bound parameter, never
  inside statement text (a failed statement's text is logged by PostgreSQL).
- **In JSON** (T8): a stored outcome row matches when any `addresses[].email`
  or `removed[].email` in it matches by the same rule. The row's stored
  outcomes are cleared as a whole (§3.4).
- **Not matched** (out of scope, §5): substrings in free text; sub-addresses
  (`a+tag@x`), dot variants, `googlemail.com`/`gmail.com`, IDN vs punycode,
  and case equivalences neither lowercasing makes (e.g. `ß`/`ss`) — these are
  treated as different addresses.

| T2 team invitation, every status | **delete** the invitation | its token stops working; an accepted invitation's member stays a member (membership is account-bound and never touched) |
| T3 roster entry | **delete** (its assignments T4 go with it) | as the runbook; the entry is the address, and is the manager's record about the person, also when linked to an account |
| T4 assignment | **delete** | |
| T5 1:1 history | **delete** | keyed by the person's address |
| T6 cached figures | **delete** | a cache; recomputed only for roster entries |
| T7 co-host address invitation | **delete** the invitation | as if the owner removed it; the link and its other hosts are unchanged |
| T8 stored co-host outcomes | **clear** the stored request digest and outcomes of each matching key, as the 24-hour expiry does; owner, key, link and time stay | a keyed retry of that creation within 24 h then gets the existing "key reused" answer instead of a replay |
| T9 booking | **anonymise** into PAC-40's erased state (name and email blank, erasure time set) **and blank the notes** (OQ-2), on **any** link — live, paused or deleted — and any status | the booking keeps its times, status, calendar references and use count, so busy time and `uses` do not change; already-erased bookings no longer match and are not counted again; a keyed public-booking retry of an erased booking within 24 h gets "key reused" instead of a replay (§2.5) and books nothing |

An erased booking on a live or paused link is shown to its owner as erased
(the way the archive shows one), never as a booking with a blank name and
blank email; the contract statement in "Inherited scope" is corrected. Because
the web parses the live bookings list strictly (§2.5), the **web must accept
the new shape before any live booking is erased**: the contract stage fixes the
order; the runbook makes "the web release that reads erased live bookings is
deployed" a precondition of using the tool (erased live bookings exist only
after an operator runs it).

### 3.5 Transaction, locks, concurrency, idempotence

- One run is **one transaction**: either every place in §3.4 is erased and the
  audit record written, or no data changes. A timeout, deadlock, cancellation
  or database error rolls everything back and exits with the failure code. The
  operator reruns.
- **Live requests come first.** The run must not make a live request fail:
  - the whole transaction is bounded in duration, **below** the live paths'
    10 s per-wait cap (PAC-101 §4.2), so a live request waiting on a row the
    tool holds gets it before its own cap; past the bound the tool rolls back
    and exits 1;
  - the tool takes its locks in an order compatible with PAC-101 §4.1 (link
    before its host and booking rows) and PAC-129 D-8 (team row before
    membership rows), so no lock cycle with a live path exists. The contract
    states the tool's lock order and which side a deadlock can choose as the
    victim; if a cycle is still possible, the victim must be the tool.
- **Live writes**: a matching row committed **before the run starts** is
  erased. A row written concurrently and committed after the run's statement on
  that place is not (it is a new copy, e.g. the person booked again); a rerun
  finds it. The runbook says to rerun once if the person was active.
- **Two concurrent runs** for the same address both succeed; no row is
  erased by both; their **erased** counts add up to the rows that existed
  (the "kept" counts are reported by both).
- **Idempotence**: a second run finds zero to erase and erases nothing; its
  only write is its own audit record (zero erased counts). It exits success.
- **Migrations**: the command behaves like the PAC-71 subcommands — pending
  migrations are applied only when the app is not serving, otherwise it refuses
  and changes nothing; it refuses while a migrator holds the maintenance lock.
  The **dry run never applies a migration**: on a schema older than the one
  this ticket needs it exits with the failure code and says so.

### 3.6 Audit record

- One operator audit record per run that commits — erasure **and dry run**
  (OQ-6) — zero counts included, with: the action (erase address, or erase
  address dry run), operator, reason, time, per-place counts (erased or
  would-erase, and kept), and the matching account ids (empty when none) with
  whether the acknowledgement was given.
- It contains **no address, no hash or other derivative of the address, no
  name** from the erased rows, and no row ids of erased rows. (A hash of an
  address is still personal data and is reversible by dictionary.)
- The operator name and the reason are refused (usage error, nothing read) when
  either contains the address under the §3.3 rule's lowercasings. The runbook
  tells operators to put the request's ticket reference in the reason — that
  is how a later audit ties the record to the request.
- A refused run (account-held without acknowledgement) and a failed run write
  no record: no data changed and no counts were committed. A dry run refused
  for an account writes its record (it is a completed lookup).
- No activity entry is written for the users whose data changed, and nobody is
  emailed (OQ-3).

### 3.7 Input, output and exit codes

- The address is read from **standard input** (one line), never from the
  command line, so it stays out of shell history and process listings (OQ-5).
  An address given on the command line is a usage error.
- Output, on success and on dry run: one line per place of §3.4 with its count
  (erased, would-erase on a dry run, or kept), and a total; on a dry run, a line
  stating no data changed. When accounts match, their ids.
- **Never** the address, a name, a title, a note, a link slug, or a row id of an
  erased row — on standard output, standard error, the backend log, the
  database log or Sentry. Errors are reported by class (SQLSTATE or a fixed
  word), never by the driver's message, which can repeat row data
  (`storage/focus_blocks.go:153-159`); the tool does not reuse the PAC-71 path
  that prints an error as is (§2.4).
- Exit codes:
  - **0** done (including "nothing found"), or dry run done;
  - **1** failure: database unreachable, schema too old, migration refused,
    maintenance lock held, lock or duration bound exceeded, deadlock, any query
    error — no data changed;
  - **2** usage: missing or invalid address, address on the command line,
    missing operator or reason, operator/reason containing the address —
    nothing read;
  - **3** account-held: the address belongs to an account and the
    acknowledgement was not given (§3.2) — no data changed.

### 3.8 Runbook

The "Erasing an address" section is rewritten to use the tool: when to use it;
the precondition that the web reads erased live bookings (§3.4); how to give
the address on standard input; the dry run first; the account-held case and
its acknowledgement (§3.2), still stating that a person with an account must
be searched by address too; what it erases and keeps (§3.4); what it cannot
reach (free text, in-process cache ≤ 15 min, backups ≤ 14 days, container logs
until rotation, provider calendars, sent emails, re-detection from a manager's
calendar and re-creation while an account exists, §2.7); the exit codes; the
rerun advice; and that the hand-written SQL is withdrawn. It keeps listing
every place of PAC-129 §3.11 and the phrases PAC-129 AC-27's check requires.

## 5. Explicitly out of scope

- **Account deletion.** No account deletion exists today (§2.4); this tool
  never changes an account. Follow-up (OQ-1).
- **Free text**: titles, notes of other bookers, activity entries (typed NLP
  text, meeting titles), meeting briefs, analytics top titles, no-meeting-zone
  labels, calendar URLs. Neither searched nor changed: substring matching would
  erase other people's content and has no reliable boundary.
- **Address equivalence beyond trimming and the code's two lowercasings**
  (sub-addressing, dots, domain aliases, IDN, full case folding).
- **Suppression of re-ingestion** (manager detection from a calendar, a new
  invitation, a new booking, normal use of an existing account): no blocklist
  is kept (OQ-4b).
- **Copies outside the database**: backups (until their 14-day retention),
  container logs (until rotation), Sentry, providers' calendar events, emails
  already sent, the backend's in-process free/busy cache (≤ 15 minutes). The
  runbook states them.
- **Notifying anyone** (the erased person, team owners, managers, link owners):
  the operator answers the requester through whatever channel the request came
  by (OQ-3).
- **An HTTP, web or MCP surface for the tool**: operator-only, like every other
  `paceday-operator` command. (The web change in AC-6w is only to read erased
  live bookings.)
- SF-005 (booker email not validated): unchanged; the matching rule tolerates
  invalid stored values.

## 7. Rollback

- Reverting the code removes the command; **erasures already done stay done**.
  Only a backup taken before the erasure (≤ 14 days) holds the values, and
  restoring one to undo an erasure defeats the request; after any restore the
  operator must rerun the erasures done since that backup (the audit records'
  times and the ticket references in their reasons list them).
- The audit actions are a schema change (the allowed-action list). Its down
  step must not delete or rewrite erase records (PAC-71 rule); the contract
  stage decides how (e.g. the down step leaves the widened list in place or
  refuses while erase records exist).
- The live-bookings contract change: the web reads the list strictly (§2.5),
  so a web that predates the change, facing an erased live booking, shows **the
  whole bookings list as unreadable** for that link (no data loss; other links
  unaffected). Hence the order: web able to read the new shape first, and the
  runbook precondition before the tool is used (§3.4). Rolling the web back
  after live bookings were erased brings that unreadable list back for the
  affected links; the runbook's rollback note says so.
