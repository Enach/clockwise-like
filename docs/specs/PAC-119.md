## 1. Problem

A link owner creates a scheduling link in the link editor. Sometimes the server saves the link but its answer never reaches the browser. The connection drops, the client's 135 s bound expires, a proxy answers 502 or 504, or the server's own time budget answers 503 after the save committed. The editor then shows "Paceday didn't confirm this. It may or may not have been applied — refresh to check before trying again." It stays open with the owner's input.

The natural next step is to press **Create link** again, and that creates **a second link**. It has the same title and settings and a different public URL. If the first save listed co-hosts, each invitee now holds two pending invitations for what looks like one link.

The cost to the owner:
- They must notice the duplicate, work out which URL they already shared, and delete the other one.
- Their invitees see duplicate invitations. A co-host who accepts only one of them leaves the other link without their calendar.
- A booker may be sent the "wrong" link and book on it. The owner then cannot delete it without affecting that booking.

PAC-112 accepted this risk explicitly (spec §5) and asked for this follow-up. PAC-112 also made it more likely to matter: a create now carries its co-host list in the same request, so a duplicate create also duplicates invitations.

## 2. Current behaviour

### 2.1 The server: create (clockwise-like `ae8b535`)

`createLink` (`backend/api/handlers_scheduling_links.go:464-526`), in order:
1. Decodes the body. Invalid JSON is `400 "invalid request body"` (`:467-470`).
2. Normalises and validates the fields. Each failure is a 422 (`:471-476`; PAC-112 D-9). A blank co-host entry is a 422 (`:477-480`).
3. Reads the owner (`:481-485`) and the owner's zone. A failed zone read is a 500 that creates nothing (`:488-492`).
4. Slug:
   - With no slug sent, it generates one (`:493-502`) with `GenerateSlug` (`backend/engine/booking.go:83-101`). The base is `{first-name}-{duration}min`. While the candidate exists (`storage.SlugExists`, `backend/storage/scheduling_links.go:966-971`, deleted links included), it appends `-` and 4 random hex characters, up to 10 tries.
   - With a slug sent, an existing slug is `409 "slug already exists"` (`:503-509`).
5. Writes everything in one transaction through `storage.CreateSchedulingLinkWithCoHostsCtx` (`backend/storage/guarded_writes.go:397-407`), which calls `createSchedulingLinkWithCoHosts` (`scheduling_links.go:1417-1440`). The transaction holds:
   - the link insert (`CreateSchedulingLink`, `:97-125`);
   - the owner's `accepted` host row, a plain insert (`:1425-1430`);
   - when a co-host list is carried, the list with its per-address outcomes (`setCoHostList`).
6. Answers 201 with the saved link plus `co_host_changes` (`writeSavedLink`, `handlers_scheduling_links.go:447-454`). `co_host_changes` is present exactly when the request carried the list. The roster in `hosts` is read at answer time, non-strictly (`toSchedulingLinkDTO`, PAC-112 §2.4).

The transaction goes through `withLinkWriteTx` (`backend/storage/session.go:175-195`):
- with a PAC-71 session guard, its first statement is the generation re-check (`withGenerationTx`, `:204-215`). The re-check is `SELECT session_generation FROM users WHERE id = $1 FOR KEY SHARE` (`recheck`, `:129-131`). `FOR KEY SHARE` blocks a production generation advance, which first takes `FOR UPDATE` on the user row through `lockAccountExclusive` (`session.go:88-100`, called from `operator.go:84` and `signin.go:222`): such an advance waits until the transaction ends. A raw non-key `UPDATE` of the generation is not blocked, so it can commit after the re-check (corrected after the contract challenge, m-1);
- each lock wait is then bounded by `LinkLockTimeout` (10 s; `setLinkLockTimeout`, `scheduling_links.go:503-507`);
- a 422 for an over-long list (`ErrCoHostListTooLong`) and any other error roll everything back (`handlers_scheduling_links.go:517-524`).

**PAC-71 guard on the answer.** `requireAuth` re-reads the session generation once per request and answers 401 when it moved (`backend/api/middleware.go:122-131`). An in-request re-check that finds it moved turns whatever the handler had decided into requireAuth's 401, through `guardedResponseWriter` (`middleware.go:155-215`).

**Nothing makes create idempotent:**
- The request carries no key. The handler reads no `Idempotency-Key` (it is read only on public booking, `backend/api/handlers_booking.go:350`, `:575-588`).
- Each call generates a fresh slug, and titles are not unique.
- Two identical creates therefore give two links. The second has a suffixed slug when the first took the base (`booking.go:89-99`).
- **A deleted link is never purged.** A PAC-40 delete is soft (`UPDATE scheduling_links SET deleted_at = NOW(), active = false`, `scheduling_links.go:217-221`). Every by-id read filters `deleted_at IS NULL` (`:159`), so a deleted link is not found by any read. No code outside tests deletes link rows.
- **Normalisation today.**
  - `normalized()` resolves the aliases and trims the title (`schedulingLinkInput`, `handlers_scheduling_links.go:81-100`; `normalized`, `:184` onwards).
  - `CreateSchedulingLink` applies the remaining defaults (`scheduling_links.go:98-112`): usage `reusable`, durations `[30]`, days Monday–Friday, horizon 60, refusal message `generic`.
  - A JSON `"co_host_emails": null` decodes to a nil slice exactly like an absent key, and nil means "no list" (`createSchedulingLinkWithCoHosts`, `:1431-1433`).
  - The co-host write trims each entry (`TrimECMASpace`), lowercases it with Postgres `lower()` (`lowerAll`), and looks each lowered address up once (`setCoHostList`, `:1252-1265`).
- **Concurrent creates of the same base slug** both pass `SlugExists`. The second insert then hits the slug's unique constraint (`migrations/009_scheduling_links.up.sql:4`) and answers `500 "create failed"` (`handlers_scheduling_links.go:521-523`). That is today's behaviour for any two owners whose first names and first durations match, keyed or not (§5).

**CORS** already allows the header on every route: `Access-Control-Allow-Headers: Content-Type, Authorization, Idempotency-Key` (`middleware.go:250`, PAC-82).

**Proxy.** nginx sets no `proxy_next_upstream` (`nginx/nginx.conf`), so it never re-sends a POST upstream (nginx's default excludes non-idempotent methods). Upstream reads time out at 130 s (`nginx.conf:82`).

### 2.2 The PAC-82 precedent (public booking)

What PAC-82 built, for comparison in D-3:
- **Carrier.** An optional `Idempotency-Key` header of 16–255 characters `[A-Za-z0-9_-]` (`handlers_booking.go:568-588`).
  - Absent or empty means no key.
  - A malformed value, or the header on two field lines, is `400 "invalid Idempotency-Key header"`.
- **Storage.** The key is a nullable column on the booking row itself (`038_booking_idempotency_key.up.sql`). It has a format check and a partial unique index on (link, key).
  - No separate table, so no expiry job is needed (PAC-82 contract §9, "A key table separate from `bookings`").
  - The down migration drops only the key.
- **Matching** (PAC-82 contract §1.2). The request's booking details are compared with the stored row. Same key, same link and same details within 24 h by the database clock (`BookingIdempotencyTTL`, `scheduling_links.go:600`) is a replay. A different payload, or an age of 24 h or more, is `409 "idempotency key already used"`.
- **Replay body.** It is built from the stored row. Fields that identify the booking are identical; link-level fields are current. There is no replay marker header (PAC-82 contract §2.3).
- **Concurrency.** A lookup in the handler is an optimisation. The authoritative decision is a lookup inside the save, plus the unique index.
  - The insert **detects** a violation of `bookings_link_idempotency_key` (`scheduling_links.go:760-768`).
  - The caller then **rolls the transaction back and resolves on the bare connection, outside any transaction** (`_ = tx.Rollback()`, then `ResolveIdempotencyKey(conn, …)`, `:552-563`; the resolver is `:610-640`).
  - That is safe for an anonymous booker. For a signed-in owner it would bypass the PAC-71 re-check (D-5).
  - Only the key's own constraint triggers the resolve.
- **Web.** One fresh random key per booking attempt (`newBookingAttemptKey`, smart-calendar-flow `src/api/schedulingLinks.ts:594-608`), kept in page memory only. It is re-sent only by that attempt's "Try again" (`schedulingLinks.ts:564-583`; `src/pages/PublicBooking.tsx:901`).

### 2.3 The web client (smart-calendar-flow `66b340e`)

## 3. Desired behaviour

From the link owner's point of view.

### 3.1 The attempt key

1. **One press of Create link, however many times it is sent, makes at most one link** [F, D-1].
   - The editor labels each logical create with a random **attempt key** and sends it with the create.
   - The server remembers which link each of the owner's keys created.
2. **Keys are scoped to the owner's account** [F, D-3.1]:
   - the same key from another owner is unrelated: it creates that owner's own link and learns nothing about the first owner's;
   - the same key from another session of the same account (a new sign-in, another tab) is resolved as that account's key.
3. **Format and absence** [F, D-2]:
   - the key follows PAC-82's format and carrier rules;
   - a malformed key is refused with 400 and nothing is created. The 400 comes **before any body validation**, the "body is not valid JSON" 400 included, as in PAC-82;
   - a create without a key, or with an empty one, behaves exactly as today for every client: the e2e suite and any API caller.

### 3.2 How a keyed create is resolved: precedence

When a create carries a key that the owner has already used, exactly one outcome applies. **The first matching row wins** [F, factory decision B-1]:

| # | The link that key created | Age of the original save | This request vs the original | Outcome | Writes |
|---|---|---|---|---|---|
| 1 | deleted | any | any | **deleted refusal**. It says the link this save created was deleted, and names nothing to edit. | none |
| 2 | live | 24 h or more | any | **expired refusal** (§3.6). Never a replay, never a create. | none |
| 3 | live | under 24 h | same request (§3.3) | **replay** (§3.4) | none |
| 4 | live | under 24 h | different request | **key-reused refusal**, naming the live link (OQ-1) | none |

Further rules for the table:
- A key the owner has not used (nothing stored) is a new create, which stores the key in the same transaction as the link.
- The three refusals are distinguishable from each other and from every other refusal of create, in particular from "slug already exists", which shares the conflict status today.
- "Age" is measured by the database clock from the original save's stored time: the time the save's transaction stored with the key, which is that transaction's `now()` (its start, as PAC-82's `created_at`). The commit instant cannot be observed. AC-11 ages exactly this stored time.
- **Deleted wins over everything.** A soft-deleted link is never purged (§2.1), so without row 1 a deleted original would fall under rows 2–4. Row 4 would then send the editor to a link that no read can find.
- **Expired wins over the body comparison.** From 24 h on, the request's content no longer matters. So the stored fingerprint and outcomes are never needed after the window (§3.6).
- A session whose generation moved gets the 401 before any of these (§3.5).

### 3.3 What "the same request" means

The request is reduced to a **normalised form**, and two requests are the same when their normalised forms are equal [F, D-3.2; factory decision on minor 5]. The server stores only a **SHA-256 digest of the normalised form**, never the raw body (factory decision on M-2).

The normalised form:
- **Fields.** Each field after the server's own normalisation: aliases resolved (`durations` with `duration_options`, `days` with `days_of_week`, the window aliases, as today's precedence decides), the title trimmed, and an absent slug the same as an empty one.
- **Defaults.** Every default the save would apply is applied **before hashing**. An absent usage is the same as "reusable", an absent horizon the same as 60, an absent refusal message the same as "generic", absent durations the same as [30], and absent days the same as Monday–Friday.
- **Co-host list presence.** `null` and an absent list are the same: "no list". An empty list is different from "no list", because it is a different save (PAC-112: a carried list is reported, an absent one is not).
- **Co-host list entries.** Each entry is trimmed as the save trims, and lowered by the same lowering the co-host write uses (`lowerAll`, `scheduling_links.go:1202`). The entries are then deduplicated and sorted.
- **Formatting.** JSON key order and whitespace never matter.

Why the list is compared this way:
- Two lists that are equal after this reduction name the same people, and so would give the same outcomes for each person.
- For ASCII addresses it is the editor's own notion of "the co-hosts changed" (PAC-112 §3.2; `coHostSave.ts:22-35`), so a retry the web considers unchanged is never refused. The editor lowers with JS `toLowerCase` (`coHostSave.ts:22`), which can differ from the server's lowering for non-ASCII letters. Such a mismatch only produces a key-reused refusal, from which the editor recovers (§3.8 item 2).
- The replay still returns the original outcomes, which echo the entries as the original request spelled them.

Two requests that would save different links, or invite different people, never have the same normalised form.

### 3.4 The replay

A retry of the same request (row 3) is answered as the original was [F, D-2, D-3]:
- the same status (201) and the same link: same identity and public URL;
- **the same co-host outcomes and counts** as the original save reported. Nothing is invited, removed or re-evaluated: a co-host who declined or was removed in between is not re-invited;
- the link's fields and roster as they stand now [OQ-4], exactly as every other answer that carries a link;
- nothing written: no second link, no host row, no invitation.

Replay comes **before the slug checks** [F, factory decision on M-1]:
- when a key is present, the key is resolved before the slug pre-check;
- a keyed create is never answered "slug already exists" while its own key is stored, however the conflict is detected. Detection can be the pre-check or the slug's unique constraint at insert. Either one makes the server resolve the key again (§3.5), and a stored key then decides by the table.

Validation decided before any write still comes first: the key 400, the body 400, the field 422s and the blank-entry 422. A request that passed it once passes it again.

Refusals decided inside the write come **after** key resolution. The over-5 422 is one of them: it is decided inside the write from the raw entry count (`len(entries) > CoHostListLimit`, `scheduling_links.go:1260`). So a retry whose list normalises to the original's (§3.3) is replayed, even when it would be the 422 if sent fresh. Example: an original `[b, g]` retried as `[b, B, b, g, G, b]`. Nothing is written and the same link comes back.

### 3.5 Session guard and concurrency

**Every replay and every refusal is decided and answered under a PAC-71 re-check** [F, factory decision on B-2; D-5]:
- the key is read inside a transaction in which the PAC-71 re-check ran **before** the key read;
- the re-check runs **again after** that read, before the answer;
- if either re-check finds the generation moved, the answer is requireAuth's 401 and contains nothing of the link: no replay, no refusal;
- no replay or refusal is ever decided from a read on a bare connection, or in a transaction without the re-check. That covers a lookup before the write and the resolution after a conflict. This is where this spec departs from PAC-82 (`scheduling_links.go:552-563`).

**Concurrent duplicates** [F, D-4]. When two requests with the same owner and key are in flight together:
- exactly one link is created;
- the loser waits for the winner. Its transaction then ends with the conflict, and it resolves in a **new, short transaction** that re-runs the PAC-71 re-check before reading the key (and again after, as above). It then answers by the table: replay or key-reused refusal;
- a session revoked while the loser waited therefore gets the 401;
- the loser never gets a 500 or "slug already exists" because of the winner;
- if the winner fails and rolls back, the loser proceeds as a new create;
- the existing 10 s bound on lock waits applies. A wait that exceeds it is the 500 with nothing created, and a later retry then resolves by the table.

**Failures store nothing.** A create that was rolled back stored no key, so a later request with that key is a new create. That covers a stale session, a 422, a 500 and the lock bound.

### 3.6 Window and retention

[F, factory decisions on B-1, M-2, minor 3; OQ-2, OQ-5]

- **Within 24 hours** of the original save, by the database clock, a retry can be replayed (row 3).
- **From 24 hours on**, the key gets the expired refusal (row 2) **for ever**. Soft-deleted links are never purged, so the association between key and link is kept for as long as the database holds the link, which is for ever. It is never a second link.
- **What is kept for ever**: the owner, the key, the link it created, and the time of the original save. None of these contains an address.
- **What is kept only for the window**: the stored co-host outcomes (which contain addresses, including addresses of people with no Paceday account) and the request digest. Both are removed **within one hour after the window ends**. No address typed into a create outlives about 25 hours anywhere in the key store.
- **Cleanup schedule.** The cleanup runs **at backend start-up and then every hour**, so the one-hour bound holds across restarts and deploys (PAC-116 restarts the backend on every deploy). Each run is a tracked cron unit and drains like the others (PAC-81).

### 3.7 The editor's attempt key

[F, D-7]

- The editor makes a fresh key the first time Create link is pressed in a create-mode editor.
- It re-sends that key on every further Create link press in the same editor session, whatever the previous failure was: a lost answer, a budget 503, any 5xx, any 4xx.
- The key is dropped when:
  - the create succeeds: the editor closes, or becomes an editor of the created link and sends edits;
  - the editor closes;
  - the editor turns into an editor of an existing link after the key-reused or expired refusal;
  - the deleted refusal arrives.
- Reopening the editor for a new link starts a new logical create with a new key, even after a lost answer. Its form is blank, so a save from it is a deliberate new create.
- Edits never carry a key.
- The key lives in page memory only: never in `localStorage`, `sessionStorage`, IndexedDB, a cookie, the URL or the history state. A reload starts a new logical create [OQ-6].

### 3.8 What the editor does and says

[F, D-7; factory decisions on B-1, M-4]

1. **Outcome unknown.** This covers a lost answer, the budget 503 and any 5xx on a create.
   - The message says that pressing Create link again will not create a second link, and does not ask the owner to refresh before trying again.
   - The PAC-83 wording for every other write is unchanged, edits from this editor included.
2. **Key-reused refusal** (row 4), the OQ-1 default:
   - The editor becomes an editor of the named link, as PAC-112 §3.10 does after a create that stays open, and it re-reads that link's strict baseline.
   - **Everything the owner typed is kept as unsaved edits on top of that baseline**: the title and every setting, and the co-host chips exactly as the owner left them. The baseline's arrival does not replace the chips.
   - The next save applies them as an edit. The fields are sent as usual. The co-host list is sent under PAC-112's changed-list rule: the complete list when the chips differ from the new baseline as case-insensitive sets, and nothing otherwise.
   - The message says exactly that: **"Your earlier save already created this link. What you changed since, co-hosts included, is not saved yet — press Save changes to apply it to this link."**
   - If the baseline read fails, co-host editing is disabled, as PAC-112 §3.3 requires. The message then says that the co-host changes cannot be applied until the link's co-hosts load, and that the other changes will be saved. The next save carries no list.
3. **Expired refusal** (row 2, a live link) [OQ-9 default]. The editor behaves exactly as for the key-reused refusal, with a message that names the cause: the earlier save, more than a day ago, already created this link.
   - Row 2 fires whatever the body, so the owner may have changed nothing. The expired message therefore **claims no change**: it never says that something was changed since. It only says that the form is now an editor of that link and that Save changes saves the form to it.
   - If the link was edited since (in another tab, say), the next Save changes overwrites those edits with this form's values. **That is accepted.** Any open editor has the same last-write-wins behaviour today, so this adds no new risk.
4. **Deleted refusal** (row 1):
   - The editor shows a message that the link this save created was deleted, and that saving again creates a new link.
   - It **stays a create editor** with a new key for the next press, and keeps the typed values.
   - It **never** reads or PATCHes the deleted link. The refusal names nothing it could edit.
5. **The links page catches up.** When the editor closes after a create whose outcome is unknown, the links list is refreshed. A link that the lost-answer save did create then appears without a manual reload. The key-reused and expired refusals, which name the link, also refresh the list when they arrive. "Outcome unknown" ends only with a 201 or the deleted refusal, never with another failure. When co-host editing is disabled after a refusal, the message points to that link on the Links page, never to reopening the editor (contract challenge M-1).
6. **No close path while a save is pending** [factory decision on M-3; OQ-8].
   - While any save, create or edit, is pending, the drawer cannot be closed by the X button, Escape, a click outside, or Cancel.
   - An answer therefore always lands in the editor session that sent it.
   - Closing after the save settles is unchanged.

### 3.9 Demo mode and release

- **Demo mode** keeps working and ignores the key. The demo create cannot lose its answer, so there is nothing to replay.
- **Release.** Remembering keys needs a schema change, so a migration, released under PAC-116's stop-traffic rule.
  - The server merges and deploys before the web (README §1).
  - A keyed web against a server without this work behaves exactly as today: the header is already allowed by CORS, and this route ignores it.

## 5. Explicitly out of scope

- **Keyless clients.** A create without a key keeps today's behaviour, including duplicates. Only the web sends one; MCP has no create.
- **Edits after a lost answer.** An edit sets absolute values and is safe to repeat for the fields. Re-sending one with a co-host list reports `already_host` where the first answer said `invited`, which is true of the second save. Nothing duplicates.
- **Other create operations** (events, habits, teams and others). Public booking is already covered by PAC-82.
- **Detecting duplicates by content.** Owners legitimately create look-alike links.
- **Keeping the key across a reload or in storage** (OQ-6).
- **Concurrent creates of the same base slug by different owners, or keyless** (§2.1): the second answers 500. Pre-existing; AC-7 and AC-29 only remove it for same-key pairs. Follow-up candidate:

- **The editor's slug preview** (§2.3) shows a URL the server never uses. Follow-up candidate:

## 7. Rollback

- **Migration.** One additive migration stores the key store described in §3.6. It is applied under PAC-116's stop-traffic rule (runbook "Applying migrations"). With the shipped single backend, nothing extra is needed beyond the deploy order.
- **Down migration** (development and tests only, runbook "Rollback"). It loses only keys, digests and stored outcomes. Every link and host row survives. After it, retries are no longer recognised and may duplicate, as today.
- **Production rollback** follows the runbook: fix forward, or restore the pre-deploy backup and accept losing links created since. An image-only rollback is impossible, because the previous binary refuses a database at the new version (PAC-116 §2.1). The release notes say so [OQ-7].
- **Web.** Reverting the web PR alone is always safe: the server treats keyless creates as today. The server merges and deploys first, and the web reverts first (README §1).
- **Server reverted with the web still keyed.** The header is ignored, and duplicates become possible again. Nothing breaks.

Each has a default. The factory proceeds on the default unless the owner answers otherwise before the contract stage.

- **OQ-1 (owner): the same key with a different request, link live, under 24 h.**
  - **Default:** the key-reused refusal names the link. The editor becomes an editor of it, keeps everything typed (chips included) as unsaved edits, and the next save applies them (§3.8 item 2; AC-20, AC-31).

- **OQ-2 (owner): after 24 h, refused or forgotten?**

- **OQ-4 (owner): the replay's link fields.**
  - **Default: current values**, with the original identity and outcomes (AC-3), as PAC-82 §2.3 does. The editor seeds the links list from the answer (`LinkEditDrawer.tsx:336-345`), and a frozen copy would overwrite fresher data there.
- **OQ-5 (owner): retention of addresses.**
  - **Default:** outcomes and digest are kept for 24 h and removed within the following hour, with a cleanup at start-up and hourly (§3.6, AC-12).
  - The owner should confirm that about 25 h is acceptable.
- **OQ-6 (owner): should the key survive a reload?**
  - **Default: no**, page memory only (AC-23), as PAC-82 D-8 does.
- **OQ-7 (release-manager): release note.**
  - **Default:** a line under runbook "Rollback" naming this migration, as was done for PAC-87.
- **OQ-8 (owner): no close path while a save is pending.**
  - **Default: every save**, create and edit, and all four paths (AC-27).

## 9. Decisions and reasons

- **D-1 [F]: a client-chosen attempt key, not a client-generated slug, and not server-side content matching.**
  - **Client slug, rejected.** A slug is public and global. "Slug already exists" cannot tell the owner's own earlier link from someone else's, and the original outcomes could not be replayed. Generation also uses the owner's name and suffixes collisions server-side (`booking.go:83-101`).
  - **Content matching, rejected.** Titles are not unique, and owners create similar links on purpose.
  - **Attempt key, chosen.** It labels exactly one press, it is the factory's precedent (PAC-82), and CORS already allows it.
- **D-2 [F]: reuse PAC-82's conventions** where the reasons carry over:
  - the same carrier and format;
  - absent or empty means keyless;
  - a malformed key is a 400 before any body validation;
  - a 24 h window by the database clock;
  - a conflict status for refusals;
  - no replay marker;
  - a uniqueness guarantee inside the write as the authority.

  The contract fixes names and texts.
- **D-3 [F]: where this differs from PAC-82, and why.**
  1. **Scope per owner, not per link.** A create has no link yet, and the actor is the authenticated owner.
  2. **Matching against a digest of the normalised request, not against the stored row.** A link is edited freely, while a booking is not. The digest is SHA-256 over the normalised form of §3.3, never the raw body, and it is removed with the outcomes.
  3. **The outcomes must be stored.** Co-host outcomes cannot be rebuilt from later state, so the PAC-82 argument against a separate key store does not carry over in full. Retention is bounded (§3.6). Whether the key sits on the link row with the outcomes apart, or everything sits in one store whose rows are reduced at cleanup, is the contract's choice; AC-12 constrains both.
  4. **Three refusals with a fixed precedence** (§3.2). PAC-82 has one, because bookings are never deleted and its caller is anonymous. Here the key-reused and expired refusals name the owner's own live link so the editor can recover. The deleted refusal names nothing.
  5. **Replay before the slug checks**, and any slug conflict on a keyed create re-resolves the key (§3.4, AC-4, AC-30). Bookings have no such self-conflict.
  6. **Resolution after a conflict runs under the PAC-71 re-check**, in a new transaction, never on the bare connection (§3.5, D-5).
- **D-4 [F]: concurrency is decided by a uniqueness guarantee on (owner, key) inside the create's transaction.**
  - The loser resolves in a new short guarded transaction.
  - A keyed create re-resolves its key after **any** conflict on the key or the slug: the slug pre-check's 409 or the slug's unique constraint. Concurrent same-key creates also generate the same slug, so the conflict can arrive on the slug first (AC-7(a), AC-30). PAC-82 resolves only on its key's constraint (`scheduling_links.go:767`).
- **D-5 [F]: replays and refusals are decided under PAC-71 re-checks before and after the key read** (§3.5).
  - A replay decided outside the transaction, or on the bare connection after a wait, could hand stored outcomes (addresses) to a session revoked mid-request. The re-check before the key read, in a new transaction after any wait, closes that.
  - The re-check after the read is redundant in production and is kept as cheap defence. A production advance takes `FOR UPDATE` through `lockAccountExclusive`, which waits for the `FOR KEY SHARE` that the first re-check holds, so it cannot commit between the two. It catches only a writer that bumps the generation without that lock: a raw `UPDATE`, which is how the AC-10 and AC-29 tests move it (`pac71_guard_writer_test.go:52`). Corrected after the contract challenge, m-1.
  - What stays open is the answer's own reads after the transaction, which is the exposure every PAC-71 guarded write already accepts.
  - AC-10 places its seams before any key read, and between the key read and the second re-check. AC-29 covers the loser's wait.
- **D-6 [F]: retention.** 24 h window, then the expired refusal for ever. Outcomes and digest are removed within an hour of the window. The cleanup runs at start-up and hourly, as a tracked cron unit (`backend/main.go:49-60`).
  - The PAC-40 erasure cron (`@every 24h` with a start-up run, `main.go:76-82`) is the pattern for the start-up run, not for the interval. An `@every` timer restarts with each process, so without a start-up run a deploy could postpone the cleanup.
- **D-7 [F]: the key belongs to one editor session's create.**
  - Re-sending it after a 4xx is harmless, because failed attempts store nothing (AC-9).
  - Reopening the editor starts over, because the form is blank.
  - No close path while a save is pending removes the only way an answer could reach a later session.
  - After the key-reused or expired refusal, keeping the chips as unsaved edits honours what the owner did after the lost answer. PAC-112's changed-list rule decides whether a list is sent.
