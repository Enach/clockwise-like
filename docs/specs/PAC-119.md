## 1. Problem

A link owner creates a scheduling link in the link editor. Sometimes the server saves the link but its answer never reaches the browser. The connection drops, the client's 135 s bound expires, a proxy answers 502 or 504, or the server's own time budget answers 503 after the save committed. The editor then shows "Paceday didn't confirm this. It may or may not have been applied — refresh to check before trying again." It stays open with the owner's input.

The natural next step is to press **Create link** again, and that creates **a second link**. It has the same title and settings and a different public URL. If the first save listed co-hosts, each invitee now holds two pending invitations for what looks like one link.

The cost to the owner:
- They must notice the duplicate, work out which URL they already shared, and delete the other one.
- Their invitees see duplicate invitations. A co-host who accepts only one of them leaves the other link without their calendar.
- A booker may be sent the "wrong" link and book on it. The owner then cannot delete it without affecting that booking.

PAC-112 accepted this risk explicitly (spec §5) and asked for this follow-up. PAC-112 also made it more likely to matter: a create now carries its co-host list in the same request, so a duplicate create also duplicates invitations.

## 2. Current behaviour

### 2.1 The server: create (clockwise-like `ae8b535`)

`createLink` (`backend/api/handlers_scheduling_links.go:464-526`), in order:
1. Decodes the body. Invalid JSON is `400 "invalid request body"` (`:467-470`).
2. Normalises and validates the fields. Each failure is a 422 (`:471-476`; PAC-112 D-9). A blank co-host entry is a 422 (`:477-480`).
3. Reads the owner (`:481-485`) and the owner's zone. A failed zone read is a 500 that creates nothing (`:488-492`).
4. Slug:
   - With no slug sent, it generates one (`:493-502`) with `GenerateSlug` (`backend/engine/booking.go:83-101`). The base is `{first-name}-{duration}min`. While the candidate exists (`storage.SlugExists`, `backend/storage/scheduling_links.go:966-971`, deleted links included), it appends `-` and 4 random hex characters, up to 10 tries.
   - With a slug sent, an existing slug is `409 "slug already exists"` (`:503-509`).
5. Writes everything in one transaction through `storage.CreateSchedulingLinkWithCoHostsCtx` (`backend/storage/guarded_writes.go:397-407`), which calls `createSchedulingLinkWithCoHosts` (`scheduling_links.go:1417-1440`). The transaction holds:
   - the link insert (`CreateSchedulingLink`, `:97-125`);
   - the owner's `accepted` host row, a plain insert (`:1425-1430`);
   - when a co-host list is carried, the list with its per-address outcomes (`setCoHostList`).
6. Answers 201 with the saved link plus `co_host_changes` (`writeSavedLink`, `handlers_scheduling_links.go:447-454`). `co_host_changes` is present exactly when the request carried the list. The roster in `hosts` is read at answer time, non-strictly (`toSchedulingLinkDTO`, PAC-112 §2.4).

The transaction goes through `withLinkWriteTx` (`backend/storage/session.go:175-195`):
- with a PAC-71 session guard, its first statement is the generation re-check (`withGenerationTx`, `:204-215`);
- each lock wait is then bounded by `LinkLockTimeout` (10 s; `setLinkLockTimeout`, `scheduling_links.go:503-507`);
- a 422 for an over-long list (`ErrCoHostListTooLong`) and any other error roll everything back (`handlers_scheduling_links.go:517-524`).

**PAC-71 guard on the answer.** `requireAuth` re-reads the session generation once per request and answers 401 when it moved (`backend/api/middleware.go:122-131`). An in-request re-check that finds it moved turns whatever the handler had decided into requireAuth's 401, through `guardedResponseWriter` (`middleware.go:155-215`).

**Nothing makes create idempotent:**
- The request carries no key. The handler reads no `Idempotency-Key` (it is read only on public booking, `backend/api/handlers_booking.go:350`, `:575-588`).
- Each call generates a fresh slug, and titles are not unique.
- Two identical creates therefore give two links. The second has a suffixed slug when the first took the base (`booking.go:89-99`).
- **Concurrent creates of the same base slug** both pass `SlugExists`. The second insert then hits the slug's unique constraint (`migrations/009_scheduling_links.up.sql:4`) and answers `500 "create failed"` (`handlers_scheduling_links.go:521-523`). That is today's behaviour for any two owners whose first names and first durations match, keyed or not (§5).

**CORS** already allows the header on every route: `Access-Control-Allow-Headers: Content-Type, Authorization, Idempotency-Key` (`middleware.go:250`, PAC-82).

**Proxy.** nginx sets no `proxy_next_upstream` (`nginx/nginx.conf`), so it never re-sends a POST upstream (nginx's default excludes non-idempotent methods). Upstream reads time out at 130 s (`nginx.conf:82`).

### 2.2 The PAC-82 precedent (public booking)

What PAC-82 built, for comparison in D-3:
- **Carrier.** An optional `Idempotency-Key` header of 16–255 characters `[A-Za-z0-9_-]` (`handlers_booking.go:568-588`).
  - Absent or empty means no key.
  - A malformed value, or the header on two field lines, is `400 "invalid Idempotency-Key header"`.
- **Storage.** The key is a nullable column on the booking row itself (`038_booking_idempotency_key.up.sql`). It has a format check and a partial unique index on (link, key).
  - No separate table, so no expiry job is needed (PAC-82 contract §9, "A key table separate from `bookings`").
  - The down migration drops only the key.
- **Matching** (PAC-82 contract §1.2). The request's booking details are compared with the stored row. Same key, same link and same details within 24 h by the database clock (`BookingIdempotencyTTL`, `scheduling_links.go:600`) is a replay. A different payload, or an age of 24 h or more, is `409 "idempotency key already used"`.
- **Replay body.** It is built from the stored row. Fields that identify the booking are identical; link-level fields are current. There is no replay marker header (PAC-82 contract §2.3).
- **Concurrency.** A lookup in the handler is an optimisation. The authoritative decision is a lookup inside the save, plus the unique index: on a violation of `bookings_link_idempotency_key`, the save re-reads and resolves (`scheduling_links.go:760-768`, `ResolveIdempotencyKey` `:610-640`).
- **Web.** One fresh random key per booking attempt (`newBookingAttemptKey`, smart-calendar-flow `src/api/schedulingLinks.ts:594-608`), kept in page memory only. It is re-sent only by that attempt's "Try again" (`schedulingLinks.ts:564-583`; `src/pages/PublicBooking.tsx:901`).

### 2.3 The web client (smart-calendar-flow `66b340e`)

**API call.** `schedulingLinksApi.createLink` (`src/api/schedulingLinks.ts:383-399`):
- validates locally (`assertValidLinkBody`, `:389`);
- sends one `POST /scheduling-links/` with `backendLinkBody(input)` plus the co-host list only when the caller passed one (`:391-395`);
- then reads `/auth/me`, a failure of which is swallowed (`:396`).

The body never carries a slug: `backendLinkBody` (`:195-212`) has no slug key, which `schedulingLinks.test.ts:382` pins ("omits slug on create so the backend generates it"). No request headers are passed: `requestApi` accepts headers (`src/api/client.ts:601-608`), but createLink passes none.

**No automatic re-send anywhere:**
- `requestApi` is "one request, never re-sent here" (`client.ts:596-600`, PAC-83).
- The app's QueryClient sets `queries: { retry: false }` (`src/App.tsx:25-29`). Mutations keep react-query's default of no retry, and the editor's `useMutation` (`src/components/links/LinkEditDrawer.tsx:314-372`) sets none.
- **The only retry is the owner pressing Create link again.**

**Error wording.** The create is classified as a `write` (`src/api/effects.ts:55`). The editor renders errors with `apiErrorMessage(e, effectOf("schedulingLinksApi.updateLink"))` (`LinkEditDrawer.tsx:366-371`), which is also `write`. For a lost answer (`isAnswerLost`: unreachable, the client bound, or a gateway error; `client.ts:147-149`) the message is `API_MESSAGES.lostWrite`. For the budget 503 it is `budgetRead + budgetWriteSuffix` ("… Refresh to check whether it was applied.") (`client.ts:411-418`, `:447-456`; PAC-83 AC-17, AC-19). In both cases the drawer stays open with the input (`onError` sets the error; nothing resets the form).

**The editor's create flow** (`LinkEditDrawer.tsx`):
- **Create or edit** is decided by `editingId` (`:138-139`). It starts as the opened link's id, or `null` for a new link.
- **On open**, an effect resets every field and `editingId` (`:203-246`). Closing only zeroes `baselineRead` (`:204-207`). The component stays mounted between opens (`src/pages/Links.tsx:501`, `openCreate` `:397-400`).
- **On success**, the answer's link seeds the list cache, and the list and invitations are invalidated (`:328-347`). Then either:
  - **the editor stays open** (PAC-112 §3.10: some address was not added) and becomes an editor of the created link: `setEditingId(saved.id)`, slug set from the answer, and a strict baseline re-read (`:348-361`). A later save is a PATCH and never a second create (PAC-112 AC-24);
  - **or the editor closes** with a toast (`:362-363`).
- **On error**, nothing about the list is invalidated (`:366-371`). The links page therefore does not show a link that a lost-answer create did save until something refetches the list.
- **The slug field** is derived from the title by `slugify` until edited (`:117`, `:248-251`), and the editor previews the public URL from it (`:665`). The value goes into the payload (`:322`), but `backendLinkBody` drops it, so the server always generates the slug. The preview can therefore differ from the real URL (§5).
- **Closing while a save is pending.** The Cancel button is disabled while the mutation is pending (`:757`), but the `Sheet` passes `onOpenChange` through unguarded (`:427`). By reading, Escape or a click outside still closes the drawer mid-save. If the owner then opens "New link" before the old answer arrives, the old mutation's `onSuccess` acts on the new session: it closes it, or turns it into an editor of the old link (`:348-363`). This was not executed; AC-27 makes it falsifiable.

**Demo mode.**
- `demoOrReal` (`src/api/demoGate.ts:41-50`) runs the demo implementation, which gets the op's `args` (`[input]`, `schedulingLinks.ts:390`).
- The demo create (`src/demo/schedulingLinks.ts:415-436`) is synchronous, cannot lose its answer, and cannot fail after validation (PAC-112 §2.1).
- PAC-82's booking key is likewise passed outside `args`, and the demo ignores it (`schedulingLinks.ts:576`; demo `bookSlot` `:513-517`).

## 3. Desired behaviour

From the link owner's point of view.

1. **One press of Create link, however many times it is sent, makes at most one link** [F, D-1]. The editor labels each logical create with a random **attempt key** and sends it with the create. The server remembers which link each of the owner's keys created.
2. **A retry of the same create is answered as the original was** (a *replay*) [F, D-2, D-3]:
   - same status (201), the same link (same identity and public URL);
   - **the same co-host outcomes and counts** the original save reported. Nothing is invited, removed or re-evaluated again: a co-host who declined or was removed in between is not re-invited;
   - the link's fields and roster as they stand now [OQ-4], exactly as every other answer that carries a link;
   - nothing is written. In particular no second link, no host row and no invitation.
3. **What "the same create" means** [F, D-3]. The retry must carry the same key, come from the same owner, and carry the same request: the same fields after the server's normalisation, and the same co-host list entry for entry (order and spelling as sent; "no list" differs from "an empty list").
   - Formatting differences that do not change what would be saved (JSON key order, whitespace) are the same request.
   - The comparison is against the original **request**, not against the link's current state. An edit made in between therefore never turns a genuine retry into a refusal.
4. **The same key with a different request is refused** [F, D-3; OQ-1]:
   - nothing is created and the existing link is unchanged;
   - the refusal is distinguishable from every other refusal of create, in particular from "slug already exists", which shares the conflict status today;
   - it names the link that key created. Only the owner can receive it (item 6), so this reveals nothing to anyone else.
5. **Keys are scoped to the owner's account** [F, D-3]:
   - the same key from another owner is unrelated: it creates that owner's own link and learns nothing about the first owner's;
   - the same key from another session of the same account (a new sign-in, another tab) is a retry.
6. **A retry is subject to the session rules like any create** (PAC-71) [F, D-5]:
   - a request whose session generation moved gets the 401 and neither the replay nor the refusal;
   - a create that was rolled back stored no key, so a later request with that key is a new create. That covers a stale session, a 422, a 500 and the lock bound.
7. **Concurrent duplicates** [F, D-4]. When two requests with the same owner and key are in flight together:
   - exactly one link is created;
   - the other request waits for the first and then gets the replay (same request) or the refusal (different request);
   - neither gets a 500 or "slug already exists" because of the other;
   - if the first fails and rolls back, the second proceeds as a new create;
   - the existing 10 s bound on lock waits applies. A wait that exceeds it is the 500 with nothing created, and a later retry is then a replay.
8. **Replay comes before the checks that depend on state the original changed** [F, D-3]. A retry of a create that sent an explicit slug is replayed, never refused as "slug already exists" by its own link. Validation of the request itself (400 / 422) may still come first, since a request that passed it once passes it again.
9. **Window and retention** [F, D-6; OQ-2, OQ-5]:
   - a retry is replayed for **24 hours** from the original save, by the database clock (PAC-82's window);
   - from 24 hours on, the same key from the same owner is refused as in item 4, for as long as the link exists. It is never a second link;
   - the stored co-host outcomes contain addresses, including addresses of people with no Paceday account. They are kept only for the window and removed within one hour after it ends. The link itself and its association with the key stay.
10. **A retry after the original link was deleted** [OQ-3] creates nothing and does not bring the deleted link back. It gets its own refusal, distinguishable from item 4's, which says the link this save created has been deleted.
11. **The key format and its absence** [F, D-2]:
    - the key follows PAC-82's format and carrier rules. A malformed key is refused with 400 and nothing is created;
    - a create without a key behaves exactly as today, for every client: the e2e suite and any API caller.
12. **The editor's attempt key** [F, D-7]:
    - the editor makes a fresh key the first time Create link is pressed in a create-mode editor;
    - it re-sends that key on every further Create link press in the same editor session, whatever the previous failure was (lost answer, budget 503, any 5xx, 4xx);
    - the key is dropped when the create succeeds (the editor closes, or becomes an editor of the created link and sends edits), when the editor closes, and after item 10's refusal;
    - reopening the editor for a new link starts a new logical create with a new key, even after a lost answer. The form is blank then, so a save from it is a deliberate new create;
    - edits never carry a key;
    - the key lives in page memory only. A reload starts a new logical create [OQ-6].
13. **What the editor says** [F, D-7]:
    - after a create whose outcome is unknown (lost answer, budget 503, 5xx), the message says that pressing Create link again will not create a second link, and does not ask the owner to refresh before trying again. The PAC-83 wording for every other write, edits of this editor included, is unchanged;
    - after item 4's refusal [OQ-1 default], the editor becomes an editor of the link the key created, as PAC-112 §3.10 does after a create that stays open. The owner's typed field values stay, the co-host chips come from the strict baseline read of that link, and a message explains: "Your earlier save created this link. Save again to apply your latest changes." The next save is an edit of that link;
    - after item 10's refusal, the message says the link this save created was deleted and that saving again creates a new one. The next press sends a new key.
14. **The links page catches up**. When the editor closes after a create whose outcome is unknown, the links list is refreshed, so a link that the lost-answer save did create appears without a manual reload.
15. **The editor cannot be closed while a save is pending.** Escape and a click outside are ignored then, as the Cancel button already is. An answer can therefore never land in a later editor session [F, D-7; OQ-8].
16. **Demo mode** keeps working and ignores the key. The demo create cannot lose its answer, so there is nothing to replay.
17. **Release.** Remembering keys and outcomes needs a schema change, so a migration, released under PAC-116's stop-traffic rule. The server merges and deploys before the web (README §1). A keyed web against a server without this work behaves exactly as today, because the header is already allowed by CORS and ignored on this route.

## 4. Acceptance criteria

Actors:
- **A** is a link owner, **A2** is a second signed-in session of A's account, and **Z** is another owner.
- **B** is a Paceday user whose address is domain-confirmed. **C** is an address no account carries.
- **K** is a well-formed key.

Test layers:
- `[contract]` is a backend handler or storage test against the test database (testcontainers PostgreSQL 16). Server state is asserted only at `[contract]` or `[e2e]`.
- `[unit]` is a web test against a mocked transport.
- `[e2e]` is the full compose stack with nothing mocked. A lost answer is simulated by letting the request reach the server and then aborting its response in the browser (Playwright `route.fetch()` then `route.abort()`).

Criteria that pass today are marked *regression guard*. Every other criterion fails today, for the reason given.

**Replay**

AC-1. Given A creates a link with key K listing B and C, and gets 201 with link L (B invited, C not added), when A sends the identical request with K again, then:
- the answer is 201 with L's id and slug, and the same co-host outcomes and counts (B invited, C not added, invited 1, not added 1);
- A owns exactly one link with that title;
- B has exactly one host row, on L, and B's invitation list holds L once.

*Fails today: a second link with a suffixed slug, and B invited twice.* [contract]

AC-2. Given A creates a link with K and **no** co-host list, when A repeats it with K, then the answer is 201 with L's id, and neither answer carries co-host outcomes. *Fails today: second link.* [contract]

AC-3. Given L was created with K listing B, and before the retry A renames L (an edit) and B declines, when A repeats the original request with K, then:
- the answer is 201 with L's id and **L's current title and roster**;
- the outcomes still report B as invited;
- B's host row is still `declined` and no new row exists.

*Fails today: second link.* [contract]

AC-4. Given A created L with K, sending an explicit slug S, when A repeats it with K, then the answer is the 201 replay of L, never `409 "slug already exists"`. *Fails today: 409.* [contract]

**Same key, different request**

AC-5. Given L was created with K, when A sends K with a different title, with a co-host list differing by one entry, with the list's letter case changed, or with "no list" where the original sent an empty list, then each answer is the key-reused refusal and nothing is created:
- the refusal is not `409 "slug already exists"` and identifies L;
- L and its host rows are unchanged.

Given instead the same request with JSON keys reordered and whitespace changed, then it is the replay. *Fails today: each creates a link.* [contract]

**Scope**

AC-6. Given L was created by A with K:
- when Z sends the identical request with K, then Z gets 201 with a new link Z owns, and the answer contains nothing of L (not its id, slug or title);
- when A2 (a different session of A, signed in after the original) sends it, then A2 gets the replay of L.

*Fails today: A2 creates a second link.* [contract]

**Concurrency**

AC-7. Given a test seam that holds A's first keyed create (K) after its link insert and before its commit, when A sends the identical request with K and the seam is then released, then:
- exactly one link exists;
- both answers are 201 with the same id and the same outcomes;
- neither is a 500 or a slug 409.

Repeat with the second request's title changed: then one link, the first answer 201, the second the key-reused refusal. *Fails today: two links, or a 500 when both generated the same base slug.* [contract]

AC-8. Given the seam makes A's first keyed create fail inside its transaction (the co-host write seam of PAC-112 AC-20) while a second identical request with K waits, then the first answer is the 500, the second is 201 with a new link, and exactly one link exists. *Fails today: the second may answer 500 or create alongside.* [contract]

**Failures store nothing**

AC-9. Given a keyed create (K) that is refused or fails, each time followed by a request with K and a corrected body, then that request is 201 with a new link, never the key-reused refusal. The failures:
- a 422 (6 new co-host entries);
- a 500 (owner-host write seam);
- a 401 from a generation moved mid-request (PAC-71 seam).

*Fails today only in the sense that no key exists; the criterion pins that a failed attempt never consumes a key.* [contract]

**Session guard**

AC-10. Given L was created with K, and a seam moves A's session generation after `requireAuth` and before the retry's create step, when A's retry with K is handled, then the answer is requireAuth's 401, and its body contains nothing of L. [contract]

**Window, retention, deletion**

AC-11. Given L was created with K, and its stored creation time is set back by 24 h minus 1 s, then a retry is the replay. Set back by 24 h, it is the key-reused refusal and no link is created. *Fails today: second link.* [contract]

AC-12. Given stored outcomes of two creates aged 25 h and 23 h, when the server's cleanup runs, then the 25 h outcome no longer exists and the 23 h one does. Both links, and the key association of the older one, still exist: a retry of the older one is the key-reused refusal. Given the cleanup's schedule, it runs at least once an hour. [contract]

AC-13. Given L was created with K and then deleted (PAC-40), when A repeats the request with K, then:
- the answer is the deleted refusal, distinguishable from AC-5's;
- no link is created;
- L stays deleted and absent from A's list.

*Fails today: second link.* [contract]

**Key format and keyless creates**

AC-14. Given a create whose key is 15 characters long, contains a character outside `[A-Za-z0-9_-]`, is quoted, or is sent on two header lines, then the answer is the 400 and no link exists. Given an empty key, the create behaves as keyless. *Fails today: the key is ignored and the link created.* [contract]

AC-15. Given two identical keyless creates from A, then two links exist, and every existing e2e create (§2.4) passes unchanged. *Regression guard.* [contract] [e2e]

**Web: the attempt key**

AC-16. Given a new-link editor, when A presses Create link and the answer is lost, then A presses it again without changing anything. Both requests carry the same key, which matches the 16–255 `[A-Za-z0-9_-]` format, and the same body. ## 5. Explicitly out of scope

- **Keyless clients.** A create without a key keeps today's behaviour, including duplicates. Only the web sends one; MCP has no create.
- **Edits after a lost answer.** An edit sets absolute values and is safe to repeat for the fields. Re-sending one with a co-host list reports `already_host` where the first answer said `invited`, which is true of the second save. Nothing duplicates, so no key is needed.
- **Other create operations** (events, habits, teams and others). Each needs its own analysis. Public booking is already covered by PAC-82.
- **Detecting duplicates by content** (same title and settings). Owners legitimately create look-alike links; only the attempt key says "the same press".
- **Keeping the key across a reload or in storage** (OQ-6).
- **Concurrent creates of the same base slug by different owners, or keyless** (§2.1): the second answers 500. Pre-existing; AC-7 only removes it for same-key pairs. Follow-up candidate:
  > **Link create answers 500 when two creates generate the same slug at once.** `GenerateSlug` checks for existence and then inserts, so two concurrent creates whose owners share a first name and first duration both pick `name-30min`, and the second hits the unique constraint as `500 "create failed"`. Retry generation on a slug unique violation inside the create.
- **The editor's slug preview** (§2.3) shows a URL the server never uses. Follow-up candidate:
  > **The link editor previews a public URL the server will not use.** On create the editor shows `slugify(title)` but never sends it, and the server generates `{first-name}-{duration}min[-xxxx]`. Show no URL until the server answers, or send the slug.
- **API-069** and other audit rows on accept, decline and leave.

## 7. Rollback

- **Migration.** One additive migration stores the key association and the outcomes. It is applied under PAC-116's stop-traffic rule (runbook "Applying migrations"): with the shipped single backend, nothing extra is needed beyond the deploy order.
- **Down migration** (development and tests only, runbook "Rollback"). It loses only the keys and the stored outcomes. Every link and host row survives. After it, retries made within 24 h of a create are no longer recognised and may duplicate, as today.
- **Production rollback** follows the runbook: fix forward, or restore the pre-deploy backup and accept losing links created since. An image-only rollback is impossible, because the previous binary refuses a database at the new version (PAC-116 §2.1). The release notes must say so [OQ-7].
- **Web.** Reverting the web PR alone is always safe: the server treats keyless creates as today. Order: the server merges and deploys first, and the web reverts first (README §1).
- **Server reverted with the web still keyed.** The header is ignored and duplicates are possible again; nothing breaks.

## 8. Open questions

- **OQ-1 (owner): the same key with a different request.** What should the editor do after the owner changed the form following a lost answer?
  - **Default:** the server refuses with the identity of the link the key created. The editor becomes an editor of that link, keeps the typed values, and says so (§3.4, §3.13; AC-5, AC-20). The owner's next save applies the changes as an edit, and no duplicate is possible.
  - Alternative: the editor rotates the key whenever the form changes. That is simpler, but an edited retry then creates a duplicate, which is the defect this ticket is about.
  - Alternative: the editor closes and points to the links list.
- **OQ-2 (owner): after the 24 h window, is the same key refused or forgotten?**
  - **Default: refused** for as long as the link exists (§3.9, AC-11), as PAC-82 does for bookings. It only matters for an editor left open with a lost answer for more than a day.
  - Alternative: forgotten. The key is a new create, and the key association can expire with the outcomes.
- **OQ-3 (owner): a retry after the created link was deleted.**
  - **Default:** a distinct refusal, nothing created, and the link not restored (§3.10, AC-13, AC-21).
  - Alternative: treat it as a new create. The owner then gets a link without being told the first one existed.
- **OQ-4 (owner): what the replay's link fields show.**
  - **Default: current values**, with the original identity and outcomes (§3.2, AC-3), as PAC-82 §2.3 does. The editor seeds the links list from the answer (`LinkEditDrawer.tsx:336-345`), and a frozen copy would overwrite fresher data there.
  - Alternative: a byte-identical copy of the original body.
- **OQ-5 (owner): retention of stored outcomes.** They hold addresses typed by the owner, some of non-users.
  - **Default:** kept 24 h, then removed within one hour by a periodic cleanup (AC-12), as the PAC-40 erasure cron does.
  - The owner should confirm that 25 h of retention is acceptable.
- **OQ-6 (owner): should the key survive a page reload?**
  - **Default: no**, page memory only (AC-23), as PAC-82 D-8 does.
  - A reload after a lost answer starts a new logical create. Item 14 (the list refreshes) and a refresh make the earlier link visible first.
- **OQ-7 (release-manager): release note.**
  - **Default:** the runbook's general rule (fix forward or restore) applies, with a line under "Rollback" naming this migration, as was done for PAC-87.
- **OQ-8 (owner): closing the editor during a pending save.**
  - **Default: blocked for every save**, create and edit (§3.15, AC-27), matching the disabled Cancel button.
  - Alternative: allow closing, and make a late answer apply only to the session that sent it.

## 9. Decisions and reasons

- **D-1 [F]: a client-chosen attempt key, not a client-generated slug, and not server-side content matching.**
  - **Client slug, rejected.**
    - The slug is a public, global identifier. A retry with the same slug would be answered "slug already exists", which cannot tell the owner's own earlier link from someone else's.
    - The replay of the original answer, with its co-host outcomes, would be impossible.
    - Today's generation uses the owner's name and suffixes collisions server-side (`booking.go:83-101`). Moving it to the web would change every link URL the web creates.
  - **Content matching, rejected.** Titles are not unique, and owners create similar links on purpose.
  - **Attempt key, chosen.** It labels exactly one press, it is the precedent the factory already has (PAC-82), and CORS already allows it.
- **D-2 [F]: reuse PAC-82's conventions** where the reasons carry over:
  - same carrier and format;
  - absent or empty means keyless;
  - a malformed key is a 400 before anything is written;
  - a 24 h window by the database clock;
  - a conflict status for a reused key;
  - no replay marker, since the editor treats a replay as a success;
  - a lookup outside the write is only an optimisation, and the decision inside the write plus a uniqueness guarantee is authoritative.

  The contract fixes names and texts.
- **D-3 [F]: where this differs from PAC-82, and why.**
  1. **Scope: per owner, not per link.** A booking key is scoped to the link being booked. A create has no link yet, and the actor is the authenticated owner.
  2. **Matching against the original request, not the stored row.** A booking row never changes after it is saved, but a link is edited freely. Comparing with the link's current state would turn a genuine retry after an edit into a refusal. The server therefore keeps a fingerprint of the normalised request.
  3. **The outcomes must be stored.** A booking replay can be rebuilt from the booking row. The co-host outcomes of a create cannot be rebuilt from later state, because invitees accept, decline or get removed. They must be stored, so the PAC-82 rejection of "a separate key store … needs its own expiry job" does not carry over in full. Retention is bounded because the outcomes hold third-party addresses (§3.9, OQ-5). Whether the key lives on the link row, as PAC-82 does, with only the outcomes stored apart, or everything lives in one store, is the contract's choice. Either way it is a migration under PAC-116.
  4. **The refusal names the link.** PAC-82's refusal names nothing, because its caller is an anonymous booker. Here the caller is the owner of the named link, so naming it lets the editor recover (OQ-1).
  5. **Replay before the slug checks** (§3.8, AC-4). Bookings have no equivalent self-conflict.
  6. **A deleted original** has its own refusal (OQ-3). Bookings are never deleted.
- **D-4 [F]: concurrency is decided by a uniqueness guarantee on (owner, key) inside the create's transaction.**
  - The loser waits for the winner and then resolves as a retry.
  - A keyed create that hits **any** unique violation re-checks its key before answering. Concurrent same-key creates also generate the same slug, so the violation can arrive on the slug's constraint first. PAC-82 resolves only on its key's constraint (`scheduling_links.go:767`), which would leave a 500 here (AC-7).
- **D-5 [F]: the replay is decided under the same PAC-71 re-check as the create.** A replay must not hand link data to a session revoked mid-request (AC-10).
- **D-6 [F]: 24 h window, refused afterwards (OQ-2), outcomes removed within an hour of the window (OQ-5).** The cleanup reuses the backend's cron units (`backend/main.go:49-60`, PAC-81 drain) and is subject to the same graceful drain.
- **D-7 [F]: the key belongs to one editor session's create.**
  - It is made at the first Create link press and re-sent on every press until success, close, or the deleted refusal.
  - Re-sending on 4xx too is harmless, because failed attempts store nothing (AC-9), and it keeps the rule simple.
  - Reopening the editor starts over, because its form is blank (§3.12).
  - Blocking close while a save is pending (OQ-8) removes the only way an answer could reach a later session.
  - The message change is limited to create, the one write that gains retry safety.
