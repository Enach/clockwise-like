### Blocking

**B-1. The deleted refusal, the expired refusal and the key-reused refusal can apply to the same request, and the spec does not say which wins. With the OQ-1 default, the web then turns the editor into an editor of a deleted link.**
- §3.10 defines the deleted refusal only for "a retry". §3.3 defines a retry as the same key, the same owner **and the same request**. So a request with the key of a deleted link L and a *different* body falls under §3.4. That refusal "names the link that key created", which is the deleted L.
- §3.9 says that from 24 h on, the key "is refused as in item 4, for as long as the link exists". A PAC-40 delete is soft: `UPDATE scheduling_links SET deleted_at = NOW(), active = false` (`backend/storage/scheduling_links.go:219-220`). Nothing purges link rows: no `DELETE FROM scheduling_links`/`users` exists outside tests. A deleted link therefore "exists" for ever, so after 24 h §3.9 and §3.10 both apply to a deleted original.
- **Consequence on the web.** Under the OQ-1 default (§3.13, AC-20), the key-reused refusal makes the editor an editor of L, with chips from L's strict baseline read. Every by-id read of a deleted link is not found (`scheduling_links.go:159`). So the baseline read fails, and the next save is a PATCH to a deleted link. The owner never sees the §3.10 message.
- AC-13 has no age and no body variation, so no criterion catches this.
- **Resolve**: state the precedence between the three outcomes for every combination of {live, deleted} × {same request, different request} × {< 24 h, ≥ 24 h}. In particular, say whether a deleted original always gets the deleted refusal whatever the body and age. Add AC-13 variants for "deleted + different body" and "deleted + ≥ 24 h", plus the matching web criterion beside AC-21.

**B-2. The concurrent loser's decision can escape the PAC-71 re-check, and no criterion would notice.**
- D-4 models the loser on PAC-82: hit the unique violation, then "re-check its key before answering". In PAC-82 that re-check runs **after the transaction is rolled back, on the bare connection, outside any transaction**:
  - `_ = tx.Rollback()`, then `ResolveIdempotencyKey(conn, …)` (`backend/storage/scheduling_links.go:552-563`).
  - That is safe for a booker with no session. It is not safe here.
- A Postgres unique violation aborts the transaction. So the loser's decision must be made in a new statement, after the transaction that held the PAC-71 re-check (`withGenerationTx`, `backend/storage/session.go:204-215`) is gone.
  - That re-check is a `FOR KEY SHARE` read of `users` (`session.go:131`). It does not block a generation bump, so the generation can move during the loser's wait of up to 10 s.
  - `guardedResponseWriter` overrides the answer only when a re-check marked the guard stale (`backend/api/middleware.go:186-188`). The first transaction's re-check passed, before the wait.
  - A loser that resolves the PAC-82 way therefore hands the replay, with stored co-host addresses, to a session revoked mid-request.
- D-5 states the principle, but its only falsifier is AC-10. AC-10 moves the generation "after requireAuth and before the retry's create step", which is the sequential path. It never exercises the loser's wait.
- The same gap applies to the handler-level lookup that D-2 allows as "only an optimisation". If that lookup answers the replay or a refusal without a re-check, AC-10 detects it only if its seam sits before the lookup. "Before the retry's create step" does not say so.
- **Resolve**:
  - require explicitly that every replay and every refusal, including the one decided after a unique violation and any decided before the write, is answered only under a PAC-71 re-check that follows the decision's read;
  - add a criterion: the loser waits on the winner, its generation moves during the wait, and it gets requireAuth's 401 with nothing of L;
  - pin AC-10's seam as "before any read of the key";
  - extend AC-10 to the key-reused and deleted refusals, not only the replay.

### Major

**M-1. A keyed create with an explicit slug can still get "slug already exists" because of its own concurrent twin. That contradicts §3.7 and §3.8.**
- With an explicit slug, the handler checks `SlugExists` **before** the transaction and answers 409 (`backend/api/handlers_scheduling_links.go:503-508`).
- D-4's rule, "re-check on any unique violation", covers only violations raised inside the write.
- Sequence: request 2's pre-write key lookup misses (request 1 has not committed). Request 1 commits. Request 2's `SlugExists` now sees request 1's slug and answers 409. That is "slug already exists" because of the other request, which §3.7 forbids. It is also the self-conflict §3.8 says never happens.
- AC-4 is sequential and AC-7 uses generated slugs, so neither catches it.
- **Resolve**: require that a keyed create is never answered "slug already exists" while its own key is stored, however the slug conflict is detected. Add an AC-7 variant with an explicit slug, where the seam holds request 2 between its key lookup and its slug check.

**M-2. The fingerprint is outside the retention rule.**
- §3.9 and OQ-5 bound the retention of stored outcomes to 25 h because they hold addresses, some of people with no account.
- D-3.2 adds a stored "fingerprint of the normalised request". §3.3 makes the co-host list, "order and spelling as sent", part of it.
- Nothing says the fingerprint is removed with the outcomes, and §3.9 keeps "the link itself and its association with the key" for ever. After 24 h the fingerprint has no use, because every request is refused whatever its body. Yet as written it may keep the same addresses for ever. An unsalted digest of a low-entropy email address is no protection.
- **Resolve**: state the fingerprint's retention, either removed with the outcomes or able to reveal no address. Make AC-12 assert that no address survives the cleanup anywhere in the key store, not only "the outcome".

**M-3. The close-during-pending fix misses the Sheet's own close button.**
- §2.3, §3.15 and AC-27 name Escape and a click outside.
- `SheetContent` also renders a `SheetPrimitive.Close` "X" button (`smart-calendar-flow src/components/ui/sheet.tsx:60-63`). `LinkEditDrawer` uses that `SheetContent` (`LinkEditDrawer.tsx:428`) and passes the raw `onOpenChange` (`:427`), so the X closes the drawer mid-save too.
- AC-27 would pass with the X still working, and §3.15's claim that an answer "can never land in a later editor session" would be false.
- The bug claim itself holds by reading:
  - the drawer stays mounted (`src/pages/Links.tsx:501`);
  - the opening effect resets `editingId` (`LinkEditDrawer.tsx:211`);
  - `onSuccess` calls `onOpenChange(false)` or `setEditingId(saved.id)` (`:354`, `:363`), which act on whatever session is open then.
- **Resolve**: §3.15 and AC-27 must cover every way the drawer can close (Escape, outside click, the X), or state the requirement as "no close path while pending" with a criterion per path.

**M-4. The OQ-1 default's message promises something the default does not do.**
- After the key-reused refusal, "the owner's typed field values stay, the co-host chips come from the strict baseline read". The message then says "Save again to apply your latest changes."
- The owner's co-host changes made after the lost answer (the chips) are discarded, not applied. That is exactly the case §3.3 makes likely: any change to the list, even remove-then-re-add, which reorders it (`LinkEditDrawer.tsx:414`, `:420`), triggers the refusal.
- An owner who removed a co-host before pressing again is told the next save applies it, but it does not.
- **Resolve**: either the message must say that co-host changes were not kept, or the default must keep them. In both cases AC-20 must assert what happens to a changed chip list.

### Minor

1. **Labels: AC-8, AC-9 and AC-10 pass today.**
   - AC-8: today the first create rolls back, the second inserts (it waits on the slug index only when both slugs match, and then proceeds), and exactly one link exists. "Fails today: the second may answer 500 or create alongside" is wrong: neither outcome leaves two links or a 500 on the second.
   - AC-9: today the key is ignored and every corrected request is 201.
   - AC-10: today the in-transaction re-check gives the 401.
   - The spec's own rule says "Criteria that pass today are marked *regression guard*". Mark them so, or rewrite them so that they fail today.
2. **AC-7 does not force the slug-first path D-4 is written for.** It passes or fails by whichever unique index Postgres reaches first. Require both variants: both requests generate the same base slug (the base is free), and the base is taken (different suffixed slugs, so only the key constraint can collide).
3. **Precedent misquoted (OQ-5, D-6).** "Removed within one hour … as the PAC-40 erasure cron does": that cron runs `@every 24h` (`backend/main.go:82`) and has a start-up run (`:76-79`). An `@every` schedule restarts its timer on every start, and PAC-116 deploys restart the backend. "Within one hour after the window" then holds across a deploy only if the cleanup also runs at start. AC-12 checks only the schedule; it should state the bound across a restart.
4. **Citation (§2.2).** "On a violation … the save re-reads and resolves (`scheduling_links.go:760-768`)": `:760-768` only *detects* the violation. The re-read is at `:552-563`, after rollback and outside the transaction, which is the behaviour B-2 is about.
5. **Fingerprint normalisation is underdefined.**
   - `normalized()` resolves the aliases (`durations`/`duration_options`, `days`/`days_of_week`, `window_start`/`window_start_time`; `handlers_scheduling_links.go:81-101`, `:184+`) and trims the title. `CreateSchedulingLink` applies further defaults (`scheduling_links.go:98-112`).
   - Say whether "after the server's normalisation" includes defaults: is an absent `usage_type` the same as `"reusable"`, and an absent `booking_horizon_days` the same as 60?
   - Say that `"co_host_emails": null` is "no list". Go decodes it to nil exactly like an absent key, while AC-5 distinguishes "no list" from `[]`.
   - Give the reason the co-host list is compared raw while every other field is compared normalised. The server trims, lowercases and dedups entries (`scheduling_links.go:1252-1265`). The reason is presumably that outcomes echo entries as sent, but it must be written down.
   - The web already sends lower-cased chips in a stable order (`LinkEditDrawer.tsx:395`, `:414`), so the strict rule costs the web nothing.
6. **Order of the key 400 is unspecified.** A malformed key combined with invalid JSON, or with a 422 body: which answer wins? PAC-82 pinned this order (contract AC-17). AC-14 does not.
7. **e2e inventory (§2.4) omits the UI create** at `e2e/tests/scheduling-links.spec.ts:184`. It will start sending a key once the web ships. It should keep passing, so add it to AC-15/AC-26's list. The seed's direct `INSERT INTO scheduling_links` rows (`e2e/seed/seed.sql:279`, `:340`, `:445`) name their columns explicitly, so an additive nullable column does not break them. Nothing to change, but the inventory should say it was checked.
8. **AC-23 is weak.** It forbids only `localStorage` and `sessionStorage`. §3.12 says "page memory only", so either state that or also exclude IndexedDB and the URL.
9. **§3.9 wording.** "For as long as the link exists" means for ever, given soft delete. Say so, and see B-1.

### On the eight OQ defaults
- **OQ-1**: sound in principle, but see M-4 (the message and the chips) and B-1 (a deleted original).
- **OQ-2**: refusing for ever is consistent *only* because §3.9 keeps the key association while the cleanup removes the outcomes. AC-12 correctly pins that the association survives the cleanup.
  - A contract that puts the key, the fingerprint and the outcomes in one store and deletes whole rows would re-allow a second link after cleanup. AC-12 catches that, so this is consistent.
  - The fingerprint must not survive with the association (M-2).
- **OQ-3**: sound once its precedence is defined (B-1).
- **OQ-4**: sound. The replay may say "B invited" next to a roster showing B declined. AC-3 pins that deliberately.
- **OQ-5**: acceptable once minor 3 and M-2 are addressed.
- **OQ-6, OQ-7**: sound.
- **OQ-8**: sound once it covers the X button (M-3).

### Areas I examined and found sound
- **Deadlock.** The create transaction takes only `FOR KEY SHARE` row locks (the re-check, the FKs, invitee rows). A same-key loser waits on the winner's uncommitted index entry, and the winner never waits on the loser. Whichever store holds the key, there is no cycle.
- **Lock bound.** The loser's wait counts against the 10 s `lock_timeout`, giving a 500 with nothing written. §3.7 states this correctly.
- **Rollback.** PAC-116's stop-traffic rule, "no image-only rollback after a migration", and the down-migration claims match the runbook (`runbook.md:98-130`, `:244-262`).
- **Web lifecycle.** The key lifecycle in §3.12 and D-7 is coherent: nothing re-sends automatically, and the only retry is a press in the same session.
- **Demo mode.** The demo create is synchronous, and passing the key outside `args` mirrors PAC-82.
- **Inherited scope.** No open audit row or `x-uncertain` marker sits on the create operation.
