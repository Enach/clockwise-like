## 1. Problem

A Paceday user can learn whether **any** email address belongs to a Paceday account. They type the address into the Manager "Add person" form, or send the same request directly. The answer, the roster that follows, and the analytics view all say whether an account exists. The "On Paceday" badge is the visible form of the same bit.

This hurts the people being looked up, not the person looking:
- Account existence is personal data. An employer can check whether staff use a tool. Anyone can check whether a person is a customer, or test a list of leaked addresses to find targets for phishing that impersonates Paceday.
- The person gets no notice and has given no consent.
- Nothing limits how often it can be done. Each check costs one request, and the add needs no team.

The manager has a legitimate need for some of this information. Once a person has joined one of the manager's teams, the manager already knows they are on Paceday. With their consent, the manager is entitled to their Paceday figures (PAC-60). The fix must keep that, and remove the signal for everyone else.

### 2.1 How an account link is made today

- **Manager add** calls `storage.ConfirmedHolder(email)` (`handlers_manager.go:360`). That returns the one account carrying the address domain-confirmed, ignoring case (`storage/identity.go:156-172`). If there is one, the link is stored (`:365-367`). A failed lookup is the 500 (SF-010).
- **Detection** does the same for every address it finds in the manager's 1:1 events (`engine/manager.go:248-262`), and upserts a global roster row (`:280`). Candidates come from the manager's **own** calendar (`:203-216`). Anyone can create a recurring 1:1 event with any address, so this is a slower route to the same lookup.
- **Formal members.** In the team-scoped roster, every Paceday member of the team who has no assignment is added as a synthetic `source: "formal"` entry, with the link set to their account (`handlers_manager.go:722-737`). On patch or schedule, such a member gets a stored roster row with the link (`:772-812`), but only if they hold the address domain-confirmed (`:790`).
- **The link is sticky.** The upsert keeps an existing link when the new one is null (`storage/manager.go:92`).
- **Added people** (PAC-129) never get a link (`handlers_manager.go:736-761`; PAC-129 D-13).

### 2.2 How the link is used

- **Paceday-user flag**: `member_user_id != nil`, on both the roster read (`:299`) and analytics (`:653`).
- **Member week** branches on the link (`engine/manager.go:453-585`):
  - `source: "added"` → empty, nothing read, nothing stored (`:456-458`).
  - **Linked** → the **PAC-60 gate** first (`:469-478`): the viewer must own a team the linked account is a member of (`storage/teams.go:350-366`). If not, the answer is all zeros with `data_available: false`, and **no provider call** is made. If the gate passes, the cache is checked (4 h), then the member's **consent** (`analytics_shared_with_manager`, `:503-516`; the column defaults to true, `016_manager.up.sql:5`; no profile row reads as not shared). With consent, the member's `analytics_weeks` row is read (`:517-532`). Without consent, the answer is zeros. The result is cached with `is_paceday_user = true`.
  - **Not linked** → the cache is checked, then free/busy is read through the **viewer's** credential (`:533-563`; `engine/freebusy_service.go:124`, one provider call with a 5 s limit, `:154`; personal-mail domains are never queried, `:18-19`, `:137`). - **Cache** (`team_analytics_cache`, `016_manager.up.sql:34-46`) is keyed by viewer, address and week. It stores `is_paceday_user`. A linked read checks the PAC-60 gate before the cache (`engine/manager.go:460-463`), so figures cached before the gate are not served on that branch (`engine/manager_scope_test.go:108-124`).

## 3. Desired behaviour

### 3.1 The rule: a person's Paceday status is shown only when the viewer can already see it [F, D-1]

For a viewer in Manager mode, an address counts as **visible on Paceday** only when it belongs to an account the viewer can already see elsewhere in Paceday. That is, when either:
- **(a) Shared team.** The account is a **Paceday member** of a team the viewer is also a Paceday member of, in either role. A Paceday member is someone who accepted an invitation, or who created the team. An added person (PAC-129) never qualifies. Every team member already sees these people, with their address and their Paceday kind, in the team's member list.
- **(b) Same organisation.** The account belongs to the viewer's organisation. Every member of an organisation already sees its accounts in the organisation's member list.

**Which accounts an address maps to** (challenge B-1). There are two questions, answered separately.

1. **The flag ("visible on Paceday").** The address is visible when **any** account in (a) or (b) carries it, at **any** standing. Addresses are compared ignoring letter case, after the address normalisation the Manager paths already use.
   - This mirrors exactly what the two lists show the viewer. Both lists show accounts at any standing.
   - So the flag reveals nothing beyond those lists, including standing. Requiring domain-confirmed standing here would hide the flag for an unconfirmed co-member whom the team list shows as a Paceday member. That would *reveal* their standing.
   - A carrier **outside** (a) and (b) is never consulted. In a case-collision pair (two accounts whose addresses differ only by case, legacy rows with `email_key` NULL, migration 035), only the carrier inside (a) or (b) makes the address visible. The other carrier changes nothing.
2. **Paceday figures.** Which account the figures belong to depends on how the roster entry knows that account. Both cases then need the PAC-60 gate and consent (§3.3). [F, revision 2, option (i)]
   - **Known through team membership.** This is the synthetic `formal` entry of the team-scoped roster, made from a Paceday member of the team (`handlers_manager.go:722-737`). No address is resolved: the account is the team member itself. Figures keep **today's rule**: PAC-60 plus consent, with **no standing check**.
     - This keeps today's figures for unconfirmed co-members: unbound legacy accounts until their next sign-in, and accounts created on mailbox evidence.
     - It reveals nothing new, because team membership is already disclosed to every member (§2.3).
   - **Resolved from an address.** This is a manual or detected roster row (`source` `manual` or `auto`), whose address must be mapped to an account. That is a PAC-71 granting site, so figures are read only for the account `storage.ConfirmedHolder` returns: the one account carrying the address, domain-confirmed, ignoring case (`storage/identity.go:156-172`). It is the same rule the old add applied when it stored the link, and the same rule the formal-member write uses (`handlers_manager.go:790`).
     - If the address is visible but has no such holder (the visible carrier is unconfirmed, or a case-collision gives two carriers), the row is **visible but not entitled**. It shows the flag and "no data", and nothing is read.
     - "No data" is also the answer when consent is withheld.
   - **Organisation-only accounts** never pass PAC-60, which needs a team the viewer owns. So the organisation path never yields figures, whatever the standing.

**Why this rule and not a narrower one:**
- It reveals nothing the viewer cannot already read in Paceday, so it is not an oracle.
- It keeps the badge where it matters to a manager: their reports, who share a team with them or, most often, a company domain.
- Restricting (a) to teams the viewer **owns** would hide the badge for people the viewer already sees as Paceday members, with no privacy gain.
- Dropping (b) would hide it for most same-company reports, also with no privacy gain.

**Rule (b) is coupled to the organisation member list, and inherits its exposure** (challenge B-3).
- (b) is defined as "an account the organisation member list returns to the viewer". It is not a separate organisation rule.
- Today that list is itself an oracle for consumer domains that are missing from the generic-domain list (O-11). For a viewer at such a domain, (b) shows the flag for addresses at that domain. The viewer can already enumerate those through O-11, so (b) adds nothing, but it carries O-11's exposure until O-11 is fixed.
- When follow-up F-2 narrows the organisation rule, for example by completing the generic-domain list or restricting the member list, (b) narrows with it automatically. The contract states the coupling, and an AC pins it (AC-17).
- **Dropping (b) until F-2 lands was rejected.** It would remove the badge for real company colleagues, while O-11 stays open whatever this ticket does.

### 3.2 Everything else is indistinguishable from "no account" [F, D-2, D-3]

For an address that is **not** visible on Paceday, every Manager answer is the same whether or not an account holds it. This covers the add, the patch, the roster, analytics, detection, the web, error codes and texts, and the work the server does.

- **The add and the patch** never look the address up. Their answers carry no account identifier for anyone. The field that carried one stays in the answer, always empty (D-4).
- **Detection** never looks the address up and stores no account link.
- **The roster and analytics** show the person as not visible on Paceday:
  - no "On Paceday" flag;
  - figures estimated from free/busy read through the viewer's own calendar connection, exactly as for an address with no account (D-3). That is meeting time, and free time estimated from it; never focus time; "no data" when the calendar cannot be read.
- **No Paceday-held data** (weekly analytics, focus, settings) of an account outside the rule is ever read for the viewer.

**Consequence, stated plainly** (OQ-2, challenge N-2). Today a Paceday user who shares no team with the viewer shows "no data". After this change they show the same free/busy estimate as anyone else at their domain. This is what makes the two cases indistinguishable.
- The read uses only the viewer's own calendar permissions at the provider, which the viewer could exercise directly in their calendar app. No Paceday-held data is read.
- **Consent inversion.** A Paceday user who withheld sharing with their manager, and who is **not** visible to V, gets a meeting-time estimate shown to V. Their own team owner sees "no data" (§3.3). A member removed from V's team (AC-11) moves from "no data" to an estimate.
- Paceday consent governs only data Paceday holds. This estimate is provider data, read through V's own credential. It is the same estimate V gets for any non-user at that domain.

**Accepted residuals** (each on the same footing: the viewer could observe it directly through their own calendar provider):
- **Provider-side shapes** (challenge N-3). Paceday writes focus and habit events into its users' calendars (`calendar/events.go:75`, `calendar/client_factory.go:63`). A holder's real free/busy can therefore show Paceday-shaped busy blocks. Paceday cannot hide what the provider returns, and the viewer would see the same blocks in their calendar app. AC-4's fixture uses identical busy intervals on purpose, to isolate what Paceday adds.
- **Visibility-read cost** (challenge B-4). The visibility decision is one database statement of the same shape for every address: "accounts in (a) or (b) carrying this address". For an address outside the rule it returns no rows, whether or not an account carries the address elsewhere. Any difference is an index probe inside one statement. It is not separable from network jitter, and no branch runs a second read when a carrier exists (AC-8).
- **Global case-variant carrier** (re-challenge N-1). For an entry resolved from an address, `ConfirmedHolder` counts carriers globally. A legacy case-variant account outside V's teams and organisation therefore turns a visible co-member's manual-row figures into "no data". This is not a usable oracle: no new case collision can be created (`users_email_key_unique`, migration 035; sign-in refuses two or more carriers, `storage/signin.go:121-122`), and the owner sees one fixed state with nothing to compare it against.
- **Standing of an owned co-member, inferred through a manual row** (re-challenge N-2; it still applies under option (i), but only for manual rows). An owner whose co-member shares analytics and has a stored week can compare the `formal` entry (figures) with a manual row for the same address ("no data"), and infer that the member's address is unconfirmed. The owner learns only the standing of a member of their own team, and only by setting up the comparison themselves. Accepted. Removing it would need either a standing check on `formal` entries (the regression revision 2 rejects) or giving up PAC-71 at the address-granting site.

### 3.3 What the viewer legitimately gets for a visible person

For an address visible on Paceday under §3.1:
- **Flag**: "On Paceday", in the roster and in analytics.
- **Paceday figures**: the PAC-60 rule and consent, as today:
  - only when the viewer **owns** a team the person is a Paceday member of (PAC-60);
  - and only when the person shares analytics with their manager (consent);
  - plus, **only for an entry resolved from an address** (a manual or detected row), the single domain-confirmed holder (§3.1 item 2). A `formal` entry, known through membership, has no standing check, as today.
- **Visible but not entitled**: the row shows the flag and "no data" when any of these holds:
  - the viewer is not such an owner (a co-member, or same organisation only);
  - for an entry resolved from an address, there is no single domain-confirmed holder;
  - consent is withheld.

  The row is not replaced by a free/busy estimate. Existence is already known to this viewer, so nothing is revealed.
- **One deliberate change, for unconfirmed co-members' manual rows.** Today the old add refused to link an unconfirmed holder, so such a row took the external estimate. Now it is visible, so it shows the flag and "no data" (the no-read branch). Its `formal` entry, if V has no manual row, keeps its figures. Listed in §6 and pinned by AC-19.

### 3.4 State is re-derived on every read: three branches [F, D-7]

The flag and the branch are decided at read time, from the viewer's current teams and organisation. Every row takes exactly one of three branches:

| Branch | When | What is read | What may be served from the cache |
|---|---|---|---|
| **Paceday figures** | visible, single confirmed holder, PAC-60 owner, consent given | the holder's stored weekly analytics | only a row computed on this branch |
| **No read** | visible but not entitled (§3.3) | nothing | **nothing**. "No data" is computed and never served from the cache. |
| **Estimate** | not visible | free/busy through the viewer's credential | only a row computed on this branch |

Consequences:
- If the person leaves the viewer's only shared team, the next read takes the estimate branch. No Paceday figure computed earlier is served to that viewer again, from any cache.
- If they become visible (they join a shared team or the viewer's organisation), the next read takes the Paceday or no-read branch. A cached estimate is not served on either (challenge N-1).

### 3.5 Stored links are erased, and no new link is written [F, D-6, D-12]

- At deploy, every stored account link that does not satisfy §3.1 for its roster's owner is erased. Links that do satisfy it are kept, only so that an image rollback still works (§7).
- After deploy, **no** Manager path writes a link: not the add, not detection, and not the formal-member write in patch and schedule. That write still creates the roster row and assignment, behind the same PAC-71 confirmed-holder entry check (`handlers_manager.go:790`), but stores no link.
- Nothing the server answers depends on a stored link.

**Effect on PAC-71 rule (b)** (challenge B-2).
- PAC-71's emptiness check counts a roster row pointing at an account as data that makes the account non-empty (`storage/emptiness.go:49`). That rule is **not amended** here. PAC-71 deliberately counts relations other users create (a pending co-host counts too), and changing that is PAC-71's decision, not this ticket's.
- The effect of D-6 is therefore on the **data** only:
  - an unbound legacy account whose only "data" was an erased link becomes empty, so it binds under rule (b) on authoritative evidence;
  - an account with a kept link stays non-empty.
- This is intended. An erased link was written by someone else typing the address, so the account carries no data of its own. Rule (b) exists to let the address's real owner in on authoritative evidence. Today a stranger's add can block that owner, and the erasure removes that.
- After deploy no new link is written, so no Manager action can make an account non-empty any more (AC-18).
- **Kept links are frozen** (re-challenge N-3). After the migration, nothing writes, refreshes or erases a kept link, even if the co-member later leaves the team or the organisation. It therefore keeps that account non-empty under PAC-71 rule (b) indefinitely. This is the conservative direction. The column is now write-never, which F-2 and PAC-71's owners should know.

### 3.6 Web

- The "On Paceday" badge is shown only from the server's flag. The client never infers it.
- The analytics note for an estimated row must not claim the person is **not** a Paceday user, because they may be one. Default wording: "Meeting time estimated from your calendar. Focus time is shown only for Paceday members of your teams who share it." [F]
- The demo never guesses the flag from a domain (as PAC-129 AC-35 does for teams).
- The "degraded" banner keeps its rule. After the server change it no longer separates holders from nobodies (O-6).

### 3.7 Compatibility

- **Old clients** keep working. Every answer stays valid under the previous contract, because the account-identifier field is still present and is null. The Paceday-user flag keeps its name and type; only its meaning narrows (§3.1).
- **Old web after a backend deploy**: shows fewer badges, and nothing else changes.
- **New web against an old backend** (release window): unchanged, because the web reads the same flag.

## 7. Rollback

- **Migration.** It only erases account links (AC-12). The down migration is a no-op and **cannot restore** them. That is harmless, because a link outside §3.1 was itself the leaked bit. Applied under PAC-116's stop-traffic rule (`docs/runbook.md`).
- **Image rollback.** The previous backend reads stored links again:
  - links within §3.1 were kept, so co-member reports keep their figures;
  - erased holders show as externals until the old add or the old detection re-creates their link. That brings the oracle back, which is expected on a rollback.
- **Web-only rollback** is safe. The old web reads the same flag, and the old note wording reappears.
- **Release note** (challenge N-6):
  - The erase is **irreversible**. The down migration is a no-op, and an image rollback does not restore erased links.
  - An operator who wants full rollback fidelity snapshots `manager_team_members` before deploy (`pg_dump -t manager_team_members`).
  - Erasing may make some unbound legacy accounts empty, so they become bindable under PAC-71 rule (b) (§3.5). This is intended, and it is listed in the note so that support recognises it.
  - PAC-116's stop-migrate-start is automatic (`docs/runbook.md:98-123`). No extra traffic step is needed.
- **Data minimisation note.** Old Paceday-figure rows in the Manager analytics cache become unreachable (D-7), but they stay stored. Purging them is listed for follow-up F-2's data-minimisation pass, or for PAC-134. It does not block this ticket.
