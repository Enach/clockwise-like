### Blocking

**B-1. AC-13 is false as written, and so is the §3.4 promise "A retry therefore cannot produce a second link".**
- An all-or-nothing create (D-4) stops a *failed* create from leaving a link behind. It does nothing for the case AC-13 names: "the network fails after a create was sent". If the server committed and only the answer was lost, a retry of the same form creates a second link.
  - Nothing deduplicates a create today. The web never sends a slug (`smart-calendar-flow src/api/schedulingLinks.ts:170-181`, pinned by `schedulingLinks.test.ts:110` and `:280`).
  - The server therefore generates one, with a random suffix whenever the base is taken (`backend/engine/booking.go:83-101`), so the second create always succeeds.
  - Link create has no idempotency key. The only one in the API is the public booking's (PAC-82, `backend/api/gen/paceday.gen.go:116-118`).
  - Titles are not unique, so "at most one link of that title" cannot hold.
- AC-13 also says it is "proven by a transport test that drops the answer". A mocked transport cannot show what the server stored, so the test passes or fails by how the mock is written, not by the product.
- **Resolve**: either (a) require create to be safe to retry after a lost answer, as an observable criterion tested end to end against the server, which brings that requirement into the contract stage; or (b) drop AC-13, correct §3.4 and OQ-3's reasoning ("keeps a retry from making a second link"), and list the duplicate create after a lost answer under §5 as accepted.

**B-2. The OQ-1 default (the drawer stays open after a save) is unsound as specified. Once the drawer stays open after a create, the next Save creates another link.**
- The editor decides between create and edit from its `link` prop alone (`LinkEditDrawer.tsx:122`, `:260-261`).
- That prop is a snapshot taken when the drawer opens: `setEditingLink(link)` at `src/pages/Links.tsx:402`, passed at `:501`. For a new link it is `null` (`:398`), and nothing replaces it with the saved link.
- So the default exactly as written ("stays open, shows the saved link, removes the refused chips") leaves the editor in create mode. Pressing Save again posts a second create.
- The same stale snapshot breaks D-3 and the success message:
  - `initialEmails` (`LinkEditDrawer.tsx:141-144`) still holds the roster from before the save. After an in-drawer save, "did the owner change the co-hosts in this session?" and "who is new?" are measured against the wrong baseline.
  - Chip states (`chipStateFor`, `:217-224`) also read the old roster.
- **Resolve**: OQ-1's default must state what follows a save that keeps the editor open:
  - after a successful create, the open editor edits *that* link, and no further save from it creates a link;
  - the baseline for D-3 and for the counts in §3.5 becomes the server's answer to that save;
  - add a criterion for each of these.
  - Or change the default to "close" and keep the persistent report.

**B-3. §2.2 and §3.7 misdescribe what the server does with the owner's own address on create. D-1 makes the defect reachable from the web, and AC-15 only guards the client.**
- §3.7 says the owner's address is "skipped in silence by the server". That is true for PATCH: `uid == ownerID → continue` (`backend/storage/scheduling_links.go:875`).
- It is **not** true for create.
  - `createLink` resolves each listed address with `ConfirmedHolder` and calls `AddLinkHostCtx(..., "pending")` (`backend/api/handlers_scheduling_links.go:429-435`) with no owner check.
  - `AddLinkHost` is an upsert: `ON CONFLICT (link_id, user_id) DO UPDATE SET status = EXCLUDED.status` (`scheduling_links.go:273-281`).
  - Listing the owner's own confirmed address on create therefore **demotes the owner's host row from `accepted` (written at `:425`) to `pending`**.
- Consequences I could trace in code:
  - the owner then matches `GetPendingInvitesForUser` (`scheduling_links.go:382-388`), so their own link shows up in their invitation list;
  - the owner drops out of `GetAcceptedHosts` (`:360-364`), which the booking engine and the public page use (`backend/engine/booking.go:61`, `:451`; `handlers_booking.go:97`, `:114`).
  - I did not trace the full effect on slot computation.
- This is the same upsert that API-048 fixed for `POST /{id}/hosts` and PATCH (`docs/factory/api-audit.md:306`, "Fixed (PAC-61)"). It survives on create, and the contract's create description does not mention it (`contracts/openapi/openapi.yaml:7563-7570`).
- Today the web cannot reach it, because it does not send the list on create. D-1 makes it reachable for any client that does not apply AC-15, including an older web build or any API caller.
- **Resolve**:
  - correct §2.2;
  - add a server criterion: given a create whose list contains the owner's own address, the owner stays an accepted host and that address gets a defined, reported outcome. A `[contract]` test.
  - state that outcome's wording for the owner (see M-6);
  - record the create-path remnant of API-048 in the inherited scope.

### Major

**M-1. D-3 protects only the save that leaves co-hosts unchanged. A save that changes co-hosts on a degraded roster still silently removes every co-host the editor never received.**
- The chips come from the links list (`LinkEditDrawer.tsx:166`), which is built non-strictly (`handlers_scheduling_links.go:463`, `:336-353`).
- A failed roster read gives an empty roster. A failed user read gives a host with no email, which hydrates as a chip with no address.
- If the owner then adds one person, D-3 sends the list, and the server removes every host not in it (`scheduling_links.go:863-869`).
- That breaks §3.2 ("a save never removes a co-host the owner did not remove"), and AC-5 does not catch it because AC-5 changes only the title.
- **Resolve**: make D-3's alternative ("a save that carries the list is based on a roster known to be complete") a requirement for the *changed* case, and add a criterion: degraded roster, the owner adds G, saves → E is still a host. Make it `[contract]` or `[e2e]`, not unit-only.

**M-2. Case and duplicates are not specified, so the counts in §3.5 and AC-14 are ambiguous.**
- `addCoHost` lowercases what the owner types (`LinkEditDrawer.tsx:316`). Hydrated chips keep the server's stored case (`:166`; the server returns `user.Email`, `handlers_scheduling_links.go:345`).
- The duplicate check is an exact, case-sensitive match (`:323`). So with a chip `Pat@Acme.com` present, the owner can add `pat@acme.com`. The "new" count (`:264`) and the chip state (`:218`) use case-sensitive `includes` too.
- The server folds case (`CarrierIDs`, `identity.go:165-184`; `ConfirmedHolder`, `:152-161`). Two spellings of one person therefore reach one host row.
- The spec does not say whether outcomes and counts are per listed address or per person, or what the editor does with two spellings of one person. A response keyed by address could count one invitation twice.
- **Resolve**: state that outcomes and counts are per person, and that the editor refuses a duplicate regardless of case. Add a criterion with a mixed-case duplicate.

**M-3. Removing the last co-host has no criterion.**
- Problem 1 is "removing a co-host does nothing". The easiest way to get it wrong in the new path is to treat an empty list as "no list".
- The server distinguishes the two: `[]` sets an empty list, an absent key leaves co-hosts alone (`openapi.yaml:7950-7953`; `scheduling_links.go:857`).
- AC-2 and AC-3 always leave a co-host in place.
- **Resolve**: add a criterion: a link with B only; A removes B and saves → B is not a host. `[e2e]`.

**M-4. The single wording in D-6 is untrue for two of the three cases it covers.**
- §3.3 and AC-6 fix the text "there is no Paceday account with this address". For D (carried unconfirmed) and for the case collision, a Paceday account *does* carry that address.
- The owner will act on that text, for example by telling a colleague to sign up when they only need to confirm their address. That conflicts with PAC-83 ("no invented data", §6).
- Telling the cases apart is not needed. One wording that is true in all three cases satisfies both D-6 and PAC-83.
- **Resolve**: require one wording that is true for all three cases and reveals nothing about standing. Drop the false sentence from §3.3 and AC-6.

**M-5. The inherited scope is understated.**
- API-053 is declared inherited, but **no acceptance criterion resolves it**. Under "touch it, fix it" (README §7.1) the work would ship with the finding still open.
- The same defect exists on PATCH, which this work also changes (D-2 changes its answer):
  - `dayNumbers` (`handlers_scheduling_links.go:136-153`) is also applied at `:573`;
  - there, `{"days":["mon","Montag"]}` *silently saves Monday only* instead of failing;
  - it is not in the audit row (`api-audit.md:311` names only POST).
- The API-048 remnant on create (B-3) is not listed.
- **Resolve**: add criteria that resolve API-053 on create, and state whether the PATCH variant is in or out (it should be registered either way). List the API-048 create remnant.

**M-6. The per-address outcome set is incomplete.**
- §3 and AC-8 have two outcomes, invited and not added. The server has at least four:
  - newly invited;
  - already a host and kept, with status unchanged (PAC-61);
  - the owner's own address (skipped on PATCH at `scheduling_links.go:875`; demoted on create, B-3);
  - cannot be invited.
- There is also a fifth case the keep set creates: an address carried *unconfirmed* by an account that is already a host is kept (`CarrierIDs` at any standing, `scheduling_links.go:863`) but could not be invited.
- The spec must say how each is reported, so that "not added" is never shown for someone who stays a host, and the owner's address is never described as "no Paceday account".
- **Resolve**: list every outcome, with its wording and count, and give each a criterion.

**M-7. The co-host list has no size limit, and the spec makes the list the main input.**
- The cap of 5 is client-only (`LinkEditDrawer.tsx:327`). The contract has no `maxItems` on either `co_host_emails` (`openapi.yaml:11026-11032`, `:16050-16056`). The API never wraps a request body in `MaxBytesReader` (its only use in the backend is `backend/auth/ms_idtoken.go:483`, on an identity-provider response).
- On PATCH, each address costs lookups inside the transaction that holds the link's lock (`scheduling_links.go:863-881`), and PAC-101 makes bookings wait on that lock for up to 10 s.
- With D-1/D-2 the answer also grows with one outcome per address.
- §5 dismisses this in one line ("not changed here") with no reason.
- **Resolve**: either specify the server's answer to a list over a stated maximum (a criterion), or record the decision to leave it unbounded, with the reason and a follow-up ticket.

### 2. New findings

#### Blocking

**P2-B1. §3.10 makes the save's answer the new baseline. That answer's roster is built non-strictly, so the silent removal of M-1 comes back through the drawer that stays open (OQ-1).**
- Both create (`handlers_scheduling_links.go:439`) and PATCH (`:648`) answer through `writeLink` (`:364-367`). `writeLink` calls `toSchedulingLinkDTO(..., false)` (`:306-310`).
- A failed host-rows read gives `hosts: []`. A failed user read gives a host with `"email": ""` (`:336-353`; `Email` has no `omitempty`, `:66`).
- The web then injects the owner from `/auth/me` when the roster lacks one (`schedulingLinks.ts:140`). So an emptied roster looks exactly like an owner-only link.
- §3.3 marks a baseline untrusted only when "the roster could not be loaded, or when any host in it lacks an address". An emptied *answer* roster meets neither condition.
- Sequence:
  1. The save's answer is degraded, and the save has a "couldn't be added" outcome, so the drawer stays open.
  2. §3.11 sets the chips from that answer: no co-hosts.
  3. The owner adds G and saves.
  4. The list is [G], and E is silently removed.
- That breaks §3.3 ("never removes a co-host the owner did not remove") and is the issue's core harm.
- **Resolve**: require that a baseline taken from a save's answer is trusted only when that answer's roster could not have degraded. If it may be degraded, co-host editing is disabled exactly as in AC-6. Add a criterion: a degraded answer roster after a save that keeps the drawer open → the next co-host change is not sent, or E is still a host afterwards ([unit] for "not sent", [contract]/[e2e] for E kept). Whether the answer becomes strict or the editor re-reads is for the contract stage.

#### Major

**P2-M1. AC-6's first condition ("empty because the load failed") cannot be observed from the source the editor reads today, so the criterion can pass without protecting anything.**
- The links list answers 200 with `hosts: []` when its roster read fails (`:463`, non-strict).
- After `normalizeSchedulingLink` injects the owner (`schedulingLinks.ts:140`), that is identical to a healthy link with no co-hosts.
- A strict read that fails rather than degrades exists: the single-link `GET /{id}`, `buildSchedulingLinkDTO(..., true)` at `:515`. D-3 leaves using it to the contract and plan ("the contract and plan choose how").
- An editor that keeps hydrating from the list can therefore never detect the empty case, while a unit test that mocks some "failed load" still passes.
- Separately, §2.4 cites `TestPAC25GetLinkHostStatusFailureForCoHostIs500` for the strict roster. That test covers the reader check. The roster test is `TestPAC25GetLinkRosterFailureIs500` (`handlers_scheduling_links_test.go:815`).
- **Resolve**: state as a requirement that a trusted baseline comes only from a read that fails rather than degrades, and that the list's roster is never a trusted baseline for a save that carries the list. Define "could not be loaded" as "that read failed". Fix the test citation.

**P2-M2. OQ-4's default makes it impossible to remove a single co-host from a link that already has more than 5.**
- The editor hydrates every co-host (`LinkEditDrawer.tsx:166`). Its cap check applies only when *adding* (`:327`), and it shows "N/5 co-hosts" (`:638`).
- On a link with 7 co-hosts, removing one sends 6 entries. AC-19 makes that a 400 with nothing saved. To remove one person, the owner must remove two. That contradicts §3.1 ("a removed chip removes that person"), and removal is problem 1 of this issue.
- D-8's justification is false for these links: "no list the editor builds is refused".
- These links can still be created after this work: `POST /{id}/hosts` stays unbounded (§5), and an older web build can use it during the rollback window.
- **Resolve**: OQ-4 must state what the owner can do on such a link. Either (a) a save that only removes co-hosts is accepted whatever the count, or (b) the editor tells the owner before saving that the list must be brought to 5 or fewer, never letting them discover it from a 400. Add a criterion either way, and correct D-8's claim.

**P2-M3. The new 400s (D-8, D-9; AC-19, AC-27, AC-28) break these operations' own status convention without a reason.**
- On create and PATCH, 400 means only an unparseable body (`handlers_scheduling_links.go:381`, `:547`; contract create `'400'`: "Body is not valid JSON").
- Every field-validation failure is 422 (`:233-299`, `SchedulingLinkValidationError`). That includes `days_of_week` out of range (`:254`), the exact numeric twin of an unrecognised day name.
- So the same mistake, "day not understood", would answer 422 when spelled `[9]` and 400 when spelled `["Montag"]`.
- The web mirrors 422 for validation (`LinkValidationError`, `schedulingLinks.ts:289-295`).
- Backward compatibility, checked:
  - No first-party client sends the `days` alias. The web sends only `days_of_week` (`schedulingLinks.ts:171`). `mcp/` has no scheduling-link code. e2e never sends `days`. The only backend test that does sends valid names (`handlers_scheduling_links_test.go:135`).
  - So the change is safe for first-party code. For a third-party caller, the `["Montag"]` case moves from 422 to 400, which breaks a client that branches on 422.
- **Resolve**: either use 422 (consistent with the operation and with the numeric twin) or give the reason for 400 in §9 and accept the status change for `["Montag"]` explicitly.

### 2. New findings (minor only)

**P3-m1. The spec does not say where the "over 5 only if it adds" rule is evaluated, and a concurrent edit can change its answer.**
- "Reaches a current host" depends on the host set at the moment of the check. Example: a link has 7 hosts. Tab 2 removes X. Tab 1, whose baseline still holds X, removes only Y and saves 6 entries including X.
  - X no longer reaches a current host, so tab 1's save is a 422, although the owner only removed someone.
  - If the rule were evaluated outside the PATCH transaction (PAC-101 takes the link lock with its UPDATE first, `scheduling_links.go:844-856`), the opposite race could also let a list that re-adds X through, past the cap.
- Neither outcome is silent and nothing is lost, so this is not a major.
- **Resolve**: state that the rule is decided against the host set inside the same transaction as the write. Have the contract give the 422 a message that does not read as "you added too many" when the owner only removed someone. Last-save-wins (§5) stays as decided.

**P3-m2. D-8's recommended cheap pre-check contradicts §3.6 on lists that only keep.**
- The pre-check is: refuse more than max(5, current co-host count) entries before any lookup. Entries count as sent, while the count is of co-hosts.
- Two kinds of keep-only list break it: one with two spellings of a current co-host (AC-18 allows this), and one that includes the owner's own address. Each has more entries than the link has co-hosts, so the pre-check refuses it. §3.6 says such a list "is accepted at any length".
- The editor never sends these, since it refuses duplicates and the owner's address (AC-14, AC-17). An API client can.
- **Resolve**: the contract stage either counts the same way in both places, or drops the pre-check, or narrows §3.6. It is a recommendation, so this is not a spec defect in itself; it is recorded so the contract does not inherit the contradiction.

**P3-m3. Two halves of the new criteria pass today and are not labelled regression guards.**
- AC-33's `[unit]` half: today `addCoHost` already refuses at 5 or more chips (`LinkEditDrawer.tsx:327`).
- AC-32's `[contract]` half: today a PATCH listing 6 of 7 hosts is accepted and removes the seventh (`scheduling_links.go:863-869`). It fails today only at `[e2e]`, where the web sends no list. As a contract test it is still worth keeping: it guards against a plain `maxItems: 5`.
- **Resolve**: label both halves as regression guards, per the spec's own rule ("criteria that pass today are marked regression guard").
