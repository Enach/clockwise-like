# Spec — PAC-116: migrations take their strongest lock on a live-read table first (lock-upgrade deadlock against an in-flight booking save)

- **Linear**: https://linear.app/paceday/issue/PAC-116 (split from PAC-110 item 1)
- **Status**: draft (awaiting spec-challenger)
- **Author**: spec-author (factory)
- **Verified against**: clockwise-like `origin/main` `c2609a6` (migrations 001–039; 033 was never used)
- **Inherited scope**: none. No HTTP operation changes, so no `x-uncertain` marker or `docs/factory/api-audit.md` finding is touched.
- **Owner decisions**: Q1–Q3 confirmed 2026-11-14 (`.claude/factory/owner-decisions.md`, "PAC-116 migration lock order"). Q1: the rule covers `bookings`, `scheduling_links`, `scheduling_link_hosts` and `users`. Q2: it is enforced by a Go test that parses the up migration files, with no PostgreSQL reproduction test. Q3: operator behaviour is unchanged (PAC-84 untouched), and the runbook's guidance stands.

Decision marks used below: **[O]** = owner decision (Q1–Q3 above); **[F]** = factory decision, recorded here and open to challenge; **[OQ]** = needs the owner (§8).

A note on naming. The spec rules say §3–§5 should not name tables. This spec names the four covered tables anyway, because the owner's Q1 decision is phrased as that list of tables, and the rule cannot be stated without them. It names no file, package, function or test.

## 1. Problem

A migration can deadlock against a public booking that is being saved at the same moment. PostgreSQL then aborts one of the two transactions with SQLSTATE `40P01`. If the booking is aborted, the booker gets a 500 and their booking is not saved. If the migration is aborted, the server or the operator command fails to start, and the database is left marked dirty at that version (runbook "Rollback").

Here is how the cycle forms. Suppose a migration first takes a lock on `bookings` that lets readers in, such as `CREATE INDEX` (SHARE), and later in the same transaction asks for ACCESS EXCLUSIVE, such as `ALTER TABLE ... ADD COLUMN`. Meanwhile a booking save reads `bookings` (ACCESS SHARE, compatible with SHARE) and then tries to insert (ROW EXCLUSIVE, which must wait for the migration's SHARE). The migration's ACCESS EXCLUSIVE request in turn waits for the save's ACCESS SHARE. Each waits for the other.

Today no migration does this. Nothing stops the next one from doing it, though, and two paths run migrations against a database that may be serving traffic (§2.2). The same lock-upgrade shape applies to the other tables that live booking and session paths read (Q1).

Who pays: a booker whose save is aborted (500, booking lost, they must retry), or an operator whose deploy or `paceday-operator encryption` command fails half-way and must be rolled back from a backup.

## 2. Current behaviour

### 2.1 How migrations run

- `storage.Migrate` (`backend/storage/db.go:128-133`) and `storage.Open` (`db.go:27-41`, called by the server at `backend/main.go:192`, before it listens) both call `runMigrations` (`db.go:44-84`). That function uses golang-migrate v4.19.1 (`backend/go.mod:11`) with the `postgres` driver on one dedicated connection (`db.go:50-54`), using `&postgres.Config{}`, so `MultiStatementEnabled` is false.
- With `MultiStatementEnabled` false, the driver reads the whole `.up.sql` file and sends it as one `ExecContext` with no arguments (golang-migrate `database/postgres/postgres.go:265-296`). Under pgx v5.10.0 (`go.mod:13`), a call with no arguments always uses the simple query protocol (pgx `conn.go:515-518`, "Always use simple protocol when there are no arguments"). PostgreSQL runs a multi-statement simple query as **one implicit transaction**, unless the text itself contains transaction control. **Each migration file is therefore one transaction.** Its locks build up statement by statement and are all released when the file ends.
- The version row is written in separate transactions: dirty before the file runs, clean after it (golang-migrate `migrate.go:738-750`, `SetVersion` at `postgres.go:355`). Before any of this, the migrator takes a session-level `pg_advisory_lock` with its own generated `bigint` key (`postgres.go:241`), so only one migrator runs at a time.
- No up migration contains `BEGIN`, `COMMIT`, `CONCURRENTLY` or `LOCK TABLE` at top level. `grep` finds only the PL/pgSQL `BEGIN` inside `023`'s `DO` block and `034_encryption_at_rest.down.sql`.

### 2.2 When a migration meets live traffic

- **Server start** (`main.go:192`). Migrations run before the server listens (runbook "Deploy order" step 4, `docs/runbook.md:78-80`). With one backend, the old process has stopped by then ("Paceday runs one backend; a deploy is not zero-downtime", `runbook.md:238`). With several backends ("With several backends, roll the change to every one", runbook "Rotating the encryption key"), the backends still running serve traffic while the newest one migrates.
- **The operator** (`backend/cmd/paceday-operator/encryption.go:181`). Every `encryption` subcommand, `status` included, calls `storage.Migrate` after its schema checks and before taking the maintenance lock. `rotate-data-key` and `convert` are documented as run with `compose exec backend ...` against the running stack (runbook "Rotating a data key"). An operator binary newer than the schema therefore applies the pending migrations with backends live. Only `decrypt-all` and `reset-lost-key` require every backend to be stopped (runbook "Encryption key - stop the backend first").

### 2.3 What the live paths take on the covered tables

- **Booking save** (`SaveBookingOnLiveLink`, `backend/storage/scheduling_links.go:542`). The steps, in order: the link `FOR SHARE` (`:657-663`; ROW SHARE on `scheduling_links`); the host sets (`:670-674`, reads of `scheduling_link_hosts` and the link, ACCESS SHARE); the advisory keys `8201`–`8203` (`:680-682`); reads of `bookings` (`:709`, `:723`, `:734`, ACCESS SHARE); and the insert (`:758`, ROW EXCLUSIVE on `bookings`, plus the FK's KEY SHARE on the link). PAC-82 contract §3 and §4.4 bind this order.
- **Session guard** (`backend/storage/session.go:131`). This is `SELECT session_generation FROM users ... FOR KEY SHARE`, inside write transactions (ROW SHARE on `users`). `users` rows are also locked `FOR UPDATE` or `FOR NO KEY UPDATE` by sign-in, org and operator paths (`session.go:97`, `orgs.go:55`, `org_ai.go:567`, `operator.go:89`, `operator.go:286`).
- **Erasure** (`backend/storage/booker_erasure.go:116`). The link `FOR UPDATE`, then `bookings`, then the owner's `users` row (KEY SHARE).
- None of these paths takes SHARE or anything stronger on a covered table. Live paths take only ACCESS SHARE, ROW SHARE and ROW EXCLUSIVE.

### 2.5 A gap the issue does not name

The rule as decided (Q1) is about the order of locks on one table. A migration that takes a strong lock on one covered table and later a strong lock on a *second* covered table can also form a cycle with the save. An example: SHARE on `bookings`, then ACCESS EXCLUSIVE on `scheduling_links`. The save holds the link `FOR SHARE` and waits to insert into `bookings`. That is a lock-order problem across tables, not an upgrade. 037 takes `scheduling_links` before `bookings`, which is the save's own order, so it is safe. Nothing checks this. See OQ-1.

## 3. Desired behaviour

Take a migration file that touches one of the covered tables (`bookings`, `scheduling_links`, `scheduling_link_hosts`, `users` [O]), where that table existed before the file runs. Within the file, the first statement that locks the table takes the strongest lock the file ever takes on it. "Strongest" is measured against what live paths take (§2.3): ACCESS EXCLUSIVE outranks EXCLUSIVE, which outranks SHARE and SHARE ROW EXCLUSIVE, which outrank everything else (D-2). A migration author meets the rule in one of two ways:

- put the statements that take ACCESS EXCLUSIVE on the table first (as 037 and 038 do); or
- start the file with an explicit `LOCK TABLE <table> IN ACCESS EXCLUSIVE MODE`, which always satisfies the rule for that table, whatever follows.

A migration that keeps the rule cannot form a lock-upgrade cycle with a booking save, a session guard or erasure on that table. When it asks for its first lock on the table it holds nothing there. Once that lock is granted, it never asks for a stronger one there.

The build enforces the rule [O Q2]. A test reads every up migration file and fails when a file breaks the rule. The failure message names the file, the table, the statement that took the first lock (with its mode), and every later statement that asked for more (with its mode), and it says how to fix it. The test is a parser, not a database run. It must not be fooled by comments, letter case, quoting, schema qualification, or table names inside string literals. A statement it cannot classify fails the test instead of being guessed at (D-5). The only exception is a file that has already taken ACCESS EXCLUSIVE on that table, because nothing later can then make the order worse.

There is deliberately **no exemption mechanism** (D-4). Every failure has a fix in plain SQL: a leading `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE`.

PAC-82's contract, §4.4 (lock order and deadlock table), gains this rule and a row for "save / DDL on a live-read table". This is done as a dated amendment note, and the approved text is kept.

Operator behaviour, the server's start sequence and the runbook do not change [O Q3].

## 4. Acceptance criteria

All of these are `[unit]`: a Go test with no database (Q2). Unless an AC says otherwise, "a file" means a synthetic up migration fed to the checker in the test, next to the real files. Each AC fails today because no such check exists.

**The rule**

AC-1. Given a file that runs `CREATE INDEX` on `bookings` and then `ALTER TABLE bookings ADD COLUMN`, when the check runs, then it fails. The message names the file, `bookings`, statement 1 (SHARE) and statement 2 (ACCESS EXCLUSIVE). [unit]

AC-2. Given the same two statements in the other order (ALTER first, as 038 does), the check passes. [unit]

AC-3. Given the AC-1 file starting with `LOCK TABLE bookings IN ACCESS EXCLUSIVE MODE;`, the check passes. The same holds for `lock bookings;` (no `TABLE` keyword, and no mode, which means ACCESS EXCLUSIVE). It also holds for a single `LOCK TABLE scheduling_links, bookings IN ACCESS EXCLUSIVE MODE` covering two tables. [unit]

AC-4. Given a file whose leading `LOCK TABLE bookings IN SHARE MODE` is followed by an `ALTER TABLE bookings ADD COLUMN`, the check fails. A leading lock only helps when it is at least as strong as everything after it. [unit]

AC-5. For each covered table, AC-1 passes with `bookings` replaced by that table. Given the AC-1 order on a table that is not covered (for example `settings`), the check passes. [unit]

AC-6. Given a file that creates a table named `bookings` and then indexes and alters it in any order (the checker run on that file alone, with no earlier files), the check passes. A table created in the same file is not visible to any other transaction, so it is not live. [unit]

AC-7. Given `UPDATE users SET ...` followed by `CREATE INDEX ... ON users`, the check fails (ROW EXCLUSIVE then SHARE). Given `SELECT ... FROM users` followed by `UPDATE users`, the check passes (both are at the level live paths take). [unit]

**Statements that lock a second table**

AC-8. Given `CREATE TABLE t (u UUID REFERENCES users(id))` followed by `ALTER TABLE users ADD COLUMN x INT`, the check fails on `users`. The FK's SHARE ROW EXCLUSIVE on the referenced table counts as a lock on `users`. The same applies to `ALTER TABLE t ADD COLUMN u UUID REFERENCES users(id)` and to a table-level `FOREIGN KEY (...) REFERENCES users`. [unit]

AC-9. Given `INSERT INTO t ...`, where an earlier file gave `t` an FK to `users`, followed by `CREATE TABLE z (u UUID REFERENCES users)`, the check fails on `users`. The insert's implied FK check takes ROW SHARE on `users`, and SHARE ROW EXCLUSIVE comes after it. [unit]

AC-10. Given `ALTER TABLE t DROP CONSTRAINT t_user_id_fkey`, `ALTER TABLE t DROP COLUMN user_id`, or `DROP TABLE t`, where `t` has an FK to `users`, and given an earlier statement in the file that takes a weaker lock on `users`, the check fails. Dropping an FK takes ACCESS EXCLUSIVE on the referenced table. [unit]

AC-11. Given `DROP INDEX idx_bookings_link` after a weaker lock on `bookings`, the check fails. The index is resolved to its table from the earlier files. Given `DROP INDEX some_unknown_index` (created by no file), the check fails, saying the index could not be resolved. [unit]

**Robust parsing**

AC-12. Each of these variants of the AC-1 file gives the same verdict, the same statement numbers and the same modes (the quoted statement text may differ in case and quoting): upper, lower and mixed case keywords; `"bookings"` and `public.bookings` and `"public"."bookings"`; `--` and nested `/* */` comments between and inside statements; a statement split over many lines; and a trailing statement with no `;`. [unit]

AC-13. Given a string literal or a dollar-quoted string containing `ALTER TABLE bookings ADD COLUMN x` or `users`, in an `INSERT` or a `COMMENT`, it is not read as a statement or as a table reference. The same goes for a comment containing `;`, which does not split a statement. [unit]

AC-14. Given a `DO $$ ... $$` block (or `CALL`) whose body names a covered table, the check fails as "cannot classify" unless the file's first lock on that table was ACCESS EXCLUSIVE. Given a `DO` block that names no covered table (as in 023), it is ignored. A `CREATE FUNCTION` body is never executed by the migration and is not read as a lock. [unit]

AC-15. Given any statement the classifier does not know that names a covered table outside literals (for example `GRANT SELECT ON users TO x`, `CREATE POLICY ... ON bookings`), the check fails as "cannot classify", with the same ACCESS EXCLUSIVE exception as AC-14. [unit]

AC-16. Given a top-level `BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT` or `RELEASE`, or any `CONCURRENTLY` form (index build, index drop, reindex, detach), in any up file, the check fails. Such a statement breaks the one-transaction-per-file premise of §2.1, or cannot run inside a transaction at all. A PL/pgSQL `BEGIN` inside a `DO` body does not count. [unit]

**The real files**

AC-17. Given the repository's up migration files (001–039 today, and every later one), when the check runs on all of them in version order, then it passes. It covers every `*.up.sql` file, and it fails if it found none (an empty glob must not pass). [unit]

AC-18. A failure message contains, on separate lines: the file name, the table, the first locking statement's number in the file, its mode and its first 80 characters, and the same three fields for each statement that broke the rule. It ends with one fix line naming both remedies of §3. [unit]

AC-19. Given each row of the contract's classification table (§4 of the contract), a one-statement case asserts the mode the classifier gives each table. These table-driven cases are the classifier's specification: a row without a case fails review. [unit]

**Contract**

AC-20. PAC-82's contract §4.4 carries a dated "Amended by PAC-116" block. The block adds the row "save / DDL on a live-read table" and the binding migrations rule, and keeps the approved table and text unchanged. The PAC-82 manifest records the amendment in an `amendments` entry and keeps `contractRevision` 1.1 (amendment notes do not bump, as PAC-14's). [contract]

## 5. Explicitly out of scope

- **A PostgreSQL reproduction of the deadlock** [O Q2]. The test parses; it never runs a migration against a database to provoke `40P01`.
- **Down migrations.** Q2 names the up files. Downs run only by hand or through `paceday-operator encryption downgrade-schema`, with backends stopped (runbook "Rollback", "Encryption key - stop the backend first").
- **Lock order across two covered tables** (§2.5). Not enforced; OQ-1.
- **Row-lock ordering** between a migration's data changes and live writers on the same rows. This is a different class (row locks, not table-lock upgrades). The rule bounds only table-lock levels.
- **`lock_timeout` in migrations**, a retrying migrator, or `CONCURRENTLY` index builds outside a transaction. Each changes how migrations run, and Q3 keeps that unchanged. They are recorded as alternatives in the contract's rationale.
- **Tables outside Q1** (for example `settings`, `sso_events`). Q1 lists the tables that live booking or session paths read. Others may be added by a later decision, and the list is one constant.
- **Changing the operator** [O Q3]. PAC-84 is untouched. The operator keeps calling `storage.Migrate` for every subcommand.

## 6. What must not change

- Every migration file 001–039 is byte-for-byte unchanged (D-7). `TestEveryMigrationHasADownFile` and the up/down round trip (`backend/storage/migrations_down_test.go`) keep passing.
- How migrations run (§2.1): one implicit transaction per file, the session advisory lock, and the dirty and clean version writes. Nothing in the runtime path changes, because the check is test-only code.
- PAC-82's approved §4.4 text and table, and every other section of the PAC-82 contract. PAC-82's AC-24 (no `40P01` among concurrent saves) keeps passing.
- The OpenAPI bundle and the generated code (no HTTP change).

## 7. Rollback

Revert the PR. The check disappears and nothing at runtime changes. There is no migration and no stored data. The PAC-82 amendment note reverts with it. A later migration merged while the check existed stays compliant, and that does no harm.

## 8. Open questions

- **OQ-1 (owner, non-blocking; default: not in PAC-116):** should a second rule fix the order in which a migration locks two or more covered tables, to match the live paths' order? That order is `scheduling_links` → `scheduling_link_hosts` → `bookings`, the save's order (§2.5). `users` has no single safe position. Erasure locks it after `bookings`. Account deletion locks it before the link tables, through cascades. The default is to record the gap in the PAC-82 §4.4 amendment as advice ("take covered tables in that order, and do not combine `users` with another covered table at SHARE or stronger outside a maintenance window") and to file a follow-up ticket if the owner wants it enforced. Resolve: owner reply on PAC-116.
- **OQ-2 (stage 3, plan-author; non-blocking):** is the classifier a small hand-written lexer (the factory default) or a vendored SQL parser? This is resolved in the plan, and the contract's classification table binds either way. A full PostgreSQL grammar (for example a cgo binding of the server's parser) would be heavier than the rule needs, and on Windows it would break the cgo-free backend build.

## 9. Decisions

| ID | Decision | Mark |
|---|---|---|
| D-1 | Covered tables: `bookings`, `scheduling_links`, `scheduling_link_hosts`, `users` | [O Q1] |
| D-2 | "Strength" is the level at which a lock blocks what live paths take (§2.3). 0 = blocks none of ACCESS SHARE, ROW SHARE, ROW EXCLUSIVE (ACCESS SHARE, ROW SHARE, ROW EXCLUSIVE, SHARE UPDATE EXCLUSIVE). 1 = blocks ROW EXCLUSIVE only (SHARE, SHARE ROW EXCLUSIVE). 2 = blocks ROW SHARE and ROW EXCLUSIVE (EXCLUSIVE). 3 = blocks all three (ACCESS EXCLUSIVE). The rule: no statement after the first lock on a table takes a higher level than that first lock. Levels come from PostgreSQL's table-level conflict table. Two lower modes that differ in conflicts with each other but not with any live mode (for example ROW EXCLUSIVE then SHARE UPDATE EXCLUSIVE) cannot form a cycle with a live path, so the rule does not order them. | [F] |
| D-3 | Per file, not per run: each file is one transaction (§2.1); locks do not carry over between files | [F], verified |
| D-4 | **No exemption mechanism.** A leading `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` makes any file pass for that table, so an exemption would only ever buy a weaker lock, at the cost of the guarantee | [F] |
| D-5 | Fail closed: a statement the classifier cannot classify (unknown kind, `DO`/`CALL` body, unresolvable index) fails when it names a covered table, unless ACCESS EXCLUSIVE is already held on that table | [F] |
| D-6 | Implied locks count: FK references (SHARE ROW EXCLUSIVE on the referenced table), FK checks of inserts and updates (ROW SHARE on the referenced table), FK drops (ACCESS EXCLUSIVE on the referenced table). The checker learns FKs and index names by replaying the earlier files in version order, with no database | [F] |
| D-7 | No existing migration violates the rule (§2.4); none is edited. Editing an applied migration would change fresh installs without changing any deployed database | [F] |
| D-8 | Transaction control and `CONCURRENTLY` are refused in up files, so the one-transaction premise the rule rests on cannot silently break | [F] |
| D-9 | Contract shape: an amendment note on PAC-82 §4.4 (PAC-81/PAC-86 style) plus a PAC-116 manifest. No OpenAPI change; contractHash unchanged | [F] |
| D-10 | Operator, server start and runbook unchanged | [O Q3] |
