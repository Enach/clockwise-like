# Spec — PAC-116: apply pending migrations only while the app is not serving (lock-upgrade deadlock against an in-flight booking save)

- **Linear**: https://linear.app/paceday/issue/PAC-116 (split from PAC-110 item 1)
- **Status**: revision 3, draft (awaiting spec-challenger). Revision 3 resolves the revision-2 challenge (S1–S4, kept below) and applies the factory decision that `encryption status` stays a read-only probe. Revision 1 (a SQL-reading lock-order checker) is **superseded**: it is summarised at the end of this file, and its challenge is kept verbatim as history.
- **Author**: spec-author (factory)
- **Verified against**: clockwise-like `origin/main` `c2609a6` (migrations 001–039; 033 was never used)
- **Inherited scope**: none. No HTTP operation changes, so no `x-uncertain` marker or `docs/factory/api-audit.md` finding is touched.
- **Owner decisions** (`.claude/factory/owner-decisions.md`, "PAC-116"):
  - Q1 (2026-11-14): the live-read tables are `bookings`, `scheduling_links`, `scheduling_link_hosts` and `users`. It is kept as the statement of what is at risk; the new rule protects every table.
  - Q2 and Q3 of 2026-11-14 are **reversed** by the revision of 2026-11-14 after the challenge on #281. Pending migrations are applied only when the app is not serving, and the operator tool refuses otherwise. The PAC-84 contract is amended. The SQL-reading checker is dropped.

Decision marks below: **[O]** = owner decision; **[F]** = factory decision, recorded here and open to challenge; **[OQ]** = needs the owner (§8).

## 1. Problem

A migration can deadlock against a public booking that is being saved at the same moment. PostgreSQL then aborts one of the two transactions with SQLSTATE `40P01`. If the booking loses, the booker gets a 500 and their booking is not saved. If the migration loses, the server or the operator command fails half-way, and the database is left marked dirty at that version (runbook "Rollback").

The issue's example is a lock upgrade. A migration takes a lock that lets readers in (`CREATE INDEX`, SHARE) and later asks for ACCESS EXCLUSIVE (`ALTER TABLE`), while a save that already read `bookings` waits to insert. The challenge on revision 1 showed that the problem is wider:

- row locks held by live sign-in paths make a SHARE-first migration deadlock too, and the real migration 022 has that shape;
- foreign-key actions lock tables a migration never names;
- functions, views and triggers hide what a statement locks.

A sound "safe migration" rule would need a model of every lock PostgreSQL takes for every statement. Revision 1 showed that such a model is not achievable as a parser.

Every one of those cycles needs a live transaction on the other side. The owner's decision removes that side: **pending migrations are applied only while no app process is serving.**

Who pays today: a booker whose save is aborted (500, booking lost), or an operator whose deploy or `paceday-operator` command fails half-way and must be rolled back from a backup.

## 2. Current behaviour

### 2.1 How a migration run works

- `storage.Open` / `storage.OpenAs` (`backend/storage/db.go:24-41`) open the pool and call `runMigrations` (`db.go:44-84`). So does `storage.Migrate` (`db.go:128-133`). `runMigrations` uses golang-migrate v4.19.1 (`backend/go.mod:11`) with the `postgres` driver on one dedicated `*sql.Conn` (`db.go:50-54`) and `MultiStatementEnabled` false.
- Each `.up.sql` file goes to the database as one `ExecContext` with no arguments (golang-migrate `database/postgres/postgres.go:265-296`). Under pgx v5.10.0 (`go.mod:13`, pgx `conn.go:515-518`) that uses the simple query protocol, so **each file is one implicit transaction**. The version row is written in separate transactions: dirty before the file runs, clean after it (golang-migrate `migrate.go:738-750`).
- Before `Up`, golang-migrate takes a session `pg_advisory_lock` with its own generated key (`postgres.go:241`) and holds it for the whole `Up`. A second migrator therefore waits until the first finishes, and then finds nothing to apply. A binary older than the schema gets an error from `Up`, because the database version is not among its files.
- Nothing in this path looks at whether the app is serving.

### 2.2 The three paths that apply migrations

1. **The backend at start.** `backend/main.go:192` calls `storage.Open(dsn)` before the key load (`:205`, `startEncryption`), before the crons, and before the listener. Migrations therefore run before the process writes its heartbeat or listens.
   - With **one backend**, a deploy (`compose up -d backend`, runbook "Deploy order" step 4, `docs/runbook.md:78-80`) recreates the container. Compose stops the old container (graceful drain, up to about 43 s, runbook "Expected interruption during a deploy") and then starts the new one, so the new one migrates with no other backend serving.
   - With **several backends**, the runbook only says to roll a key change "to every one" ("Rotating the encryption key"). Nothing stops a new backend from migrating while the others still serve.
2. **`paceday-operator encryption <sub>`** (`backend/cmd/paceday-operator/encryption.go:181`). Every subcommand, `status` included, calls `storage.Migrate` before taking the maintenance lock (`:186`).
   - It refuses to migrate a database **below** migration 034 (`:148-165`, PAC-84 review #3).
   - It is documented as run with `compose exec backend …` against the running stack for `convert` and `rotate-data-key` (runbook "Rotating a data key").
   - Only `decrypt-all`, `reset-lost-key` and `downgrade-schema` check that no backend is live (`:198-209`, exit 6).
3. **PAC-71's subcommands** `free-address`, `reassign` and `advance-all` (`backend/cmd/paceday-operator/main.go:56`, `storage.OpenAs(dsn, app)`). They migrate unconditionally on open. The runbook runs `advance-all` with `compose exec backend …` against the running backend ("PAC-71 release").
   - `booker-erasure` does not migrate (`main.go:39-43`).

### 2.3 What already shows that the app is serving

- **Heartbeats (PAC-84).** Table `encryption_backend_heartbeats` (migration 034).
  - Every backend upserts its row at the start of the key load (`storage/encryption_keys.go:327-346`, `LoadKeyring`; `main.go:205`), every 30 s afterwards (`HeartbeatInterval`, `:41`; the refresher `:479-562`), and deletes it on graceful shutdown (`backend/encryption.go:167-174`).
  - `LiveHeartbeats` (`:90-120`) returns rows seen within 90 s (`HeartbeatLive`, `:42`).
  - The key load is mandatory: a missing key refuses the start (`main.go:182-185`). So **every backend since PAC-84 heartbeats before it listens**.
  - A backend killed without a graceful shutdown keeps counting as live for up to 90 s.
- **`application_name`** (PAC-84 contract §4.3). The backend's pool is `paceday-backend` (`encryption_keys.go:27`, `db.go:24`). The operator uses `paceday-operator encryption <sub>` (`:30`) or `paceday-operator <sub>` (`main.go:52-55`). Backends older than PAC-84 set none.
- **The maintenance lock** `(8400, 1)`. It is a session advisory lock on a dedicated connection (`TryMaintenanceLock`, `encryption_keys.go:170-187`), with the holder named from `pg_locks JOIN pg_stat_activity` (`MaintenanceHolder`, `:125-140`).
  - Write-then-check already exists between backend and operator. The backend writes its heartbeat *then* refuses to start if `decrypt-all` or `reset-lost-key` holds the lock (`:328-337`). Those commands take the lock *then* refuse if any heartbeat is live (`encryption.go:198-209`).
  - A running backend's refresher shuts the process down when it sees such a holder (`:487-492`).
- **Other sessions.** Nothing today counts the client sessions on the database.

### 2.4 Who is on the other side of the deadlock

These are the live transactions on the Q1 tables (unchanged from revision 1, as confirmed by the challenge):

- the booking save `SaveBookingOnLiveLink` (`storage/scheduling_links.go:542`, steps at `:657-663`, `:680-682`, `:709-758`);
- the session guard (`storage/session.go:131`, `FOR KEY SHARE` on `users`);
- sign-in (`storage/signin.go:222` → `session.go:97` `FOR UPDATE`, then `signin.go:263` `UPDATE users`);
- `SetUserOrg` (`storage/orgs.go:55`, then `:62`);
- erasure (`storage/booker_erasure.go:116`);
- the operator's own `advance-all` (`storage/operator.go:286`, then `:289`).

Each of them belongs to a backend or to an operator process, and each is a client session on the database.

## 3. Desired behaviour

A process that is about to apply pending migrations does so only after it has established that no other process is serving the app. It holds a lock that keeps any app process from starting to serve until it has finished.

1. **One procedure, three callers.** The backend at start, the mutating `paceday-operator encryption` subcommands, and PAC-71's subcommands apply pending migrations only through the same procedure. A process with nothing pending takes no lock and runs no serving check, so existing `exec` usage against a running stack keeps working once the backend has migrated. Before it acts on the database, it still checks that no migrator holds the lock (item 3).
   - **`encryption status` is a read-only probe** (D-10). It never migrates and never refuses because the app is serving. With migrations pending, it reports them and the serving state, then its usual report, and exits as today.
   - **The schema's state is read first and honestly** (D-11, D-12):
     - a version the binary has no file for (above its highest, or in a gap) stops every path with today's error ("no migration found for version N"), before any check;
     - a dirty version stops every path with today's dirty error, unless a migrator holds the lock: then it is a migration in progress, and the answer is "lock held, being applied by `<holder>`".
2. **"Serving" is decided fail-closed** (D-1). The app is serving when **either**
   - a backend heartbeat was seen in the last 90 s, **or**
   - any other client session is connected to the same database.

   Each signal covers the other's blind spot:
   - Heartbeats see a backend whose pool has no open connection at that instant.
   - Sessions see a backend that has opened its pool but not yet written a heartbeat, a backend older than PAC-84 that never heartbeats, a running operator command, and any stray client. The check refuses on them all instead of guessing which are harmless.
   - Sessions of **other roles** count even when PostgreSQL hides their details from the migrating role (D-9, challenge S1).
   - The only sessions not counted are other migrators' (named `paceday-migrate: …`). Such a session belongs to a process that has not served yet, and that checks the lock before it does (D-13, challenge S4). So two migrators started together never refuse each other as "serving": exactly one applies.
3. **The procedure** (D-2), in this order:
   - take the existing maintenance lock under a name that says "migrating";
   - read the schema version again (another process may have just finished);
   - check serving;
   - apply;
   - release.

   On the other side, a backend that starts writes its heartbeat first, then refuses to start when a migrator holds the lock, as it already does for `decrypt-all` and `reset-lost-key`. A running backend that sees a migrator shuts down, as it already does for those two. An operator subcommand that found nothing to apply opens its working connection first, then refuses when a migrator holds the lock (D-14). Write-then-check on both sides means one of two racing processes always sees the other.
4. **Refusal** says what was seen, so the operator can act:
   - each live heartbeat, with instance, host and seconds since it was seen;
   - each other session, with pid, `application_name`, user, client address, start time and state, as far as PostgreSQL shows them;
   - or the lock holder.

   It also says what to do: stop every backend (a graceful stop removes its heartbeat; a killed one stops counting 90 s after its last heartbeat), close or terminate the listed sessions, then run again. **Nothing is applied and the version is not marked dirty.**
5. **No override** (D-4). No flag, environment variable or confirmation prompt applies migrations while the app is serving.
6. **The backend at start** follows the same rule (D-3).
   - A single-backend deploy keeps working unchanged: compose stops the old container before starting the new one.
   - With several backends, a new backend refuses to start while an older one still serves. The deploy procedure becomes stop every backend, start one (it migrates), then start the rest. The refused backend exits non-zero and Docker's `restart: unless-stopped` (`docker-compose.prod.yml:52`) retries it, so it comes up by itself once the others are stopped.
7. **Documents**:
   - PAC-84's contract (§4.3, §5.3, §8.1, §8.2) gets dated amendment notes;
   - PAC-82's §4.4 PAC-116 note is rewritten: the "save / DDL on a live-read table" row is prevented operationally by this rule;
   - the runbook gains the stop-migrate-start procedure.

## 4. Acceptance criteria

All criteria marked `[integration]` run against a real PostgreSQL 16 (the backend suite's test database, `backend/internal/testdb`, testcontainers in CI). "Pending" means the database's version is below the binary's highest migration. The usual setup is a database migrated to the highest version minus one, or the 034 heartbeat table created by migrating up to 034 first. "Simulated app session" means a second `*sql.DB` opened by the test with `application_name = paceday-backend` holding at least one idle connection. "Simulated heartbeat" means a row in `encryption_backend_heartbeats` with `seen_at = now()` and a random instance id.

**Operator refuses while serving**

AC-1. Given pending migrations and a simulated heartbeat seen 5 s ago (no other session), when `paceday-operator encryption convert` runs, then it exits 6 and stderr names the instance, host and age, and says to stop every backend first. The schema version is unchanged and not dirty, and no audit row is written. The same holds for `rotate-data-key` (exit 6) and for `advance-all` (exit 1, same message). (`status` never refuses: AC-22.) [integration]

AC-2. Given pending migrations, no heartbeat, and one simulated app session, the operator refuses as in AC-1. The message lists that session's pid and `application_name`. Repeat with the session's `application_name` empty (a pre-PAC-84 backend) and with `psql`: both refuse. [integration]

AC-3. Given pending migrations, a heartbeat last seen 91 s ago, and no other session, the operator applies the migrations (version = highest, not dirty) and then runs its subcommand as today. [integration]

AC-4. Given pending migrations, no heartbeat and no other session, the operator applies them. Given **no** pending migrations, a live heartbeat and a simulated app session, `convert`, `rotate-data-key`, `status` and `advance-all` run exactly as today, with no refusal and no serving check (the existing PAC-84 and PAC-71 tests keep passing). [integration]

AC-5. Given a database that has no heartbeat table yet (below 034), PAC-71's `advance-all`, no other session and pending migrations, it applies them. With one other session it refuses. (`encryption` subcommands keep refusing below 034 with today's message; that rule is unchanged.) [integration]

**Backend at start**

AC-6. Given pending migrations and a simulated live heartbeat or app session, when the backend starts, then it exits non-zero before listening, with the AC-1 / AC-2 message. The version is unchanged and not dirty. [integration]

AC-7. Given pending migrations and nothing else connected, the backend migrates and becomes ready (`/api/ready` 200), as today. Given nothing pending and other backends live, it starts as today, with no refusal. In both cases, once it is ready, `pg_stat_activity` holds no session whose `application_name` starts with `paceday-migrate:` from the backend: the migrator handle is closed before it serves (contract §3 step 2; the name is excluded from "other sessions" only on that premise, §4.4). [integration]

**Races**

AC-8 (app starts during a migration). The migrator is held after its serving check, before it applies (test seam). A backend then starts with **nothing pending for its own version**. It writes its heartbeat, sees the migrating holder, deletes its heartbeat and exits non-zero with the message: migrations are being applied by `<holder>` (pid), start after it ends. Once the migrator releases, the same backend starts normally. [integration]

AC-9 (migration starts while an app is starting). A backend is held after writing its heartbeat, before its lock check (test seam). An operator with pending migrations then takes the lock, sees the heartbeat, and refuses (AC-1). Nothing is applied, and the backend then starts normally. [integration]

AC-10 (two migrators). An operator and a starting backend with the same pending migrations start together (released at a barrier), with nothing else connected. **Exactly one applies them.** The other either refuses because the maintenance lock is held (operator exit 5, backend non-zero, holder named), or finds nothing pending and continues as AC-4/AC-7. Neither refuses as "serving". The version is applied once and is never dirty. [integration]

AC-11 (running backend sees a migrator). A running backend whose heartbeat went stale but which is still alive (simulated: its heartbeat row deleted) has its refresher tick while a migrator holds the lock. It begins its graceful shutdown with a log line naming the migrator, as it does today for `decrypt-all`. [integration]

AC-12. The migrator's own other connections do not count as "another session": an operator subcommand whose pool was opened before the procedure is not refused by itself. A second operator process's working connection does count (AC-2). A session named `paceday-migrate: …` does not (AC-21). [integration]

**No override**

AC-13. Given the AC-1 refusal, re-running with `--force`, `-force`, `--yes` or `--override` is a usage error (exit 2). For every flag each subcommand registers (enumerated from its flag set, not from a hand-written list), running under the AC-1 conditions with that flag set to a valid value still refuses with the AC-1 exit code and applies nothing. For the operator, every environment variable name the run reads (recorded through its injected `getenv`) set to "true" or "1" still refuses. For the backend, AC-6 is repeated with every `PACEDAY_*` / `MIGRATE*` name that appears in non-test backend Go source set to "true", and still refuses. [unit + integration]

**Unchanged edges**

AC-14. A dirty database **with no migrating holder** still stops every path with today's golang-migrate error ("Dirty database version N. Fix and force version."); the procedure neither clears nor sets dirty. (Dirty with a holder: AC-19.) `booker-erasure` still applies nothing. `downgrade-schema` keeps its own heartbeat check (exit 6) and is not routed through the procedure (it runs down steps, not pending ups). [integration]

**Revision-3 additions (challenge S1–S4, `status`)**

AC-18 (S1, roles). The database has a second role `monitor` (LOGIN, not superuser, not in `pg_read_all_stats`) with one idle session on the application database. The migrator connects as a third role that is also not a superuser and not in `pg_read_all_stats`, and owns the schema. With pending migrations, the migrator refuses as serving, and lists the hidden session as pid with "?" fields. Repeat with the migrator as a superuser: still refuses, with the fields shown. [integration]

AC-19 (S2, dirty during a migration). Migrator A is held **inside** a migration file through a seam, so `schema_migrations` shows that version dirty while A holds the lock. Then:
- a backend starts: it refuses non-zero with "being applied by `<A's application_name>` (pid)";
- `encryption convert` and `advance-all`: they exit 5 and 1 respectively, with the same text;
- `encryption status`: it reports the migration in progress and its holder, and exits 5.

None of their outputs contains "Dirty database version". Once A finishes, each runs as AC-4/AC-7. [integration]

AC-20 (S3, schema newer than the binary). The database is at the binary's highest version + 1 (a row in `schema_migrations` with no file in the binary), clean. The backend start, `encryption convert`, `advance-all` and `encryption status` each stop with today's error text ("no migration found for version N"). The backend exits non-zero before listening, the operator subcommands exit 1, and nothing is written. The same applies for a version in a gap between two of the binary's files. [integration]

AC-21 (S4, simultaneous migrators). Two backends, and separately two operator processes (`advance-all`), with the same pending migrations are released together at a barrier, 20 times on fresh databases. In every run exactly one applies them, the other gets "lock held" or "nothing pending", **no run refuses as "serving"**, and the version is never dirty. A session started by the test with `application_name = 'paceday-migrate: test'` and no lock does not make a migrator refuse. [integration]

AC-22 (`status` is a probe). With pending migrations and a live heartbeat plus an app session, `encryption status` applies nothing. It prints the pending range ("schema at version X; this release's migrations up to Y are pending, not applied") and the serving state (live heartbeats, other sessions). It then prints its usual report for what the current schema has, and exits as today: 0, 3 under `--check` with plain values, or 1 if a read fails. With nothing pending, its output is today's plus no pending line. [integration]

AC-23 (operator after "nothing to do"). Migrator A holds the lock (seam after its check). `advance-all`, with nothing pending for its own version, opens its working connection, sees the migrating holder, and exits 1 with "being applied by …". It locks no account. [integration]

**Documents**

AC-15. `contracts/features/PAC-84.md` carries dated "Amended by PAC-116" notes in §4.3 (the migrating holder and the two-signal check), §5.3 (start order step 3) and §8.1/§8.2 (operator migration rule, exit 6 widened). The approved text is kept. [contract]

AC-16. `contracts/features/PAC-82.md` §4.4's PAC-116 note says that the "save / DDL on a live-read table" pair is prevented operationally (no migration is applied while a save can run) and points to this rule. The revision-1 lock-order rule is marked superseded. [contract]

AC-17. `docs/runbook.md` has the "Applying migrations: stop, migrate, start" procedure, with "Deploy order" step 4 and the operator sections pointing to it. It covers:
- a single backend, several backends, and an operator binary newer than the schema;
- how to read and clear a refusal;
- a connection pooler: idle server connections block migrations until `server_idle_timeout`, and migrators connect directly or through session pooling, never through a transaction pooler;
- a lock holder on a dead host lingers until TCP keepalive: find it in `pg_stat_activity` and `pg_terminate_backend` it;
- the `pg_isready` health check can briefly cause a refused start, which Docker retries. [doc]

## 5. Explicitly out of scope

- **Zero-downtime migrations.** The runbook already says "a deploy is not zero-downtime". This rule makes a migrating deploy a full stop for every backend, even when the release has only one migration.
- **Making individual migrations safe against live traffic** (lock order, `CONCURRENTLY`, `lock_timeout`). Revision 1's checker is dropped [O]. A migration may take any lock it needs, because nothing live is there.
- **Down migrations.** `downgrade-schema` keeps PAC-84's own heartbeat check. Manual `migrate … down` is a runbook procedure with the backend stopped.
- **Processes that do not hold a database session or heartbeat** (for example nginx or the web app). They cannot be on the other side of a lock.
- **Backends older than PAC-116 started *during* an operator's migration.** They do not run the new lock check. They still go through golang-migrate's lock and fail on a schema newer than their files (§2.1). The only gap is a few milliseconds between the migrator's check and golang-migrate taking its own lock (OQ-2).
- **Stopping the app automatically.** The operator refuses; it never stops anything.

## 6. What must not change

- With nothing pending, no path takes the lock or checks serving (an operator subcommand only checks that no migrator holds the lock, AC-23). PAC-84's `convert`, `rotate-data-key` and `status`, and PAC-71's subcommands, keep running against a live stack, together with their tests (`backend/cmd/paceday-operator/encryption_test.go`, `main_test.go`, `downgrade_above_test.go`, `backend/main_pac84_test.go`).
- The single-backend deploy (runbook steps 1-6), the readiness contract (`/api/ready`) and the compose health check.
- PAC-84's existing refusals: below-034, `decrypt-all` / `reset-lost-key` / `downgrade-schema` heartbeat check, exit codes 2, 4 and 5, and the backend refusal for destructive holders.
- Migration files 001–039 (none is edited) and how a file runs (one implicit transaction).
- The OpenAPI bundle and generated code. There is no HTTP change.

## 7. Rollback

Revert the stage-4 PR. Every path migrates as today, with no check and no lock. There is no migration and no stored data, and the heartbeat table is unchanged. The amendment notes and the runbook procedure revert with the contract and docs PRs. The stop-migrate-start procedure stays good practice either way.

## 8. Open questions

- **OQ-1 (owner, non-blocking; default D-4: none):** is an emergency override wanted after all, for example `--apply-while-serving <database name>`, which writes an audit row and logs a warning? The factory found no case it would serve. Every refusal clears by stopping a process, terminating a session, or waiting 90 s, and the override's only effect would be to recreate the deadlock risk.
- **OQ-2 (owner, non-blocking; default: accept and document):** a backend **older than PAC-116** started within milliseconds of an operator's migration could pass golang-migrate's lock before the migrator takes it, and serve during the migration (§5). The runbook already says to stop every backend and start the new release only. Closing it fully would need the check to run while golang-migrate's lock is held, which its API does not expose.
- **OQ-3 (stage 3, plan-author):** existing tests that call `storage.Open` / `storage.Migrate` with pending migrations while the test holds another pool on the same database may now be refused. The plan greps them (callers include `api/testhelpers_test.go`, `main_pac84_test.go`, `cmd/paceday-operator/*_test.go`) and decides between restructuring each one and a test-only seam that cannot be reached from a flag or environment variable.
- **OQ-2 also covers** an operator binary **equal to** the current schema (for example the running release's `advance-all`) started just before a newer migrator's first file. It finds nothing pending, and by AC-23 it refuses only if its working connection opens after the migrator took the lock. Otherwise its session is listed and the migrator refuses. The residual is the same few milliseconds.
- **OQ-4 (owner, non-blocking; default: refuse):** a monitoring agent permanently connected to the application database would block every migration until it is stopped for the deploy. Default: refuse, and the runbook says to stop it. An allow-list of named clients would be an exemption, and is not added without an owner decision.

## 9. Decisions

| ID | Decision | Mark |
|---|---|---|
| D-0 | Revision 1 (a parser-enforced lock-order rule) is superseded by "stop traffic". Pending migrations are applied only when the app is not serving; the operator refuses otherwise; the PAC-84 contract is amended (Q3 reversed); the checker is dropped (Q2 reversed) | [O] 2026-11-14 |
| D-1 | **Serving = a live heartbeat (90 s) OR any other client session on the database.** Heartbeats are the existing lease (every backend since PAC-84, before it listens, every 30 s, deleted on graceful stop), but they cannot see a backend between opening its pool and its first heartbeat, nor pre-PAC-84 backends. Sessions see those and every operator or stray client, but miss a backend whose pool happens to have no connection open. Either signal alone has a hole, and both together fail closed. A new dedicated advisory lock held by the backend while serving was rejected: it would need a connection pinned for the process's whole life, which the pool caps (PAC-81 AC-A10) do not budget for, and it would vanish silently if that connection dropped | [F] |
| D-2 | **Gate = the existing maintenance lock `(8400,1)`, held on the migrator's dedicated connection whose `application_name` marks it as migrating.** Write-then-check on both sides (PAC-84 §4.3's existing pattern). Reusing the lock also serialises a migration against `convert`, `rotate-data-key` and the automatic conversion, which must not run against a schema that is changing. A new lock id would need its own holder lookup and still need that serialisation | [F] |
| D-3 | **The backend's start is a migrator like any other.** It runs the same procedure when (and only when) something is pending. A single-backend deploy already has no other instance up, because compose stops the old container first, so it passes unchanged. With several backends, the rule turns "start a new one while others serve" from a silent risk into a refusal that clears once they are stopped | [F] |
| D-4 | **No override.** Each refusal is cleared by an operator action (stop the backends; terminate the listed sessions; wait at most 90 s for a killed backend's heartbeat), and the message says which. An override could only be used to migrate while serving, which is the defect. Owner may revisit (OQ-1) | [F] |

## Challenge — 2026-11-14 (revision 2)

**Verdict**: accept-with-changes (REVISE). The "stop traffic" design is sound: write-then-check on both sides closes the race for every backend from PAC-116 on, and both heartbeat ages use the database's `now()`. Three blocking defects remain, all in the edges of §2 and §3, and S1 was fixed directly. Small fixes are in `3b92890`.

### Blocking

**S2. Step 1 reads the version without any lock, so it sees the *transient* dirty row of a migration in progress.** golang-migrate marks the target version dirty *before* the file runs and clean after it (`migrate.go:738-750`). Today every path calls `Up()`, which takes golang-migrate's lock **before** reading the version (`migrate.go:265-277`). It therefore waits out a running migration and never sees that row. The new step 1 and §2 ("a dirty row is not pending: golang-migrate's error stops the path as today") change this.

Example. While migrator A applies 040, a second backend or `paceday-operator encryption status` runs step 1. It reads `040, dirty` and stops with "Dirty database version 40. Fix and force version." That is not "as today". It is also dangerous: runbook "Rollback" tells the operator to fix and `force` a dirty version, while A is still applying it.

**Resolve:** in §2/§3, a dirty row seen while the maintenance lock has a migrating holder (or golang-migrate's lock is held) is "lock held", with the §5 text naming the holder. Only a dirty row with no holder is today's dirty error. Add an AC: hold a migrator inside a file through a seam, then start a backend and run `status`; both say "being applied by …", and neither says "dirty".

**S3. "Nothing pending, so callers behave exactly as today" drops today's refusal of a schema *newer* than the binary.** §2 defines pending as "version below the highest embedded version". A database at 041 with a binary whose highest is 040 is therefore "nothing to do", and §4.1 then opens the pool "without migrating".

Today, `Up()` fails with "no migration found for version 41" (`readUp` → `versionExists`, `migrate.go:536-537`), so an older binary refuses to start on a newer schema. The spec's §2.1 even relies on this for old backends. After PAC-116, a PAC-116+ binary rolled back without its down migrations would serve against the newer schema silently.

**Resolve:** §2 and §3 step 1 must state that a version absent from the binary's files (above its highest, or a gap) stops every path with today's error, before any check. Add an AC: a schema one version above the binary's highest, then backend start and operator both refuse as today.

**S4. AC-10 ("exactly one applies them") is not guaranteed, and simultaneous starts can all refuse.** The lock winner's step 5 counts the loser's connections as "other sessions": its step-1 read or its step-2 handle trying the lock. So with two backends started together (or `--scale backend=2`, or two operators), the winner may refuse as **serving** while the loser refuses as **lock held**. Nothing is applied and both exit.

Docker's restart backoff is the same for both containers, so they can collide again. This is rare, because the windows are milliseconds, but it is not excluded, and AC-10 as written would be a flaky test.

**Resolve:** choose one.
- (a) A session whose `application_name` starts with `paceday-migrate:` is not an "other session". This holds because every such session belongs to a process that has not served and will check the lock before serving. It requires the step-1 read to use the migrator name too, and to be closed before the process does anything else.
- (b) AC-10's outcome set allows "no one applied; not dirty; a rerun applies once", and the runbook says a refused simultaneous start retries by itself.

(a) also makes AC-12 simpler.

**S1 (fixed in `3b92890`, needs an AC).** In PostgreSQL 16, `pg_stat_activity.backend_type` is NULL for a session of another role unless the reader is a member of that role or of `pg_read_all_stats`. Only datid, pid, usesysid, application_name and the xids are shown to all callers (`pgstatfuncs.c` `pg_stat_get_activity`, REL_16_STABLE, lines 335-365 and 620-650). The filter `backend_type = 'client backend'` therefore failed **open** for exactly the sessions it claimed to count: `psql` as another role, or a monitoring role, under a non-superuser migrating role.

§2 now counts a NULL `backend_type`, and it asks for a migrating role that sees every session, so that autovacuum workers (visible as usesysid 10 with a NULL type) are not counted. The shipped compose role is the image superuser, so default deploys were not exposed. **Add an AC:** a session of a second, non-superuser role, with the migrator connected as a non-superuser without `pg_read_all_stats`, must still refuse.

### Non-blocking

1. **pgbouncer or another pooler between the app and PostgreSQL.**
   - Its idle server connections stay up (`server_idle_timeout`, 600 s by default) after every backend stops. They show as other sessions, so a migration is refused until the pooler is stopped or `RECONNECT`ed. That fails closed, but the runbook should say so.
   - A migrator *through* a transaction-mode pooler breaks session advisory locks (both `(8400,1)` and golang-migrate's) and `pg_backend_pid()`. §3 should require the migrator to connect directly, or through session pooling. No pooler ships today.
2. **A leaked lock after a crash.** Session advisory locks are released when the session ends (confirmed in the PostgreSQL docs), so a crashed operator on the same host releases at once.
   - A host or network death leaves the server-side session alive until TCP keepalive notices it: about 2 h at Linux defaults, unless `tcp_keepalives_idle` is set. Meanwhile backends refuse to start ("being applied by …"), and a migration file's open transaction keeps its locks.
   - The runbook's "lock held" bullet should say how to find the holder (pid in the message) and `pg_terminate_backend` it once it is certain the process is gone.
3. **`pg_isready` health check.** `pg_isready -U clockwise -d clockwise` (`docker-compose.prod.yml:41`) makes a full connection to the app database. A start that falls inside one is refused as serving and retried by Docker. That is harmless, but it is a source of flakes for the AC tests if any of them use a health-checked container.
4. **`status` exits 6 with pending migrations.** It is a read-only probe today (exit 0/1 with `--check`). Consider reporting "N migrations pending, not applied" with exit 1 under `--check` instead of refusing. That is an owner/author choice; today's text is consistent but changes `status`'s meaning.
5. **OQ-2 residual (old backend in the step 5 → `Up` window).** Acceptable as documented. Two conditions make the window apply: the old backend's pool is not connected at step 5 (it would otherwise be seen), and it must run golang-migrate's `Up` in the milliseconds before the migrator's `Up`. Older backends that are already serving heartbeat and are refused.
6. **OQ-3: CI stacks.** `go test -p 1`, and `internal/testdb` gives every test its own database (the admin connection is on another database, so it does not count), so parallel packages are not refused. e2e: the stack backend migrates a fresh database at `compose up`, and `startup.spec.ts`'s extra backends find nothing pending, so no check runs. The remaining risk is a test that holds a second pool on its own database while calling `Open` with pending migrations, which is what OQ-3 already scopes.
7. **AC-13** was rewritten so it is testable (flags enumerated from each flag set; environment names recorded through the operator's injected `getenv`).
8. **§6 seam.** "An unexported variable set from `_test.go`" is unreachable from the `main` and `cmd/paceday-operator` tests. It is now the existing `storage/test_seams.go` pattern (exported `Install…(tb TB, …)`).
9. **Runbook.** A duplicated "as the backend." sentence was fixed. Refusals that do not exist yet are now marked "from PAC-116's implementation on" (several backends, `advance-all`, operator section). The session query now counts hidden rows. The runbook now says how a refused start shows (`Restarting`, `compose logs`, `/api/ready`), including the 90 s heartbeat of a killed single backend.

### Verified clean

- **Clock.** Both sides use the database clock. `WriteHeartbeat` sets `seen_at = now()` on conflict, with the column default on insert. `LiveHeartbeats` compares `seen_at > now() - make_interval(secs => 90)` (`encryption_keys.go:61-70`, `:90-95`). There is no client-clock skew.
- **Race.** The backend writes its heartbeat, then reads the holder. The migrator takes the lock, then reads the heartbeats. Both are autocommitted, so one always sees the other. `MaintenanceHolder` reads `application_name` (shown to all roles) through `pg_locks`, which is also unrestricted, so a migrating holder is recognised across roles.
- **Advisory-lock interaction.** There is no deadlock between `(8400,1)` and golang-migrate's lock. The only process that can hold golang-migrate's lock while the migrator holds `(8400,1)` is a pre-PAC-116 binary inside `Up`, and it waits on nothing the migrator holds. PAC-84 `convert`, `rotate-data-key` and `decrypt-all` use `TryMaintenanceLock` (non-blocking), after migrating, and get exit 5 against a migrator.
- **Exit codes.** Consistent with PAC-84 (`exitLock = 5`, `exitBackends = 6`, `encryption.go:25-31`) and PAC-71 (0/1/2, `main.go`).
- **Single-instance compose.** `compose up -d backend` recreates the container, stopping the old one first (`stop_grace_period: 50s`). A graceful stop deletes the heartbeat (`backend/encryption.go:167-174`). `ConnMaxIdleTime` lets an idle backend hold no connection, which the 30 s heartbeat covers.
- **Amendments.** PAC-84.md and PAC-84.yaml only add text (no removed lines). PAC-82.md only adds, apart from the header revision line. All three manifests parse as JSON. `allowedPaths` covers `db.go`, `encryption_keys.go`, `main.go`, both operator files, `test_seams.go` and tests. `forbiddenPaths` excludes migrations and any bypass.
- **Gates.** The OpenAPI bundle sha256 is unchanged.

## Challenge — 2026-11-14 (revision 3, confirmation pass)

**Verdict**: ACCEPT. S1–S4 are closed. Two gaps that the fixes opened are closed by small edits in this commit. One non-blocking note is recorded for the plan.

### S1–S4
- **S1 (hidden sessions): closed.** §2 counts a NULL `backend_type`, and AC-18 tests it with a second non-superuser role.
- **S2 (transient dirty): closed after one fix.** §2's order is unknown → dirty → pending → current, and a dirty row with a migrating holder reads as "being applied" (exit 5).
  - The gap: a lock-free reader reads the version, then the holder. A migrator that writes clean and unlocks *between those two reads* left "dirty, no holder", which is today's dirty error together with the runbook's `force` advice. This is the S2 hazard again, in a narrower window.
  - *Fixed:*
    - §2 "Read order": a lock-free "dirty, no holder" is never final.
    - §3 step 1 now goes on to the lock, and step 4 decides under it, where no PAC-116 migrator can be inside a file.
    - §5.1 `status` re-reads once.
    - D-11 is aligned.
- **S3 (newer schema): closed.** Unknown is classified first, before any lock, with today's `no migration found` error on every path, `status` included (AC-20, gap version included).
- **S4 (simultaneous starts): closed.** Sessions named `paceday-migrate:` are excluded, and AC-10 and AC-21 require exactly one to apply.

### Does the S4 exemption open a hole?
A serving process cannot carry the name, provided the handle is closed before the process does anything else (§3 step 2). An excluded process then either holds the lock or checks the holder after opening its working connection: a backend through §4.1, an operator through §4.5. So it cannot serve while a migrator holds the lock.

The premise is a code property, so it needs a test. *Fixed:* AC-7 now also asserts that once the backend is ready, no `paceday-migrate:` session of it remains in `pg_stat_activity`.

### Is the §4.5 operator write-then-check sound?
Only if the operator's presence is continuous. A backend's presence is its heartbeat lease. An operator's presence is a connection, and a pool can close an idle one: idle and lifetime limits, or a bad-connection retry. That would leave a gap after the holder read in which a migrator's step 5 sees nobody.

*Fixed:* §4.5 reads the holder on a connection that the subcommand keeps open until it ends (a pinned `*sql.Conn`, or the transaction it runs in). The mutating `encryption` subcommands are already sound: they hold `(8400,1)` for the whole run.

### Is `status` consistent as a probe?
Consistent across:
- spec §3 and D-10;
- contract §5.1 and the §5 table ("not `status`");
- the PAC-84 §8.1 and §8.2 notes;
- manifest AC-1, AC-19 and AC-22.

The runbook said "never refuses", while §5.1 exits 5 during a migration. *Fixed:* the runbook now says "never refuses as serving; exits 5 while a migration is in progress".

Remaining asymmetry, left as the author's choice: `--check` exits 0 with migrations pending above 034, but 1 below 034.

### Non-blocking
- `booker-erasure status` is a read-only operator subcommand. It is not routed through §3 and does not run §4.5. A multi-table read during a migration can still be the other side of a deadlock, and the deadlock detector may abort the migration and leave the version dirty. It is a manual command that is unlikely to run during a stop, so this is a note for the plan: give it §4.5's holder check (exit 1 on a migrating holder).

## Superseded: revision 1 (2026-11-14)

Revision 1 proposed a rule enforced by a Go test parsing `backend/storage/migrations/*.up.sql`. For each of the four Q1 tables, a migration had to take its strongest lock first, measured by a live-blocking "level" (0: AS, RS, RE, SUE; 1: S, SRE; 2: E; 3: AE), with a leading `LOCK TABLE … IN ACCESS EXCLUSIVE MODE` as the universal remedy, fail-closed classification and no exemption. It checked 001–039 and reported no violation.

The challenge below rejected it with four blocking counterexamples:

- B1: row locks after a level-1 first lock (migration 022 is one);
- B2: overstated first locks hiding upgrades (REINDEX, TRUNCATE, non-`public` names, `search_path`);
- B3: implied locks from foreign-key actions;
- B4: indirection through functions, views and triggers.

The owner then chose "stop traffic" instead. The full revision-1 text is at commit `2c13c9c`. Its findings stay valid as the reason no migration may run against a serving app: §2.4 lists the live transactions they found.

## Challenge — 2026-11-14 (of revision 1; kept as history)

**Verdict**: accept-with-changes (REVISE). The details, with concrete migrations, are in `contracts/features/PAC-116.md` "Challenge — 2026-11-14".

### Blocking
1. **§3's guarantee is false.** The text reads: "a migration that keeps the rule cannot form a lock-upgrade cycle … on that table". When the first lock is SHARE or SHARE ROW EXCLUSIVE, a later statement that waits on a *row lock* deadlocks with a live path. The live path holds that row lock under ROW SHARE and then asks for ROW EXCLUSIVE. Two live paths do this: sign-in (`signin.go:222` → `session.go:97` `FOR UPDATE`, then `signin.go:263` `UPDATE users`) and `SetUserOrg` (`orgs.go:55`, then `:62`). Migration 022's shape (`CREATE TABLE … REFERENCES users`, then `INSERT … JOIN users`) is a real instance, so §2.4's "022 ok" is wrong. **Resolve:** extend the rule and D-2. After a level-1 first lock on T, no later statement may take or wait for row locks on T. Then decide what happens to 022 (edit it with a leading `LOCK`, or pin it as a frozen historic record), and amend D-7 and AC-17 to match. Add ACs.
2. **The implied locks in D-6 are incomplete.** RI actions on tables that *reference* the written table are missing. `DELETE FROM organizations` sets `users.org_id` to NULL: ROW EXCLUSIVE and row locks on users, unseen. Deleting from users or scheduling_links cascades into the link tables and bookings. **Resolve:** add them to D-6, with an AC.
3. **The "first lock" may never be overstated.** REINDEX and ALTER INDEX (an index-level AE, while the table itself holds only SHARE), TRUNCATE (no lock on the tables it references), and non-`public` or temp tables with a covered name, or a `search_path` change, all hide an upgrade. **Resolve:** add a requirement to §3 and D-5, with ACs.
4. **Fail closed through indirection (D-5).** A function call, a view, or a trigger or rule on a non-covered table can lock a covered table without naming it. Today AC-14 says a `CREATE FUNCTION` body "is not read as a lock", but nothing says what happens when the function is called. **Resolve:** add a requirement and ACs.
