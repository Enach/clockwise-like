## 1. Problem

The owner of a scheduling link manages its co-hosts in the link editor. Today three things go wrong, and the owner is never told:

1. **Removing a co-host does nothing.** The owner removes a co-host's chip and saves. The editor reports success, but the person stays a host on the server. If they had accepted, their calendar still constrains the link's slots. If they had not answered, the invitation stays in their list.
2. **Adding someone who cannot be invited fails silently.** A co-host must be the single Paceday account holding that address, and must hold it confirmed. The server refuses any other address. The editor ignores the refusal and shows "Invites sent to N co-hosts", counting the refused address. Until the next reload it even shows that person as a pending co-host.
3. **Server and network failures on an invitation are also hidden** behind the same success message.

The owner pays in two ways. They believe a teammate shares the link when nobody was invited. Or they believe someone was removed while that person's calendar still blocks the link's slots.

The success message also claims that invites were "sent". Nothing is sent. A co-host invitation is an in-app entry that the invitee sees on their Links page. No email exists for it (§2.4).

## 2. Current behaviour

### 2.2 The server: create (clockwise-like `f45b611`)

`createLink` (`backend/api/handlers_scheduling_links.go:376-440`) accepts `co_host_emails` (`:97`). It does, in order:
- reads the owner and their zone (`:390-401`);
- generates a slug when none is given (`:402-411`, `engine/booking.go:83-101`);
- inserts the link (`:420`);
- inserts the owner's `accepted` host row (`:425`). If that write fails, the answer is 500 **and the link stays created** (`:425-427`);
- for each listed address (`:429-436`):
  - resolves it with `storage.ConfirmedHolder` (`backend/storage/identity.go:152-161`);
  - skips it when nobody holds it confirmed, or when the lookup fails (`:431-434`);
  - otherwise **upserts** a `pending` row through `AddLinkHostCtx`, discarding the result and any error (`_, _ =`, `:435`);
- answers 201 regardless (`:437-439`).

None of these writes share a transaction.

Consequences:
- **The owner's own confirmed address demotes the owner.** `AddLinkHost` is `ON CONFLICT … DO UPDATE SET status = EXCLUDED.status` (`scheduling_links.go:273-281`), and there is no owner check on create.
  - The owner then appears in their own invitation list (`GetPendingInvitesForUser`, `scheduling_links.go:382-388`).
  - The owner drops out of `GetAcceptedHosts` (`:360-376`).
  - This is API-048's upsert, still live on this path. PATCH skips the owner (`:875`).
- **The owner's own address, when not confirmed or shared by case-differing accounts**, gets no holder from `ConfirmedHolder` (`identity.go:157`). It is skipped like any address that cannot be invited.
- **Duplicate creates are not prevented.** Nothing makes create idempotent. The web never sends a slug (`schedulingLinks.ts:170-181`; pinned by `schedulingLinks.test.ts:110`, `:280`). Generation appends a random suffix when the base is taken (`engine/booking.go:89-99`), and titles are not unique.
- **Status convention.** On create and PATCH, 400 means only that the body is not valid JSON (`:381`, `:547`; contract create `'400'`). Every field-validation failure is 422 (`:233-299`, `SchedulingLinkValidationError`), including `days_of_week` out of range (`:254`).
- **Day spellings.** `days_of_week` wins over the `days` alias whenever it is carried (create `:186-189`, PATCH `:569-574`; PAC-40 D-5).
- **The list's length is unlimited.** Neither request schema has `maxItems` (`openapi.yaml:11026-11032`, `:16050-16056`). No request body is wrapped in `http.MaxBytesReader`; its only backend use is `auth/ms_idtoken.go:483`.
- **A blank entry** is skipped: `CarrierIDs` ignores it (`identity.go:169`), and `ConfirmedHolder` finds no holder.
- **Reachability.** The web does not send `co_host_emails` today, so none of the above is reachable from the web. The e2e suite sends it (`e2e/tests/public-booking.spec.ts:624`) with an invitable address.
- The contract documents the silent skip (`openapi.yaml:7563-7570`, `:11026-11032`). It mentions neither the owner demotion nor the half-created link.

### 2.3 The server: edit and single invitation

**PATCH** (`handlers_scheduling_links.go:639`) calls `storage.UpdateSchedulingLinkAndCoHostsCtx` (`backend/storage/guarded_writes.go:384-394`). When `co_host_emails` is present, `[]` included, it writes the fields and the co-host list in one transaction (`updateSchedulingLinkAndCoHosts`, `scheduling_links.go:844-883`, PAC-101). An absent key leaves co-hosts alone (`:857`). With the list present:
- **Keep set** (`:863`, `CarrierIDs`, `identity.go:165-184`): every account carrying a listed address at any standing, ignoring case (PAC-71 AC-43). An existing host is therefore kept when listed by an address they carry only unconfirmed.
- **Removal** (`:867`, `RemoveLinkHostsExcept`, `:312-321`): every non-owner host not in the keep set.
- **Invitation** (`:870-881`, `InviteLinkHost`, `:287-308`): a listed address with exactly one confirmed holder who is not the owner. An existing host keeps their status (PAC-61). The owner's own address is skipped (`:875`), and so is any other address that cannot be invited.
- Any lookup or write error is a 500 with nothing changed. Each address costs lookups inside the transaction that holds the link's lock, and bookings wait up to 10 s on that lock (PAC-101).
- **The 200 answer does not say what happened to any address**, or who was removed (`openapi.yaml:7950-7983`, `:16050-16056`).

**`POST /{id}/hosts`** (`handlers_scheduling_links.go:719-772`, `routes.go:198`):
- owner only (403, `:736-738`);
- an address with no single confirmed holder, **or a failed lookup**, answers `404 {"error":"user not found"}` (`:749-753`);
- a new invitee gets 201; an existing host gets 200 with their row unchanged (`:754-771`); a failed write gets 500;
- no limit on how many hosts a link accumulates, so links with more than 5 co-hosts can exist.

**No owner route removes one co-host** (`routes.go:183-202`). A PATCH carrying the list is the only way.

### 2.4 The roster in answers, and what an invitation is

**Non-strict reads.** The create and PATCH answers (`handlers_scheduling_links.go:439`, `:648`) carry the roster through `writeLink` (`:364-367`), which calls `toSchedulingLinkDTO(..., false)` (`:306-310`). The links list is built the same way (`:463`). A failed roster read degrades instead of failing:
- a failed read of the host rows gives `hosts: []`, without the owner;
- a failed user read gives a host with `"email": ""` (`:336-353`; `schedulingHostDTO.Email` has no `omitempty`, `:66`).

After the web injects the owner (§2.1, `:140`), an emptied roster cannot be told from a link with no co-hosts.

**Strict read.** The single-link `GET /{id}` builds the roster strictly (`buildSchedulingLinkDTO(..., true, true)`, `:515`) and answers 500 instead of degrading. This is pinned by `TestPAC25GetLinkRosterFailureIs500` (`handlers_scheduling_links_test.go:815`).

**Invitations and email.**
- An invitation is the `pending` host row only. The invitee sees it in `GET /scheduling-links/host-invites` (`:775`); the web lists it on `src/pages/Links.tsx:231-232`.
- **No email exists for a co-host invitation.** The backend sends email for the team invite (`sendTeamInviteEmail`, `api/handlers_teams.go:644`) and the booking confirmation (`engine/booking.go:771`, `:815`) only.
- No foreign key points at `scheduling_link_hosts` (migration `009_scheduling_links.up.sql:16-24`). Removing a host leaves bookings untouched.

## 3. Desired behaviour

Written from the link owner's point of view. "Can be invited" keeps today's rule: exactly one Paceday account holds the address, confirmed (PAC-71).

1. **What the editor shows is what gets saved.** When a save that changed the co-hosts succeeds, the link's co-hosts on the server are exactly the editor's chips, minus the addresses reported as not added (§3.4):
   - an address that can be invited becomes a pending co-host;
   - a removed chip, the last one included, removes that person. Their pending invitation disappears; if they had accepted, the link stops using their calendar. Bookings already made on the link stay as they are;
   - someone who was already a co-host keeps their status.
2. **The baseline, and when a save changes the co-hosts** [F, D-3]:
   - The **baseline** is the link's co-host list as given by a read that fails instead of degrading.
   - The editor takes it when it opens on an existing link, and again after every save that keeps it open.
   - **Neither the links list nor a save's answer is ever the baseline.** Both can silently return an incomplete roster (§2.4).
   - For a new link, the baseline is empty until the first successful save.
   - A save **changes the co-hosts** when the chips differ from the baseline, compared as sets of addresses ignoring case. Removing a chip and adding it back is no change.
   - A save with no change leaves the server's co-hosts untouched; the editor does not send the list. A save with a change sends the complete list.
3. **A save never removes a co-host the owner did not remove.**
   - While the baseline is not available, co-host editing is disabled with a visible reason. That covers both a pending read and a failed one. The owner can still save the link's other fields.
   - Reopening the editor retries the read.
4. **Every listed address gets a reported outcome, from the server's answer to that save** [F, D-2]. The counts come from the same answer.

   | Outcome | When | Wording (meaning; the contract fixes the exact text) | Counted as |
   |---|---|---|---|
   | invited | a new pending co-host was created | "invited — they can accept from Paceday" | invited |
   | already a co-host | the person was already a host and keeps their status (PAC-61), including when listed by an address they carry only unconfirmed | no message; the chip shows their status | not counted |
   | own address | the address resolves to the owner (create and PATCH) | "that's your own address — you're the link's owner" | not counted |
   | couldn't be added | anything else: no single confirmed holder | "couldn't be added as a co-host" | not added |

   - "Couldn't be added" is true whether nobody holds the address, someone holds it unconfirmed, or several accounts share it, and it reveals nothing about which.
   - The answer also reports **who was removed** by this save.
5. **Counts are per person.** Two listed addresses that reach the same account count once, and both report that person's outcome. The editor refuses an address that is already a chip, ignoring case.
6. **The list has a limit** [F, D-8].
   - The server refuses with a 422 and saves nothing when the list has more than 5 entries **and** at least one entry does not reach a current host of the link.
   - A save that only removes co-hosts, or keeps the existing set, is accepted at any length. So the owner of a link that already has more than 5 co-hosts can still remove one at a time.
   - The editor's cap of 5 when adding stays, so the editor never builds a list the server refuses.
   - A blank entry is refused with a 422 and nothing saved.
7. **The owner's own address.**
   - The editor refuses it when it is added, in any case.
   - The server, for any client, never changes the owner's host row because of the list.
   - The server reports "own address" when the address resolves to the owner.
   - When the owner's address cannot be resolved (held unconfirmed, or shared by case-differing accounts), the server cannot tell it is the owner's and reports "couldn't be added". That is acceptable: the wording is still true, and the owner's row is still unchanged.
8. **A failure saves nothing and says so.**
   - On any server or network failure, the editor shows an error, no success message, and keeps the owner's input.
   - An edit that fails changes neither the fields nor the co-hosts (PAC-101).
   - A create that fails creates nothing: not the link, not the owner's host row, not a co-host [F, D-4; OQ-3]. This covers a failed owner-host write, a failed co-host lookup and a failed co-host write.
   - It does **not** protect against a retry after a lost answer (§5).
9. **The success message is true.**
   - Its counts (invited, removed, not added) come from the server's answer to this save, not from a client diff, so a concurrent change elsewhere cannot make it lie.
   - It says people were invited and can accept from Paceday. It never says anything was "sent" or emailed.
10. **The editor stays open after a save that has addresses not added** (OQ-1 default):
    - it lists them with the wording above;
    - it re-reads the baseline (§3.2);
    - after a successful create, the open editor edits the created link: any further save from it edits that link and never creates another.
    A save with nothing to report closes the editor as today.
11. **The editor never shows a co-host the server does not hold.** Chips, the list cache seeded by a save, and the links list show only hosts the server returned.
12. **Day names** (API-053) [F, D-9].
    - An unrecognised day name in the `days` alias is refused with a 422 naming the problem, on create and on edit, instead of being dropped. A mixed list is refused too.
    - When `days_of_week` is also carried, it wins and the alias is ignored entirely, unrecognised names included, as the canonical-spelling rule already says (PAC-40 D-5).
13. **Demo mode follows the same rules**, so it does not promise behaviour the real app lacks.

## 4. Acceptance criteria

Actors:
- **A** is the link owner.
- **B** and **G** are Paceday users whose addresses are domain-confirmed.
- **C** is an address no account carries.
- **D** is an address carried only unconfirmed.
- **E** is a co-host who has accepted.

- `[e2e]`: the full compose stack, nothing mocked.

## 5. Explicitly out of scope

- **A retry after a lost answer can create a second link. This is an accepted risk.** If a create commits but its answer never reaches the editor, the owner sees an error and keeps their input. Saving again creates a second link with a different slug (§2.2). No idempotency key is added here. Follow-up candidate, to be opened by the factory:
  > **Link create is not safe to retry after a lost answer.** `POST /api/scheduling-links` has no idempotency key and the server generates a fresh slug per call, so an owner whose create answer is lost and who saves again gets two links. Specify retry-safe create (for example an idempotency key as on public booking, PAC-82) and have the link editor send it. Found by PAC-112's challenge (B-1).
- **Inviting people who are not Paceday users**, or emailing anyone about a co-host invitation (OQ-2).
- **The rule for who can be invited** (PAC-71). It is unchanged; this work only reports it.
- **Two editors saving the same link at once.** With the complete list, the last save wins: one tab can remove a co-host another tab added, or re-invite someone who left meanwhile. §3.9 keeps the messages true regardless.
- **A cap on how many hosts a link holds.** D-8 limits what a list may add. The single-invitation operation stays unbounded, and links that already have more than 5 co-hosts keep them. Follow-up candidate:
  > **No server-wide limit on request body size or on co-hosts per link.** No API request body is size-limited (`MaxBytesReader` unused), and `POST /scheduling-links/{id}/hosts` lets a link exceed the 5-co-host cap that PAC-112 applies to lists adding someone. Decide a body-size limit and whether the cap applies per link.
- **Making the links list's or the save answer's roster strict.** D-3 never uses either as a baseline.
- **API-069** and the editor's unsent `slug` field (`schedulingLinks.test.ts:110`, `:280`).

## 7. Rollback

- No migration is expected.
- Reverting the web PR restores the per-address requests, which still work against the new server. The single-invitation operation is unchanged, and the list limit does not touch requests without a list.
- Reverting the server PR restores today's answers. A web build expecting per-address outcomes must then say it cannot tell which addresses were added, never that all were. The contract defines that fallback.
- Order: the server merges first (README §1), so a web-only revert is always safe.
- Host rows written in the window are ordinary rows.

## 8. Open questions

Each has a default. The factory proceeds on the default unless the owner answers otherwise before the contract stage.

- **OQ-1 (owner): after a save with addresses not added, does the editor close?**
  - **Default: it stays open**, with §3.10's rules: a strict re-read for the baseline, and a create becomes an edit of the created link (AC-24, AC-25, AC-30, AC-31).
  - Alternative: close, and show the list in a persistent toast.
- **OQ-2 (owner): should a co-host invitation notify the invitee by email**, or invite a non-user to sign up?
  - **Default: no**; separate ticket if wanted.
- **OQ-3 (owner): on create, if any part of the write fails, does the link exist?**
  - **Default: no** (D-4), covering the owner row and the co-hosts (AC-20 to AC-22).

  - Neither option protects against a retry after a lost answer (§5).
- **OQ-4**: closed in revision 3 by factory decision D-8. The owner of a link that has more than 5 co-hosts can remove one at a time and keep the rest, and cannot add anyone until the list is 5 or fewer (AC-32, AC-33).

## 9. Decisions and reasons

- **D-1 [F] (approach (a)): the editor saves the co-host list with the link, in the same request, on create and on edit, whenever it differs from the baseline.**
  - It is the only way to remove a co-host (§2.3).
  - It makes a save one all-or-nothing write instead of 1+N requests.
  - It removes the client-side diff that fabricates pending hosts.
- **D-2 [F] (approach (b)): the outcome for each address, the counts, and who was removed come from the server's answer to the save, and the editor reports them.**
  - (a) alone moves the silent skip into the server; (b) alone leaves removal broken.
  - The outcomes are explicit in the answer, so the client does not derive them from a roster or re-implement PAC-71's rules. The contract fixes the shape.
- **D-3 [F] (factory decision on P2-B1 and P2-M1): the baseline comes only from the strict single-link read, on open and after every save that keeps the editor open.**
  - The links list and the save's answer both degrade silently (§2.4). With the owner injected client-side, an emptied roster looks healthy, so no client check can detect it.
  - The strict read answers 500 instead (PAC-25), which the editor can see.
  - A failed read disables co-host editing only, so the owner is never blocked from saving other fields.
  - Outcomes and counts still come from the save's answer: they describe that write, which a later read cannot.
  - "Changed" is a case-insensitive set difference against the baseline.
- **D-4 [F, pending OQ-3]: create becomes all or nothing**, covering the link, the owner's host row and the co-hosts. Today a failure either leaves a half-created link (`:425-427`) or is swallowed (`:431-435`), and D-1 makes those paths reachable from the web.
- **D-5 [F]: an address that cannot be invited does not fail the save.** Reporting it is enough.
- **D-6 [F]: one wording, "couldn't be added as a co-host"**, for every address that cannot be invited, including the owner's own unresolved address (§3.7). It is true in all those cases and leaks nothing about another account (PAC-71, API-072). The server's outcome carries no finer reason.
- **D-7 [F]: chips after a save come only from the server** (PAC-83, "never invented data"): from the strict re-read (D-3), never from the form.
- **D-8 [F] (factory decision on P2-M2): a list longer than 5 is refused with 422 only when it contains an entry that does not reach a current host of the link.**
  - "Reach" uses the keep rule (any account carrying the address, ignoring case).
  - 5 matches the cap the owner sees when adding (`LinkEditDrawer.tsx:327`, `:638`).
  - A list that only removes or keeps is always accepted, so links already above 5, which the unbounded single-invitation operation can still produce, can be pruned one person at a time.
  - It bounds what a single save can add, and so the invitation lookups done under the link's lock (PAC-101).
  - Recommendation to the contract stage: refuse a list longer than max(5, the link's current co-host count) before any lookup, so a long list of junk cannot cost one lookup per entry under the lock.
  - The contract states the limit in both request schemas. A JSON-schema `maxItems` alone cannot express the "only removes or keeps" exception, so the description must carry it.
  - A blank entry is refused with 422 (§3.6).
- **D-9 [F] (factory decision on P2-M3): every new validation failure is 422**: list too long, blank entry, unrecognised day name.
  - On these operations 400 means only that the body is not valid JSON, and every field-validation failure is 422 (§2.2), including the numeric twin of an unknown day name (`:254`). So `["Montag"]` keeps today's status code and changes only its message.
  - The alias is ignored entirely when `days_of_week` is carried (PAC-40 D-5).
