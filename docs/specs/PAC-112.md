# Spec — PAC-112: link editor, co-host changes are not all saved and invite failures are hidden

- **Linear**: https://linear.app/paceday/issue/PAC-112 (split from PAC-105, item 2; the defect was first recorded in `contracts/features/PAC-101.md` §8)
- **Status**: draft (revision 1, awaiting spec-challenger)
- **Author**: spec-author (factory)
- **Verified against**: clockwise-like `origin/main` `f45b611`; smart-calendar-flow `origin/main` `cf93a4d`
- **Inherited scope**:
  - **API-053** (`docs/factory/api-audit.md:311`, Reported, medium): `POST /api/scheduling-links` drops day names it does not recognise, so `{"days":["Montag"]}` fails as "at least one day is required". It is inherited because D-4 changes what the create operation does. If the contract stage finds a way to meet §4 without modifying the create operation, it is not inherited, and the contract must say so.
  - `x-uncertain`: **none**. The operations involved (`createSchedulingLink`, `updateSchedulingLink`, `inviteSchedulingLinkHost`) carry no marker. The bundle holds 5 markers in total, none of them on scheduling links (`contracts/openapi/openapi.yaml`, grep `x-uncertain:`).
  - Not inherited: API-069 (duplicate invite routes, Confirmed) covers the list, accept and decline routes. This work does not change them.

Decision marks: **[F]** = factory decision, recorded here and open to challenge; **[OQ]** = needs the owner (§8). The ticket left the approach to this stage: (a) send the co-host list with the save, (b) report invite failures, or both. The recommendation is **both, with the server's answer as the only source of truth** (D-1, D-2). §9 gives the reasons.

## 1. Problem

The owner of a scheduling link manages its co-hosts in the link editor. Today three things go wrong, and the owner is never told:

1. **Removing a co-host does nothing.** The owner removes a co-host's chip and saves. The editor reports success, but the person stays a host on the server. If they had accepted, their calendar still constrains the link's slots. If they had not answered, the invitation stays in their list. The removal only seems to have worked until the page is reloaded.
2. **Adding someone who cannot be invited fails silently.** Co-hosts can only be existing Paceday users. They must hold that address as a confirmed address, and nobody else may share it. Other addresses are refused. The editor ignores the refusal and still shows "Invites sent to N co-hosts", counting that address. Until the next reload, it even shows the refused person as a pending co-host.
3. **Server and network failures on an invitation are also hidden** behind the same success message.

The owner pays in two ways. They believe a teammate shares the link when nobody was invited. Or they believe someone was removed while that person's calendar still blocks the link's slots. Nothing on the page shows the difference until a reload, and even then nothing explains it.

A smaller part of the same problem: the success message says invites were "sent". Nothing is sent. A co-host invitation is an in-app entry that the invitee sees on their Links page. No email exists for it (§2.4).

## 2. Current behaviour

### 2.1 The web editor (smart-calendar-flow `cf93a4d`)

- **Chip list.** `LinkEditDrawer.tsx:139` keeps the co-host chips as a list of addresses. Opening an existing link fills it from `link.hosts` (non-owner hosts, `:166`). That roster comes from the links list query (`schedulingLinksApi.listLinks`, `src/api/schedulingLinks.ts:310-318`).
  - `addCoHost` (`:315-333`) lowercases the address and checks its shape, duplicates and a cap of 5 on the client.
  - It does not refuse the owner's own address.
  - `removeCoHost` (`:335-337`) only drops the chip.
- **Save.** The mutation (`:252-262`) passes `co_host_emails: coHosts` to `schedulingLinksApi.createLink` / `updateLink`. **Neither forwards the list to the server.**
  - `backendLinkBody` (`schedulingLinks.ts:164-182`) builds the create and update bodies with no co-host key.
  - Create: `POST /scheduling-links/` (`:348`), then one `POST /scheduling-links/{id}/hosts` per listed address under `Promise.allSettled` (`:350-352`). Every rejection is discarded.
  - Update: `GET /{id}` (`:372`), then `PATCH /{id}` without co-hosts (`:391`). It then posts `/hosts` only for listed addresses that are not already hosts in that fresh read (`:393-403`), again under `Promise.allSettled`. **No request removes a host**, so a removed chip has no server effect.
  - Both paths then re-read the link (`:353-356`, `:404-407`). They **append a fabricated `pending` host** (`pendingHost`, `:191-193`) for every listed address the server does not hold (`:358-359`, `:409-411`). A refused address therefore appears as a pending co-host in the cache the editor seeds (`LinkEditDrawer.tsx:268-279`). It disappears at the next refetch (`:280`).
- **Messages.** `onSuccess` (`:263-288`) counts `newCount` as the chips that were not in the roster at open (`:264`). Whatever the server did, it shows `Invites sent to ${newCount} co-host(s)` (`:282-283`), or "Link updated" / "Link created", and closes the drawer (`:287`). `onError` (`:290-295`) is reached only when the link write itself fails (create or PATCH), or when a read after it fails.
- **Tests that pin today's mechanism.**
  - `src/api/schedulingLinks.test.ts:70-114` asserts the per-address `/hosts` call after create.
  - `:116-142` asserts that update posts only new addresses ("never existing ones").
  - No web test covers removal, a refused invitation or the toast.
- **Demo mode.** The demo implementation (`src/demo/schedulingLinks.ts:350-381`) already treats the list as the complete co-host set: it removes unlisted hosts. Demo mode and the real backend therefore disagree today.

### 2.2 The server: create (clockwise-like `f45b611`)

- `createLink` (`backend/api/handlers_scheduling_links.go:376-440`) accepts `co_host_emails` (`:97`).
- It inserts the link (`:420`) and the owner's accepted host row (`:425`). Then, for each address (`:429-436`), it resolves the address with `storage.ConfirmedHolder` (`backend/storage/identity.go:152-161`) and adds a `pending` row (`:435`).
  - An address with no single domain-confirmed holder is skipped (`:432-434`).
  - **So is a failed lookup** (`e != nil` → `continue`, `:432`).
  - **A failed host write is discarded** (`_, _ =`, `:435`).
  - The answer is still 201.
- The co-host inserts are not in the link's transaction. A failure after `:420` leaves the link created.
- The web does not send this key today (§2.1), so these swallowed failures cannot be reached from the web. The e2e suite sends it (`e2e/tests/public-booking.spec.ts:624`).
- The contract says so: create description, `contracts/openapi/openapi.yaml:7563-7570` ("unknown emails are silently skipped"), and `CreateSchedulingLinkRequest.co_host_emails`, `:11026-11032` ("the response gives no indication that an invite was dropped").

### 2.3 The server: edit and single invitation

- **PATCH** (`handlers_scheduling_links.go:639`) calls `storage.UpdateSchedulingLinkAndCoHostsCtx` (`backend/storage/guarded_writes.go:384-394`). That writes the link's fields and, **when `co_host_emails` is present**, the co-host list in one transaction (`updateSchedulingLinkAndCoHosts`, `backend/storage/scheduling_links.go:844-883`, PAC-101):
  - **Keep set** (`:863`, `CarrierIDs`, `identity.go:165`): every account carrying a listed address at any standing, ignoring case (PAC-71 AC-43).
  - **Removal** (`:867`, `RemoveLinkHostsExcept`, `scheduling_links.go:312-321`): every non-owner host not in the keep set.
  - **Invitation** (`:870-881`, `InviteLinkHost`, `:287-308`): a listed address with a single domain-confirmed holder that is not the owner. An existing host keeps their status (PAC-61). Any other address is skipped silently (`:875-877`).
  - Any lookup or write error is a 500 with nothing changed (PAC-101).
  - **The 200 answer does not say which addresses were skipped.**
  - The contract states all of this (`openapi.yaml:7950-7983`, `UpdateSchedulingLinkRequest.co_host_emails` `:16050-16056`).
- **`POST /{id}/hosts`** (`handlers_scheduling_links.go:719-772`, route `backend/api/routes.go:198`) is owner-only (403, `:736-738`).
  - An address with no single domain-confirmed holder answers `404 {"error":"user not found"}` (`:749-753`). The message is the same whether the address is unknown, held only unconfirmed, or shared by several accounts, so the answer does not reveal standing (PAC-71; API-072).
  - A new invitee gets 201, an existing host 200 with their row unchanged (`:754-771`), and a failed write gets 500.
  - Contract: `openapi.yaml:8262` onward.
- **No route lets the owner remove one co-host** (`routes.go:183-202`). Only the co-host can leave (`/{id}/leave`). A PATCH that carries `co_host_emails` is the only way to remove one.

### 2.4 The roster in answers, and what an invitation is

- The create and PATCH answers carry the host roster through `writeLink` (`handlers_scheduling_links.go:364-367`), which uses the **non-strict** builder (`toSchedulingLinkDTO`, `:306-310`). A failed read of the roster or of a host's user record **silently gives an emptied roster, or a host with no email** (`:336-353`).
- The single-link `GET /{id}` reads strictly and answers 500 instead (PAC-25 C-2). The links list (`:443-472`, `toSchedulingLinkDTO(..., true)`, `:463`) is non-strict. That list is what the editor hydrates its chips from (§2.1).
- An invitation is the `pending` host row and nothing else. The invitee sees it in `GET /scheduling-links/host-invites` (`handlers_scheduling_links.go:775`). The web lists it on `src/pages/Links.tsx:231-232`.
  - No email is sent for a co-host invitation. The backend's only email sender is the team invite (`sendTeamInviteEmail`, `backend/api/handlers_teams.go:644`).

### 2.5 Tests protecting the server behaviour

- PAC-61 status preservation: `TestSchedulingLinksReinviteKeepsExistingHostStatus` and `TestSchedulingLinksPatchCoHostsSetsListByDifference` (`backend/api/handlers_scheduling_links_test.go:323`, `:357`).
- PAC-71 rules for granting, keeping and removing: `TestPAC71_AC28_AC40_GrantingSitesResolveOnlyDomainConfirmedHolders` and `TestPAC71_AC43_RemovalAndKeepActOnEveryCarrier` (`backend/api/pac71_address_test.go:58`, `:153`).
- PAC-101 all-or-nothing PATCH: `TestPAC101_FailedCoHostStepChangesNothing`, `TestPAC101_DeleteDuringAPatchWaitsForItsCoHosts` and `TestPAC101_PatchAfterADeleteChangesNoCoHost` (`backend/api/pac101_test.go:447`, `:382`, `:419`).
- Gap: **no test covers create with co-hosts failing**. Nothing tests that create reports a skipped address, or that a failed co-host write on create is reported.

## 3. Desired behaviour

Written from the link owner's point of view. "Can be invited" means what it means today: exactly one Paceday account holds that address, and holds it confirmed. That rule is not changed here.

1. **What the editor shows is what gets saved.** When the owner saves the link, after creating it or editing it, and the editor reports success, the link's co-hosts on the server are exactly the chips the editor showed, minus the addresses it reports as not added:
   - an added address that can be invited becomes a pending co-host;
   - a removed chip removes that person from the link (their pending invitation disappears from their list; if they had accepted, the link no longer uses their calendar);
   - a chip for someone who was already a co-host leaves their status as it is (accepted, pending or declined).
2. **A save never removes a co-host the owner did not remove.** If the owner did not change the co-hosts in this editing session, saving other fields leaves the co-hosts exactly as they are on the server, even if the editor could not load the full list of co-hosts [F, D-3].
3. **Addresses that cannot be invited are reported, by address.** The link and the other co-host changes are still saved. The editor tells the owner which addresses were not added and why, in one wording: there is no Paceday account with this address. The wording is the same for an unknown address, one held only unconfirmed, and one shared by several accounts, so it reveals nothing about another account [F, D-6]. Those addresses do not appear as co-hosts afterwards. How the editor presents this is OQ-1.
4. **A failure saves nothing and says so.** If the server or the network fails during a save, the editor shows an error, shows no success message, and keeps the owner's input so they can retry.
   - An edit that fails changes neither the link's fields nor its co-hosts (PAC-101 already guarantees this on the server).
   - A creation that fails creates no link [F, D-4; OQ-3]. A retry therefore cannot produce a second link.
5. **The success message is true.**
   - It counts only the people this save actually invited, according to the server.
   - It says they were invited and can accept from Paceday, not that anything was "sent".
   - Removals and addresses not added are mentioned, not hidden behind a generic "Link updated".
6. **The editor never shows a co-host the server does not hold.** After a save, the co-hosts shown come from the server's answer only, never from the form.
7. **The owner's own address is refused when it is added**, with a message, instead of being skipped in silence by the server.
8. **Demo mode follows the same rules**, so it does not promise behaviour the real app does not have.

## 4. Acceptance criteria

Actors used throughout:
- **A** is the link owner.
- **B** is a Paceday user whose address is domain-confirmed.
- **C** is an address no account carries.
- **D** is an address carried only unconfirmed.
- **E** is a co-host who has already accepted.

`[e2e]` runs against the full compose stack, with nothing mocked. `[contract]` is a backend handler or contract test against the test database. `[unit]` is a web test against a mocked transport.

**Saving what is shown**

AC-1. Given A opens the editor for a new link and adds B, when A saves and the editor reports success, then on a fresh load B's invitation list contains the link and A's link shows B as pending. (Today this passes by way of the separate per-address request. It stays as the regression guard for D-1.) [e2e]

AC-2. Given a link with E (accepted) and B (pending), when A removes B's chip, saves, and reloads, then B is not a host of the link, B's invitation list does not contain the link, and E is still an accepted co-host. *Fails today: B is still pending (§2.1, no request removes a host).* [e2e]

AC-3. Given a link with E (accepted), when A removes E's chip and saves, then after a reload E is not a host, and E's busy time no longer removes slots from the link's public page. *Fails today.* [e2e]

AC-4. Given a link with E (accepted) and declined co-host F, when A changes only the title and saves, then E is still accepted and F still declined. (PAC-61, through the new save path.) [contract] [unit]

AC-5. Given A opened the editor on a link whose co-hosts the editor did not receive, because a degraded read gave an empty roster while the server holds E, when A changes only the title and saves, then E is still a host. (D-3: a save that does not change co-hosts does not rewrite them.) [unit]

**Addresses not added**

AC-6. Given A adds B and C to a link and saves, then the link is saved, B is pending, and the editor names C as not added with the wording "no Paceday account with this address". The success message counts one invitation, not two. *Fails today: "Invites sent to 2 co-hosts".* [e2e]

AC-7. Given A adds D, then an address carried by two accounts that differ only in case, then C, each in a separate save, then the editor's message for each is identical, apart from the address. [unit] And the server's answer for each is indistinguishable from C's. [contract]

AC-8. Given a save on create and on edit that lists B and C, then the server's answer for that save shows, without a second request, that B was invited and that C was not. *Fails today: on create and PATCH the answer gives no indication (`openapi.yaml:11026-11032`, `:16050-16056`).* [contract]

AC-9. Given AC-6's save has completed, then no view of the link, whether the editor, the links list or the cache seeded by the save, shows C as a co-host at any moment. *Fails today: `pendingHost` padding (`schedulingLinks.ts:358-359`, `:409-411`).* [unit]

**Failures**

AC-10. Given an edit that changes the title and adds B, when the server answers with a server error, then the editor shows an error and no success message, the drawer stays open with A's input, and on reload neither the title nor the co-hosts changed. *Fails today when the failure is on the invitation: the title is saved and "Invites sent to 1 co-host" is shown.* [unit] (server half already pinned by `TestPAC101_FailedCoHostStepChangesNothing`)

AC-11. Given a create that lists B, where the co-host write fails (test seam), then the answer is an error and no link exists afterwards, neither in A's list nor by its slug. *Fails today: 201 with the link and no co-host (`handlers_scheduling_links.go:432-435`).* [contract]

AC-12. Given a create that lists B, where looking up B's address fails (test seam), then the outcome is the same as AC-11. *Fails today: the address is skipped and the answer is 201 (`:432`).* [contract]

AC-13. Given the network fails after a create was sent, when A retries the same form, then A ends up with at most one link of that title created by these two attempts. (Follows from AC-11 and the single request of D-1. Proven by a transport test that drops the answer to the first request.) [unit]

**Messages and inputs**

AC-14. Given a save that invites two new people, removes one, and finds one address it cannot add, then the success message states those counts: two invited, one removed, one not added. Its text contains neither "sent" nor "email". [unit]

AC-15. Given A types their own address as a co-host, then the editor refuses it with a message when it is added, and no save includes it. [unit]

AC-16. Given demo mode, then AC-6, AC-9 and AC-14 hold against the demo implementation. (C is "not added" when the demo directory has no such user.) [unit]

## 5. Explicitly out of scope

- **Inviting people who are not Paceday users**, or emailing anyone about a co-host invitation (OQ-2). Today an invitation exists only in the app. This work makes the editor say so honestly; it does not add a channel.
- **The rule for who can be invited** (domain-confirmed, single holder, PAC-71). It is unchanged and only reported better.
- **Two editors saving the same link at once.** With a complete list, the last save wins: a co-host added in one tab and absent from another tab's list is removed by the other tab's save. Today's per-address path has a similar effect in the other direction: a co-host who left is re-invited by a stale chip (`schedulingLinks.ts:398-402` reads hosts fresh but trusts the chips). Detecting concurrent edits is a separate feature.
- **The 5-co-host cap** is enforced on the client only (`LinkEditDrawer.tsx:327`). Whether the server enforces it is not changed here.
- **API-069** (duplicate invite routes) and the `slug` the editor collects but never sends (`schedulingLinks.test.ts:110` pins that omission). Neither is touched.
- **The links list's degraded roster** (§2.4, non-strict). D-3 makes it harmless for saves. Making the list strict is not part of this work.

## 6. What must not change

- **PAC-61**: a co-host listed again keeps their status. Protected by `TestSchedulingLinksReinviteKeepsExistingHostStatus` and `TestSchedulingLinksPatchCoHostsSetsListByDifference`. AC-4 adds the web side.
- **PAC-71**: who can be granted, kept and removed; the case-insensitive keep set. Protected by `TestPAC71_AC28_AC40_*` and `TestPAC71_AC43_*`.
- **PAC-101**: an edit is all or nothing, ordered against a delete, with a 10 s lock bound. Protected by the `TestPAC101_*` tests named in §2.5.
- **PAC-72**: an edit that does not change the booking horizon or refusal message does not reset them (`schedulingLinks.ts:384-387`, `:178-180`). No web test sends a co-host change alongside them, which is a gap; the plan must add one.
- **PAC-83**: write errors are rendered by `apiErrorMessage` with the server's text, and no invented data is shown.
- **PAC-41**: the co-host chips' availability states. Protected by `LinkEditDrawer.pac41.test.tsx`.
- **The single-invitation operation** (`POST /{id}/hosts`) keeps its contract, including both 404 bodies (API-072, PAC-101 AC-14), even if the editor stops using it.
- **The e2e create with co-hosts** (`e2e/tests/public-booking.spec.ts:615-630`) keeps passing. It sends B, who can be invited, and expects 201.
- **Accept, decline and leave** for co-hosts are unchanged.

## 7. Rollback

- No migration is expected. Co-hosts already live in `scheduling_link_hosts`, and nothing here needs a new column.
- Reverting the web PR restores today's per-address requests, which still work against the new server, because the single-invitation operation is unchanged (§6).
- Reverting the server PR restores today's create and PATCH answers. A web build that expects the new per-address outcome then gets an answer without it. The contract must say how the editor behaves then: it must report that it cannot tell which addresses were added, never claim that all were added.
- Order: per the factory, the server merges first, so a web revert alone is always safe.
- No data needs repair after a revert. Host rows written during the window are ordinary rows.

## 8. Open questions

Each one has a default. The factory proceeds on the default unless the owner answers otherwise before the contract stage.

- **OQ-1 (owner): after a save with addresses not added, does the editor close?**
  - **Default**: the link is saved and the editor **stays open**. It shows the saved link, an alert listing the addresses not added with the reason, and those addresses removed from the chips, so the next save does not retry them.
  - Alternative: close, and show the list in a persistent toast.
  - Resolve by an answer on PAC-112.
- **OQ-2 (owner): should a co-host invitation also notify the invitee by email**, and should a non-user be invited to sign up?
  - **Default: no.** It stays out of scope (§5); a separate ticket is filed if wanted. This spec only stops the editor from implying an email.
  - Resolve by an answer on PAC-112.
- **OQ-3 (owner): on create, when the co-host step fails on the server, is the link created?**
  - **Default: no link is created** (D-4). This matches the edit path (PAC-101) and keeps a retry from making a second link (AC-13).
  - Alternative: create the link and report "co-hosts not added, try again from the editor". That keeps the server's create non-atomic and needs its own criterion in place of AC-11 and AC-12.
  - Resolve by an answer on PAC-112.

## 9. Decisions and reasons

- **D-1 [F] (approach (a)): the editor saves the co-host list with the link, in the same request, on create and on edit.**
  - It is the **only way to remove a co-host**: no owner-side removal exists apart from the list on an edit (§2.3).
  - It makes the save **one all-or-nothing write** (PAC-101) instead of one request for the link plus N invitation requests, any of which can fail after the link is already saved. N+1 requests are the reason failures can be hidden at all.
  - It removes the client's diffing against a re-read roster, which is the part that fabricates pending hosts.
  - The demo already models the list this way (§2.1).
- **D-2 [F] (approach (b)): the outcome for each address comes from the server's answer for that save, and the editor reports it.**
  - (a) alone moves the silent skip from the client into the server, whose answer today gives no indication (§2.2, §2.3).
  - (b) alone, reporting failures of today's per-address requests, leaves removal broken and keeps a save that can half-succeed.
  - Hence both.
  - Recommendation to the contract stage: make the outcome **explicit in the answer**, rather than having the client compare the returned roster with what it sent. The roster in the create and PATCH answers is built non-strictly (§2.4): a failed read empties it or drops an email without an error, so a diff would report successfully invited people as "not added". Comparing addresses also re-implements PAC-71's case and carrier rules on the client. The contract stage decides the exact shape.
- **D-3 [F]: a save sends the co-host list only when the owner changed the co-hosts in this session.** The editor hydrates its chips from the links list, whose roster degrades silently to empty (§2.4). With a complete list on every save, a title edit made on a degraded read would remove every co-host. This rule keeps that from happening. The contract stage may instead require a strict read of the roster before any save that carries the list; AC-5 holds either way.
- **D-4 [F, pending OQ-3]: create becomes all or nothing, like edit.** Today create swallows lookup and write failures for co-hosts (`handlers_scheduling_links.go:432-435`). That cannot be reached from the web only because the web does not send the list. D-1 makes it reachable, so it is fixed here. Touching the create operation brings API-053 into scope (header).
- **D-5 [F]: an address that cannot be invited does not fail the save.** It is a normal outcome, often a colleague who has not signed up yet. Failing the whole save would make the owner remove the chip just to save a title. Reporting it (D-2) is enough.
- **D-6 [F]: one wording for every address that cannot be invited.** PAC-71 and API-072 settled that the answer must not reveal whether an account holds an address unconfirmed or shares it. The editor's message must not reveal it either, and the server's per-address outcome must not carry a finer reason than today's "user not found".
- **D-7 [F]: the editor's co-host chips after a save come only from the server.** This applies PAC-83 ("never invented data") to `pendingHost`.
