## 1. Problem

The owner of a scheduling link manages its co-hosts in the link editor. Today three things go wrong, and the owner is never told:

1. **Removing a co-host does nothing.** The owner removes a co-host's chip and saves. The editor reports success, but the person stays a host on the server. If they had accepted, their calendar still constrains the link's slots. If they had not answered, the invitation stays in their list.
2. **Adding someone who cannot be invited fails silently.** A co-host must be the single Paceday account holding that address, and must hold it confirmed. The server refuses any other address. The editor ignores the refusal and shows "Invites sent to N co-hosts", counting the refused address. Until the next reload it even shows that person as a pending co-host.
3. **Server and network failures on an invitation are also hidden** behind the same success message.

The owner pays in two ways. They believe a teammate shares the link when nobody was invited. Or they believe someone was removed while that person's calendar still blocks the link's slots.

The success message also claims that invites were "sent". Nothing is sent. A co-host invitation is an in-app entry that the invitee sees on their Links page. No email exists for it (§2.4).

### 2.2 The server: create (clockwise-like `f45b611`)

`createLink` (`backend/api/handlers_scheduling_links.go:376-440`) accepts `co_host_emails` (`:97`). It does, in order:

- reads the owner and the owner's zone (`:390-401`);
- generates a slug when none is given (`:402-411`, `engine/booking.go:83-101`);
- inserts the link (`:420`);
- inserts the owner's `accepted` host row (`:425`). If that write fails, the answer is 500 **and the link stays created** (`:425-427`);
- for each listed address (`:429-436`):
  - resolves it with `storage.ConfirmedHolder` (`backend/storage/identity.go:152-161`);
  - skips it when nobody holds it confirmed, or when the lookup fails (`e != nil || !ok → continue`, `:431-434`);
  - otherwise **upserts** a `pending` row through `AddLinkHostCtx` and discards the result and any error (`_, _ =`, `:435`);
- answers 201 regardless of what happened to the co-hosts.

None of these writes share a transaction.

Consequences:
- **The owner's own confirmed address demotes the owner.** `AddLinkHost` is `ON CONFLICT … DO UPDATE SET status = EXCLUDED.status` (`scheduling_links.go:273-281`), and there is no owner check on create. The owner's row goes from `accepted` to `pending`.
  - The owner then appears in their own invitation list (`GetPendingInvitesForUser`, `scheduling_links.go:382-388`).
  - The owner drops out of `GetAcceptedHosts` (`:360-376`), which the booking engine and the public page read.
  - This is API-048's upsert, still live on this one path. PATCH skips the owner (`:875`).
- **Duplicate creates are not prevented.** Nothing makes a create idempotent: the web never sends a slug (`schedulingLinks.ts:170-181`, pinned by `schedulingLinks.test.ts:110` and `:280`), and generation appends a random suffix when the base is taken (`engine/booking.go:89-99`). Titles are not unique.
- The web does not send `co_host_emails` today, so none of this is reachable from the web. The e2e suite sends it (`e2e/tests/public-booking.spec.ts:624`) with an invitable address.
- The contract documents the silent skip (`contracts/openapi/openapi.yaml:7563-7570`; `CreateSchedulingLinkRequest.co_host_emails`, `:11026-11032`). It mentions neither the owner demotion nor the half-created link.
- There is **no limit** on the list's length. Neither schema has `maxItems` (`:11026-11032`, `:16050-16056`). No request body is wrapped in `http.MaxBytesReader`; its only backend use is `auth/ms_idtoken.go:483`, on a provider response.

### 2.3 The server: edit and single invitation

**PATCH** (`handlers_scheduling_links.go:639`) calls `storage.UpdateSchedulingLinkAndCoHostsCtx` (`backend/storage/guarded_writes.go:384-394`). When `co_host_emails` is present, `[]` included, it writes the fields and the co-host list in one transaction (`updateSchedulingLinkAndCoHosts`, `scheduling_links.go:844-883`, PAC-101). An absent key leaves co-hosts alone (`:857`). With the list present:
- **Keep set** (`:863`, `CarrierIDs`, `identity.go:165-184`): every account carrying a listed address at any standing, ignoring case (PAC-71 AC-43). An existing host is therefore kept when listed by an address they carry only unconfirmed.
- **Removal** (`:867`, `RemoveLinkHostsExcept`, `:312-321`): every non-owner host not in the keep set.
- **Invitation** (`:870-881`, `InviteLinkHost`, `:287-308`): a listed address with exactly one confirmed holder who is not the owner. An existing host keeps their status (PAC-61). The owner's own address is skipped (`:875`), and so is any other address that cannot be invited.
- Any lookup or write error is a 500 with nothing changed. Each address costs lookups inside the transaction that holds the link's lock, and bookings wait up to 10 s on that lock (PAC-101).
- **The 200 answer does not say what happened to any address**, or who was removed. The contract states the behaviour (`openapi.yaml:7950-7983`; `UpdateSchedulingLinkRequest.co_host_emails`, `:16050-16056`).

**`POST /{id}/hosts`** (`handlers_scheduling_links.go:719-772`, `routes.go:198`):
- owner only (403, `:736-738`);
- an address with no single confirmed holder, **or a failed lookup**, answers `404 {"error":"user not found"}` (`:749-753`, `err != nil || !found`);
- a new invitee gets 201; an existing host gets 200 with their row unchanged (`:754-771`); a failed write gets 500;
- no limit on how many hosts a link accumulates through it;
- contract: `openapi.yaml:8262` onward.

**No owner route removes one co-host** (`routes.go:183-202`). A PATCH carrying the list is the only way.

### 2.4 The roster in answers, and what an invitation is

- The create and PATCH answers carry the roster through `writeLink` (`handlers_scheduling_links.go:364-367`), built **non-strictly** (`toSchedulingLinkDTO`, `:306-310`). A failed read of the host rows gives an empty roster with no owner; a failed user read gives a host with `"email": ""` (`:336-353`; `schedulingHostDTO.Email` has no `omitempty`, `:66`).
- The links list is non-strict too (`:463`).
- The single-link `GET /{id}` is strict and answers 500 instead (PAC-25 C-2, `TestPAC25GetLinkHostStatusFailureForCoHostIs500`).
- An invitation is the `pending` host row only. The invitee sees it in `GET /scheduling-links/host-invites` (`:775`), and the web lists it on `src/pages/Links.tsx:231-232`.
- **No email exists for a co-host invitation.** The backend sends email in two places: the team invite (`sendTeamInviteEmail`, `api/handlers_teams.go:644`) and the booking confirmation (`sendBookingEmail` / `sendConfirmationEmail`, `engine/booking.go:771`, `:815`). Neither concerns co-hosts.
- Host rows are referenced by nothing else: no foreign key points at `scheduling_link_hosts` (migration `009`). Removing a host leaves bookings untouched.

## 3. Desired behaviour

Written from the link owner's point of view. "Can be invited" keeps today's rule: exactly one Paceday account holds the address, confirmed (PAC-71). "Baseline" is the co-host list the editor knows to be the server's: what it loaded when it opened, or the server's answer to its last save in this session.

1. **What the editor shows is what gets saved.** When a save that changed the co-hosts succeeds, the link's co-hosts on the server are exactly the editor's chips, minus the addresses reported as not added (§3.4):
   - an address that can be invited becomes a pending co-host;
   - a removed chip, the last one included, removes that person. Their pending invitation disappears; if they had accepted, the link stops using their calendar. Bookings already made on the link stay as they are;
   - someone who was already a co-host keeps their status.
2. **"Changed" means different from the baseline**, compared as sets of addresses ignoring case. Removing a chip and adding it back is no change [F, D-3].
   - A save with no change leaves the server's co-hosts untouched. The editor does not send the list.
   - A save with a change sends the complete list.
3. **A save never removes a co-host the owner did not remove** [F, D-3]. When the editor cannot trust its baseline, co-host editing is disabled with a visible reason, and the owner can still save the link's other fields. The baseline is untrusted when the roster could not be loaded, or when any host in it lacks an address. Retrying the load (for example by reopening the editor) re-enables it.
4. **Every listed address gets a reported outcome, from the server's answer to that save** [F, D-2]. The outcomes, with their wording [F, D-6]:

   | Outcome | When | Wording (meaning; the contract fixes the exact text) | Counted as |
   |---|---|---|---|
   | invited | a new pending co-host was created | "invited — they can accept from Paceday" | invited |
   | already a co-host | the person was already a host and keeps their status (PAC-61), including when listed by an address they carry only unconfirmed | no message; the chip shows their status | not counted |
   | own address | the address is the owner's (create and PATCH) | "that's your own address — you're the link's owner" | not counted |
   | couldn't be added | none of the above: no single confirmed holder | "couldn't be added as a co-host" | not added |

   - The "couldn't be added" wording is true whether nobody holds the address, someone holds it unconfirmed, or several accounts share it. It reveals nothing about which.
   - The answer also reports **who was removed** by this save.
5. **Counts are per person, not per address.** Two listed addresses that reach the same account count once, and both report that person's outcome. The editor refuses an address that is already a chip, ignoring case.
6. **The list has a limit.** The server refuses a list longer than 5 entries with a 400 and saves nothing [F, D-8]. The editor's cap of 5 stays.
7. **The owner's own address**: the editor refuses it when it is added. The server, for any client, never changes the owner's host row because of the list, and reports the address as "own address".
8. **A failure saves nothing and says so.**
   - On any server or network failure, the editor shows an error and no success message, and keeps the owner's input.
   - An edit that fails changes neither the fields nor the co-hosts (PAC-101).
   - A create that fails creates nothing: not the link, not the owner's host row, not a co-host [F, D-4; OQ-3]. This covers a failed owner-host write, a failed co-host lookup and a failed co-host write.
   - It does **not** protect against a retry after a lost answer (§5).
9. **The success message is true.**
   - Its counts (invited, removed, not added) come from the server's answer to this save, not from a comparison with what the editor thought it held, so a concurrent change elsewhere cannot make it lie.
   - It says people were invited and can accept from Paceday. It never says anything was "sent" or emailed.
10. **The editor stays open after a save that has addresses not added (OQ-1 default)**:
    - it lists them with the wording above;
    - it removes their chips;
    - the server's answer becomes the new baseline, for the chips, their states and the next save's counts and change test;
    - **after a successful create, the open editor edits the created link**: any further save from it edits that link and never creates another.
    A save with nothing to report closes the editor as today.
11. **The editor never shows a co-host the server does not hold.** Chips, the list cache seeded by a save, and the links list show only hosts from the server's answer.
12. **Unrecognised day names are refused** on create and on edit with a 400 naming the problem, instead of being dropped (API-053).
13. **Demo mode follows the same rules**, so it does not promise behaviour the real app lacks.

## 5. Explicitly out of scope

- **A retry after a lost answer can create a second link. This is an accepted risk.** If a create commits but its answer never reaches the editor (network drop, timeout), the owner sees an error and keeps their input. Saving again creates a second link with a different generated slug (§2.2). This ticket does not add an idempotency key. Follow-up candidate, to be opened by the factory:
  > **Link create is not safe to retry after a lost answer.** `POST /api/scheduling-links` has no idempotency key and the server generates a fresh slug per call, so an owner whose create answer is lost and who saves again gets two links. Specify retry-safe create (for example an idempotency key as on public booking, PAC-82) and have the link editor send it. Found by PAC-112's challenge (B-1).
- **Inviting people who are not Paceday users**, or emailing anyone about a co-host invitation (OQ-2).
- **The rule for who can be invited** (PAC-71). It is unchanged; this work only reports it.
- **Two editors saving the same link at once.** With the complete list, the last save wins: one tab can remove a co-host another tab added, or re-invite someone who left meanwhile. Detecting concurrent edits is a separate feature. §3.9 keeps the messages true regardless.

## 7. Rollback

- No migration is expected: co-hosts already live in `scheduling_link_hosts`.
- Reverting the web PR restores the per-address requests, which still work against the new server. The single-invitation operation is unchanged, and a 5-entry limit on the list does not affect requests that carry no list.
- Reverting the server PR restores today's create and PATCH answers. A web build expecting per-address outcomes must then say it cannot tell which addresses were added, never that all were. The contract must define that fallback.

## 8. Open questions

Each has a default. The factory proceeds on the default unless the owner answers otherwise before the contract stage.

- **OQ-1 (owner): after a save with addresses not added, does the editor close?**
  - **Default: it stays open** (factory decision on the challenge, B-2), with the rules of §3.10: the server's answer becomes the baseline, and after a create the editor edits the created link (AC-24, AC-25).
  - Alternative: close, and show the list in a persistent toast.
- **OQ-2 (owner): should a co-host invitation notify the invitee by email**, or invite a non-user to sign up?
  - **Default: no**; separate ticket if wanted. This work only stops the editor from implying an email.
- **OQ-3 (owner): on create, if any part of the write fails, does the link exist?**
  - **Default: no link is created** (D-4), matching PAC-101 on edit, covering the owner row and the co-hosts (AC-20 to AC-22).
  - Alternative: create the link and report "co-hosts not added". AC-20 to AC-22 would change accordingly.
  - Neither option protects against a retry after a lost answer (§5).
- **OQ-4 (owner): links that already hold more than 5 co-hosts.** They can exist through the single-invitation operation or a direct API call.
  - **Default**: they keep their co-hosts. A save that changes co-hosts must bring the list to 5 or fewer (the 400 of AC-19, shown with the server's text). A save that does not change co-hosts is unaffected (AC-5).
  - Resolution: answer on PAC-112. The factory cannot query production to count them.

## 9. Decisions and reasons

- **D-1 [F] (approach (a)): the editor saves the co-host list with the link, in the same request, on create and on edit, whenever it differs from the baseline.**
  - It is the only way to remove a co-host (§2.3).
  - It makes a save one all-or-nothing write instead of 1+N requests, which is how failures come to be hidden at all.
  - It removes the client-side diff that fabricates pending hosts.
- **D-2 [F] (approach (b)): the outcome for each address, and who was removed, come from the server's answer to that save, and the editor reports them.**
  - (a) alone moves the silent skip into the server. (b) alone leaves removal broken.
  - The outcome is explicit in the answer, not derived by the client from the returned roster: that roster is non-strict (§2.4), and a diff would re-implement PAC-71's case and carrier rules on the client.
  - The contract fixes the shape.
- **D-3 [F]: "changed" is a set difference against the baseline, ignoring case. A degraded baseline disables co-host editing** (challenge M-1).
  - Sending the complete list from an incomplete baseline removes hosts the owner never saw. Disabling only the title-only case (revision 1) did not prevent that.
  - The editor can know its baseline is complete from a read that fails instead of degrading. The single-link read is strict today (PAC-25). The contract and plan choose how the editor gets one.
- **D-4 [F, pending OQ-3]: create becomes all or nothing**: the link, the owner's host row and the co-hosts, in one unit. Today each is a separate write, and failures either leave a half-created link (`:425-427`) or are swallowed (`:431-435`). D-1 makes those paths reachable from the web.
- **D-5 [F]: an address that cannot be invited does not fail the save.** It is a normal outcome, often a colleague who has not signed up. Reporting it is enough.
- **D-6 [F]: one wording, "couldn't be added as a co-host", for every address that cannot be invited** (challenge M-4).
  - It is true whether nobody holds the address, someone holds it unconfirmed, or several accounts share it.
  - It leaks nothing about another account's standing (PAC-71, API-072).
  - Revision 1's "no Paceday account with this address" was false for two of the three cases.
  - The server's outcome must not carry a finer reason than this.
- **D-7 [F]: chips after a save come only from the server's answer** (PAC-83, "never invented data").
- **D-8 [F]: the server refuses a list longer than 5 entries with 400, and the contract states `maxItems: 5` on both request schemas** (challenge M-7).
  - 5 matches the cap the owner already sees ("x/5 co-hosts", `LinkEditDrawer.tsx:638`), so no list the editor builds is refused.
  - It bounds the lookups done while the link's lock is held (PAC-101) and the size of the outcome list.
  - The check runs before anything is written. On PATCH it applies only when the list is present.
  - The limit counts entries as sent, before folding case, so it is checkable without a lookup.
- **D-9 [F]: unrecognised day names are a 400 on both verbs** (API-053, challenge M-5), instead of being dropped. A mixed list is refused too, so a typo can never silently narrow a link's days.
