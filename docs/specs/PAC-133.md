## 0. The ticket's premises, corrected

The ticket's problem statement is right: both provider readers turn a per-calendar error into "nothing busy" (§2.1). Four of its premises need correcting or sharpening.

1. **The MCP free-slot tool never names a calendar.** The ticket says the tool must report an *attendee* as unknown. The tool has no attendee parameter (`mcp/tools.go:129-139`). It sends only `start` and `end`, the backend turns an absent attendee list into an empty one (`backend/api/handlers_calendar.go:199-202`), and the provider is asked about zero calendars. The e2e fake answers that with an empty object (`e2e/fake-google/freebusy.go:36-53`). So today the tool tells a model "here is the free/busy for your range: `{}`", whatever is in anyone's calendar, the user's own included. Fixing SF-032 alone changes nothing the tool says.
2. **Compression apply's re-check asks about nobody.** Apply re-checks each move with an empty calendar list (`backend/engine/compression.go:172`), and a failed re-check is ignored (`:173`, `err == nil && …`). The "attendee conflict at proposed time" branch (`:174`) is unreachable: the string appears nowhere else in the repository, and the only engine double answers `{}` (`backend/engine/focus_time_test.go:81-83`). So apply verifies nothing for anyone, readable or not.
3. **Team availability is not a free/busy consumer.** The pinned behaviour "an unreadable member is free for slot offering" (`backend/engine/pac81_test.go:266-289`) comes from team availability reading each member's own calendar with that member's credential (`backend/engine/team_availability.go:132-145`). It never goes through a provider free/busy reader. This work therefore cannot break it by construction, and it stays pinned as it is (§6).
4. **The Microsoft reader cannot be reached by e2e.** Graph's base address is a constant (`backend/calendar/outlook_client.go:16`). The e2e stack sends `graph.microsoft.com` to the recording sink, which serves nothing (`e2e/docker-compose.e2e.yml:175`; `e2e/fake-google/sink/main.go:1-14`; `e2e/SEAM-REQUIRED.md`). The ticket's "Microsoft fake schedule error" is therefore a backend-test fake, not an e2e one [F, D-8; OQ-7].

## 1. Problem

Paceday asks a calendar provider "when is this person busy?" on the user's behalf. The provider can answer, per person, "I can't tell you": the address does not exist, the user is not allowed to see that calendar, or the provider had an internal error for that one calendar. Paceday reads that answer as "this person has nothing on their calendar".

Who pays, and how:
- **The link editor** shows a co-host whose calendar the user cannot see as "synced", with no busy time. (Find a time is not affected: it reads team members' own calendars, §0 item 3.)
- **Manager analytics** for an external team member show a full week of free time and zero meeting minutes, marked as measured, when nothing was measured.
- **Meeting suggestions** (web, NLP bar and the MCP tools) propose slots as if an unreadable attendee were free, and never say that one attendee was not checked. The MCP "create event" tool books the first such slot directly. That harm is **fixed**, not just reported: with an unknown attendee the tool now asks before booking (§3.5 item 4, factory decision on m-3).
- **Compression** proposes moving a meeting onto a time "with no conflict" for an attendee whose calendar was never read, and apply moves it without checking anyone.
- **The MCP free-slot tool** returns an empty answer for every call, which a model reads as a free calendar.
- **The wrong answer is cached** for 15 minutes as "known", so even a retry repeats it. And the cache key ignores the end of the range, so a one-day answer is served for a one-week question (SF-033).

What it costs: double bookings, and moved meetings that collide with people's real commitments. Management numbers are invented. Each of these is presented with the same confidence as a real answer.

### 2.1 The provider readers

**Google** (`calendar/freebusy.go:15-41`):
- It makes one `freebusy.query` call, with every address as an item (`:16-25`). A failed call returns the error (`:26-28`).
- For each entry of `resp.Calendars` it copies the busy windows (`:30-39`).
- **The entry's `Errors` list is never read.** An entry that carries `notFound` (or any other reason) and an empty `Busy` becomes an address with an empty busy list, indistinguishable from a free calendar.
- **Groups.** Google's answer also has `Groups`, the "expansion of groups": each requested group id maps to the calendar ids it expanded into, plus the group's own `Errors` (`calendar-gen.go:2143-2147` `FreeBusyResponse.Groups`; `:2065-2069` `FreeBusyGroup`).
  - The expanded members appear in `Calendars`, under ids nobody asked for.
  - The reader ignores `Groups` but copies every `Calendars` entry. So **a group's members' busy time is in the result today**, keyed by member id, and it constrains every consumer that merges or scans the whole map (§2.5, §2.6).
  - The group id itself is absent from the result, and a group-level error is lost.
- A busy window whose timestamp fails to parse becomes the zero time, because the parse error is discarded (`:34-35`). The contract already says so (`contracts/openapi/paths/calendar.yaml`, `RawGoogleBusyWindow`).
- An address the provider did not return at all is simply absent from the result.

**Microsoft** (`calendar/outlook_client.go:110-145`):
- It makes one `/me/calendar/getSchedule` call, with every address (`:111-117`). A failed call returns the error (`:128-130`).
- For each `value` entry it keeps the items whose status is not `free` (`:131-142`).
- The response struct has no `error` member (`:118-127`), so **a schedule that carries an error is decoded as a schedule with no items**, i.e. free.
- Item timestamps' parse errors are discarded (`:136-137`).
- An address not returned is absent from the result.

**WebCal**: `WebcalClient.GetFreeBusy` answers an empty map for every address (`calendar/webcal_client.go:48-50`). It is reachable only through `calendar.NewProvider` (`calendar/client_factory.go:14`), which has no production caller. Dead code.

### 2.2 Participant lookup (FreeBusyService)

`FreeBusyService.Query` (`engine/freebusy_service.go:92-195`):
- **Addresses.** They are lowercased and trimmed (`:108`). Personal domains are never queried and come back `unknown` with no busy time (`:17-29`, `:110-112`).
- **Cache key.** `requester:email:UTC-date-of-start` (`:106`, `:114`). It ignores the start's time of day and the whole end (SF-033). A hit is served as is (`:115-117`).
  - The handler holds one long-lived service, so the cache lives for the process (`api/handlers_freebusy.go:29-31`).
  - The cache has no size bound. An expired entry is deleted only when the same key is read again (`:197-215`).
- **One provider call.** Every uncached address goes in one call under a 5 s timeout (`:126-134`), with the requester's Outlook (`:144-154`) or Google (`:155-164`) credential.
  - **The reader's error is discarded** (`fetched, _ =`, `:153`, `:162`), so a failed call leaves `fetched` nil.
- **Coverage.** An address is `known` iff it is a key of `fetched` (`:179-184`). So:
  - a failed call makes every address `unknown` (correct);
  - an address absent from the answer is `unknown` (correct; a Google group id is therefore `unknown` today);
  - **an address with a per-calendar error is `known` with an empty busy list** (SF-032).
- **Caching.** The result is cached 15 minutes (`:178`, `:188-190`), unknown or known. The exception: a degraded result computed while the requester's credential is recorded as lost is not cached (`:167-176`, PAC-67 AC-20).
- **No window check.** The handler parses `start_time` and `end_time` and **never checks that the end is after the start** (`api/handlers_freebusy.go:59-68`; API-077, SF-034).
- **Three views.** The answer carries each participant three times: `participants[].status`, `busy{}` and the legacy `results[].coverage` (`:76-100`). `status` has two values, `known` and `unknown` (contract `FreeBusyParticipant`, PAC-41 D-2).

**Manager analytics for an external member** (`engine/manager.go:488-507`):
- It builds a fresh service per call and asks for one week.
- When coverage is `known`, it sets meeting minutes to the busy total, free minutes to `totalWorkMinutesPerWeek - busy`, and `DataAvailable = true` (`:493-505`).
- The row is then cached in `team_analytics` (`:510-520`; SF-040).
- **So an unreadable external member shows 0 meeting minutes and a full week free, as measured.**
- With coverage `unknown`, the code already leaves `DataAvailable` false, and the web shows that as "no data".

### 2.3 Raw lookup

`calendarHandlers.freeBusy` (`api/handlers_calendar.go:183-218`):
- **Order of answers.** `start` and `end` must parse as RFC3339, else a plain-text 400 (`:188-197`). These checks come **before** the credential is loaded (`:204-208`). So a user with no Google credential who sends a bad date gets the 400, not the 401. There is **no `end > start` check** (SF-034).
- **Attendees.** `attendees` is split on `,` with no trimming and no validation (`:199-202`). An absent value is an empty list, and **the requester's own calendar is not added**.
- **The answer.** The Google reader's map is encoded as is (`:210-217`). A failed call is the 500 (`:211-214`). So:
  - **an unreadable address appears with `[]`**, exactly like a free one;
  - an address Google did not return is absent;
  - a group's members appear under their own ids, and the group id is absent.
- An Outlook-only user gets the 401 `calendar not connected` (`:137-145`).
- **Who reads the body.** The MCP tool, plus two Go tests: `TestPAC26CalendarFreeBusyWindowKeys` decodes it as `map[string][]json.RawMessage` (`api/pac26_wire_keys_test.go:187-210`), and e2e `seam.spec.ts:179-192` checks arrival only. The web's generated zod schema `RawGoogleFreeBusyMap` has no runtime user.

### 2.5 Meeting suggestions

`SmartScheduler.Suggest` (`engine/smart_schedule.go:59-143`):
- **One Google free/busy call** covers the requester's own calendar (`client.calendarID()`, which is `primary`, `calendar/client.go:32`) plus every attendee (`:70-71`). A failed call fails the whole request (`:72-74`), and the handler answers 500 (`api/handlers_schedule.go:168-171`).

### 2.6 Compression

**Preview** (`SuggestForDay`, `engine/compression.go:56-160`). For each meeting the user organises:
- **Attendees** are the non-self, non-declined guests (`extractAttendees`, `:247-255`).
- **Candidates.** The candidate positions come from `generateAdjacentPositions` (`:113`, `:257-277`): the work start, plus each other movable meeting's end and the position just before it. That is at most 1 + 2 × (other movable meetings) positions.
- **The check.** Each candidate that passes the overlap filter (`:115-127`) is checked with one free/busy call for the attendees over the candidate interval (`:129-134`).
  - A failed call skips the candidate (`:131`).
  - Otherwise `hasConflict` looks for any overlapping window anywhere in the map (`:288-297`), group members included.
  - The meeting is proposed at the first passing candidate that gains more than 30 minutes, and the loop `break`s (`:142-154`).
  - **An unreadable attendee has no windows, so there is "no conflict", and the move is proposed.**
- **Overlap with its own time.** A candidate may overlap the meeting's own current time: the overlap filter excludes the meeting itself (`:106`). Attendees are then busy over it because of this very meeting, so such a candidate fails the check.
- **Cost.** Free/busy calls per meeting with attendees run from 1 (the first candidate passes) to every candidate (a busy attendee). Week mode repeats it for five days (`api/handlers_schedule.go:58-69`). Every call is on the request context, under the 15 s per-call provider limit (`backend/internal/outbound/outbound.go:38`).

**Apply** (`Apply`, `:162-197`). The request carries only `event_id`, `proposed_start` and `proposed_end` (`api/handlers_schedule.go:86-110`). For each posted proposal, apply:
- makes one free/busy call **with a nil calendar list** (`:172`), so the answer is about nobody and `hasConflict` is always false. A failed call is ignored (`:173`);
- then reads the event (`:178-182`), moves it (`:184-190`) and writes the audit entry (`:192`).

Failures are reported as strings `"<event_id>: <reason>"` in `failed` (`:174`, `:180`, `:188`). The handler adds `"<event_id>: invalid time format"` for unparseable times (`handlers_schedule.go:105-108`).

The web has no compression UI (smart-calendar-flow: `compressionPreview`/`compressionApply` appear only in `src/api/client.ts:1155-1160` and the demo mocks).

  - None of these paths uses the PAC-81 per-item pool.

## 3. Desired behaviour

### 3.1 The rule

1. **Per requested address, a provider read ends in one of three outcomes** [F, D-1]:
   - **readable**: the busy windows are complete (possibly none);
   - **unknown, partial**: the provider reported an error for the address **and** some busy windows. The windows are kept, and the address is unknown [F, factory decision on M-2];
   - **unknown**: an error with no windows, or the address is not mentioned in the answer, or the whole call failed (as today).
2. **Groups (Google)** [F, factory decision on M-1].
   - An address the provider answers under its group expansion is a **group**. Its members are the calendars listed for it.
   - The members' busy windows keep constraining every consumer, as they do today. The members are part of the group's answer, not "unrequested extras", and are never dropped.
   - The group is readable when the expansion has no error and every member is readable. Otherwise the group is unknown, and every busy window its members did report is kept.
   - A group whose expansion failed is unknown.
3. **The blocking rule (normative)** [F, factory decision on P2-M3]. This rule binds every consumer of these readers, in this spec and outside it:
   - **Reported windows block, even when the address is unknown.** A busy window the provider reported blocks and constrains wherever windows are used, whatever the address's outcome: readable, unknown-partial, or a group's member.
   - **An unknown address with no reported windows does not block.** Its missing time constrains nothing. Unknown only means "there may be more busy time than shown".
   - **Unknown is never presented or used as free.** A consumer that reports availability reports the address as unknown, never as free.
4. **Readable with nothing busy stays free.** A readable address with no busy windows is free, as today. This work must not turn real free time into unknown.
5. **PAC-129 must adopt the blocking rule** [F, factory decision on P2-M3].
   - **What it must change.** PAC-129's binding contract text says "unknown does not block" (`contracts/features/PAC-129.md:304-306` at `6192cd8`), and so does its spec (`PAC-129.md:262`). As written, that would offer a slot over busy time the provider reported for a partial-unknown added person, or for a group added person with one unreadable member. PAC-129 must read: an added person whose availability is unknown does not block **beyond the busy windows reported for them**, and those windows block as a busy person's do.
   - **Who changes it.** The factory fixes PAC-129's contract and cross-references separately. Until PAC-129 says this, it disagrees with this spec, and this spec's rule wins (PAC-129's backend merges after PAC-133).
   - **PAC-129's cross-references to this spec**, for that fix. PAC-129 cites the draft's AC numbers; the current ones are:

     | PAC-129 cites (at `6192cd8`) | Meaning there | PAC-133 AC now |
     |---|---|---|
     | AC-4 (`PAC-129.md:24`, `:436`) | Google `notFound` is unknown | **AC-1** (reader) / **AC-5** (participant lookup, e2e) |
     | AC-5 (`:24`, `:436`) | Microsoft schedule error is unknown | **AC-4** (reader) / **AC-6** (participant lookup) |
     | AC-7 (`:17`, `:438`) | the SF-033 scenario | **AC-8** |
     | AC-15 (`:24`, `:597`) | the MCP free-slot assertion | **AC-20** |

### 3.2 Participant lookup (web link editor, manager analytics, PAC-129)

1. **Status.** An unknown address has status `unknown` in all three views of the answer. It carries the busy windows that were reported for it (§3.1 items 1-2), possibly none. It is never `known`. A group address is `unknown` unless it is readable under §3.1 item 2.
2. **Caching** [F, D-2]. An unknown result is cached exactly as a known one is, under the existing rules: 15 minutes, and nothing is cached while the requester's credential is recorded as lost (PAC-67 AC-20 unchanged). A repeated question within the window makes no provider call.
3. **The cache answers only the same question** [F, D-3; SF-033]. A cached entry is reused only for the same requester, the same address and the same range, start and end both as exact instants. A different end, or a different start on the same day, is asked again. The contract text that states the key changes with it.
   - **Accepted consequence** (P2-m1). The link editor, the main web consumer, starts its range at `new Date()` (smart-calendar-flow `LinkEditDrawer.tsx:318-320`). So every drawer opened after the web's own 5-minute, hour-bucketed cache has expired (`coverageCache.ts:59-64`) is a new backend key and a provider call. Today the same calls hit for the whole UTC day. Backend cache hits are therefore rare for the link editor. This is accepted: correctness over hit rate. A later report that the backend cache "rarely hits" for the link editor is this decision, not a regression.
4. **The cache is bounded** [F, factory decision on m-9]:
   - it is a least-recently-used cache with a fixed maximum number of entries;
   - adding an entry past the maximum evicts the least recently used one;
   - an expired entry is never served, and it is removed when it is found or evicted;
   - the maximum is the plan's choice, recorded in the contract text.
5. **Manager analytics** for an external member whose calendar is unknown shows no data, never zero meeting minutes and a full free week. This needs no change of its own: it already handles `unknown` (§2.2), so it follows from item 1.
6. **A window that does not move forward is refused** [F, D-4; API-077, SF-034]:
   - an end that is not after the start is a 400 with a fixed message;
   - it comes after the existing 400s, and before the cache and any provider call;
   - the other 400s, and their order, are unchanged.
7. **What stays**:
   - personal domains are `unknown` without a provider call;
   - a failed call makes every address `unknown`;
   - at most 20 addresses per request;
   - the 5 s timeout;
   - one provider call per request;
   - the requester's own credential is used.

### 3.3 Raw lookup

1. **The requester's own calendar is always read** [F, factory decision on M-5]. The backend adds it to every request, whatever attendees are named. The answer identifies it as the user's own calendar, in a way a reader of the answer can recognise, not by an address the caller has to guess. A request never asks the provider about zero calendars.
2. **Each address the caller named, and the user's own calendar, appear** with an outcome under §3.1:
   - **readable**: with its windows, keyed by the same window keys as today;
   - **unknown**: marked unknown, with any windows that were reported.

   No address appears both unknown and as a plain empty busy list. An address the provider did not mention is unknown, no longer absent.
3. **Groups.** A group appears with its outcome, and its members' windows stay in the answer, as they are today.
4. **Breaking change.** The 200 body's shape changes [F, D-5; OQ-2]. The contract stage chooses the shape; the spec requires only items 1-3. The consumers are the MCP tool, which changes with it (§3.4), and the two Go tests in §6.
5. **A window that does not move forward is refused** with a plain-text 400, in the operation's existing 400 style (SF-034) [F, D-4].
6. **Order of answers** [F, m-7]:
   - The new 400 sits with the parse 400s, **before** the credential is loaded. So an inverted window from a user with no Google credential gets the 400, not the 401, as an unparseable date does today.
   - A failed provider call stays the 500, and a missing credential stays the 401.
   - The own calendar being unknown is not a 500: it is reported as unknown.
7. **Second opinion** (API-091). A Go contract test decodes the 200 against the bundle's schema for this operation.

### 3.4 MCP free-slot tool

1. **The tool covers real calendars** [F, D-6; SF-102 to be]:
   - it gains an optional attendee argument and passes the named addresses through;
   - it does not name the user's own calendar: the backend adds that (§3.3 item 1);
   - a call with no attendees therefore still covers the user's own calendar.
2. **Unknown is said explicitly.**
   - For each unknown calendar, the tool's answer carries the unknown marker the contract fixes, and never shows that calendar with an empty window list.
   - The tool's description tells the model that "unknown" means "not checked", not "free".
   - The tool still relays what the backend says and computes no slots of its own.
3. **The window rule** (§3.3 item 5) reaches the model as the tool's usual "Error: …" text.

### 3.5 Meeting suggestions (web modal, NLP, MCP)

1. **Unknown attendees do not constrain beyond what was reported** [F, D-7; ticket item 4].
   - An unknown attendee's missing time does not constrain the slots, as today.
   - Windows that were reported for an unknown attendee (partial, or a group's members) do constrain.
   - Readable attendees constrain as today.
2. **The answer names whose availability was unknown**:
   - every attendee that is unknown under §3.1, groups included, and nobody else;
   - when everyone was read, an empty list that is present, not an absent list;
   - names are given as the caller sent them (a group is named by the group address).
3. **The requester's own calendar unknown fails the request** [F, D-7; OQ-4], with the operation's existing 500, as a failed provider call does today. Slots built on a calendar Paceday could not read are not offered to the person they are for.
4. **MCP `create event` with an unknown attendee takes two explicit steps** [F, factory decisions on m-3 and P2-M1, replacing the draft's OQ-5 default].
   - **First call.** With one or more unknown attendees, it **books nothing**. It returns:
     - the exact proposed start and end;
     - the names of the unknown attendees;
     - a request for confirmation that says how to accept.
   - **The acceptance call** carries:
     - the exact start that was shown, in a new optional start argument;
     - an explicit acceptance flag (`accept_unknown: true`);
     - the unknown names it accepts, echoed from the first answer.

     The duration, title and attendees are as in the first call. The tool is stateless, so the accepted names must travel with the call: that is the only way to tell that the unknown set grew (see below).
   - **Re-verification at booking.** Before booking, the tool has the backend check that slot, and exactly that slot, for every readable attendee, the requester included:
     - **a readable attendee, or the requester, is now busy over it**: refuse, book nothing, and tell the caller to ask again (call without a start);
     - **the unknown set grew**, i.e. someone not among the accepted names is now unknown: refuse in the same way;
     - **the requester's own calendar is now unknown**: refuse in the same way (§3.5 item 3);
     - **otherwise**: book exactly the start shown, with the original duration. The booked slot is the one shown, never a recomputed "first slot".
   - **Without the start argument, nothing is booked past an unknown attendee**, whatever the acceptance flag says. The tool answers as a first call.
   - **With no unknown attendee**, a call without a start books as today, and a call with one books that start after the same check.
   - **Rationale.** This is a safety default. Paceday must never book over attendees whose calendars it could not check without an explicit second step that names them. That is the harm §1 lists. Re-verification closes the gap between the two calls: the slot shown may have stopped being free, and new attendees may have become unknown. Carrying the exact start avoids rebooking at a different time, because suggestions are not reproducible between calls (the range starts at "now", `mcp/tools.go:42`, `:304-305`).
   - **Ownership.** The factory settled this as a safety default, because the alternative ships the harm. **The owner may override it later**, e.g. back to "book and report" (OQ-5).
5. **MCP `suggest meeting`** relays the new list as part of the body.
6. **Web**: the "Suggest a time" modal shows which attendees' availability is unknown, when there are any [OQ-6]. The link editor's chips follow §3.2 item 1 with no code change.
7. **NLP parse surfaces a scheduler failure, and the user sees it** [F, factory decisions on m-4 and P2-M2; SF-037 first clause]:
   - **Backend.** When its suggestion step fails (including the new own-calendar case of item 3), the parse answer carries an error in its existing error field, instead of silently giving no slots.
   - **Precedence.** An error the LLM already set wins and is kept unchanged. The suggestion failure is written only when no error is set.
   - Everything else in the parse answer is unchanged. NLP parse does not list the unknown attendees (§5).
   - **Web.** Today, for a meeting intent with no slots, the Dashboard shows "No available slots found for that request." whatever the error says (smart-calendar-flow `src/pages/Dashboard.tsx:181-184`); it reads the error only on the fall-through branch (`:195`). After this change, a meeting intent with no slots and an error shows the error. With no error, the message is unchanged. This ships in the planned web UI PR.
   - **SF-037's first clause is fixed only when both halves are in place.** Until the web half merges, the register keeps it open.

### 3.6 Compression

1. **Preview: no move justified by an unknown attendee** [F, D-7; ticket item 5].
   - A candidate position is proposed only if every attendee is readable and free over it.
   - If any attendee is unknown at a position, or has reported busy time over it, the position is not proposed, and the next position is tried, as for a busy attendee.
   - A meeting with an attendee who is unknown everywhere gets no proposal.
   - Preview keeps today's handling of the meeting's own time (§2.6).
2. **Apply verifies, against the event's real attendees** [F, D-7; SF-103 to be]. Before moving a meeting, apply reads its current attendees, by the same rule as preview (non-self, not declined), and checks them over the proposed time.
   - **The meeting's own current time is excluded from the check** [F, factory decision on m-10]. Over the part of the proposed interval that overlaps the meeting's current interval, the attendees are already committed to this very meeting, so a move does not create a new conflict there.
     - This is intended. A shift of a meeting by less than its own length must not be refused because of itself.
     - It also means a second commitment an attendee has over that same overlap is not detected. Free/busy cannot tell the two apart, and the move adds no new conflict there.
   - The outcomes:
     - **An attendee busy over the rest of the proposed time**: not moved, reported with today's "attendee conflict" reason.
     - **An attendee unknown, or the check itself failed**: not moved [OQ-8]. Reported as **unverified**, with a reason distinct from the conflict reason and from every other failure reason.
     - **Everyone readable and free**: moved, as today.
     - **No attendee other than the user**: moved without a check, as preview does.
3. **Apply's answer keeps its shape**: moved meetings in the applied list, everything else in the failed list with its reason. The new reason is documented. That is a description change, not a shape change.
4. **Provider calls are bounded, not equal to today's** [F, factory decision on B-1; D-9]:
   - **Preview** makes **at most one free/busy call per candidate position per meeting with attendees**. That is today's worst case: a busy attendee already exhausts every candidate.
     - A meeting with an unknown attendee now reaches that bound where today it stopped at the first candidate.
     - The plan may make fewer calls, for example one call per meeting over the work day.
   - **Apply** makes at most one free/busy call and exactly one event read per proposal: it reads the event before the check, rather than after.
5. **When the bound does not fit the budget** [F, factory decision on B-1]:
   - **Why it fits where today fits.** A calendar whose worst case fits the 90 s budget today fits after this change. The bound is the same, so no calendar is pushed past the budget by a new kind of work.
   - **Why it can still run out.** External, often unreadable, attendees are the common case, so preview now reaches the bound more often. Week mode multiplies it by five. A large week can reach the budget.
   - **What the answer is then.** Preview answers **the documented 503** `{"error":"request timed out"}`. It never returns a partial 200, with or without unchecked candidates marked.
   - **Why the 503 and not a partial answer.** A partial week answer is exactly what PAC-36 removed (a missing day must not look like "nothing to compress"). The 503 is already the middleware's answer, and a client already knows to retry it.
   - **The contract** lists the 503 on the preview operation, as it does for the other operations that reach the budget in normal use.

### 3.7 What does not change

- **Team availability** treats a member whose calendar cannot be read as free for slot offering (§0 item 3). PAC-129 changes what it reports; this work does not.
- **Scheduling-link slots and booking** refuse on an unreadable host (PAC-72 D-6, PAC-81). They do not use these readers.
- **Apply's provider calls per proposal** stay within today's counts (§3.6 item 4).
