## 0. The ticket's premises, corrected

The ticket's problem statement is right: both provider readers turn a per-calendar error into "nothing busy" (§2.1). Four of its premises need correcting or sharpening.

1. **The MCP free-slot tool never names a calendar.** The ticket says the tool must report an *attendee* as unknown. The tool has no attendee parameter (`mcp/tools.go:129-139`). It sends only `start` and `end`, the backend turns an absent attendee list into an empty one (`backend/api/handlers_calendar.go:199-202`), and the provider is asked about zero calendars. The e2e fake answers that with an empty object (`e2e/fake-google/freebusy.go:36-53`). So today the tool tells a model "here is the free/busy for your range: `{}`", whatever is in anyone's calendar, the user's own included. That is a worse silent failure than SF-032, and fixing SF-032 alone changes nothing the tool says.
2. **Compression apply's re-check asks about nobody.** The ticket says apply should report an unreadable attendee as unverified. Today apply re-checks each move with an empty calendar list (`backend/engine/compression.go:172`), and a failed re-check is ignored (`:173`, `err == nil && …`). The "attendee conflict at proposed time" branch (`:174`) is unreachable, and no test exercises it (searched for the string: only `compression.go:174`). So apply verifies nothing for anyone, readable or not.
3. **Team availability is not a free/busy consumer.** The pinned behaviour "an unreadable member is free for slot offering" (`backend/engine/pac81_test.go:265-287`) comes from team availability reading each member's own calendar with that member's credential (`backend/engine/team_availability.go:139`), never through a provider free/busy reader. This work therefore cannot break it by construction, and it stays pinned as it is (§6).
4. **The Microsoft reader cannot be reached by e2e.** Graph's base address is a constant (`backend/calendar/outlook_client.go:16`), and the e2e stack sends `graph.microsoft.com` to the recording sink, which serves nothing (`e2e/docker-compose.e2e.yml:175`; `e2e/fake-google/sink/main.go:1-14`; `e2e/SEAM-REQUIRED.md`). The ticket's "Microsoft fake schedule error" is therefore a backend-test fake, not an e2e one [F, D-8; OQ-7].

## 1. Problem

Paceday asks a calendar provider "when is this person busy?" on the user's behalf. The provider can answer, per person, "I can't tell you": the address does not exist, the user is not allowed to see that calendar, or the provider had an internal error for that one calendar. Paceday reads that answer as "this person has nothing on their calendar".

Who pays, and how:
- **Find a time and the link editor** show a co-host or attendee whose calendar the user cannot see as "synced", with no busy time. The user picks a slot that person may well be busy in.
- **Manager analytics** for an external team member show a full week of free time and zero meeting minutes, marked as measured, when nothing was measured.
- **Meeting suggestions** (web, NLP bar and the MCP tools) propose slots as if an unreadable attendee were free, and never say that one attendee was not checked. The MCP "create event" tool books the first such slot directly.
- **Compression** proposes moving a meeting onto a time "with no conflict" for an attendee whose calendar was never read, and apply moves it without checking anyone.
- **The MCP free-slot tool** returns an empty answer for every call, which a model reads as a free calendar.
- **The wrong answer is cached** for 15 minutes as "known", so even a retry repeats it. And the cache key ignores the end of the range, so a one-day answer is served for a one-week question (SF-033).

What it costs: double bookings and moved meetings that collide with people's real commitments, and management numbers that are invented. Each of these is presented with the same confidence as a real answer.

### 2.1 The provider readers

**Google** (`calendar/freebusy.go:15-41`):
- one `freebusy.query` call with every address as an item (`:16-25`); a failed call returns the error (`:26-28`);

**Microsoft** (`calendar/outlook_client.go:110-145`):

## 3. Desired behaviour

### 3.1 The rule

1. **Three outcomes per address, never two** [F, D-1]. For every address it was asked about, a provider read says one of: *readable, with these busy windows* (possibly none); or *unreadable*. An address is unreadable when:
   - the provider answered an error for that address (any reason, Google or Microsoft); or
   - the provider's answer does not mention the address at all; or
   - the whole call failed (as today).
   An entry that carries both an error and busy windows is unreadable [F]: an error means the windows cannot be trusted to be complete.
2. **Unreadable is never shown or used as free.** Each consumer below says what it does with it. No consumer may turn "unreadable" into "readable with nothing busy".
3. **Readable with nothing busy stays free.** A readable address with no busy windows is free, as today. This work must not turn real free time into unknown.

### 3.2 Participant lookup (web link editor, manager analytics, PAC-129)

1. An unreadable address has status `unknown` and no busy windows, in all three views of the answer (the canonical list, the map and the legacy list). It is never `known`.
2. **Caching** [F, D-2]: an unknown result is cached exactly as a known one is, under the existing rules (15 minutes; not cached while the requester's credential is recorded as lost; PAC-67 AC-20 unchanged). A repeat question within the window makes no provider call.
3. **The cache answers only the same question** [F, D-3; OQ-1; SF-033]. A cached entry is reused only for the same requester, the same address and the same range, start and end both. A different end, or a different start on the same day, is asked again. The contract text that states the key changes with it.
4. **Manager analytics** for an external member whose calendar is unreadable: no data, never zero meeting minutes and a full free week. This needs no change of its own: it already handles `unknown` (§2.2), so it follows from item 1.
5. **A window that does not move forward is refused** [F, D-4; API-077, SF-034]. An end that is not after the start is a 400 with a fixed message, before any provider call and before the cache. The other 400s, and their order, are unchanged.
6. **What stays**: personal domains are `unknown` without a provider call; a failed call makes every address `unknown`; at most 20 addresses; the 5 s timeout; one provider call per request; the requester's own credential.

### 3.3 Raw lookup

1. The answer **marks each unreadable address as unreadable**, distinguishably from "readable, no busy windows". An unreadable address never appears with an empty busy list [F, D-5; OQ-2].
2. Every distinct address that was asked about appears in the answer, readable or unreadable. An address the provider did not mention is unreadable, no longer absent.
3. This is a **breaking change of the 200 body's shape**. Its only consumer is the MCP free-slot tool, which changes with it (§3.4). The contract stage chooses the shape; the spec requires only items 1 and 2, and that readable addresses keep their busy windows with today's window keys.
4. **A window that does not move forward is refused** with a 400 before any provider call (SF-034), in the operation's existing plain-text 400 style [F, D-4].
5. A failed provider call stays the 500; a missing credential stays the 401.

### 3.4 MCP free-slot tool

1. **The tool reads real calendars** [F, D-6; OQ-3; SF-102 to be]. A call always covers the user's own calendar, and covers any attendee addresses the caller names in an optional new attendee argument. A call never asks the provider about zero calendars.
2. **Unknown is said in words.** For each unreadable calendar, the tool's answer states that its availability is unknown. It never states, or lets the answer read as, that the person is free. The tool's description tells the model that "unknown" means "not checked", not "free".
3. The tool still relays what the backend says and computes no slots of its own. The window rule (§3.3 item 4) reaches the model as the tool's usual "Error: …" text.

### 3.5 Meeting suggestions (web modal, NLP, MCP)

1. **An unreadable attendee does not constrain the slots**, as today [F, D-7; confirming ticket item 4].
2. **The answer names whose availability was unknown**: every attendee the provider could not read, and nobody else. When everyone was read, it says so (an empty list, not an absent one). The names are given as the caller sent them.
3. **The requester's own calendar unreadable fails the request** [F, D-7; OQ-4] with the operation's existing 500, as a failed provider call does today. A proposal built on a calendar Paceday could not read for the person it is proposing to is not offered.
4. **MCP**: `suggest meeting` relays the new information as part of the body. `create event` still books the first slot when an attendee is unknown [OQ-5], and its answer says which attendees' availability was unknown when it did.
5. **Web**: the "Suggest a time" modal shows, under the slots, which attendees' availability is unknown when there are any [OQ-6]. Nothing else in the web changes behaviour; the link editor's chips follow §3.2 item 1 without a code change.
6. **NLP parse** keeps copying only the slots (§5).

### 3.6 Compression

1. **Preview: no move justified by an unreadable attendee** [F, D-7; confirming ticket item 5]. A candidate position is proposed only if every attendee was readable and free over it. If any attendee is unreadable at a position, that position is not proposed; the next position is tried, as for a busy attendee. A meeting with an attendee who is unreadable everywhere gets no proposal.
2. **Apply verifies, against the event's real attendees** [F, D-7; SF-103 to be]. Before moving a meeting, apply reads its current attendees (the same rule as preview: non-self, not declined) and checks them over the proposed time. Then:
   - an attendee busy over the proposed time: the meeting is not moved, and it is reported with today's "attendee conflict" reason;
   - an attendee unreadable, or the check itself failed: the meeting is not moved [OQ-8], and it is reported as **unverified**, with a reason distinct from the conflict reason and from every other failure reason;
   - everyone readable and free: moved, as today;
   - a meeting with no attendees other than the user: moved without a check, as preview does.
3. Apply's answer keeps its shape: moved meetings in the applied list, everything else in the failed list with its reason. The new reason is documented [F]; it is a description change, not a shape change.
4. **No extra provider calls** (PAC-81). Apply makes at most one free/busy call and one event read per proposal, as today, by reading the event before the check rather than after. Preview makes the same calls as today.

### 3.7 What does not change

- **Team availability** treats a member whose calendar cannot be read as free for slot offering (§0 item 3). PAC-129 changes what it reports, not this work.
- **Scheduling-link slots and booking** refuse on an unreadable host (PAC-72 D-6, PAC-81), unchanged; they do not use these readers.
- The number of provider calls on every path (§3.6 item 4).

## 4. Acceptance criteria

## 7. Rollback

Code and contract only: no migration, no stored data. The participant lookup's cache is in memory and is emptied by the restart a rollback causes. Reverting restores "unreadable means free" everywhere, the raw lookup's old shape (the MCP tool reverts with it, same repository), and apply's unverified moves. The web's types-only PR reverts with the contract; the modal change (OQ-6) reverts with it, and an older web ignores the added list, so the web may lag the backend in either direction without breaking. `team_analytics` rows written as "no data" while this was deployed stay "no data" until recomputed, which is accurate.

## 8. Open questions

Owner of each: the product owner, answering in Linear before the contract stage. Each default applies otherwise.

- **OQ-1: Take SF-033 (cache key) into this work?** **Default: yes.** It is the cache this work writes unknown entries into, the fix is the key, and the operation's contract text states the key and changes anyway. Consequence: PAC-129's Inherited scope should move SF-033 here, and its AC-12 becomes a regression guard (identical scenario to AC-7).
- **OQ-2: Breaking the raw lookup's 200 shape.** **Default: accept the break.** Its only consumer is the MCP tool in the same repository, changed in the same PR; no web code calls it (§2.8). Alternative: keep the map and add a separate list of unreadable addresses beside it. That keeps old readers working but still shows an unreadable address with `[]` to anyone who reads only the map, which is the defect.
- **OQ-3: What the MCP free-slot tool reads.** **Default: always the user's own calendar, plus an optional attendee list.** Without some calendar the tool cannot say anything true (§0 item 1). Alternatives: own calendar only (no attendees: ticket item 3 then has nothing to report), or attendees only (a call without attendees would still read nothing).
- **OQ-4: The requester's own calendar unreadable in meeting suggestions.** **Default: fail with the existing 500.** Offering slots for someone whose own calendar could not be read is the defect itself. Alternative: name the requester among the unknowns and offer slots anyway.
- **OQ-5: MCP `create event` with an unknown attendee.** **Default: still book the first slot, and say who was unknown.** It matches item 4's "does not constrain" and the tool's purpose. Alternative: refuse to book and return the suggestions instead, which is safer but changes what the tool does for every external attendee.
- **OQ-6: Show the unknown attendees in the web's "Suggest a time" modal now?** **Default: yes**, one line under the slots, in the web PR that follows the types. Alternative: types only, UI later; the API then says something the user never sees.
- **OQ-7: Where the Microsoft fake lives.** **Default: a backend-test stand-in for Graph's `getSchedule`**, which needs the Outlook reader's address to be settable in tests (the plan's choice). An e2e Microsoft stand-in would need a Graph seam, Microsoft sign-in in e2e and an Outlook-connected e2e user (`e2e/SEAM-REQUIRED.md`); follow-up candidate.
- **OQ-8: Apply with an unreadable attendee: refuse or move-and-flag?** **Default: refuse (not moved, reported unverified).** Apply is the last point at which Paceday can avoid moving a meeting onto someone's commitment, and the preview never proposes such a move (§3.6 item 1), so a refusal only hits stale or hand-built proposals. Alternative: move and report "moved, unverified for U"; that needs a new place in apply's answer.
- **OQ-9: An inverted window, and an empty one (end = start), on both lookups.** **Default: both are a 400** with a fixed message; no provider call. Alternative: answer an empty result for an empty window. The provider itself refuses an empty range (the fake mirrors it: `e2e/fake-google/freebusy.go:31-33`), so a 400 is the honest answer.
