## BLOCKER

### B-1. AC-26 ("preview makes the same free/busy calls as today") contradicts §3.6 item 1 and AC-21

- **The claim.** `PAC-133.md:207` says "Preview makes the same calls as today". AC-26 (`:283`) says "for a preview, the number of free/busy calls **equals** today's for the same calendar". D-9 (`:353`) says the same.
- **Why it fails.** Today a meeting with an unreadable attendee U is proposed at the **first** candidate that passes the overlap filter and gains more than 30 minutes. The free/busy check reports "no conflict" (`compression.go:129-134`), and the loop `break`s at `:154`. Under §3.6 item 1 (`:200`) that candidate is rejected and "the next position is tried". For an attendee who is unreadable everywhere, **every** remaining candidate costs one more free/busy call (`:130` runs once per candidate). So for the calendar of AC-21 (`:273`), the call count rises strictly whenever today's proposal was not at the last candidate.
- **Consequence.** AC-21 and AC-26 cannot both pass on the same fixture. An implementer has to break one of them or game the count.
- **Resolution.** Restate §3.6 item 4, D-9 and AC-26 as a **bound**, not an equality. For example: preview makes at most one free/busy call per candidate position per meeting, which is today's worst case (a busy attendee already exhausts the candidates); apply makes at most one free/busy call and one event read per proposal. Make AC-26 assert the bound on the AC-21 fixture.
- **PAC-81.** Also state whether the larger typical preview cost still fits the 90 s budget. External attendees are the common case for "unreadable", so after this change, preview in week mode will walk every candidate for most meetings that have one. If the bound is accepted as is, say so; do not claim "no extra calls".

## MAJOR

### M-1. "Not mentioned → unreadable" mishandles Google group addresses

- **What Google returns.** `FreeBusyResponse` has a `Groups` member: "Expansion of groups". Each `FreeBusyGroup` lists the `Calendars` it expanded into, plus its own `Errors` (`google.golang.org/api@v0.292.0/calendar/v3/calendar-gen.go:2143-2147`, `:2065-2069`). A requested group id is answered through `groups`, and its members appear in `calendars`, keyed by member ids nobody asked for.
- **Today.** The Google reader copies every `calendars` entry (`freebusy.go:31-39`). Suggestions merge every entry of the map (`smart_schedule.go:76-82`), and compression's `hasConflict` scans every entry (`compression.go:288-297`). So **group members' busy time constrains slots today**.
- **What the spec says.** §3.1 (`PAC-133.md:158-162`) covers only "every address it was asked about". It says nothing about:
  - entries the provider returned that were not asked for (expanded members);
  - a group id that is answered under `groups` rather than mentioned in `calendars`;
  - a group-level error.
- **The risk.** A faithful implementation of "every requested address is readable-with-windows or unreadable" can drop the members' windows and name the group as unknown. That turns real busy time into "does not constrain", which is exactly §3.1 item 2's defect.
- **Resolution.** State what each consumer does with a group address and with returned-but-unrequested calendars, and that a member's reported busy time keeps constraining. Add an AC at the reader layer (a fake answer with a `groups` entry), and one at the suggestions layer.

### M-2. "Error plus busy windows → unreadable" discards busy time that was reported

- **The combination.** §3.1 makes such an entry unreadable (`PAC-133.md:162`). §3.2 item 1 gives an unreadable address "no busy windows" (`:168`). §3.5 item 1 says unreadable "does not constrain" (`:191`).
- **The result.** For suggestions, windows the provider reported as busy are dropped, and a slot may be offered on top of them. Today those windows constrain (`smart_schedule.go:76-82`). This is the one place where the change makes suggestions *worse* than today, and it contradicts §3.1 item 2 ("never shown or used as free").
- **Resolution.** Require that busy windows reported for an unreadable address still constrain (suggestions) and still block (compression), and are shown wherever the consumer shows windows (raw lookup). Or justify discarding them. Extend AC-2 (`:225`) to the suggestions layer.

### M-3. The spec's own rule breaks tests it pins as unchanged, through the shared engine double

  - `TestSmartScheduler_Suggest_WithMock` (`smart_schedule_test.go:137`).

- **Resolution.** §6 must say that the shared engine double changes to answer every requested calendar as readable (free unless told otherwise), and that the pinned tests change only in their double. Add a guard that the double cannot answer "free" for an address it was not told about.

### M-4. e2e: in the fake, a requester calendar with no events is "notFound", which collides with OQ-4's 500

## MAJOR

### P2-M1. MCP `create event`'s "book on acceptance" cannot book "that slot": the slot is not reproducible and is not carried

- **What the spec requires.** §3.5 item 4 (`PAC-133.md:298-301`) and AC-26 (`:525-530`) say: a first call returns "the proposed slot", and "a further call that explicitly accepts those unknown attendees books **the slot**" / "makes the create request **for that slot**".
- **Why that slot cannot be recomputed.** The tool is stateless, and its suggestions are not reproducible between two calls:
  - with no `preferred_date`, the range starts at `time.Now()` (`mcp/tools.go:42`, `:304-305`);
  - candidates step 30 minutes from the range start (`smart_schedule.go:100-105`).

  So the second call's first slot differs from the first call's (10:07 then 10:09). The unknown set and the readable attendees' busy time may also have changed in between.
- **What the spec leaves open.** It does not say:
  - whether the acceptance carries the slot (a tool argument), or the tool keeps state;
  - whether the booking re-checks the readable attendees;
  - what happens when the second call's unknown set differs from the one accepted, e.g. a new unknown V.
- **Consequence.** AC-26's second bullet is not implementable as written. An implementation that re-runs suggestions books a different slot than the one the model showed the user. One that books the carried slot unchecked can book over a readable attendee who became busy in the meantime.
- **Ownership.** This is also a product change to every MCP booking that has an external attendee (most will now take two calls). It was made as `[F]`, while the draft offered it to the owner as OQ-5's alternative.
- **Resolution.**
  - State what the acceptance call carries (the slot, and the accepted names).
  - State that booking re-verifies, and what it answers when the slot or the unknown set no longer matches. Booking must never happen past an unknown attendee who was not accepted.
  - Make AC-26 assert the booked slot is the one shown.
  - Either return OQ-5 to the owner with this default, or record why the factory may settle it.
