**One premise is wider than stated.** The ticket frames this as a gap in the generic list. It is really a **standing** gap. A domain that is on no list (a small ISP, a university alumni forwarder, a company's mailing-list alias) is open the same way to anyone whose address Google verified at it. Completing the list cannot close that. Only the account's standing can (§3.1).

## 1. Problem

Paceday groups accounts into an "organisation" by the domain of their email address. Members of an organisation can list every other member, with email, name and picture. They also share an organisation AI configuration, can try to become its SSO administrator, and see one another as "On Paceday" in Manager mode.

The grouping trusts the address's domain, not proof that the domain vouches for the person. Two consequences:

- **Consumer providers become fake organisations.** Anyone who signs in with an address at `orange.fr`, `web.de`, `hotmail.fr` or any of the many providers missing from the 21-entry list joins an organisation of every Paceday user at that provider, and can list them all. That is a bulk answer to "which of these people use Paceday", the same personal-data harm PAC-130 removed from Manager mode, for whole providers at once. The people listed get no notice and gave no consent.
- **Company organisations admit people the company never vouched for.** An address verified only by mailbox (a consumer Google account registered with a work address) joins the company's organisation. It sees the colleague list and the organisation AI configuration, can spend the organisation's AI key, and is bound by the organisation's "no personal keys" policy. PAC-71 already decided that such an address "resolves to nobody" at granting sites (`auth.yaml`, `CurrentUserResponse.addressStanding`). Organisation membership is a granting site that PAC-71 did not list.

The fix must keep the legitimate case: colleagues at a real company domain, vouched for by the company's identity provider, grouped together for SSO, organisation AI and the Manager badge.

### 2.1 How an organisation is created and joined

- **Created on first join.** `UpsertOrg` inserts the domain's organisation row, or renames it (`storage/orgs.go:19-28`). The name is derived from the domain (`domain.go:92-101`). Nothing else creates organisations. `CreateTeam` never sets `teams.org_id` (`storage/teams.go:52-57`), so that column is always null and nothing reads it.
- **Joined on every sign-in, whatever the standing.** The join rule reads only the domain. Every successful Google, Microsoft and SSO sign-in calls it, including a reach of an already-bound account (rule 1), for the account the identity is bound to and its stored address (`handlers_pac71_auth.go:186-189`). A failure is logged and reported, and the sign-in goes on (PAC-122 SF-071, `:198-204`).
- **Never left.** `SetUserOrg` only moves an account to the organisation it is told (`storage/orgs.go:53-79`). Nothing clears `users.org_id`, except deleting the organisation row (`ON DELETE SET NULL`, `migrations/007_organizations.up.sql:8`). A stored address never changes on sign-in (PAC-71 D-7), so membership, once made, is permanent.
- **Leaving ends organisation-AI consent.** When the organisation changes, all of the account's organisation-AI confirmations are deleted (PAC-87, `storage/orgs.go:41-52`, `:70-74`).
- **Which accounts carry which standing** (`storage/identity.go:67-72`; `storage/signin.go:289-300`):

| How the account was made or bound | Evidence | Standing |
|---|---|---|
| Google, address at the account's Google Workspace domain (`hd` equals the domain) | authoritative | domain_confirmed |
| Google, `gmail.com` / `googlemail.com` (`handlers_pac71_auth.go:83`) | authoritative | domain_confirmed (but these domains are on the consumer list) |
| Google, any other verified address (a consumer Google account on a non-Google address) | mailbox | unconfirmed |
| Microsoft, address on a domain verified in the user's Entra tenant (`:280-293`) | authoritative | domain_confirmed |
| Microsoft, otherwise | none | refused for a new account (`signin.go:146-148`) |
| Microsoft personal account (any `hotmail.*`, `outlook.*`, `live.*`) | n/a | refused until PAC-77 (`:261-266`) |
| SSO (OIDC) with a verified email at the provider's domain (`handlers_sso.go:168-187`) | authoritative | domain_confirmed |
| Legacy account (before PAC-71) not yet signed in since | none recorded | unconfirmed until its next sign-in binds it (migration 035) |

- **Standing is fixed once an account is bound** (revision 1, challenge B-1).
  - A sign-in that reaches a bound account never changes its address or standing (`storage/signin.go:175-179`, PAC-71 D-7).
  - A new identity for an address that a bound account carries is refused (rule 3, `:125-128`).
  - So an account bound on mailbox evidence stays `unconfirmed` for good. When its person later signs in with the company's Workspace or Entra identity for the same address, that sign-in is **refused**.
  - Only two operator steps change standing:
    - `reassign` (`storage/operator.go:184-260`, documented in `docs/operator/PAC-71-account-recovery.md` §3b) rewrites the binding and sets the standing from the evidence it is given;
    - `free-address` (`:120-140`) sets the standing to `unconfirmed` and replaces the address with a placeholder at `paceday.invalid`, **keeping `org_id`**. That leaves an organisation association whose domain no longer matches the address.

  Only an **unbound legacy** account gets a new standing from an ordinary sign-in: it binds under rule (a) or (b) with that sign-in's evidence.

- **Who can make an SSO provider or an organisation AI configuration for a domain.** Only a member who passes the admin step-up:
  - **Google:** `hd` equals the organisation domain and the account is a Workspace admin (`api/handlers_sso_stepup.go:612-630`).
  - **Microsoft:** the tenant has verified the organisation domain and the account holds a qualifying Entra role (`:637-668`).
  - **Break-glass:** an operator-listed address held `domain_confirmed` (`:780-785`).

  So **no configuration can exist on a consumer-domain organisation**, except one an operator made through break-glass.

### 2.5 Why the obvious fixes do not work on their own

- **Completing the consumer list** cannot be done. Consumer mail domains number in the thousands, change over time, and include ISPs, regional portals and forwarders (§1). Any domain the list misses is open again. The list is also shared with sign-in detection (C-8), so every entry changes another feature.
- **MX-based provider detection** (PAC-97, `auth/sso_detect.go:316-390`) answers only "Google", "Microsoft" or "choose". It cannot tell a consumer provider from a company:
  - every host under `google.com` counts as Google (`:367`), so Gmail and a Google Workspace company look the same;
  - the Outlook.com consumer host is deliberately not matched (`:370-375`), so `hotmail.fr` is "choose", like any self-hosted company;
  - a provider that hosts its own mail (`orange.fr`, `web.de`) is indistinguishable from a company that does;
  - a failed lookup is "choose", cached for a minute (`:57-63`), so membership would depend on DNS weather.
- **Restricting the list to "org admins"**: Paceday has no persistent admin role. The step-up gives a single-use, purpose-bound grant that lasts minutes (`migrations/030_sso_admin_stepup.up.sql:17-33`). An admin role would be a new feature, and it would remove the colleague directory that PAC-130 rule (b) relies on.
- **The public suffix list** says which part of a name is registrable. It says nothing about who provides mail there, so it does not answer this question.

## 3. Desired behaviour

### 3.1 Membership requires the domain to vouch for the person [F, D-1]

An account belongs to an organisation **only when all three hold**:
1. its standing is **domain-confirmed**: the identity provider that signed it in is the domain's own (Google Workspace for that domain, an Entra tenant that verified the domain, or the domain's SSO provider);
2. its address's domain is **not on the consumer list**; and
3. the organisation is **the one for its address's domain**: the organisation's stored domain equals `ExtractDomain` of the account's stored address (`domain.go:19-25`), exactly. That is the same derivation that named the organisation when it was created (`storage/orgs.go:84-88`). [revision 1, challenge B-2; definition fixed in revision 2, re-challenge N-1]
   - **One definition, used everywhere.** Every place that evaluates condition 3 in SQL uses **one** SQL expression for the address's domain: the read-time rule (if the plan puts it in SQL), the migration, and §7.1's query 1. A Go test asserts that this expression equals `ExtractDomain` over a fixture set that covers ASCII upper case, surrounding whitespace, a second `@`, no `@`, and upper-case non-ASCII letters. The PAC-75 comparison is not used here: it governs domains a client sends, not stored ones.
   - **No regression for subdomains.** Organisations have always been keyed by the full host that `ExtractDomain` returns, and `UpsertOrg` never renames a domain. So `mail.acme.com` and `acme.com` were always separate organisations, and condition 3 changes nothing for them.

Every other account belongs to **no** organisation.

Condition 3 is needed because production can store a mismatch: `free-address` keeps the association after replacing the address (§2.1), and the fixtures in §6 plant one. Without it, a confirmed account at one domain could sit in another domain's organisation and read its list and configuration. This is PAC-71's granting-site rule applied to organisation membership: "only a `domain_confirmed` address acts as a person at the granting sites".

Why this rule:
- **It closes the oracle without depending on a complete list.** At a consumer provider nobody can be domain-confirmed. Gmail is the exception and is on the list, and Microsoft personal accounts are refused. So no consumer-domain organisation has members, and none can be listed.
- **It keeps every legitimate organisation feature.** SSO and organisation AI are writable only through a step-up that already requires the domain's own identity provider (§2.1). The members it removes are exactly the ones those features could never have been configured for.
- **Admin- or SSO-only membership was rejected** (D-2). It would make organisations exist only after an admin had stepped up. Most company accounts would lose the colleague badge (PAC-130 rule (b)) for no privacy gain, since a Workspace or Entra account at the domain was already vouched for by the company.

**Accepted residual.** "Domain-confirmed" trusts the identity provider's own verification of the domain: Google's for `hd`, Microsoft's for verified domains, the configured IdP for SSO. PAC-71 rests on the same trust, and this spec does not re-litigate it. A consumer mail provider that hosts its customers on Google Workspace or Entra would form a real organisation. That is the domain owner's choice, as for any company.

### 3.2 The rule holds at every read; sign-in keeps the stored association in line [F, D-3]

**At every read.** No membership answer anywhere may treat as a member an account that does not satisfy §3.1 **at the moment of the read**, whatever stored the association: an older release, a fixture, an operator step or the restore rehearsal. This covers C-1 to C-7, including C-3b's AI spend and the step-up callback. How this is enforced is the contract's and the plan's choice.

**At sign-in.** After every successful sign-in the stored association is brought in line with §3.1:
- it **joins** its domain's organisation when the account qualifies;
- it **leaves** any organisation when the account does not.

An account that does not qualify never causes an organisation to be **created** or read. Whether to join is decided from the caller's own standing, domain and the list before anything keyed on the domain runs (AC-1).

**Leaving follows PAC-87's order.** It takes the same users-row lock as the organisation change and the AI confirmation (`FOR NO KEY UPDATE`, `storage/orgs.go:60`, `storage/org_ai.go:560-570`). It deletes every organisation-AI confirmation of the account in the same transaction, so a later rejoin asks again.

**Accepted residual.** An AI call that read its state before the leave committed may complete once on the organisation's key. This is the same window PAC-87 accepts for a configuration change.

**A failed membership update** keeps today's handling: the sign-in goes on, and the failure is logged and reported (SF-071).

**Standing is fixed once bound, so sign-in rarely changes membership** (challenge B-1). For a bound account, the outcome of the sign-in step changes only when:
- the consumer list changed;
- an operator step changed its standing or address (§2.1); or
- a stored association predates this rule.

The one ordinary case where it changes is an **unbound legacy** account whose next sign-in binds it with authoritative evidence. That account joins.

**An account bound on mailbox evidence never joins by itself.** This is PAC-71's own behaviour, and this spec does not change it. When its person signs in with the company's Workspace or Entra identity for the same address, the sign-in is refused (rule 3; AC-15). The recourse is the operator `reassign` with authoritative evidence (§2.1). After it, the account's next sign-in joins. A self-service path is follow-up F-3.

### 3.3 The consumer list: completeness is not a security property; only Microsoft's personal domains are added [F, D-4]

**Under §3.1, the list matters only for domains where a consumer address can be domain-confirmed** (revision 1, challenge N-1). At `orange.fr`, `free.fr`, `sfr.fr`, `wanadoo.fr`, `laposte.net`, `web.de`, `gmx.*`, `t-online.de` and every other provider that is not its users' identity provider, **nobody can be domain-confirmed**, except through an operator `reassign` or break-glass SSO. Adding such domains changes no membership. A provider the list misses is closed by the standing condition, not by the list. A consumer address can be domain-confirmed in only these cases:
- Gmail, already listed;
- Microsoft's personal-account domains, once PAC-77 accepts personal Microsoft sign-in;
- an operator step.

**The exact addition** is Microsoft's personal-account domains for the markets Paceday serves:
- `hotmail.fr`, `hotmail.co.uk`, `hotmail.de`, `hotmail.it`, `hotmail.es`, `hotmail.be`;
- `live.fr`, `live.co.uk`, `live.de`, `live.it`, `live.nl`, `live.be`;
- `outlook.fr`, `outlook.de`, `outlook.it`, `outlook.es`;
- `windowslive.com`.

Admission rule for each entry: when the plan is written, its MX resolves only to the Outlook.com consumer host (`*.olc.protection.outlook.com`, `auth/sso_detect.go:370-375`). An entry that fails this is dropped. The rule is mechanical, not a judgement.

The plan **records every dropped entry** with the MX answer it saw, and the **reviewer checks that record** against the diff (revision 2, re-challenge N-2). AC-2, AC-11 and AC-16 enumerate the list that ships, so a silent drop would otherwise go unnoticed.

PAC-77 needs these domains on the list before it can make them domain-confirmed. That is pinned by AC-2's "every entry".

**Not added: the ISP domains the ticket names** (`orange.fr`, `free.fr`, `laposte.net`, `web.de`, `gmx.de` and others).
- Under §3.1 their only effect would be on sign-in detection: `generic` instead of the MX path's answer (C-8).
- Changing what those users are offered at sign-in is a PAC-98 product question, not a security fix.
- AC-1 proves that an unlisted provider is closed.

**Rejected** (D-4):
- **Vendoring a public free-mail list** (thousands of entries):
  - such lists are compiled for sign-up filtering and mix in disposable and business domains;
  - here a false positive costs a real company its organisation, SSO routing and organisation AI;
  - under §3.1 a false negative costs nothing;
  - every entry would also change detection.
- **MX-based classification**, for the reasons in §2.5. PAC-97's detection is not reused for membership.

**Detection** for the added domains changes from the MX path (today `choose`, since the consumer host is deliberately not matched) to `generic`, like `outlook.com`. PAC-98's per-entry table gains a row for each one (`auth/pac98_detect_test.go:66-89`). They stay `generic` until PAC-77.

**A future list change** is enforced at once by §3.2's read-time rule. It ships with a clean-up migration of §3.5's shape, under the same gate and the same set-equality test (D-10).

### 3.4 The member list: kept, narrowed by the rule, and honest about failures [F, D-7, D-8]

- The list returns the accounts of the caller's organisation under §3.1. It is the same set as PAC-130 rule (b), as today.
- A caller in no organisation (every consumer-domain account, every unconfirmed account) gets the empty list. The answer is the same whether zero or many accounts exist at the caller's domain (AC-1).
- A caller whose row **cannot be read** (a fault) gets the 500, not the empty list (API-047, SF-075). A failed member read is already the 500 (`handlers_org.go:33-38`).
- A caller whose row **does not exist** gets 200 `[]` (revision 1, challenge N-3). This is an account deleted under a live session, which the middleware lets through and the session guard marks stale (`api/middleware.go:125-142`). Such an account belongs to no organisation, so the empty list is the true answer and reveals nothing.
- The listed fields do not change. `provider` is documented as the three values written today.
- **Why keep it rather than remove it** (D-7):
  - PAC-130 rule (b) is justified by "the viewer can already read this in the member list". Removing the list would turn (b) into a per-address existence signal backed by nothing the viewer can see. Keeping (b) without the list would contradict PAC-130's principle, and dropping (b) would remove the badge for same-company colleagues.
  - After §3.1, the list is the directory of colleagues the company's own identity provider vouched for. That is the disclosure a company directory already makes.
  - **Removal stays the owner's call** (OQ-3). It costs nothing to consumers, because there are none, but it forces a PAC-130 amendment.

### 3.5 Existing memberships that fail the rule end at deploy [F, D-5, D-6]

A migration ends, at deploy, every stored membership that fails §3.1:
- **every account whose standing is unconfirmed**, including unbound legacy accounts (OQ-2):
  - an **unbound legacy** account rejoins at its next sign-in, if that sign-in binds it with authoritative evidence;
  - an account **bound on mailbox evidence** never rejoins by itself. Its standing is fixed (§3.2), and the recourse is the operator `reassign`;
- every account whose address's domain is on the consumer list;
- every account whose organisation is not the one for its address's domain (§3.1 condition 3).

For each such account, its organisation-AI confirmations end (PAC-87's leaving rule).

**The migration's consumer set is the release's list.** The domains it treats as consumer are exactly that release's `GenericDomains()`, enumerated. A Go test compares the two (AC-16). The migration holds the set as a SQL literal while the list lives in Go, which is why the test is needed.

**The gate** (challenge B-4). The detach is unconditional **only once the gate is clear**:
- If any SSO provider or organisation AI configuration exists for a domain on the consumer list, the migration **aborts**, changes nothing, and names the domains.
- It does not skip that domain or proceed partially, because either would leave a configuration of unclear provenance (only break-glass can create one, §2.1) attached to a domain whose members were silently detached.
- The release manager runs the same check before deploy (§7). An abort is therefore a missed pre-check, not a surprise.

**Effect on PAC-71 rule (b)** (revision 1, found while answering B-2).
- PAC-71's emptiness check counts an organisation-AI confirmation as data of the account (`storage/emptiness.go:67`).
- Deleting a detached **unbound legacy** account's confirmations can therefore make it empty, so it binds under rule (b) on authoritative evidence. That is the same "data, not rule" effect as PAC-130 D-12.
- It is intended: the confirmation was consent to a membership that no longer exists.
- An account that wrote an organisation AI configuration (`org_ai_write`, `:66`) keeps that data and stays non-empty.

**PAC-130's kept roster links** (migration 042) whose only justification was organisation co-membership (`042_manager_member_link_erase.up.sql:24-27`) are **left as they are** (challenge N-5):
- they are write-never and read by no answer (PAC-130 §3.5);
- their only reader is PAC-71's emptiness check (`storage/emptiness.go:49`), where keeping them is the conservative direction;
- erasing them is part of follow-up F-2's data-minimisation pass.

What the migration **keeps**:
- **Organisation rows** are not deleted, even when they are left with no members. Deleting a row would cascade to the operator record (`sso_events`), step-up grants, and organisation AI configuration and confirmations (`migrations/030:23`, `:42`; `031:18`, `:39`). A row with no members is unreachable: every reader reaches an organisation through a member.
- **Organisation AI configurations and SSO providers.** None can exist on a consumer-domain organisation except by break-glass (§2.1). On a company organisation they were written by a verified admin and stay valid for the remaining members.
- **Unused step-up grants** of detached accounts. They expire within minutes, and a non-member cannot consume one (C-5's gate step 1).

Effects that follow, intended and listed in the release note (§7):
- **A detached account that followed its organisation's AI** reads `nothing_configured` (row 6) until it chooses a key or rejoins. A detached account bound by "personal keys not allowed" is no longer bound.
- **PAC-130 rule (b) narrows** (§3.6).
- **G-3 residual.** An organisation row created by an account that is now detached keeps its `created_at`. A remaining member can still see when the first Paceday account at their own company's domain signed in. Accepted: it is their own company.
- **Admin continuity** (challenge N-7, checked):
  - Paceday has no persistent admin, and grants are single-use and last minutes.
  - An account bound on mailbox evidence could never pass the step-up's identity check at Google anyway (`handlers_sso_stepup.go:795-806`). The only admins detached are therefore unbound legacy accounts, which rejoin when their next sign-in binds them with authoritative evidence.
  - Organisation rows, tenant pins, SSO providers and AI configurations survive (D-6). An organisation left with no members gets them back at the next qualifying sign-in, through `UpsertOrg`'s conflict path.
  - Domain-keyed SSO sign-in is unaffected.

### 3.6 Effect on PAC-130's badge [F, D-9]

Rule (b) stays defined as "the accounts the member list returns to the viewer". After this spec:
- a viewer who is not domain-confirmed, or who is at a consumer domain, has an empty (b). For them only rule (a), shared teams, can make an address visible;
- an unconfirmed account at the viewer's own company domain is no longer in (b). Its address takes the estimate branch unless the two share a team.

What does **not** change:
- **No Paceday figures move.** Organisation-only accounts never got figures (PAC-60). A row that leaves (b) moves from PAC-130's no-read branch (flag and "no data") to the estimate branch, the same answer as for an address no account holds. That is PAC-130 §3.2's consent-inversion case, already accepted there (OQ-2 of PAC-130).
- **Byte-identity stays the test.** For an address outside (a) and (b), the answers are the same whether an account holds it or not (PAC-130 AC-4).

PAC-130 statements that become false, which the contract stage amends with a pointer to PAC-148:
- `is_paceday_user`'s "until then (b) carries the list's exposure for consumer domains" (`openapi.yaml:13417-13419`);
- PAC-130 AC-10's sub-case "an unconfirmed carrier … in V's organisation" (`docs/specs/PAC-130.md:349`). After PAC-148 such a carrier is not in V's organisation, so the case shows the estimate. Its test (`api/pac130_test.go:631-632`, `uOrg`) is rewritten, not deleted.

### 3.7 Web

No web change is expected. The web learns membership through three things (§2.4):
- `ai_status.inOrganization`;
- the organisation AI read;
- the step-up options' membership 403.

All three already handle a non-member: they hide the organisation section, the "organization" option and the step-up entry, and they show row 6 for a stale "organization" choice. §6 pins this as a regression, and AC-13 proves it end to end. The types regenerate for the contract's description changes and the `provider` enum.

### 3.8 Compatibility

- **Old clients**: every answer keeps its shape. More accounts get the empty list, no `org` on `/api/auth/me`, `inOrganization: false`, and the existing 403 `org_membership_required` on organisation operations. All of these are documented answers today.
- **New `500`** on the member list when the caller cannot be read. It is already documented for a failed member read.
- **Detection**: the added domains answer `generic`, a documented value.

## 5. Explicitly out of scope

- **A persistent organisation-admin role**, or admin-only membership (D-2). The step-up stays the only admin proof.
- **Removing the member list** (OQ-3; D-7 keeps it).
- **A self-service way for a bound account to upgrade its standing** (for example, a mailbox-bound account proving its address through the company's Workspace or Entra identity). PAC-71 fixed standing at binding, and the operator `reassign` is today's recourse (§3.2). Follow-up **F-3**.
- **Adding consumer ISP domains** (`orange.fr`, `free.fr`, `laposte.net`, `web.de`, `gmx.*` and others) to the list. Under D-1 they change no membership, only what sign-in detection offers, and that is a PAC-98 product question (§3.3).
- **Reconciling the free/busy personal-domain list** (`engine/freebusy_service.go:18-29`, 10 entries) with the consumer list. It decides only whether Paceday asks the viewer's provider for free/busy, never membership or account existence. Follow-up **F-1**.
- **Deleting organisation rows with no members**, the G-3 `created_at` residual, and PAC-130's kept roster links that are justified only by organisation co-membership (§3.5). Follow-up **F-2**, the data-minimisation pass PAC-130 §7 already opened.
- **PAC-77** (personal Microsoft sign-in). This spec only requires that Microsoft's personal-account domains are on the list before PAC-77 can make them domain-confirmed. That is pinned by AC-2's "every entry", and it is a stated constraint on PAC-77.
- **Re-examining how identity providers verify domains** (Google `hd`, Entra verified domains). That is PAC-71's premise, accepted here.
- **`teams.org_id`**, which nothing writes or reads (§2.1).
- **The scheduling-link co-host oracles** (PAC-130 O-10, O-10b), which are PAC-130's F-1.

## 7. Rollback

- **Migration.** It only clears memberships and deletes organisation-AI confirmations (AC-7). The down migration is a no-op and **cannot restore** them. That is acceptable, because each cleared membership was the leak.
  - It runs under PAC-116's automatic stop-migrate-start (`docs/runbook.md:98-123`).
- **If the in-migration gate aborts** (revision 2, re-challenge B-1).
  - **Which gate is primary.** The **primary** gate is §7.1's query 2, run by the release manager before anything is deployed. It stops the release with nothing touched. The in-migration abort is **defence in depth** for a skipped or stale pre-check.
  - **What an abort leaves** (AC-17):
    - **no data row is changed**, because the file's work is one transaction and it rolled back;
    - `schema_migrations` is at the **new** version with `dirty = true`, because golang-migrate marks it dirty before running the file (`storage/migrate_when_stopped.go:543-553`; `docs/runbook.md:176-178`).
  - **Neither image starts on that state.** The new backend and the previous image both refuse a dirty database (`docs/runbook.md:345-349`), so "roll back to the previous image" alone does **not** work.
  - **Recovery**, one of:
    1. **Force to the previous version** (preferred, because no data changed). With every backend stopped, set `schema_migrations` to the previous version with `dirty = false`. That is golang-migrate's `force <previous version>`, and plain SQL `UPDATE schema_migrations SET version = <previous>, dirty = false` is equivalent. Check it with the runbook's `SELECT version, dirty FROM schema_migrations` (`docs/runbook.md:846`). Then start the **previous** image, resolve the offending SSO provider or organisation AI configuration as the owner decides (§7.1), and redeploy the new image. The plan adds this procedure to the runbook, next to "Rollback on the same host".
    2. **The runbook's "Rollback on the same host"** (`docs/runbook.md:343` onwards): set the volume aside, restore the pre-deploy backup, deploy the previous version. This is always valid, but heavier than needed here.

  Forcing is safe **only** because this file's changes are known to have rolled back. The procedure says not to use it after any other failed migration, and never while a migration is still running (`docs/runbook.md:160-161`).
- **Image rollback.** The previous backend joins on the domain alone again, so squatters rejoin at their next sign-in and the oracle returns. That is expected on a rollback. Accounts that do not sign in stay detached, which is the safe direction.
- **Web-only rollback**: nothing to roll back (§3.7).

### 7.1 Pre-deploy gate (release manager, before the migration runs)

`:listed` is the release's consumer list, the same set as the migration's (AC-16), passed as a lower-case `text[]`.

**Query 1, memberships that will end, per organisation domain** (reported to the owner: OQ-2):

```sql
SELECT o.domain,
       count(*) FILTER (WHERE u.address_standing <> 'domain_confirmed')                    AS unconfirmed,
       count(*) FILTER (WHERE o.domain = ANY(:listed))                                      AS consumer_domain,
       count(*) FILTER (WHERE lower(substr(u.email, strpos(u.email, '@') + 1)) <> o.domain) AS other_domain,
       count(*)                                                                              AS ending
  FROM users u JOIN organizations o ON o.id = u.org_id
 WHERE u.address_standing <> 'domain_confirmed'
    OR o.domain = ANY(:listed)
    OR lower(substr(u.email, strpos(u.email, '@') + 1)) <> o.domain
 GROUP BY o.domain
 ORDER BY ending DESC;
```

**Query 2, configurations on listed domains** (the stop condition):

```sql
SELECT 'sso_provider' AS kind, lower(domain) AS domain FROM sso_providers WHERE lower(domain) = ANY(:listed)
UNION ALL
SELECT 'org_ai_configuration', o.domain
  FROM org_ai_configurations c JOIN organizations o ON o.id = c.org_id
 WHERE o.domain = ANY(:listed);
```

**Stop condition:** query 2 returns any row. The release stops, and the release manager reports the rows to the owner. Such a configuration can only have been made through break-glass (§2.1). Its fate (delete it, or drop the domain from the list) is decided before release, never by the migration. The migration applies the same check and aborts on it (AC-17), so a skipped pre-check cannot detach anyone silently.

The domain expression in query 1 is a placeholder for the **one** SQL expression that §3.1 condition 3 defines and tests against `ExtractDomain`. Query 1 and the migration use that expression verbatim (revision 2, re-challenge N-1).

### 7.2 Release note

- **Who leaves their organisation:** accounts whose address is not confirmed by their domain's identity provider. That is:
  - accounts made with a consumer Google account on a work address;
  - accounts not signed in since PAC-71;
  - any account whose organisation is not the one for its address's domain.

  They lose the organisation AI: they see "nothing configured" until they choose their own key. They disappear from colleagues' member lists and from the Manager "On Paceday" badge unless they share a team.
- **Legacy accounts** (not signed in since PAC-71) rejoin automatically at their next sign-in with their company account, and are asked to confirm the organisation AI again.
- **Accounts bound on mailbox evidence do not rejoin, ever, on their own.** Their standing is fixed (PAC-71). A sign-in with the company's Workspace or Entra identity for the same address is **refused**, because the address belongs to the already-bound account.
  - **Support** handles these with the operator `reassign` (`docs/operator/PAC-71-account-recovery.md` §3b), with authoritative evidence. The account then rejoins at its next sign-in.
  - The runbook's "Account recovery" section points at this case.
  - Expect these requests after a company adopts Google Workspace or Entra (OQ-1).
- **The erase is irreversible.** An operator who wants full rollback fidelity snapshots the account-to-organisation association and `org_ai_confirmations` before deploy.
- **Before deploy**, run §7.1. Report query 1 to the owner, and stop on query 2.
- **Sign-in detection** answers `generic` for the added Microsoft personal-account domains.
- **Legacy accounts may become bindable.** Deleting a detached unbound legacy account's organisation-AI confirmations may leave it empty. It then binds on authoritative evidence at its next sign-in (PAC-71 rule (b)). This is expected, not a support incident, as for PAC-130's link erase (`docs/runbook.md:336-341`). (Revision 2, re-challenge N-3.)

## Challenge — 2026-11-19

**Verdict**: REVISE (reject in the role file's terms). The direction holds: D-1 closes the ticket's oracle without needing a complete list, and D-7, D-8 and D-9 are sound. Four blocking items must be fixed in the body before contract work. Read against clockwise-like `ddd2cd2` (spec head `b81e912`), smart-calendar-flow `5920bd6` and the Linear issue (no comments).

### Blocking

1. **Standing never changes after binding, so the promised remedy for mailbox-bound accounts does not exist.**
   - `reachBound` never rewrites `address_standing` ("The stored address and standing are never changed", `storage/signin.go:175-179`). Rule 3 refuses any new identity for an address that a bound account already carries (`storage/signin.go:125-128`).
   - So U, a consumer Google account bound on mailbox evidence to `u@acme.com`, can never become domain-confirmed. When U later signs in with the real Workspace account for the same address, that sign-in is **refused**. It is not a rejoin.
   - The only route to confirmation is the operator step `ReassignAccount` with authoritative evidence (`storage/operator.go:184-260`).
   - Three statements in the body are therefore false for every non-legacy account they cover:
     - §7's release note: "until they … sign in again with their company account".
     - §3.5's "rejoins at its next sign-in if that sign-in confirms it".
     - D-3's framing that membership "is decided again" at sign-in. Standing is fixed, so a re-decision can only flip on a consumer-list change or an operator step.
   - OQ-1 also misses a real owner consequence. When a company moves to Workspace or Entra **after** staff signed up with consumer Google accounts on their work addresses, those accounts stay outside the organisation for good, and they cannot even sign in with the new company identity, unless an operator reassigns them.
   - **Resolves it:**
     - §3.2, §3.5 and §7 state that standing is permanent for a bound account and name the recourse, which is the operator reassign, or open an OQ for a self-service path.
     - The release note says that support must handle these accounts.
     - OQ-1 includes the "company adopts Workspace later" case.
     - An AC pins it: U, after detach, signs in with the Workspace identity for the same address. The expected answer is the refusal, not a rejoin.

2. **§3.2's "whatever stored it" has no AC for the ticket's own oracle or for G-4's actual harm, which is spending the key.**
   - AC-4's planted variant repeats only these checks: the org-AI read, confirm and patch; the SSO list, options and create; the settings read; the key choice; and rule (b). It does not plant:

### Blocking

1. **An abort does not "change nothing", and the previous image does not start on what it leaves.**
   - Migrations run through golang-migrate (`storage/migrate_when_stopped.go:543-553`). It marks the version dirty **before** running the file, and the mark stays when the file fails.
   - The runbook says so itself:
     - `docs/runbook.md:176-178`: "that file's changes roll back and the version stays dirty";
     - `:345-349`: the backend "refuses to start" on a dirty database, `restore.sh` refuses to restore over it, and recovery is to set the volume aside and restore from backup.
   - So when the gate trips:
     - AC-17's "no row changes" is false for `schema_migrations`, which is left dirty at the new version.
     - §7's "the documented rollback to the previous image applies" is wrong. The previous image refuses the dirty database too.
     - The deliberate safety net therefore turns into a restore-from-backup incident, even though no data changed.
   - **Resolves it.** Say what an abort leaves and how to recover, then pin it:
     - Either an abort leaves the database in a state the previous image starts on (version not advanced, not dirty),
     - or §7 states the dirty state and names the exact recovery: the runbook's "Rollback on the same host", or a documented `force` to the previous version, which is safe because the file's changes rolled back.
     - AC-17 asserts that state: which `schema_migrations` row, and whether it is dirty, besides "no other row changes".

### Non-blocking

1. **Condition 3 should use the same derivation that named the organisation.**

So `mail.acme.com` and `acme.com` were always separate organisations, and condition 3 changes nothing for them.
   - **The comparison is under-specified.** §3.1 compares "as PAC-75 compares domains": ASCII case only, no trimming (`domain.go:58-74`). But `organizations.domain` was written by `ExtractDomain`, which trims and lower-cases with Unicode rules (`domain.go:19-25`). §7.1's query uses Postgres `lower(substr(...))`, a third derivation.
   - For an address whose domain has upper-case non-ASCII letters, sign-in would re-associate the account each time while the read-time rule excludes it.
