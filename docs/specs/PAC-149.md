## 1. Problem

Any Paceday user can learn whether **any** email address belongs to a Paceday account, and for those that do, learn the account's internal identifier, display name and picture. They create a scheduling link (anyone can), then invite the address as a co-host, either one at a time or five per request in the link editor's co-host list. The answer says "user not found" or "invited", and the link's host list then shows the person's name and picture.

This is the same personal-data harm PAC-130 removed from Manager mode and PAC-148 removed from the organisation member list:
- whether someone uses Paceday is personal data (an employer checking staff, a stalker checking a person, a phisher filtering a leaked address list to Paceday customers);
- the person looked up gets no notice and gave no consent;
- nothing limits the rate.

After PAC-130 and PAC-148 this is the remaining cheap, unlimited existence oracle the factory has found. Both earlier specs deferred it here (PAC-130 §5, F-1; PAC-148 §5).

The legitimate need to keep: an owner invites a colleague to co-host; the colleague accepts in Paceday; from then on the link's slots respect the colleague's calendar. Today that works only if the colleague already has an account. After this change it must work the same whether they have one or join later.

### 2.1 How a co-host is created today

- **Single invite.** Owner check (`:991-994`), then `ConfirmedHolder(body.Email)` (`:1002`). No holder → 404 "user not found", nothing written (`:1007-1009`). A holder → the locked write: an existing row of that account is returned unchanged with 200 (PAC-61); the owner's own account gets the owner row; at 5 or more non-owner rows the 422 (PAC-120); otherwise a new `pending` row and 201 (`scheduling_links.go:838-878`). The 201/200 body is the raw row: `id`, `link_id`, `user_id`, `status`, `invited_at`, `responded_at`.
- **Co-host list.** Under the link's lock, the host set is read with each host's stored address (`readLinkHostSet`, `:1243-1263`). Each distinct entry (ECMA trim, database `lower()`) gets **one carriers lookup** (`carriersOfTrimmed`, `storage/identity.go:135-154`), and the outcome is decided in this order (`lookupCoHost`, `:1392-1425`):
  1. `own_address`: the single domain-confirmed carrier is the owner;
  2. `already_host`: some carrier, at any standing, is a non-owner host (the PAC-71 keep rule);
  3. `invited`: a single domain-confirmed carrier that is not a host gets a `pending` row;
  4. otherwise `not_added`: nobody, an unconfirmed carrier, or several carriers, undistinguished.

  A list longer than 5 is refused (422) at the first entry that reaches no current host or the owner (`:1326-1338`). Non-owner hosts carried by no entry are removed (`removeCoHostsExcept`, `:1431-1460`), and the answer lists them with their account id, address and status. `invited_count` counts distinct accounts (contract `SchedulingLinkCoHostChanges`).
- **No email** is sent by either path (§0).
- **Accept / decline** match only a host row keyed by the caller's account; no row → 404 (PAC-30).
- **Deleted links.** Delete is a soft delete with no restore (`DeleteSchedulingLink`, `scheduling_links.go:224-236`; PAC-40 D-2). Host rows of a deleted link are kept (the deletes in `RemoveLinkHost` and accept/decline require a live link, `:423-458`), and pending invitations to it are omitted from the invitation list (`:397-405`). PAC-40's scheduled erasure (daily, `main.go:150-154`, `:436`) removes booker data only, and only for a deleted link that has an un-erased booker and whose last booking ended at least 90 days ago (`ListBookerErasureDue`, `storage/booker_erasure.go:51-64`; `BookerRetention`, `:24`). A deleted link with no bookings, or whose bookers were already erased, is never revisited. Nothing ever erases host rows.
- **Leave** (`POST /{id}/leave`, `handlers_scheduling_links.go:1100-1131`; `RemoveLinkHost`, `scheduling_links.go:423-441`) has **no status filter**: a pending or declined invitee can leave, which deletes their row (204). The owner gets 400 "owner cannot leave link"; no row is the 404 (PAC-30).
- **Accept / decline** update the caller's row **whatever its status** (`RespondToHostInvite`, `:443-458`): a declined host can later accept, and an accepted one can decline.
- **Roster order.** Both roster reads order by `invited_at` only (`GetLinkHosts`, `scheduling_links.go:339-343`; `readLinkRoster`, `:1562-1567`). Every row written by one list save gets the same transaction `NOW()`, so their relative order is unspecified.
- **Address normal forms differ by path.** The list trims ECMA-262 `\s` and compares with the database `lower()` (`TrimECMASpace`, `lowerAll`, `:1268-1300`, `:1313-1325`). The single invite checks blankness with `strings.TrimSpace` (`handlers_scheduling_links.go:995`) and resolves with `CarriersOf`, which trims with `strings.TrimSpace` (`storage/identity.go:127-129`). The team and Manager paths trim, lowercase in Go and require `net/mail` to parse the address unchanged (`normalizeManagerEmail`, `api/handlers_manager.go:871-881`).
- **Who holds a pending row today.** Not only holders. Migration 035 gave every pre-PAC-71 account `address_standing = 'unconfirmed'` by default (`storage/migrations/035_identity_binding.up.sql:26`), so pending rows made before PAC-71 can point at an unbound legacy account (unconfirmed until its next sign-in binds it). An account can also stop being a holder after its row was made: a legacy case-variant account carrying the same address, or an operator `free-address`, which replaces the address with a placeholder and sets the standing to unconfirmed (`storage/operator.go:126-138`). Accept and decline today ignore standing: they match the row by account.
- **Who sees the roster.** The owner and accepted co-hosts (PAC-25, `:723-737`). Public pages show **accepted** hosts only (`api/handlers_booking.go:97-118`, `:138-150`), so pending invitees never appear publicly.

## 3. Desired behaviour

### 3.1 The rule: an invitation is to an address, and nothing the inviter sees depends on accounts until the invitee acts [F, D-1, D-2]

From the owner's side, inviting a co-host is recording "I invited this address". The server never looks the address up to find an account, on either the single invite or the co-host list. Everything the owner (or an accepted co-host) can observe about a **pending** invitation is a function of the address the owner typed and of the link, never of whether an account carries it:

- the status code, body and error text of the single invite;
- each list entry's outcome and the counts;
- how the pending invitation appears in every link read, and in the removal report;
- the co-host limit;
- the work the server does (§3.6).

"Indistinguishable" has PAC-130's meaning: same status and `Content-Type`, bodies byte-identical after replacing the address and the server-assigned invitation id and timestamps with fixed tokens.

### 3.2 What each request answers [F, D-1, D-7]

**Single invite**, for a live or paused link the caller owns, with a well-formed address:
- **new address** (not the owner's, not already invited or a host of this link): a pending invitation is recorded and the answer is "created", carrying the invitation as §3.4 shows it, and **no account identifier**;
- **an address already invited or already a host** of this link (compared as the co-host list compares, ignoring case): "unchanged", with that entry as the link reads show it, and the existing status kept (PAC-61);
- **the owner's own address**: "unchanged" with the owner's own entry, as today; decided by comparing with the owner's stored address, not by a lookup;
- **the link already has 5 co-hosts** and the address is new: the 422 limit refusal, for **every** new address alike;
- **a malformed address**: refused as a validation error, nothing written. Well-formed means what the team invitation already requires (the address normalisation used by the team and Manager paths).

The "user not found" refusal no longer exists. The unknown-or-deleted-link 404, the 403, the 400s and the 500s are unchanged.

**One normal form for addresses** (revision 1, N-5), on both paths, for validation, storage and comparison:
- **trim**: leading and trailing ECMA-262 `\s` characters (the list's set today, PAC-67); the single invite moves to it;
- **blank** after the trim: the existing refusals (single invite 400 "email is required"; list 422 blank entry);
- **well-formed**: the trimmed address, lowercased, parses as a bare address exactly as the team invitation requires;
- **stored and shown**: the trimmed address with its letter case kept;
- **compared** (duplicates, `already_host`, `own_address`, the keep rule, the invitee match): with the database's `lower()`, as the list and the carriers read do today.

**Co-host list**, each entry, in today's order:
1. `own_address`: the entry equals the owner's stored address, ignoring case;
2. `already_host`: the entry equals the address of a current non-owner entry of the link (pending invitation, accepted or declined host), ignoring case; that entry keeps its status;
3. `invited`: otherwise, a well-formed address gets a new pending invitation;
4. `not_added`: otherwise, the entry is not a well-formed address. That is now its only meaning, so the web may say so (D-7).

Counts: `invited` counts distinct new invitations (entries identical after the trim and lowercasing count once, as today). The over-5 rule refuses a list longer than 5 at the first entry that matches no current entry and is not the owner's address. Removal removes every non-owner entry whose address matches no listed entry.

The keep rule (PAC-71 AC-43, "a host listed by any letter case of an address their account carries is kept") is preserved: for a host, "an account carrying the address" and "the host's address equals the entry ignoring case" are the same test (the carriers read compares `lower()` of the stored address).

### 3.3 What is recorded for an address with no account, and what happens when they join [F, D-3, D-4, D-5]

**Recorded**: one pending invitation per (link, address), holding the address as typed (trimmed), the time, and nothing else. It is recorded **the same way whether or not an account carries the address**: the server does not know and does not ask.

Why something must be recorded for a nobody: the owner's host list must show a pending entry for every invited address. If nothing were recorded for a nobody, the next link read would show the holder's entry and not the nobody's, which is the oracle again one read later. "Accept and store nothing" was therefore rejected.

**Who can see and act on a pending invitation** (the invitee side). The address-to-account match happens **only when an invitee reads their own invitations or answers one**, and only for the invitee's own address:
- An account sees, and can accept or decline, a pending invitation exactly when it is the **holder** of the invitation's address at that moment (PAC-71: accepting gives the link access to the account's calendar, so acceptance is the granting site). An unconfirmed carrier, or either account of a case-collision pair, sees nothing and gets the existing 404 when it tries to answer.
- **An account that already has an entry on the link, or owns it,** never sees a pending invitation of that link in its list. That can happen only after an operator changed an address. Its accept and decline act on its own entry exactly as today and, in the same write, remove a pending invitation of its address on that link; the owner gets the 404. Never a 500 from a uniqueness rule (revision 1, N-4).
- **Someone who joins later** sees the invitation as soon as their account becomes the holder of the address (first sign-in with authoritative evidence for that address, or a later bind under PAC-71). Nothing is copied or converted at sign-up: the match is made at read time, so there is no sign-up hook and no new path at sign-in.
- **No email** is sent, to anyone, as today (D-4, OQ-2). Paceday does not become a relay that mails arbitrary addresses on a stranger's behalf. The owner is told plainly that Paceday does not notify the invitee (§3.7).

**When the invitee answers:**
- **Accept**: the invitation becomes an accepted host bound to that account. From then on the link's slots respect that account's calendar, exactly as an accepted co-host today. The co-host count is unchanged (the invitation was already counted).
- **Decline**: the invitation becomes a declined entry bound to that account; it keeps counting toward the limit, as a declined host does today (PAC-120).
- **Leave** removes the caller's own entry, as today, at any status (revision 1, B-2). On a **pending invitation**, leave by the address's current holder removes the invitation (204), exactly as a pending invitee can leave today. Anyone else gets the existing 404, and the owner the existing 400. Leave is under the same holder match as accept and decline (D-5), and a failed match is the 500 (D-10). The owner sees the invitation disappear; that is the invitee's own act, as with a decline (OQ-1).

**Lifetime.** A pending invitation lasts until the owner removes it, the invitee answers it, or the link is deleted; it does not expire (OQ-3), as a pending host row does not today. **Deleting the link erases its pending invitations, in the delete itself, with no delay** (revision 1, B-1). After the delete nothing can show, answer or restore them: delete is final and no restore exists (§2.1), and the archive shows no hosts. Unlike accepted hosts, they relate to no booking, so PAC-40 D-2's reason for keeping host rows does not apply to them. Tying them to the booker erasure was rejected, because it never runs for a deleted link with no bookings, or whose bookers were already erased. An invitation written concurrently with the delete is ordered by the link's lock (PAC-101): if it commits first, the delete erases it; if the delete commits first, the invite is the existing 404. Accepted and declined entries keep PAC-40 D-2. Pending invitations on links already deleted at deploy are dropped by the migration (§3.5).

**An account carrying the address is deleted** while the invitation is pending: nothing changes, because the invitation never pointed at the account. (Today the pending row cascades away, which is itself a small signal to the owner.)

### 3.4 How entries appear in the link reads and the removal report [F, D-6]

| Entry | What the owner and accepted co-hosts see |
|---|---|
| **Pending invitation** | the address as typed, status `pending`, no account identifier, no name, no picture |
| **Accepted host** | as today: account identifier, the account's stored address, name and picture. Accepting is the invitee's consent to be shown. |
| **Declined** | the address, status `declined`, **no name and no picture**; an account identifier only where the shape requires one (contract stage). The decline itself is the invitee's act, so that the entry shows "declined" is a disclosure the invitee chose (OQ-1). Name and picture are not part of that choice. |
| **The owner** | as today |

The removal report follows the same table: a removed pending invitation is reported by address and status with no account identifier.

**Order** (revision 1, N-1). Entries are listed by invitation time. Entries made by the same save keep the order of their first entry in the request. Any remaining tie is broken by the address, compared as the list compares. Nothing in the order depends on accounts. An entry keeps its position when its invitee answers.

Public pages are unchanged: accepted hosts only.

### 3.5 Invitations that exist at deploy [F, D-8]

Today's pending host rows were **not** all made for a holder (§2.1; revision 1, B-3). Rows from before PAC-71 can point at an unbound legacy account, and an account can have lost holdership since. At deploy:
- on a live or paused link, a pending row whose account carries a real address becomes a pending invitation for that address, keeping its invitation time and position, and the account-keyed row is removed;
- a pending row whose account carries an operator placeholder address (`free-address`) is **dropped**: the operator freed that address because the account was not its owner, and nobody can ever hold the placeholder;
- pending rows on links already deleted are dropped (§3.3).

After conversion each behaves exactly as any other pending invitation: shown by address, answerable by the address's holder.

**Consequence, accepted.** An invitee who can answer today but is **not** the holder of its address after deploy stops seeing the invitation. That means an unbound legacy account, or either account of a case-collision pair.
- An unbound legacy account sees it again once it binds with authoritative evidence. Its pending row no longer blocks binding (below).
- A case-collision account never sees it. The owner still sees it pending and can remove it.

Keeping account-keyed rows for these was rejected: a second kind of "pending" would behave differently from the first in ways the owner can observe. The release note carries a count query, run before deploy, by category (converted with a holder, converted without one, dropped as placeholder, dropped as deleted link), so the operator knows the size of the loss. Accepted and declined rows are kept as they are; declined rows lose name and picture in the display only (§3.4), not in storage.

Why convert rather than keep the old rows: a kept account-keyed pending row would behave differently from a new address invitation in ways the owner can observe (it disappears when the account is deleted; it carries an account identifier). Converting makes "pending" one thing.

**Effect on PAC-71 rule (b)** (as PAC-130 §3.5 D-12). The emptiness check counts any host row of the account, pending included (`storage/emptiness.go:41`), and counting relations other users create is PAC-71's decision, which is **not** amended here. The effect is on the data: a pending invitation no longer points at an account, so a stranger's invitation can no longer make an unbound legacy account non-empty and block its rightful owner's binding. Accepted and declined entries still count, because the account acted.

### 3.6 Same work for holder and nobody [F, D-2, D-11]

The inviter-side paths (single invite and co-host list) perform **no read keyed on accounts by address**. For a new address, the server does the same sequence of statements whether or not an account carries it: the link lock, the read of the link's current entries, the count, the insert. Any remaining difference would be inside the insert's index maintenance, which does not depend on accounts at all. This is proven structurally (AC-6), as PAC-130 AC-8 did, not by wall clock.

The invitee-side match (§3.3) is keyed on the **caller's own** address, so its cost reveals nothing about anyone else.

### 3.7 Web [F, D-7]

- **Save summary** after a list save: the invited line no longer promises that the invitee will see something "from Paceday" as if they had an account. Default wording (revision 1, N-6): "N co-hosts invited. Paceday doesn't email invitations, so let them know." It promises nothing about when or whether the invitee sees the invitation (an invitee signed in on mailbox evidence only does not, AC-8). The removed and fallback lines are unchanged.
- **Not added**: `not_added` now means "not a valid email address". Default wording, per address: "{address} isn't a valid email address." and in the summary "N addresses weren't valid email addresses." The editor still stays open on any `not_added` or `own_address` (today's rule, `coHostSave.ts:90-94`).
- **Chips**: "Invite pending" for every pending entry (today's rule); "On Paceday" only for an accepted entry (today's rule). The pending tooltip shows the address, because a pending entry has no name.
- **Demo**: invites every well-formed address and never shows a directory name on a pending chip; `not_added` only for a malformed address.
- **Invitee side** (invitation banner, accept, decline): unchanged.

### 3.8 Compatibility

- **Old web after the backend deploy**: it never calls the single invite. Its roster parsing is loose, so a pending entry with no account identifier, name or picture renders as an address with "Invite pending". Its strict parse of the list report may reject a report whose removal item has no account identifier; the old web then shows its existing fallback sentence, and the save itself is reported as saved. The contract stage should prefer a shape that keeps today's report valid where possible; where it cannot, the fallback is the documented degradation for the release window, never an error.
- **Old API clients of the single invite**: the "created" body loses the account identifier (contract stage decides the shape, as a documented change). Nobody in either repo reads it.
- **Keyed create replays** (PAC-119, 24 h): a create key stored before deploy replays the outcomes it recorded then. That is a replay of an answer already given, and it reveals nothing new. Keys expire within 24 h.
- **New web against an old backend** (release window): wording says "invited" for what the old backend reports; addresses the old backend did not add are still reported `not_added` and named by the new wording as "isn't a valid email address", which is wrong for that window. Accepted: the window is minutes (README §3 paired merges), and the backend merges first.

## 5. Explicitly out of scope

- **Emailing invitees** (a sign-up invitation or a notice). Rejected for this ticket: it would let anyone make Paceday mail any address, five at a time per request, without limit (OQ-2). A deliberate notification feature, with its own abuse limits, would be a separate ticket.
- **Rate-limiting** co-host invitations. Once the answer reveals nothing, a limit adds no privacy (PAC-130 §5 took the same view of Manager add). The remaining abuse is in-app invitation spam to holders, which exists today and is bounded at 5 per link; OQ-4.
- **Expiry** of pending invitations (OQ-3).
- **Amending PAC-71 D10** (whether host relations count toward emptiness). This spec changes the data, not the rule (§3.5).
- **Removing** the deprecated alias spellings (API-069). A later ticket.
- **Team invitations** (PAC-129) and their emails: unchanged, already existence-safe (PAC-130 AC-15).
- **The provider-side residual** on free/busy coverage chips (§2.2): accepted as in PAC-130.

## 7. Rollback

- **Migration.** It converts pending rows to address invitations, and drops pending rows on deleted links and for freed placeholder addresses (AC-10, §3.5). The dropped rows are not restored by the down migration. The down migration restores a pending row for every invitation whose address has a holder at that moment, unless that holder already has an entry on the link or owns it (the existing entry survives, N-3). It **loses** pending invitations to addresses without a holder: those created after deploy for people who have not joined, and converted ones whose invitee was not the holder (§3.5). Their owners see them disappear from the host list. These invitations nobody could act on at that moment. Applied under PAC-116's automatic stop-migrate-start (`docs/runbook.md:98-123`).
- **Image rollback** after the down migration: the old server answers "user not found" again; that is the oracle returning, which is expected on a rollback.
- **Web-only rollback** is safe: the old wording reappears; the old web parses the new server's answers as §3.8 says.
- **Release note**: invitations to addresses without an account are new data (an address typed by an owner, about someone who has no account). They end with the owner's removal, the invitee's answer, or the link's deletion (§3.3, AC-17). Snapshot the host table before deploy for full rollback fidelity.
