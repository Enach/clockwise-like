## 1. Problem

The owner of a scheduling link can delete it while another request on that link
is still being handled. Each such request reads the link first ("is it live?"),
does more work, and only then writes. A delete that commits between the read and
the write is not seen, so the write lands on a link that is already deleted.

- **Bookers.** A public booking reads the link, reads every host's calendar (up
  to several seconds of provider calls), then saves the booking. If the owner
  deletes the link during the calendar reads, the booker still gets a 201
  confirmation, the hosts get calendar events, and the booker gets a
  confirmation email, for a link the owner had already withdrawn. The owner sees
  the booking only in the deleted-links archive. PAC-40's erasure copes with the
  data (AC-34), but the booker and the hosts were told a meeting exists on a link
  that no longer did. A pause (the owner switches the link off) in the same
  window has the same effect.
- **Co-hosts.** An owner's invite, or an edit that changes the co-host list, can
  add or remove host rows on a link deleted mid-request. An added row is
  invisible: the invite list hides it and accept/decline/leave answer 404. A
  removed row breaks PAC-40's promise that a deleted link keeps its host rows
  (PAC-40 D-2).
- **Test hygiene.** The issue comment worries that the PAC-40 migration-037
  down test runs on the shared test database, so a failure midway would leave
  every later test without the `deleted_at` column. §2.7 shows the premise does
  not hold on main.

## 2. Current behaviour (origin/main `8dee631`)

### 2.1 The delete (PAC-40 Part A)

- `DELETE /api/scheduling-links/{id}` reads the link (`handlers_scheduling_links.go:673`),
  checks ownership (`:682`), then runs the guarded delete through the session
  re-check wrapper (`:686`, `storage/guarded_writes.go:143-150`).
- The wrapper opens one transaction whose first statement locks the caller's
  user row `FOR KEY SHARE` (`storage/session.go:131`, `:177-193`).
- The delete itself is one statement:
  `UPDATE scheduling_links SET deleted_at = NOW(), active = false WHERE id = $1 AND deleted_at IS NULL`
  (`storage/scheduling_links.go:206-218`). It changes no column of a unique
  index, so PostgreSQL takes a `FOR NO KEY UPDATE` row lock on the link.
- `NOW()` is the transaction's start time. The delete transaction starts before
  it waits for any lock, so `deleted_at` can be earlier than the commit of a
  write that the delete waited for (see D-7).
- A CHECK keeps a deleted link inactive (`storage/migrations/037_scheduling_link_lifecycle.up.sql:21-24`).

### 2.3 What the booker sees today when the link is already gone

- **Server.** A deleted or paused link answers `404 {"error":"not found"}`
  (`handlers_booking.go:338-341`). The contract says so for `createPublicBooking`:
  "No live link with that slug: never existed, paused (`active=false`) or

  exhausted link answers `410 {"error":"link is no longer accepting bookings"}`
  (`:342-344`). Deletion never answers 410.

  `src/pages/PublicBooking.tsx:324-357`). A 404 on submit falls through to the

## 3. Desired behaviour

### 3.1 The rule: a write on a link is either before its delete or nothing

Every write that belongs to one link (a booking, a host row added, changed or
removed, the link's own fields) is ordered against that link's delete as a
whole:

- **Before the delete.** The write takes full effect and is answered as a
  success. The delete then applies to a link that includes it: the booking
  stays and appears in the owner's archive, and the host rows stay (PAC-40 D-2).
- **After the delete.** The write has no effect at all, and the caller gets the
  same answer as if the link had been deleted before the request arrived.

Nothing commits on a link after its delete has committed. This holds whatever
the timing, including a delete that commits while the write's own database
statement runs, not only between the first read and the write.

The same rule applies to pausing for bookings only: a booking that would
commit after a pause has no effect. Host writes do not depend on pausing. An
owner may still invite co-hosts to a paused link, and co-hosts may still
accept, decline or leave it, as today.

### 3.2 Booker-facing answer

A booking that loses the race to a delete or a pause gets exactly what a
booking sent after the delete gets: `404` with the body `{"error":"not found"}`.
It is never a 201, a 409, a 410 or a 503. Nothing is stored: no booking, no
host calendar event, no confirmation email, no completion unit. The answer is
the handler's own, even when the request's time budget ran out while the
booking was being saved. That is the case once the request has passed its
commit point (PAC-81 AC-A19).

### 3.3 Owner and co-host answers

- An invite that loses the race answers `404 {"error":"not found"}`, as for a
  deleted link, and adds no host row.
- An edit that loses the race answers `404 {"error":"not found"}` and changes
  nothing: neither the link's fields nor its co-host list. An edit that wins
  answers 200 with all of its changes applied together. An edit never applies
  its field changes and then fails to apply its co-host changes, or the
  reverse. If a co-host change cannot be stored, the whole edit fails with a
  500 and changes nothing. Today the edit silently answers 200 (D-5).
- Accept, decline and leave that lose the race answer `404 {"error":"not found"}`
  and change nothing, as they already do when the delete came first.

### 3.4 Waiting and failure

- A write that has to wait for a concurrent delete or edit of the same link
  waits only a bounded time. Past that bound it fails with a 500 and writes
  nothing. A booking past its commit point answers `500 {"error":"booking failed"}`,
  as for any other save error after the commit.
- Bookings on the same link do not wait for each other because of this work.
- Concurrent requests on one link never fail with a database deadlock.

### 3.5 The 037 down test

It keeps running on a database of its own. No change is needed for isolation.
A short comment states why the out-of-band down/up is safe, so that a future
move to a shared database would be noticed in review (D-8).

## 4. Acceptance criteria

"Inject a delete" means: commit the owner's delete of the link, from another
connection, at the named point in the request. "Hold a delete open" means: run
the delete's statement in a transaction that has not yet committed. Waiting is
observed from the database (the waiting session shows a lock wait), never from
wall-clock sleeps alone.

**Bookings**

AC-1. Given a live link with one accepted host whose calendar is free, when a
delete is injected after the request's link read and before the host calendars
are read, then the booking answers 404 `{"error":"not found"}`, no booking row
exists for the link, no host calendar event is created and no confirmation
email is sent. *Today: 201 and a row.* [unit]

AC-2. Given the same link, when a delete is injected after the request has
committed to saving (past the budget's commit point) and before the save is
sent, then the answer is 404 `{"error":"not found"}`, no booking row exists, no
completion unit is started (none is registered with the shutdown group, no host
event, no email), and the save's database connection is back in the pool (with
a pool of one, a following request gets a connection). *Today: 201, row,
completion unit.* [unit]

AC-3. Given a live link, when the link is **paused** (not deleted) at the AC-2
point, then the answer is 404 `{"error":"not found"}` and nothing is written.
*Today: 201.* [unit]

AC-4. Given a delete of the link held open, when a booking's save on that link
starts, then the save waits until the delete ends (the database shows the save
in a lock wait). If the delete then commits, the save stores nothing and reports
"link gone". If the delete rolls back, the save stores the booking. *Today: the
save completes at once while the delete is open, so a statement that started
before the delete committed can still commit after it.* [unit]

AC-5. Given a booking's save on a link held open (not yet committed), when the
owner's delete of that link starts, then the delete waits until the save ends.
After the save commits, the delete answers 204, the link is deleted, and the
booking is kept and listed in the owner's archive entry for that link. *Today:
the delete does not wait.* [unit]

AC-6. Given a booking whose request budget runs out while its save is waiting
for a held delete (AC-4), when the delete commits, then the answer is 404
`{"error":"not found"}`, never the 503, and nothing is written. [unit]

AC-7. Given a write on the link held for longer than the waiting bound (D-6),
when a booking's save waits for it, then the booking answers
`500 {"error":"booking failed"}` once the bound is reached, and no booking row
is written. The bound is a named value. Tests may shorten it. *Today: no bound.* [unit]

**Co-host invite**

AC-8. Given a live link and a confirmed invitee, when a delete is injected after
the invite request's link read and ownership check and before the host row is
written, then the invite answers 404 `{"error":"not found"}` and the link has no
host row for the invitee. *Today: 201 and a pending row.* [unit]

AC-9. Given a delete of the link held open, when an invite's write starts, then
it waits. On commit of the delete it writes nothing and answers 404. On
rollback it answers 201 with the pending row. [unit]

**PATCH co-host list**

AC-10. Given a live link with co-host B accepted, when the owner PATCHes
`co_host_emails` to [C] and a delete is started (and not yet committed) after
the PATCH's link-field update and before its co-host changes, then the delete
waits until the PATCH is finished. The PATCH answers 200. After both, the link
is deleted, its fields are the PATCH's, and its host rows are exactly the owner
plus C pending (B removed by the PATCH, before the delete). No host row changes
after the delete commits. *Today: the delete commits in the middle, and the
co-host writes then remove and add rows on a deleted link.* [unit]

AC-11. Given a live link, when a delete is committed after the PATCH's link
read and before its first write (the existing PAC-40 injection), then the PATCH
answers 404 and changes nothing, co-hosts included. *Already true; must stay
true. The existing test `TestPAC40_PatchRacingADeleteIs404AndWritesNothing`
continues to pass.* [unit]

AC-12. Given a PATCH that sets a new co-host list, when storing one of the
co-host changes fails, then the PATCH answers 500 and neither the link's fields
nor any host row changed. *Today: 200 with the fields changed and the co-host
change silently dropped.* [unit]

**Accept / decline / leave**

AC-13. Given an invitee with a pending row and a delete of the link held open,
when the invitee accepts (and, in separate cases, declines, or an accepted
co-host leaves), then the request waits. After the delete commits it answers
404 `{"error":"not found"}` and the host row is unchanged. After a rollback it
answers as today (200 `{"status":…}` / 204). *Today: it completes at once while
the delete is open.* [unit]

**Invite 404 bodies (API-072)**

AC-14. Given an unknown or deleted link id, the invite answers 404
`{"error":"not found"}`. Given a live owned link and an address with no
confirmed holder, it answers 404 `{"error":"user not found"}`. The two bodies
differ. [unit]

**Deadlock freedom**

AC-15. Given one link, when for a fixed number of rounds the following run
concurrently against it: bookings of distinct free slots, invites, PATCHes that
change fields and co-hosts, accepts, declines, leaves, pauses, resumes and
finally a delete, then no request answers 500, no database deadlock error
(SQLSTATE 40P01) or lock timeout occurs, and every request finishes within the
waiting bound. Every booking answered 201 exists and appears in the archive.
Every booking answered 404 does not exist. [unit]

AC-16. Given two bookings of different free slots on the same live link, when
both saves are held open at the same time, then neither waits for the other.
*Pins §3.4's "bookings do not wait for each other".* [unit]

**Contract**

AC-17. The `createPublicBooking` 404 description states that a link deleted or
paused while the request is handled also answers this 404, with nothing
written. The invite, PATCH, accept/decline and leave 404 descriptions state the
same for a delete while the request is handled. The PATCH 500 states that a
failed co-host change leaves the link unchanged. [contract]

## 5. Explicitly out of scope

- **Two bookings of the same slot at once (double booking)** and booking
  replays. Filed as PAC-82 (scope item 1). This spec must not serialize
  bookings against each other (AC-16), so it neither fixes nor worsens PAC-82.
- **The single-use / max-uses race** (PAC-40 spec OQ-4, first case: two
  concurrent bookings both pass the exhaustion check). The issue covers only the
  delete case. See OQ-2.
- **A link edited (not deleted) mid-booking**, for example hours or durations
  changed between the booking's checks and its save. The booking is judged on
  the settings it read. Not in the issue. See OQ-3.
- **Web wording** for a 404 on submit (§2.3). The server's answer is the
  existing one, and the web's current handling of it predates this race. See
  OQ-1.
- **The read paths** (slot listing, link info, invite list, archive). A read
  that started before the delete shows the link as it was. That is not a
  defect, and none of them writes the link's data.
- **API-069** (duplicate accept/decline routes) and API-019. Not touched.

## 6. What must not change

- A booking that commits before the delete is kept in full: row, host events,
  email, archive listing (PAC-40 D-2, AC-34). Protected by AC-5 and
  `TestPAC40_OwnerArchive`.
- PAC-81 AC-A19 / PAC-90: the 503 is answered only before the save is sent. The
  connection is released before the completion unit starts. A panic still
  releases the connection. Protected by `engine/pac90_test.go` (three tests) and
  `TestPAC81_BookingBudgetBeforeInsertWritesNothing`. The new "link gone"
  outcome must keep all of them passing.
- Every existing 404/409/410/429/400 path of `createPublicBooking`, and its order
  of checks (PAC-72, NEW-booking-rate-limit). No new pre-check may be placed
  before the rate limit, the link lookup or the 400s.
- PAC-61: re-inviting an existing host keeps their status and answers 200
  (`TestSchedulingLinksReinviteKeepsExistingHostStatus`). PATCH sets co-hosts by
  difference (`TestSchedulingLinksPatchCoHostsSetsListByDifference`).
- PAC-30: accept/decline/leave with no host row answer 404 and write nothing
  (`TestSchedulingLinksRespondAndLeaveWithoutHostRowIs404`, `…LeaveTwiceIs404`).
- PAC-40 K4-1 and K4-2 (`TestPAC40_PatchRacingADeleteIs404AndWritesNothing`,
  `TestPAC40_ConcurrentDeletesAnswerOne204AndOne404`).
- PAC-71: every owner and co-host write still runs under the session-generation
  re-check, and that re-check is still the first statement of its transaction.
- Paused links: invites, accept/decline/leave and owner edits still work on a
  paused link (`TestPAC40_PausedLinkStaysLiveAndResumes`).
- Bookings on one link do not serialize against each other (AC-16). No test
  pins this today. AC-16 is new.

## 7. Rollback

There is no migration and no stored-data change. Reverting the code restores
today's races. Bookings and host rows written correctly by this work stay valid
under the old code. The contract text (AC-17) reverts with it.

## 9. Commit-point semantics and lock analysis (binding constraints for the contract and plan)

This section names mechanisms because the factory brief asks for them. It
constrains the plan. It does not choose the code.

### 9.1 Why the current guards are not enough

- The booking insert's foreign key locks the link `FOR KEY SHARE`. The delete
  holds `FOR NO KEY UPDATE`. These two modes do not conflict, so the foreign key
  never orders a booking against a delete.
- A re-check written only as `WHERE EXISTS (… deleted_at IS NULL)` with no
  locking clause (the shape W6 and W7 use) reads the statement's snapshot under
  READ COMMITTED. A delete that commits after the statement started is not
  seen, and the write commits after it. AC-4, AC-9 and AC-13 fail for that shape
  on purpose.

### 9.2 Required commit-point check

- **Bookings.** The check `active AND deleted_at IS NULL` must be evaluated in
  the same statement or transaction as the booking insert, under a row lock on
  the link that conflicts with the delete's `FOR NO KEY UPDATE`. `FOR SHARE` is
  the weakest such mode:
  - it conflicts with `NO KEY UPDATE` and `UPDATE`, so the delete waits for a
    booking already holding the lock (AC-5), and a booking waits for a delete
    in progress (AC-4);
  - it does not conflict with another `FOR SHARE` or `KEY SHARE`, so bookings do
    not wait for each other (AC-16);
  - after a wait, READ COMMITTED re-evaluates the locking query's `WHERE` against
    the newest row version, so a committed delete or pause yields zero rows, and
    zero rows means "link gone".

  An `INSERT … SELECT … FROM scheduling_links WHERE id = $1 AND active AND deleted_at IS NULL FOR SHARE`
  satisfies this in one statement. So does a short transaction: lock the link
  `FOR SHARE`, check, insert, commit. Either way the statement or transaction
  stays on the reserved connection, after `budget.Commit`, detached from the
  request (§2.4).
- **Host writes (invite, PATCH co-host loop, accept/decline, leave)** use the
  same lock with the condition `deleted_at IS NULL` only. Pausing does not
  block host writes (§3.1).
- **PATCH.** The link-field UPDATE and every co-host change run in **one**
  transaction (inside the PAC-71 session re-check transaction). The UPDATE is
  that transaction's **first** lock on the link row (it is exclusive:
  `NO KEY UPDATE`, or `UPDATE` when the slug changes because slug is UNIQUE,
  `009_scheduling_links.up.sql:4`). The transaction must never take
  `FOR SHARE` on the link first and upgrade afterwards: two such PATCHes would
  deadlock. The co-host lookups (`CarrierIDs`, `ConfirmedHolder`) are
  database-only reads and may run inside it. A lookup or write error rolls back
  the whole transaction (D-5).
- **An early re-check is allowed but not enough on its own.** A fresh link read
  before the host calendar reads may answer 404 sooner and spare the provider
  calls. The commit-point check is still required.

### 9.3 Ordering against PAC-40's guarded DELETE

Each pair is serialized on the link row:

| Holder first | Then | Outcome |
|---|---|---|
| booking `FOR SHARE` (uncommitted) | delete | the delete waits. The booking commits, then the delete commits. The booking is a pre-delete booking (AC-5) |
| delete `NO KEY UPDATE` (uncommitted) | booking | the booking waits. Delete commits: 0 rows, 404 (AC-4). Delete rolls back: booking stored |
| PATCH txn (link UPDATE done, co-hosts pending) | delete | the delete waits until the PATCH commits (AC-10) |
| delete | PATCH | the PATCH's UPDATE waits, then matches 0 rows: 404, nothing written (AC-11, unchanged) |
| invite / respond / leave `FOR SHARE` | delete | the delete waits. The write is pre-delete |
| delete | invite / respond / leave | the write waits, then sees the deletion: 404, nothing written (AC-9, AC-13) |
| delete | delete | the second waits, then matches 0 rows: 404, `deleted_at` unmoved (K4-2, unchanged) |

### 9.4 Deadlock analysis

Locks each transaction takes, in order:

| Transaction | 1st | 2nd | 3rd |
|---|---|---|---|
| booking save (public, no session) | link `FOR SHARE` | new booking row (its FK: link `KEY SHARE`, same transaction) | none |
| delete | caller's user row `KEY SHARE` | link `NO KEY UPDATE` | none |
| PATCH | caller's user row `KEY SHARE` | link `NO KEY UPDATE` / `UPDATE` | host rows (delete / insert. Insert FKs: link (own lock), invitee user row `KEY SHARE`) |
| invite | caller's user row `KEY SHARE` | link `FOR SHARE` | host row insert (unique `(link_id, user_id)`) |
| accept / decline / leave | caller's user row `KEY SHARE` | link `FOR SHARE` | caller's host row |
| session-generation bump (sign-out, PAC-71) | user row exclusive | none | none |

- **Fixed order: user row(s) → link row → host or booking rows.** A deadlock
  needs two transactions taking two resources in opposite orders. Every
  transaction above respects the order, so no cycle exists.
- **User rows.** The only exclusive user-row lock (a generation bump) takes
  no link or host lock, so it cannot be part of a cycle. Every other
  user-row lock is `KEY SHARE`, which conflicts only with key changes or row
  deletes.
- **Host rows.** Reached only by a transaction already holding a lock on their
  link:
  - a PATCH holding the link exclusively excludes every host-row writer of that
    link;
  - a host writer holding `FOR SHARE` makes the PATCH wait on the link, before
    the PATCH holds any host row;
  - two host writers hold compatible `FOR SHARE` locks and touch the same host
    row only for the same (link, user) pair. They then simply queue on that row
    in the same order.
- **Share-to-exclusive upgrade** is the one classic trap. §9.2 forbids it for
  the PATCH. No other transaction updates the link row.
- **Single-statement forms.** If a host write is one statement whose `WHERE`
  carries a locking sub-select, the plan must show that the link lock is taken
  before the host-row lock. The alternative is two statements in one
  transaction (lock link, then write host row). Either is acceptable. AC-15 is
  the backstop.
- **Network calls.** No transaction holding a link lock makes a network call:
  calendar, email or provider token renewal. Host calendar reads stay before
  the commit point (§2.4). The completion unit starts after the save has
  committed and released its connection (PAC-90 item 1).
- **PostgreSQL's own detector** (`deadlock_timeout`) would turn a missed cycle
  into a 500. AC-15 asserts that none occurs.

### 9.5 Interaction with PAC-90 / PAC-81 `budget.Commit`

- The commit point stays where PAC-81 AC-A19 put it. Connection under the
  budget, then `budget.Commit`, then the guarded save on the reserved
  connection, detached from the request. The lock wait happens after
  `budget.Commit`, so the budget cannot answer the 503 during it. The handler
  answers 201, 404 (link gone) or 500 (error or waiting bound) (AC-2, AC-6, AC-7).
- **"Link gone" is a distinct outcome of the save**, not a nil booking with a
  nil error (§2.4: `startCompletion` would dereference it). On "link gone" no
  completion unit starts, and the reserved connection is released on the same
  paths PAC-90 item 1 defined: normal return, error and panic.
- The waiting bound (D-6) caps the only new unbounded wait after the commit.
  Without it, a stuck holder of the link lock would keep the request (and one
  pooled connection) past the budget indefinitely. The bound must be set in a
  way that also covers the panic path. For example, `SET LOCAL lock_timeout` inside the
  save's transaction, or a statement-level setting on the reserved connection
  that is reset before the connection returns to the pool. The plan must show
  that the setting cannot leak to the next user of the pooled connection.
- `beforeBookingConn` and `afterBookingCommit` are the injection points for AC-1
  to AC-3. AC-4 to AC-7 are proven by holding a transaction on a second
  connection and observing the waiter in `pg_locks` /
  `pg_stat_activity.wait_event_type = 'Lock'`.

## Decisions

- **D-1 (factory):** a write is linearized against the link's delete (§3.1),
  with the row lock as the ordering point. Rejected alternatives:
  - SERIALIZABLE isolation: retries, and it would also serialize bookings;
  - an advisory lock per link: a second lock namespace the delete would also
    have to take.
- **D-2 (factory):** bookings re-check `active AND deleted_at IS NULL`, as the
  issue states. Host writes re-check `deleted_at IS NULL` only, because a paused
  link still accepts invites and responses today.
- **D-3 (factory):** the losing booking answers the existing 404
  `{"error":"not found"}` (`booking.yaml:216-217`), not 410. 410 means exhausted
  in the contract, and a deleted link already answers 404 outside the race.
- **D-4 (factory):** the losing invite, PATCH and accept/decline/leave answer the
  existing 404 `{"error":"not found"}`.
- **D-5 (factory):** a PATCH applies its fields and co-hosts together or not at
  all. A failed co-host lookup or write is a 500 with nothing changed. It
  replaces today's silent 200 (`handlers_scheduling_links.go:655`, `:657-658`).
  This is required for §3.1 (one transaction), and it removes two swallowed
  errors.
- **D-6 (factory, value open as OQ-5):** a bounded wait for the link lock. 10 s
  is proposed, as `storage/session.go:93`. Past it the write answers 500 and
  writes nothing.
- **D-7 (factory):** the guarantee is about commit order, not timestamps.
  `deleted_at` is `NOW()`, the delete transaction's start (§2.1). A booking the
  delete waited for can therefore carry a `created_at` a few milliseconds after
  the link's `deleted_at`. That booking is legitimately pre-delete. No test may
  assert `created_at <= deleted_at`. The archive shows both values as stored.
  Moving `deleted_at` to the commit-time clock is not required.
- **D-8 (factory, pending OQ-4):** the 037 test-hygiene item needs no isolation
  fix (§2.7). The implementer adds a comment on
  `TestPAC40_Migration037DownKeepsEveryRow` saying it relies on `openTestDB`'s
  per-test database. A `t.Cleanup` that re-applies 037 up is unnecessary, and
  it would run against a database the same cleanup drops.

### Blocking (resolved in place)

1. **B-1 — The first draft's AC-4 required only that "the booking is not stored
   when a delete is injected", with the delete committed between statements.**
   An implementation with an unlocked `WHERE EXISTS` in the insert passes that
   test and still leaves the in-statement window (§9.1). It would also leave the
   PAC-40 issue's "under a row lock" requirement unproven.
   *Resolved:* AC-4, AC-5, AC-9 and AC-13 now hold the other side's transaction
   open and require a lock wait observed in the database. AC-16 stops the fix
   from over-locking.
2. **B-2 — Draft §3 said a losing booking is "refused" without saying which
   status, and the issue text says "404/410".** Answering 410 would contradict
   the contract's meaning of 410 (exhausted) and the out-of-race answer for a
   deleted link (404).
   *Resolved:* §3.2 and D-3 fix the 404 with the existing body.
3. **B-3 — Draft §9.5 did not deal with the zero-row result.** The draft let
   the save return "no row" without saying what happens next. On main,
   `scanBooking` turns `ErrNoRows` into `nil, nil` (`storage/scheduling_links.go:542-544`),
   and `startCompletion` would dereference `booking.ID` (`engine/booking.go:614`),
   which panics after the commit.
   *Resolved:* §2.4 and §9.5 require a distinct "link gone" outcome. AC-2
   requires no completion unit and a released connection.
4. **B-4 — PATCH atomicity was implicit.** The draft guarded each co-host write
   separately. Then a delete between the field UPDATE and the co-host writes
   gives a 200 whose co-host half silently did nothing, because the guarded
   writes match zero rows and today's code discards errors. That is neither
   "before" nor "after" the delete.
   *Resolved:* §3.3, §9.2, D-5, AC-10 and AC-12 make the PATCH one transaction,
   with the share-to-exclusive upgrade forbidden (§9.4).
